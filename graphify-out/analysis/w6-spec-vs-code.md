- **Every spec doc node in the graph resolves to a real file path under `docs/rework/`**. None are phantom. Spec doc nodes share graph communities with their target code (e.g., `spec-21-4-doctor.md` lives in community 122 alongside `src/hal0/cli/doctor_commands.py` references; `spec-p3-slots.final.md` in 296 with `slots/manager.py` adjacent calls).
- **All four ⏸ deferred specs share a single design-doc node** — `docs/superpowers/specs/2026-07-18-hal0-hermes-integration-suite-design.md` (community 595) — referenced by HP-memory, HP-provider, HP-executor queries, indicating they're held by user policy not technical blocker.
- **FLAGS-own is the largest standing orphan spec**: the `spec-flags-ownership.md` doc node has only 1 graph edge (to its own header). The board confirms ☐ status with explicit dependency chain "serialize behind SLOT-B merge; migration rides P2-config window" — i.e., it's intentionally queued behind two other in-flight lanes. Code target is `slots/manager.py` (community 3) flag-bearing fields still on slot; migration not yet drafted.
- **All four P2-* migration-window lanes are ☐ orphaned by design** — they're "orchestrator-run live steps, NOT agents" per board, scheduled into deployment windows. Their presence in the graph as code fragments (capabilities/, memory/, updater/, db/) is misleading: the *full* spec target hasn't been built.
- **One real risk**: HP-executor merged ✔ but the board flags `WORKER_BASE_PATH /api/plugins/kanban/runs` as "unpinned by contract fixtures — validate against live Hermes at next both-boxes deploy". This is a spec-to-code gap that survived acceptance.

Examples: `spec-p3-routers.md` community 139 includes `services/models_service.py` (81) and `benchmarks.py` (234); `spec-21-4-doctor.md` community 122 includes `doctor_bundle.py` (176) and `doctor_verify.py` (75); `spec-hp-realtime.md` community 539 includes `api/routes/realtime.py` (762) — graph clustering correctly grouped spec-with-its-targets in most cases.

## Risks/Smells

- **Spec-graph disambiguation cost**: graphify returned 134 nodes for the broad "what rework specs exist" query and 911 for P3-slots — high noise because specs share communities with adjacent code. A tighter `context_filter=['doc']` (or per-spec `graphify explain`) is required to isolate spec nodes; without it, the answer to "is this spec orphaned?" requires manual lookup of community membership for each candidate spec file.
- **Spec node "degree=1" is a structural smell**. `spec-flags-ownership.md` has degree 1 (only `contains` edge to its own header). Same for `spec-p3-routers.md`, `spec-p3-slots.final.md`, `spec-p3-perms.md`, `spec-21-4-doctor.md`, `spec-hp-realtime.md`, `spec-taxonomy-7-1d.md`. All seven have exactly one extracted edge — to their own internal header — and no cross-references to other specs, code, or test files. The graph treats them as opaque documents. This makes "spec vs orphan" indistinguishable from "spec vs code" without a side-channel check (the graphify CLI doesn't expose "edges of type doc→code").
- **Built-or-not determination requires graph + board cross-check**. Spec doc node presence ≠ built (FLAGS-own present, not built). Spec doc node absence ≠ not-built (P3-routers inc 3 is implicit within `spec-p3-routers.md`, not a separate doc). The board is the authoritative status; the graph confirms *which* code communities a spec targets.
- **P3-routers DoD gap not closing**: inc 2 board row notes `models.py 987 / slots.py 1289 vs DoD ≤550/≤800`. Inc 3 ☐ is the path to closing it (pull-orchestration extraction + typed-bodies). Risk: silent stall — DoD failure is documented but no owner assigned yet.
- **HP-executor live-validation gap**: the spec target `WORKER_BASE_PATH /api/plugins/kanban/runs` has no contract fixture. CI green ≠ deploy green. Risk: works-on-paper, breaks-on-Hermes. Same pattern as the historical route-collision-test (`43f29e30`) — CI passes, deploy breaks.

## Recommendations

1. **Add `edges-of-type doc→code` to graph builder** — the spec nodes currently only `contains`-point to their own headers. Spec-to-code linkage would make "spec vs orphan" a one-line query instead of a board-cross-check.
2. **Promote the four P2 migration-window specs from board-only to graph spec nodes** — `docs/rework/hal0-specs/spec-p2-config.md`, `spec-p2-memory.md`, `spec-p2-updater-b.md`, `spec-p3-runtime-db.md` — so they appear in the same queryable form as `spec-p3-routers.md`. Currently the only way to discover them is to read the board.
3. **Add a per-lane `done_criteria_communities[]` annotation** to spec doc nodes (or a sidecar `spec_to_communities.json`) so "spec X is built" becomes a deterministic lookup instead of reading board rows.
4. **HP-executor: pin `WORKER_BASE_PATH` in a contract fixture** before next both-boxes deploy, to close the same CI-green-deploy-broken class as the route-collision test. Add to hermes integration test suite under `tests/fixtures/hermes/contracts/`.
5. **FLAGS-own is the next critical path** — currently blocks slot purity, blocks P2-config's apply engine. Spec is ratified 2026-07-18, code target is `slots/manager.py` (community 3) flag-bearing fields. Should not wait for both P3-routers inc 3 + P3-runtime-db; could dispatch a narrow FLAGS-own-increment-A (model device/chat_template moves only).
6. **P3-routers inc 3 ↔ P3-runtime-db ordering**: the board notes M5 (slot re-key) renames state.json that P3-runtime-db later moves to SQLite — either fold slot-state table into SLOT wave or scope M5 so runtime-db never re-migrates. Decide at SLOT-B dispatch; current state is open.
7. **Cross-check graph P3-routers community 139 against spec section "Cross-lane coordination"**: the spec lives at `spec-p3-routers.md` L564. Verify the four steps mentioned (slot name re-keying, PortAuthority merge, pull-orchestration, MCP admin) each have a community target — pull-orchestration is inc 3 ☐, others appear merged.
