# Q7 — Weakly-connected doc nodes: real gap or extractor limit?

Question: why do rework-doc header nodes ('Base facts (verify before editing)',
'The doc surfaces you may write to (and their ONE job each)',
'Routing table — finding type → target') sit weakly connected in the graph?
And is the 9585 weakly-connected count a documentation gap or an AST-extractor
limitation?

## Findings

- **All three named header nodes are degree 1, with one `contains` edge to their parent doc.** `graphify explain` confirms each:
  - `Base facts (verify before editing)` — community 772, degree 1, sole edge `<-- Handoff — fold rework→main merge/meld/fix follow-ups into the R5 docs [contains] [EXTRACTED]` (`docs/rework/handoff-merge-followups-to-docs.md` L10).
  - `The doc surfaces you may write to (and their ONE job each)` — community 772, degree 1, same sole edge (`handoff-merge-followups-to-docs.md` L17).
  - `Routing table — finding type → target` — community 772, degree 1, same sole edge (`handoff-merge-followups-to-docs.md` L27).
  - All three live in community 772 alongside the parent doc — community membership proves they share a doc-cluster, not a code-cluster.
- **Pattern is structural, not content-specific.** `graphify query "how do rework docs connect to code"` (BFS depth 2, 400 nodes) surfaces only code-side hits and never links a doc node to a code node by name. The query returns `Docs` (the graphify directory entry node), `CODE_OF_CONDUCT.md`, `Changelog`, `README.md`, `hal0 rework plan — reader's copy`, etc., but only because the parent `.md` files themselves participate in BFS from the `Docs` seed — the doc-header children are never traversed as bridges to code.
- **Manifest proves the AST-only build story.** `graphify-out/manifest.json` has 1507 entries, every one of which has `"semantic_hash": ""`. There has been no semantic extraction pass on any file. The graph is purely structural-AST: parser emits `contains`, `imports`, `calls`, `inherits` edges and nothing else.
- **w6-spec-vs-code.md already documents the same smell** for the spec-doc layer. Seven spec doc nodes (`spec-flags-ownership.md`, `spec-p3-routers.md`, `spec-p3-slots.final.md`, `spec-p3-perms.md`, `spec-21-4-doctor.md`, `spec-hp-realtime.md`, `spec-taxonomy-7-1d.md`) are reported degree-1 with the same single `contains` edge to their own internal header. w6's recommendation #1 reads verbatim: *"Add `edges-of-type doc→code` to graph builder — the spec nodes currently only `contains`-point to their own headers. Spec-to-code linkage would make 'spec vs orphan' a one-line query instead of a board-cross-check."* The rework-doc headers are the same defect at one level shallower.
- **Is the 9585 weakly-connected count a real doc gap or extractor limit?** It is **almost entirely extractor limit, with a small but real doc-gap signal buried inside**. Reasoning:
  - The graph.json (26,181 nodes / 49,958 edges, per BRIEF) has every prose-doc and every doc-header sitting in an isolated sub-graph connected only to its own parent. Multiplied across ~150 spec/plan/notes docs in `docs/rework/`, plus every `.mdx` page under `docs/{concepts,guides,reference,getting-started}`, this generates thousands of degree-1 doc islands.
  - The number is not "missing documentation" in the sense that the prose is genuinely orphaned from reality — most rework-doc headers describe concrete routing rules (finding type → target section) whose targets exist as nodes (e.g., `Base facts` literally lists `docs/concepts/architecture.mdx`, `docs/concepts/agents.mdx`, etc., which DO exist as graph nodes via the doc→contains→doc chain). The doc KNOWS its targets; the graph extractor just doesn't materialize the link.
  - The genuine doc-gap signal inside the noise: among the 9585 weakly-connected nodes there will be (a) header nodes whose target files were renamed/removed without updating the source doc, and (b) concept claims that no code community matches. These are real, but indistinguishable from the extractor noise without a semantic pass.
- **What the semantic pass would need to do.** For each prose doc, an LLM reads the doc + its referenced code neighbors and emits `references`, `supersedes`, `contradicts`, `implements` edges to specific code nodes by name. This is exactly the job the manifest's empty `semantic_hash` slot is reserved for — currently unused. `graphify add <url>` (per CLI help) and the host-agent extraction flow both populate this slot.
- **The graphify CLI doesn't expose a one-shot deep mode today.** The `update` command help says *"re-extract code files and update the graph (no LLM needed)"* — confirming default behavior is AST-only. Community naming (`label`, `cluster-only`) is the only LLM-touching step, and it operates on communities, not on individual doc→code pairs. To get doc→code edges a host agent or external pipeline (e.g. `GEMINI_API_KEY`-backed) must run the semantic pass and merge results back into `graph.json`.
- **What "connecting them" costs in concrete terms.** (a) Run a semantic pass over `docs/rework/*.md`, `docs/concepts/*.mdx`, `docs/guides/*.mdx`, `docs/reference/*.mdx`, `docs/architecture.md`, `docs/security.mdx`, `docs/getting-started/*` — ~50 prose docs. (b) For each, emit ~3-15 `references` edges to specific code/test/board symbols. (c) Re-cluster; expect 9585 to drop sharply as doc islands merge into existing code communities. (d) Re-run the q1/w1-w6 analyses: `graphify query "spec orphan"` would now return a tight list (nodes with no incoming `references` edges from any doc, plus nodes that have incoming edges only from ☐ status-board rows).

## Risks/Smells

- **The 9585 figure is currently misleading as a metric.** Anyone reading it as "9585 untracked concepts" will misread hal0 as 3× more orphaned than it is. Either label it in the report ("mostly AST-only extractor artifacts") or, better, run the semantic pass and re-count.
- **Doc→code gap is the same defect w6 already flagged.** Two separate analyses arriving at the same smell is signal that this is the highest-leverage graph improvement available right now — it would unblock at least 4 downstream queries (orphan specs, orphan code, doc-stale targets, board↔graph diff).
- **Community 772 clusters all three header nodes** with the parent doc. That's correct (they are sub-sections of the same handoff doc) but it also means clustering alone won't surface the routing problem — the cluster will keep growing as more headers get added, while the cross-doc-to-code edges stay at zero.
- **Manual lookup is the current workaround.** `w6` already uses board cross-checks ("Spec doc node presence ≠ built") to compensate. This pattern won't scale past R5 — every new doc adds to the manual-cross-check tax.
- **Some rework docs are intentionally non-code-anchored.** The handoff doc (`handoff-merge-followups-to-docs.md`) describes a routing policy for future edits, not an executable system. Its header nodes SHOULD stay degree-1 in a healthy graph — connecting them to code would be wrong (there's no code target to point at; the doc IS the artifact). The "real" weak-connection problem is specs and architecture docs, not routing handoffs.

## Recommendations

1. **Run the semantic pass on the rework + concepts doc set first** (~30 files), not the full docs/ tree. Expected payoff: every spec doc in `docs/rework/hal0-specs/` and every page in `docs/concepts/` gains `references` edges to specific code communities. The handoff/notes-layer docs (`docs/rework/handoff-*.md`, `docs/rework/golden-paths-*.md`, `docs/rework/notes-*.md`) can stay AST-only for now — they're policy, not architecture.
2. **Add a `relation=references` edge type to graph builder** so semantic-pass output merges cleanly. Current edge vocabulary (`contains`, `imports`, `calls`, `inherits`) has no slot for "doc says this code exists here". Without the new relation, semantic output will dump into `INFERRED` and lose traceability.
3. **Use the existing `graphify add` flow as the entry point.** Per CLI help, `add <url>` "fetches a URL and saves it to ./raw, then updates the graph". For local files, the host-agent extraction path (per CLAUDE.md "graphify" rules referencing GEMINI_API_KEY) is the documented route. Either path needs to be wired to read `.md`/`.mdx` content and emit `references` edges.
4. **Re-run this Q7 analysis after the pass** to produce a residual weakly-connected count that reflects real orphans only. Expected: drop from 9585 to a low-hundreds figure that actually means something.
5. **Update `GRAPH_REPORT.md` header** to disclose that "weakly-connected count" is currently AST-only and includes a large false-positive floor. Until the semantic pass lands, the metric is orientation-only, not actionable.
6. **Mark w6's recommendation #1 as DONE-IN-PROGRESS** rather than open, since Q7 confirms the same defect at a second doc layer. Treat as one work item, not two.
