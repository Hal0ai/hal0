# hal0 Installer + Update — Consolidated Map for a Guided "Hal0 Installer Setup"

## 1. CURRENT SHAPE — install + update, phase by phase

hal0 has **two install entry shells and four ways to build a "setup"**, all converging on one Python orchestrator (`apply_setup`). Update is a separate lineage that shares almost no code with install.

### Phase 0 — Bootstrap trust boundary (one-liner path only)
- `installer/bootstrap.sh:169 main()` — `curl|sudo bash`. Runs `preflight()` (`bootstrap.sh:70`): Linux `uname` check + `need curl/tar/sha256sum/python3`. **These four are never re-checked in install.sh** — the direct `sudo bash install.sh` path skips them entirely.
- Fetches manifest, sha256-verifies tarball (fatal), cosign-verifies OIDC signature (SOFT unless `HAL0_INSTALL_REQUIRE_COSIGN=1`), unpacks, exec's `install.sh` with `HAL0_BOOTSTRAP_VERIFIED=1`.

### Phase 1 — Shell preflight (the entire up-front platform gate)
- `install.sh:154` release-verification gate (refuses unverified rootful install).
- `install.sh:219 ui_step "Pre-flight checks"` dispatches a **strict subset** of `preflight.sh:606 preflight_all()`:
  - `install.sh:221` sudo `-E` re-exec (the one real interactive prompt).
  - `preflight_arch` x86_64-only **FATAL** (`preflight.sh:228`) — the *only* truly fatal hardware gate.
  - `preflight_network` (soft), `preflight_systemd` (fatal non-dev), `preflight_python` 3.11–3.14 (fatal only if missing), `preflight_venv` (auto-installs python3-venv), `preflight_container_runtime` (podman-preferred, auto-installs podman-or-die), `resolve_hindsight_python` (builds a 3.11–3.13 for litellm), `preflight_writable` + `preflight_disk 20GB` + `preflight_ports 8080/3001`.
- **Not called during install** (doctor-only): `preflight_gpu` (`preflight.sh:467` — LXC detection + `/dev/dri`/`/dev/kfd`/`/dev/accel` + render-gid fix), `preflight_podman_forward`, `preflight_hindsight_python`.

### Phase 2 — Non-gated system mutation (runs regardless of hardware)
- Filesystem layout, seed `[models].store` (`install.sh:361-412`), venv + `pip install hal0`, build UI (soft), write config/units (`hal0-api.service` at `install.sh:606` binds `0.0.0.0`), background OpenWebUI pull.
- `install.sh:851` **first-run setup is pick-free**: `hal0 setup --auto --no-pull --no-slots --no-extensions` → box has **zero models** and derives **no LLM slots** (only seeds sentinel/wiring + writes `hardware.json`? — see §2; the CLI path does *not* persist hardware.json).
- `install.sh:892` **NPU prerequisites** (step 9, LATE, apt-only, fail-soft): libxrt-npu2 PPA + per-distro FLM `.deb` (sha256-pinned) + soft `flm validate`.
- `install.sh:1103` **slot seed loop**: copies `npu/tts/rerank/utility/img.toml` verbatim (idempotent).
- `install.sh:1180` ComfyUI scaffold (dirs + custom_nodes + `extra_model_paths.yaml`, no weights).
- `install.sh:1237` create `hal0` system user + render/video groups + FLM cache dir (gated on `/dev/accel/accel0`).
- `install.sh:1384` **Service start** (very late, multi-minute): Hindsight venv build + `pip hindsight-api`, hermes provision (`hal0 agent install hermes`, `install.sh:1534`), OpenWebUI enable, hermes gateway install fed `</dev/null`. Then reachability/QR/summary (`install.sh:1628-1711`, IP-based).

### Phase 3 — The Python orchestration core (shared by installer, CLI, HTTP)
- `src/hal0/install/orchestrate.py:152 apply_setup(Selections)` — the single in-process orchestrator. Per `SlotSelection`: `derive_device` (`profile_derive.py:52`) or skip `not_applicable_on_this_hardware`; `derive_profile` (`:91`); strict `get_curated(model_id)` (`curated.py:936`, exact-id, no alias) or skip `needs_upstream_routing`; `slot_manager.create(...)` **OFFLINE** with `enabled:True`; queue a `PullPlan` (pull is **returned, not run**). Then `_install_extensions` (best-effort subprocess), then optional sentinel.
- Selections is built four ways: `installer.py:336 install_apply` (tier manifest), `installer.py:394 install_apply_selections` (raw JSON), `setup_command.py:60 build` (--auto via `suggest_models`), `setup_ui.py` (interactive).

### Phase 4 — CLI/API setup surfaces
- **CLI**: `setup_command.py:126 setup()` → `setup_ui.py:161 run_interactive()` (WELCOME→STORAGE→EXTENSIONS→MAIN→AGENT→NPU→REVIEW→INSTALL) → `setup_install.py:44 run_install()` picks in-process vs live-API via `_api_reachable()`.
- **HTTP**: `/api/install/*` (`installer.py`), all **unauthenticated** (ADR-0012). `GET /state`, `POST /probe` (writes hardware.json), `POST /apply` (tier) / `POST /apply-selections` (raw), `POST /complete` (sentinel), `POST /services/{unit}/repair` (allowlisted).

### Phase 5 — Agent + app installs
- `agent_commands.py:101 _install_hermes` — toolchain + `hermes_provision.py:3925 PHASES` (models→`:8080/v1`, memory→MCP + Cognee card, permissions→ADR-0013 allowlist). Fully deferrable via `hal0 agent install hermes`.
- OpenWebUI: `env_writer.py:143` + `systemctl enable hal0-openwebui`. Skippable only as an enable-gate; **no** `HAL0_SKIP_OPENWEBUI`, no `hal0 app install openwebui` verb.

### Phase 6 — Update (a divergent lineage)
- `update_commands.py:197 update()` — thin client over `/api/updates/*`.
- `updater.py:1284 prepare()` (§9 steps 1-6: fetch/verify/cosign/extract, no system change; editable installs hard-refuse).
- `updater.py:1415 commit()` (§9 steps 7-9): config migrations (FATAL), seed prune (soft), mtp-clear (soft), symlink swap (FATAL), venv re-pip #495 (FATAL), `rerender_slot_units()` (`updater.py:1135`, soft, **re-renders on disk but never restarts processes**), then fail-soft `try-restart hal0-api`.
- **Structural divergence**: install renders slots via `slot_manager.create()`; update re-renders via `rerender_unit_sync` raw-TOML surgery (`updater.py:1174`). There is **no shared "reconcile box to current code" routine** — an updated box and a freshly-installed box can end up with different units for the same slot.

## 3. LEAKS & BUGS — fix now

### 3.1 CONFIRMED: leaked developer domain as every user's dashboard URL — **HIGH**
`src/hal0/cli/setup_install.py:36` → `_DASHBOARD_URL = "https://hal0.thinmint.dev"` (verified verbatim). Printed to **every** operator at `hal0 setup` completion in both branches: in-process (`:89`) and via-API (`:180`). It's the maintainer's personal reverse-proxy domain — a broken link and an information leak.
**Fix**: derive from the actual bind. The CLI already knows the base via `_shared.py:19 _api_base()` (default `http://127.0.0.1:8080`, honours `HAL0_API_URL`). Better: compute `http://<hostname>.local:<HAL0_PORT>` or the installer's already-computed LAN IP (`install.sh:1628-1711 lan_ipv4s()`), or `GET /api/config/urls` which mirrors the correct host. Never emit a `thinmint.dev` domain.

### 3.2 The `_auth.py` origin "leak" is a **false flag** — but exposes a real mismatch — **HIGH (mismatch)**
`src/hal0/api/agents/_auth.py:59-63` `DEFAULT_ALLOWED_ORIGINS` is **clean** (verified: `hal0.local`, `localhost:5173`, `127.0.0.1:8080` — no thinmint). The real thinmint leak lives only in `setup_install.py:36` (3.1). The genuine defect: the installer prints an **IP-based** dashboard URL but never writes `HAL0_ALLOWED_ORIGINS`, so reaching the dashboard by IP fails the chat-proxy WS origin check with close code 4403 (`_auth.py:218-229`). **Advertised URL and working URL disagree.**
**Fix**: have the installer derive the origin set (chosen hostname + detected LAN IPs + localhost) and seed `HAL0_ALLOWED_ORIGINS` into api.env from the same network-shape step, keeping printed URL and allowlist in lockstep.

### 3.3 utility.toml pins a **ghost (non-curated) model id** → crash-loop — **HIGH**
`installer/etc-hal0/slots/utility.toml:11` → `[model].default = "gemma-4-12b-it"` (verified). This is **not** in `CURATED_BY_ID` (exact-match only, `curated.py:936`; the real id is `gemma-4-12b-it-ud-q4-k-xl`, `curated.py:504`). On a model-less box it is neither local, pullable, nor fallback-able → `_resolve_servable_model` (`manager.py:2455`) returns it unchanged and the **enabled** slot crash-loops on a `--model` path that doesn't exist.
**Fix**: remove the `[model].default` pin (preferred clean-seed approach, §5) or at minimum correct it to `gemma-4-12b-it-ud-q4-k-xl`.

### 3.4 Bind is silently `0.0.0.0` with no loopback option — **HIGH (security posture)**
`installer/install.sh:115` (verified) hardcodes `API_BIND_HOST="0.0.0.0"`, baked into `hal0-api.service` ExecStart (`install.sh:606-622`). Combined with ADR-0012 removing network auth, the **unauthenticated `/api/install/*` surface is exposed on the whole LAN** (`api/__init__.py:1135`). Anyone reaching the port can trigger a full install, rewrite hardware.json, change slot models, restart systemd units.
**Fix**: gather bind shape up front (`loopback | lan | <ip>`), write `HAL0_BIND_HOST` to api.env, source it in both the unit and `hal0 serve` (unifying the two divergent defaults).

### 3.5 `storage_dir` is accepted but **silently ignored** — **MEDIUM**
`Selections.storage_dir` / `/apply` / `/apply-selections` / `hal0 setup --storage-dir` all accept it, but `apply_setup` never references it for pull destination (`orchestrate.py:152-223`) — pulls go to `_pull_root()` → `[models].store`. A caller choosing a custom store is no-op'd.
**Fix**: thread `storage_dir` through `apply_setup` (write `[models].store`) or remove it from the payload.

### 3.6 install-time in-process pulls run **unauthenticated** — **HIGH**
`setup_install.py:68-75 _apply_in_process` calls `apply_setup` **without** `hf_token`, so `PullPlan.kwargs['hf_token']=None` (`orchestrate.py:218`). Gated curated pulls 401/403 during a fresh install even when `HF_TOKEN` is exported.
**Fix**: read `os.environ HF_TOKEN` and thread it through `_apply_in_process → apply_setup`.

### 3.7 ComfyUI fetch scripts are **container-authored, host-executed** — **HIGH (feature-dead)**
`get_*.sh` hardcode `HF="/opt/venv/bin/hf"` (the ComfyUI *container's* venv), but `fetch.py:46` runs them as **host** subprocesses → immediate "no such file" for every auto/selection fetch. Plus `HF_TOKEN` never forwarded (`fetch.py:46`, no `env=`), and the curated workflow JSONs every `ModelVariant.workflow` references (`capabilities.py:49,107`) aren't shipped (only `sdxl_turbo_simple.json` exists).
**Fix**: `podman exec` the scripts inside the img container, or make `hf` PATH-resolvable on host + forward `HF_TOKEN`/`HF_HOME`; provision workflow JSONs per selected variant.

### 3.8 Stale avahi announcement — **MEDIUM (dead/misleading)**
`packaging/avahi/hal0.service` advertises Caddy on 443/80 with an `--auth=basic` header, but the installer ships no Caddy, no `--auth` flag, and 0 avahi refs. If ever dropped it would advertise ports nothing listens on.
**Fix**: delete the stale file and its claims, or rewrite to advertise the real bound port 8080 and drop it when avahi is present.

## 5. SEEDED-SLOT HYGIENE — verdict

**Verdict: NOT clean — all six seeded slots are PRECONFIGURED.** Every installer-seeded TOML ships (a) `enabled=true` (npu inherits the schema default `True`, `schema.py:341`), (b) a hardcoded `device`+`profile` backend binding, and (c) a hardcoded `[model].default` pin — on a box the installer deliberately left **model-less** (`install.sh:851`). None hit the benign OFFLINE "pick a model" branch (`manager.py:1084`), which only fires when the resolved model is falsy.

| TOML | enabled | device/profile | model pin | Failure on fresh box |
|------|---------|----------------|-----------|----------------------|
| `utility.toml:11` | true | gpu-vulkan/vulkan | `gemma-4-12b-it` **(ghost id)** | **crash-loop** — not curated, no fallback (§3.3) |
| `tts.toml:11` | true | cpu/tts | `kokoro-v1` | **startup download** (curated → pullable) |
| `rerank.toml:11` | true | gpu-vulkan/vulkan | `bge-reranker-v2-m3-q4_k_m` | **startup download** |
| `img.toml:18` | true | gpu-rocm/comfyui | `sdxl-turbo` | **startup download** |
| `npu.toml` | true (implicit) | npu/flm | `gemma4-it-e2b-FLM` | needs NPU HW + FLM cache present |
| `qwen3tts.toml` | **false** | gpu-rocm/tts-qwen3 | `qwen3-tts` | won't auto-start, **but not in the seed loop** (`install.sh:1103` only copies npu/tts/rerank/utility/img) |

**Two contradictions**: (1) tts/rerank/img being `enabled=true` + exact curated ids means the startup reconciler kicks off multi-GB downloads (kokoro/bge/sdxl) — directly contradicting the installer's `--no-pull` posture. (2) Every slot hardcodes a GPU/runtime backend before any hardware-aware selection.

**Recommendation (uniform policy)**: seed slots **without** `[model].default` (so they boot grey/"pick one from the dropdown"), let the guided step assign models per slot after a scan, and derive `device`/`profile` from the up-front GPU/NPU preflight instead of hardcoding. Reconcile `qwen3tts` into (or explicitly out of) the seed loop.

## 7. OPEN QUESTIONS — ranked decisions for a grilling session

1. **Does guided setup require root, or a `hal0` user?** Today install re-execs to root (`install.sh:221`), hal0-api runs as root, the `hal0` user is created *late* (`install.sh:1237`), and perms.py is a no-op in the wired `service_user='root'` mode (`perms.py:104`). Is the guided setup a root-only flow, or do we finally make the non-root `hal0` user primary — and if so, when is it created relative to the mutation steps?

2. **Is network-bind a mandatory up-front choice, or keep `0.0.0.0` default?** This gates the unauthenticated `/api/install/*` exposure (§3.4). Default LAN (trusted-home story) vs default loopback (safe) vs always-ask — and do we unify the CLI/unit split (`main.py:190` vs `install.sh:622`)?
