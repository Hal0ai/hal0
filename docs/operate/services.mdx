The hal0 platform itself is two systemd units: **`hal0-api`**, the API
daemon everything else talks to, and **`hindsight-api`**, the memory engine
it delegates recall/extraction to. Both run as the unprivileged `hal0` system
user and are managed with plain `systemctl`/`journalctl`.

<Aside type="note">
This page covers the two platform units by raw `systemctl` below, and —
further down, in Companion services — the four services in the
`/api/services` registry (OpenWebUI, ComfyUI, Hermes, Hindsight) that the
dashboard's Services page controls. Per-model inference units
(`hal0-slot@<name>.service`) have their own lifecycle; see
[Manage slots](/docs/guides/manage-slots) and the
[slot lifecycle reference](/docs/reference/slot-lifecycle).
</Aside>

## hal0-api.service

The API daemon — serves `/api/*`, `/v1/*`, and the dashboard's static
assets. Generated at install time by `installer/install.sh` (not a static
file in the repo):

```ini
[Unit]
Description=hal0 API daemon
Documentation=https://github.com/hal0ai/hal0
After=network-online.target
Wants=network-online.target

[Service]
Type=simple
User=hal0
Group=hal0
SupplementaryGroups=systemd-journal
WorkingDirectory=${API_WORKDIR}
EnvironmentFile=${API_ENV}
EnvironmentFile=-${ETC_DIR}/hermes-python.env
EnvironmentFile=-${HF_SECRETS_ENV}
ExecStart=${HAL0_BIN} serve --port ${HAL0_PORT}
Restart=on-failure
RestartSec=3
StandardOutput=journal
StandardError=journal
SyslogIdentifier=hal0-api

[Install]
WantedBy=multi-user.target
```

- **Journal read** — `SupplementaryGroups=systemd-journal` lets the daemon
  read the journal behind `/api/logs` and the MCP `logs_tail` tool. The group
  applies to this unit's process tree (children such as podman and flm
  inherit it); the `hal0` account is not added to it, so
  `hal0-agent@` units do not start with it. Under ADR-0002 the agent shares
  the `hal0` uid and can influence `hal0-api`, so this is a scoping measure,
  not an isolation boundary. The installer omits the line on a host that has
  no `systemd-journal` group. `hal0 update` does not rewrite this unit:
  re-run the installer once after updating to 1.4.0. `hal0 doctor all` warns
  (`API journal read`) until it has been. Until then the Logs page's slot
  channel and the slot log drawer show a notice naming the cause and the fix (a
  `degraded` frame, held open with keepalives) instead of reconnecting in a
  loop, the one-shot slot log tail carries the same hint, and
  `hal0 slot logs --follow` prints the reason and returns.
- **User/group** — `hal0:hal0`. Root-only operations (writing per-slot
  units, `daemon-reload`, restarting itself during an update) go through a
  narrow `sudo -n` wrapper (`hal0-systemctl`) rather than running the daemon
  as root. Every wrapper verb that takes a payload on stdin allow-lists that
  payload on the root side and writes its own validated reconstruction, so a
  hand-crafted unit body cannot smuggle a host-side `ExecStartPre=` or
  `User=root` past it. Use `hal0-systemctl check-quadlet < unit` (or
  `check-dropin <gateway|hindsight> < body`) to see why something was refused;
  both validate and echo without writing anything. Note the limit of that
  boundary: slots run under rootful podman and a slot's `[Container]` section
  legitimately mounts host paths and passes through devices, so an attacker who
  owns the `hal0` account can still author a privileged container. The wrapper
  is a check on the unit *file*, not a sandbox around slot content.
- **WorkingDirectory** — the `current` symlink in a production install, so
  `hal0 update`'s atomic swap moves it without rewriting the unit.
- **ExecStart** — no `--host` flag. The bind host comes from
  `HAL0_BIND_HOST` inside `EnvironmentFile`, so the unit and the `hal0 serve`
  CLI can never disagree about it.
- **Port** — `8080` by default (`HAL0_PORT` in `api.env`), binds `0.0.0.0`
  unconditionally.

### Config files it reads

| File | Purpose |
|---|---|
| `/etc/hal0/hal0.toml` | Main config — includes the `[security]` table (see [Authentication](/docs/operate/auth)). |
| `/etc/hal0/api.env` | Required systemd `EnvironmentFile`, mode `0600` — port, log level, network settings, provider tokens, and (post-rotation) `HAL0_ADMIN_KEY`/`HAL0_CLIENT_KEY`. |
| `/etc/hal0/hermes-python.env` | Optional — Hermes interpreter policy (`HAL0_HERMES_PYTHON=`, see below). |
| `/var/lib/hal0/secrets/hal0-api.env` | Optional, `root:root` `0600` — `HF_TOKEN` and similar secrets. |
| `/etc/hal0/upstreams.toml` | External LLM upstream definitions. |

### Hermes interpreter policy

The Hermes venv runs on exactly one Python minor, which the pinned Hermes commit decides: the newest of 3.14 and 3.12 that its `requires-python` admits. The current pin, v0.22.4 (`4d043038`), declares `>=3.11,<3.15`, so Hermes runs on a uv-managed CPython 3.14 under `/var/lib/hal0/hermes/python/cpython-3.14*`, with its dependencies installed from upstream's hash-locked `uv.lock`. Before 1.6.0 the pin capped below 3.14 and Hermes ran on 3.12; the first `hal0 update` that carries the new pin builds the 3.14 release next to the old one, switches, and rewrites `/etc/hal0/hermes-python.env` (the old 3.12 value is discarded with a `hermes-python-discarded` warning). When a build needs an interpreter for that minor, hal0 checks these in order:

1. `HAL0_HERMES_PYTHON`, the operator's override, from the environment and then from `/etc/hal0/hermes-python.env`. A value that is not the target minor is discarded with a warning, and the interpreter is re-probed. A value whose interpreter links an SQLite older than 3.51.3 is still used, with a warning.
2. A uv-managed CPython under `/var/lib/hal0/hermes/python`, fetched by the uv that ships in hal0's venv (`uv python install --managed-python`). It must link SQLite 3.51.3 or newer.
3. A system `python<minor>` (python3.14 for the current pin) that links SQLite 3.51.3 or newer, used when uv cannot fetch one. Ubuntu 26.04's `python3.14` links SQLite 3.46.1, below the floor where Hermes forces DELETE journal mode, so it is never used.

hal0's own venv interpreter is never used for Hermes.

hal0 writes the interpreter it chose back to `/etc/hal0/hermes-python.env`. `hal0 doctor` reports the SQLite version of the live Hermes interpreter, and warns below 3.51.3.

The uv that does the fetching ships in hal0's own venv (pinned to 0.13.4.x); the installer no longer installs it separately. uv's cache lives at `/var/lib/hal0/hermes/.cache/uv`. A host with no network cannot build the first 3.14 release: the build fails (status `build_failed`) and the box keeps running its current Hermes. Rolling hal0 back to 1.5.x after the 3.14 build leaves the Hermes build failing (`Hermes Python must be exactly 3.12`) until you update again; do not edit `hermes-python.env` to 3.12 on 1.5.x.

### Hermes releases

Every Hermes build (install, `hal0 agent reprovision hermes --repair` and `hal0 update` (including `hal0 update component hermes --target`)) produces an immutable release under `/var/lib/hal0/hermes/releases/<id>/` with a `release.json`. hal0 checks it (imports, `hermes --help`, an MCP probe) before the `current` symlink moves, and `/var/lib/hal0/venvs/hermes` points at `current/venv`. Activating a release stops `hal0-agent@hermes` and the gateway, switches, runs `hermes config migrate`, writes `sessions.auto_prune: false` and the persona prompt into `config.yaml`, and restarts them. If the re-check fails, hal0 switches back to `previous`, restores `config.yaml` and reports `activation_failed`. The first update to 1.6.0 therefore causes a short Hermes outage. Hermes keeps session history: `sessions.auto_prune` is set to `false`, where Hermes 0.22 would otherwise delete ended sessions after 90 idle days. The directory tree is in [Paths & files](/docs/reference/paths-and-files/#hermes-release-tree).

### Health endpoints

| Endpoint | Auth | Checks |
|---|---|---|
| `GET /api/health` | open | Shallow liveness — returns immediately, no slot/upstream/disk work. What the installer and the systemd watchdog poll. |
| `GET /api/health/system` | open | Deep health — disk headroom on state/config roots (`disk_state`, `disk_config`: `ok`, `free_mb`, `total_mb`, `floor_mb`, `path`), slot-manager responsiveness, errored-slot detection. Always `200`, with `{"status": "ok"\|"degraded", "checks": {...}}`. |
| `GET /api/status` | client | Dashboard summary poll (hardware, slots, memory-degraded flag). |

## hindsight-api.service

The memory engine — extraction, consolidation, reflection, and recall. A
static unit file shipped at `installer/systemd/hindsight-api.service`:

```ini
[Unit]
Description=hal0 shared Hindsight memory engine (platform brain)
After=network-online.target hal0-api.service
Wants=network-online.target

[Service]
Type=simple
User=hal0
Group=hal0
WorkingDirectory=/var/lib/hal0/memory/hindsight

Environment=HOME=/var/lib/hal0/memory/hindsight
Environment=HF_HOME=/var/lib/hal0/memory/hindsight/hf-cache

Environment=HINDSIGHT_API_LLM_PROVIDER=openai
Environment=HINDSIGHT_API_LLM_BASE_URL=http://127.0.0.1:8080/v1
Environment=HINDSIGHT_API_LLM_MODEL=hal0/utility
Environment=HINDSIGHT_API_LLM_API_KEY=hal0-local-noauth
EnvironmentFile=-/etc/hal0/hindsight-llm.env
Environment=HINDSIGHT_API_LLM_TIMEOUT=300
Environment=HINDSIGHT_API_SKIP_LLM_VERIFICATION=true

Environment=HINDSIGHT_API_EMBEDDINGS_LOCAL_FORCE_CPU=true
Environment=HINDSIGHT_API_RERANKER_LOCAL_FORCE_CPU=true

ExecStart=/var/lib/hal0/memory/hindsight/.venv/bin/hindsight-api --host 127.0.0.1 --port 9177

Restart=on-failure
RestartSec=3
TimeoutStartSec=120

[Install]
WantedBy=multi-user.target
```

- **Port** — `9177`, **loopback only** (`--host 127.0.0.1`). Not LAN-exposed;
  hal0-api is the thing that talks to it.
- **Dependency direction is inverted from what the ordering suggests** —
  `After=... hal0-api.service` is soft ordering only (an unknown unit name is
  tolerated), but the real dependency runs the other way: hindsight routes
  its own extraction/consolidation/reflection LLM calls back *to* hal0-api's
  OpenAI-compatible endpoint (`HINDSIGHT_API_LLM_BASE_URL=http://127.0.0.1:8080/v1`).
  hindsight-api is a consumer of hal0-api, not the reverse.
- **No TOML config** — every setting is an inline `Environment=` line in the
  unit itself, with one exception: `EnvironmentFile=-/etc/hal0/hindsight-llm.env`
  (the leading `-` means "ignore if absent") overrides the inline
  `HINDSIGHT_API_LLM_API_KEY=hal0-local-noauth` placeholder with the real
  client key. `installer/install.sh` writes that file at install time from
  `HAL0_CLIENT_KEY`/`HAL0_ADMIN_KEY` in `/etc/hal0/api.env`, and `hal0 auth
  rotate` keeps it fresh afterward. A hal0-owned drop-in,
  `hindsight-api.service.d/extraction-model.conf`, overrides the shipped unit
  without editing it. Its model line is always `HINDSIGHT_API_LLM_MODEL=hal0/memory`,
  the virtual id hal0's `/v1` resolves on every call to the local
  `[memory.graph].extraction_slot` or to the upstream model in
  `extraction_model`. Choosing a slot or an upstream model (**Engine model** on
  Settings → Data → Memory, or `hal0 memory graph enable --slot|--model|--local`)
  is therefore a config write that applies at once and never restarts the
  engine. The drop-in also carries `HINDSIGHT_API_LLM_TIMEOUT` and the extraction
  limits (`HINDSIGHT_API_LLM_MAX_CONCURRENT`, `HINDSIGHT_API_RETAIN_LLM_MAX_CONCURRENT`,
  `HINDSIGHT_API_RETAIN_MAX_COMPLETION_TOKENS`,
  `HINDSIGHT_API_RETAIN_LLM_MAX_RETRIES`, `HINDSIGHT_API_WORKER_MAX_RETRIES`,
  `HINDSIGHT_API_WORKER_TASK_RETRY_BACKOFF_SECONDS`, `HINDSIGHT_API_WORKER_MAX_SLOTS`, and the derived
  `HINDSIGHT_API_RETAIN_WALL_TIMEOUT`). Both concurrency keys use the same
  rendered `extraction_max_concurrent`, bounding consolidation, reflect and
  mental-model refresh along with retain. At the default of one, a long
  reflect or consolidation can delay retains until it finishes or reaches
  `llm_timeout_s`. Changing one rewrites the file and restarts hindsight-api, as does the first save after
  upgrading from a release that pinned a slot id there. That drop-in lives under `/etc/systemd/system`
  and hal0-api runs unprivileged, so the write and the follow-up restart both
  route through the `hal0-systemctl` wrapper
  (`write-hindsight-dropin` + `svc-restart hindsight`). If the wrapper or its
  sudoers grant is missing, the API's response carries a non-null
  `propagation.error` and the engine keeps the drop-in it had —
  check `hal0 doctor` for the seam rows. The wrapper allow-lists the drop-in
  body on the root side: only `#` comments, a single `[Service]` header and
  `Environment=` assignments of the keys listed above are accepted
  (`HINDSIGHT_API_LLM_MODEL` must be a `hal0/<name>` value), so a
  hand-crafted fragment (`ExecStart=`, `User=`, any other directive) is
  rejected rather than written. Run
  `hal0-systemctl check-dropin hindsight < body` to see why a body was refused;
  it validates and echoes without writing anything.
- **Overrides in `hindsight-llm.env` win.** systemd applies `EnvironmentFile=`
  after every `Environment=` line in the unit and its drop-ins. A
  `HINDSIGHT_API_LLM_PROVIDER`, `HINDSIGHT_API_LLM_BASE_URL` or
  `HINDSIGHT_API_LLM_MODEL` line in `/etc/hal0/hindsight-llm.env` therefore beats
  `hal0/memory` and whatever you picked under **Engine model**: hal0 reports the
  slot or model you chose while the engine runs the override. The **Engine
  running** row on Settings → Data → Memory (highlighted when an override applies),
  `hal0 memory graph status` and `engine_llm` in `GET /api/memory/graph/status`
  name the provider and model hindsight-api actually loads, read from the
  running engine process; when hal0-api can read neither the process nor the
  file, they say `cannot verify` instead of claiming no override. Remove the lines and
  restart hindsight-api to hand the choice back to hal0. The installer (on a box
  that has a key) and `hal0 auth rotate` rewrite the file with the API key line
  only, which drops any override you added.
- **Data root** — embedded Postgres at `/var/lib/hal0/memory/hindsight/.pg0`,
  pinned via the unit's `HOME=` env (Hindsight has no dedicated data-dir
  variable of its own).
- **Embedder** — hal0 records the embeddings provider and model the store was
  built with in `/var/lib/hal0/state/memory-embedder.json` and starts the
  engine on that pair. `[memory.models].embeddings_provider` and
  `embeddings_model` do not change it: a save is kept and reported as "saved;
  takes effect only through an embedder switch". When config and record
  differ, or the engine runs something other than the record,
  `GET /api/memory/models` and the `memory_embedder` row of `hal0 doctor all`
  say so and nothing is rewritten. `hal0 memory embedder switch <model>` is
  the one way to change it; see
  [Change the embedding model](/docs/guides/enable-memory#change-the-embedding-model).
- **First start** — on a box with no memory store, the installer writes the
  `showcase-lanes.conf` drop-in and the embedder record from
  `[memory.models]` before it starts the engine, so a new store is built with
  the configured embedder (`hindsight-ai/hs-embed-1` by default). That start
  downloads the embedder and the reranker into `HF_HOME` (about 260 MB each)
  and is healthy after about 25 s on a good link. A box that has a store, or
  whose store location is unavailable, is not touched.

  The installer watches that start for up to 240 s. If the engine's process
  exits first (about 21 s for a model id that does not exist, about 127 s
  when the model host cannot be reached), it looks for the cause:
  - The model host does not answer: nothing is changed. The engine keeps
    retrying and starts on the configured embedder once the host is back.
  - Otherwise it stops the engine, renders the drop-in with the
    engine-default embedder (`BAAI/bge-small-en-v1.5`) and nothing else
    changed, leaves the record alone, and starts again. Healthy: the embedder
    was the cause, and the record becomes the engine default (source
    `first-start-fallback`). Still down: something else is wrong, so the
    configured drop-in is put back and the engine keeps retrying.

  Each case prints a `!!` line. hal0-api seeds the default banks when the
  engine comes up later. An engine still on its first process at 240 s is
  left on the configured embedder; if it fails after that it restarts in a
  loop, a `.pg0` directory exists, and a re-run of the installer skips this
  step. The `memory` row of `hal0 doctor all` warns that the engine is
  degraded or unreachable. Fix the cause shown by
  `journalctl -u hindsight-api -n 40`, then run
  `sudo systemctl reset-failed hindsight-api` and
  `sudo systemctl restart hindsight-api`. To give the configured embedder up
  instead, only where the engine has never been healthy (the store is empty):
  stop `hindsight-api`, remove `/var/lib/hal0/memory/hindsight/.pg0`,
  `/var/lib/hal0/state/memory-embedder.json` and
  `hindsight-api.service.d/showcase-lanes.conf`, set
  `[memory.models].embeddings_model`, and re-run the installer.

### Config files it reads

| File | Purpose |
|---|---|
| `/etc/hal0/hindsight-llm.env` | Optional `EnvironmentFile`, `-` prefixed (ignored if absent) — supplies the real `HINDSIGHT_API_LLM_API_KEY`, written by `installer/install.sh` and kept fresh by `hal0 auth rotate`. A `HINDSIGHT_API_LLM_PROVIDER`, `_BASE_URL` or `_MODEL` line here overrides hal0's engine target. |
| `hindsight-api.service.d/extraction-model.conf` | hal0-owned systemd drop-in under `/etc/systemd/system` — sets `HINDSIGHT_API_LLM_MODEL=hal0/memory`, `HINDSIGHT_API_LLM_TIMEOUT` and the extraction limits; written when the timeout or a limit changes (`hal0 memory graph enable`, the Memory settings page) or the file is stale. |

### Health endpoint

`GET http://127.0.0.1:9177/health` — polled by the installer after start (up
to 40 × 3s) and by `hal0 doctor verify`'s memory-engine check. If
unreachable while the memory feature is enabled, hal0's own health report
degrades to `WARN "engine enabled but :9177 unreachable"` rather than
failing hard.

## Starting, stopping, and inspecting

Same commands for both units:

```sh
systemctl status  hal0-api
systemctl start   hal0-api
systemctl stop    hal0-api
systemctl restart hal0-api
systemctl enable  hal0-api        # already enabled by the installer

journalctl -u hal0-api -f         # follow
journalctl -u hal0-api -n 40      # last 40 lines — the recovery recipe install.sh itself uses
```

Swap `hal0-api` for `hindsight-api` for the memory engine. `hal0-api`'s own
self-restart path (the updater) shells out to the same `systemctl restart`
via the `hal0-systemctl` wrapper, so a manual restart and an update-triggered
one behave identically.

### Log access over HTTP

Both units' logs are also available without shell access, proxied from
journald with secret-redaction applied:

```
GET /api/logs?unit=hal0-api&n=200[&since=...&level=...]
GET /api/logs/stream?unit=hal0-api&level=...     # SSE tail
```

Swap `unit=hindsight-api` for the memory engine's logs. Both routes are
admin-tier, and both read only hal0's own units: `hal0.target`, any
`hal0-*` unit (`hal0-api`, `hal0-slot@<id>`, `hal0-agent@<id>`,
`hal0-openwebui`, `hal0-bench*`, ...), `hindsight-api` and `hermes-gateway`.
Any other unit is rejected with a 400 `system.logs_error`.
