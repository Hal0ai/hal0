hal0's slots were originally addressed on disk, in systemd, and in podman by
their mutable **name** (`/etc/hal0/slots/primary.toml`,
`hal0-slot@primary.service`, the `hal0-slot-primary` container). A rename was
therefore never a pure label change — it touched every one of those
artefacts. The **id-keying migration** flips a box over to addressing slots by
their stable, never-reused `id` instead: `primary.toml` becomes `143.toml`
(with `id = 143` and `name = "primary"` both embedded inside it so the file
stays self-describing), and the matching state file, Quadlet unit, and podman
container rename to match.

This is a **one-shot, operator-run, destructive** migration. It is never
triggered automatically by a boot or an update — you run it deliberately,
during a maintenance window.

<Aside type="danger" title="Read this before you run it">
An earlier rehearsal of this flip (on the box internally called "143")
**split-brained**: the migration itself completed cleanly, but the *running*
hal0-api was still on a version that only knew how to read name-keyed slot
TOMLs. On restart it didn't recognize the new `<id>.toml` files, so it
re-seeded name-keyed slots *alongside* them — the box ended up with both an
id-keyed and a name-keyed copy of every slot, 11 in an error state and 7
duplicated. Recovery was a restore from backup.

**The fix is sequencing, not mechanics**: the hal0 version that ships this
runbook already reads BOTH name-keyed and id-keyed slots (the bilingual
read/write layer — P3-runtime-db increments 0–3). As long as that version is
the one running when you flip, there is nothing left to read the old format
and nothing to re-seed. Do not attempt this migration on any hal0 build older
than the one this page ships with.
</Aside>

## When to run it

- You want slot renames to stop touching systemd units / podman containers
  (the whole point of the id-keyed layout).
- You're about to build on the P3-runtime-db lanes that follow this one
  (state.json → SQLite, migration 006+) — those assume an id-keyed layout.
- You are NOT required to run it. A name-keyed box keeps working exactly as
  it does today, indefinitely — this is opt-in, not a deprecation.

## Prerequisites

1. **hal0 is already updated** to a version that includes the bilingual
   read/write layer (P3-runtime-db inc0-3) and this migration CLI
   (inc4) — confirm with `hal0 --version` / your update log, not by
   assumption. This is the exact ordering the 143 rehearsal got wrong.
2. You have a maintenance window. The migration needs hal0 **stopped**
   (see below) — slots go offline for the duration.
3. Enough free space under `/var/lib/hal0/backups/` for a tarball of
   `/etc/hal0/slots`, `/var/lib/hal0/slots`, and `hal0.db` (typically small —
   low tens of MB even with many slots).

## Procedure

<Steps>

1. **(Optional) Preview the plan without touching anything.**

   ```bash
   hal0 slot migrate-id-keying
   ```

   Dry-run by default (matching the other `slot migrate-*` commands) —
   prints the computed name→id assignment for every configured slot — no
   file is moved, no id is minted. Use this to sanity-check the plan (slot
   count, which ones are already id-keyed from a prior partial run) before
   committing to downtime. (`--dry-run` still parses as a no-op alias for
   older scripts, but it's redundant now — omitting `--apply` already
   previews.)

2. **Stop hal0 first.** The migration refuses to run while `hal0-api` or any
   `hal0-slot@*` unit is active — flipping artefact names out from under a
   live runtime is exactly the split-brain scenario above.

   ```bash
   sudo systemctl stop 'hal0-slot@*' hal0-api
   ```

   Or let the migration do it for you with `--stop-services` (step 3).

3. **Run the migration.**

   ```bash
   hal0 slot migrate-id-keying --apply
   ```

   - Prints a **backup path first** — a timestamped tar under
     `/var/lib/hal0/backups/slot-id-keying-<UTC-timestamp>.tar.gz`
     containing `/etc/hal0/slots`, `/var/lib/hal0/slots`, and `hal0.db`
     (+ its `-wal`/`-shm` sidecars). This tarball is the **only rollback
     path** — the migration itself has no undo.
   - Prompts for confirmation (skip with `--yes` for scripted runs).
   - If any `hal0-slot@*` / `hal0-api` unit is still active, it warns and
     refuses; pass `--stop-services` to have it stop them for you before
     proceeding.
   - Reports each slot migrated (`name -> id.toml`) and any slot already
     id-keyed (skipped).

4. **Restart hal0.**

   ```bash
   sudo systemctl daemon-reload
   sudo systemctl start hal0-api
   ```

   `hal0-api` boots, reads the now-id-keyed slot TOMLs (via the bilingual
   loader — every stem it finds is classified id vs. name and loaded either
   way), and starts each slot's Quadlet-generated `hal0-slot@<id>.service`.

5. **Verify.**

   ```bash
   hal0 slot list
   ```

   Every previously-configured slot should appear under its real display
   name (never a bare digit) and reach its prior running state. Cross-check
   with:

   ```bash
   systemctl list-units 'hal0-slot@*' --no-legend
   ```

   Unit names are now `hal0-slot@<id>.service` (e.g. `hal0-slot@143.service`)
   rather than `hal0-slot@<name>.service`.

</Steps>

## Idempotency

The migration is safe to re-run. Its idempotency marker is the TOML's own
`id` field matching its filename (`143.toml` with `id = 143`) — an
already-migrated slot is reported as skipped, not re-migrated, and a crash
mid-run (TOML moved but the matching `state.json` not yet moved) is completed
on the next run rather than duplicated. This means retrying after any failure
is always the right first move before reaching for the backup.

## Rollback

If anything looks wrong after restart (a slot missing, duplicated, or stuck
in error):

<Steps>

1. Stop hal0 again: `sudo systemctl stop 'hal0-slot@*' hal0-api`.
2. Extract the pre-flight backup tarball over the live paths:

   ```bash
   cd /
   sudo tar -xzf /var/lib/hal0/backups/slot-id-keying-<timestamp>.tar.gz \
     --transform 's,^etc-hal0-slots,etc/hal0/slots,' \
     --transform 's,^var-lib-hal0-slots,var/lib/hal0/slots,'
   sudo cp /var/lib/hal0/backups/<extracted>/hal0.db /var/lib/hal0/hal0.db
   ```

   (Adjust the extraction to your box's actual paths if you're on a
   `HAL0_HOME`-relocated dev install rather than the FHS layout.)
3. `sudo systemctl daemon-reload && sudo systemctl start hal0-api`.
4. Confirm every slot is back to name-keyed and healthy with `hal0 slot list`
   before trying the migration again.

</Steps>
