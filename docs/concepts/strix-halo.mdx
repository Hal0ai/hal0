hal0 is hardware-agnostic in principle, but it is designed around one reference
platform: **AMD's Ryzen AI Max+ ("Strix Halo")**. This is an APU that pairs a
capable Radeon iGPU and an XDNA NPU with a large pool of memory shared between
the CPU and GPU. Understanding that shape explains most of hal0's design — the
GPU arbiter, the device choices, and the way memory is reported.

## Three compute engines, one chip

A Strix Halo machine gives hal0 three places to run a model:

<CardGrid>
  <Card title="Radeon iGPU" icon="seti:default">
    The integrated GPU runs LLM and image workloads through either ROCm
    (`gpu-rocm`, which requires `/dev/kfd`) or Vulkan (`gpu-vulkan`, which
    requires a render node and a Vulkan-validated runner image). It's detected
    as an AMD `amdgpu` device; the marketing name comes from the system at
    probe time.
  </Card>
  <Card title="XDNA NPU" icon="seti:config">
    The AMD XDNA NPU is driven by FastFlowLM (FLM) on the `npu` device. hal0
    detects it via the `amdxdna` driver (the `/dev/accel` device nodes), and one
    `flm serve` process serves the NPU trio — chat, STT, and embeddings.
  </Card>
  <Card title="CPU" icon="laptop">
    The Ryzen CPU is always available as the `cpu` device and is the home for
    CPU-only runtimes such as text-to-speech.
  </Card>
</CardGrid>

These map directly to four of hal0's five canonical devices: `gpu-rocm`,
`gpu-vulkan`, `npu`, and `cpu`. (The fifth, `gpu-cuda`, exists too — see the
note on NVIDIA below — but it has nothing to do with Strix Halo, which has no
NVIDIA silicon.) A slot's `device` field is what picks one of these — see
[Capabilities & profiles](/docs/concepts/capabilities-and-profiles) for why
that ownership lives on the slot, not the profile, as of v1.0.

## ROCm or Vulkan on the iGPU

The iGPU can run LLM slots through two backends. hal0 treats them as distinct
devices, and a slot always names one explicitly — the runner is launched with
an explicit device pin, never "whatever llama.cpp picks":

- **ROCm** (`gpu-rocm`) — AMD's compute stack, and the lane hal0 seeds where
  the box can run it. It needs the `/dev/kfd` compute node visible to hal0 and
  to the slot containers; a `gpu-rocm` slot without it refuses to load.
- **Vulkan** (`gpu-vulkan`) — the Mesa/RADV path. It needs only a DRM render
  node (`/dev/dri/renderD*`), which makes it the lane for boxes where `/dev/kfd`
  was never forwarded — an unprivileged LXC, for instance. It is also the lane
  the non-llama.cpp Vulkan runtimes use (Kokoro TTS, whisper.cpp, ComfyUI).

On the current validated runner, **Vulkan is the faster of the two on this
hardware** — +13.96% prefill and +20.45% decode on a Strix Halo box, with much
tighter variance ([full numbers](/docs/reference/hardware-matrix)). ROCm is
seeded anyway, because it carries hal0's validation history and is the lane
MTP/speculative decode is tuned against. That choice is revisited at GA; in the
meantime switching is a supported, one-command operation — see below.

<Aside type="caution">
**The Vulkan LLM lane is gated on the runner image, by design.**

hal0's LLM slots all run one runner image, a single HIP + Vulkan build. On the
`ade07ba` lineage that image's Vulkan backend emitted invalid tokens for every
model it served, at full nominal speed, while HTTP 200, container health,
`hal0 doctor` and the streaming `done` frame all read green — hal0 shipped a
release where an entire box served nonsense and every dial was in the green.

The image was fixed, and the lane came back with two permanent guards:

1. A `gpu-vulkan` LLM slot may only launch from a runner image whose Vulkan
   backend has been validated. Anything else — including the old lineage — is
   refused at slot load, by name, with the ticket number.
2. Every LLM slot, on every lane, must pass an output-sanity probe before it
   is marked ready. A backend that emits nonsense fails readiness in about a
   second instead of serving it for hours.

If you pin a slot to your own runner image, expect the Vulkan lane to refuse
it until that image is added to the validated set. That refusal is the feature.
</Aside>

### Switching a slot to the Vulkan lane

Both lanes are first-class, and moving between them is a normal operation —
not a workaround:

```sh
hal0 slot edit agent --hardware vulkan     # gpu-rocm -> gpu-vulkan
hal0 slot edit agent --hardware rocm       # and back
```

In the dashboard, open the slot's drawer and change **Device** in the same
place. Either way the slot is re-rendered and restarted on the new lane.

Two checks stand between the switch and serving traffic, and both are the
point rather than an obstacle:

1. **Preflight** — the target lane's devices must be present (`/dev/kfd` for
   ROCm, a render node for Vulkan) and, for Vulkan, the slot's runner image
   must be one whose Vulkan backend is validated. A refusal here names the
   image and the reason.
2. **Output sanity** — the slot answers a fixed prompt before it is marked
   ready. A lane that emits nonsense fails in about a second instead of
   serving it.

Why you might switch: the measured prefill/decode advantage above. Why you
might not: MTP / speculative-decode profiles are tuned on the ROCm lane, so a
slot leaning on those may do better where it is.

## Unified memory is the tuning target

The defining feature of Strix Halo — and the reason it's such a good fit for
local inference — is **unified memory**. The iGPU doesn't have a large dedicated
VRAM bank; instead it shares the system's RAM through a GTT pool. A single large
memory pool can be handed to whichever engine needs it, so you can load models
far larger than a typical discrete GPU's VRAM would allow.

![The dashboard Unified Memory bar — one 128 GB pool with each slot's allocation colour-coded and the free headroom that actually remains](/screenshots/unified-memory-hero.png)

This shapes how hal0 reports memory. It does **not** add system RAM to GPU VRAM,
because on a unified-memory APU that would double-count — the GPU's memory *is*
host RAM shared via GTT. Instead the probe derives a single
**unified-memory pool** figure and surfaces that as the headroom you actually
have. (hal0 detects the unified-memory shape by recognising the tiny VRAM
carve-out alongside a large GTT pool; on a discrete GPU it reports VRAM and RAM
separately.) When running inside a container or VM with a memory cap, hal0 also
reads the cgroup limit and treats it as a third constraint, so the reported
headroom reflects what you can really use.

Because one pool is shared, two GPU workloads can't both hold their weights at
once. That's exactly why the [GPU arbiter](/docs/concepts/slots#the-gpu-arbiter)
exists: it gives the GPU's memory to either the LLM slots or the image slot, one
group at a time, rather than letting them fight over the pool.

![The Slots view: the iGPU GTT carve-out bar above the Inference Engine, where iGPU and FLM (NPU) slots share the unified-memory pool](/screenshots/npu-occupancy.png)
*The shared GTT carve-out above the Inference Engine — iGPU slots and FLM (NPU) slots both draw from one unified-memory pool.*

## What the hardware probe detects

![hal0 hardware metrics panel showing CPU, GPU, NPU, RAM, and disk readings](/screenshots/hardware-metrics.png)
*The hardware dashboard panel after a successful probe run.*

hal0 ships a hardware probe that inspects the machine and writes the result for
the rest of the system to read. It detects the CPU (model, cores, threads),
system RAM and available memory, the GPU(s) and their ROCm/Vulkan capability,
the NPU (presence, vendor, driver), the unified-memory pool, any cgroup memory
cap, and free disk space. It also classifies the **platform** — `strix-halo` is
its own value, alongside generic ones such as `bare-metal-amd-gpu`,
`bare-metal-nvidia-gpu`, `lxc`, `kvm`, `proxmox-kvm`, and `wsl2` — and the
dashboard uses that to label memory as "unified" only on the platforms where
that's true.

<Aside type="caution">
CUDA has nothing to do with Strix Halo — there's no NVIDIA silicon on this
chip, and the hardware probe classifies an NVIDIA-equipped host as
`bare-metal-nvidia-gpu`, never `strix-halo`. But hal0 is not exclusively a
Strix Halo tool: it also ships an **experimental** `gpu-cuda` device for
discrete NVIDIA GPUs on *other* hosts (the upstream
`ghcr.io/ggml-org/llama.cpp:server-cuda` image, run via
`nvidia-container-toolkit`/CDI; without CDI present the installer falls back
to Vulkan on that same NVIDIA card). None of this changes the story on this
page — hal0's reference platform, and the one every default and bench number
here is tuned for, remains the AMD Strix Halo APU on Linux x86_64.
</Aside>
