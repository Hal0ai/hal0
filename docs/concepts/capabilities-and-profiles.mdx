Three distinct ideas shape every slot in hal0: **capabilities** describe what
you want a slot to do, **profiles** describe the whole tune it runs with
(flags, context window, thinking default, vision, MTP), and the **slot itself**
describes where it runs. The model row sits beside them and records only
facts about its file. Each setting has exactly one owner, and the boundary is
enforced at every write path, not just a naming convention.

## Capabilities: what a slot does

A **capability** is an overlay the dashboard uses to group related slots under
one operator-friendly idea. Rather than make you hand-configure each underlying
slot, you pick a capability and its child, and hal0 reconciles the real slot for
you. The capability groups are:

| Capability | Children → underlying slot |
|---|---|
| `embed` | `embed` → `embed`, `rerank` → `rerank` |
| `voice` | `stt` → `stt`, `tts` → `tts` |
| `img` | `img` → `img` |
| `vision` | `vision` → `vision` |

Chat is deliberately **not** a capability group — it lives in the dedicated chat
slot and is configured directly, not through the capability overlay.

The selected capabilities are stored in `capabilities.toml`. When you apply a
change, the orchestrator computes one atomic change set across both
`capabilities.toml` and the affected slot TOML — they're written together so the
two can never drift mid-apply — and only then drives the slot lifecycle:
turning a capability on loads its slot, turning it off unloads it, and changing
the model or device swaps it. On first boot, hal0 seeds `capabilities.toml`
from whatever the slots already declare, so the overlay reflects reality
immediately.

An apply that enables a child (`enabled: true`) whose selected model has no
weights on disk is refused with `409 capability.model_not_downloaded` before
anything is written or started. When the model is pullable, the error
`details` carry a `pull_endpoint` (`/api/models/{id}/pull`). Pull first, then
apply — or stage the choice with `enabled: false`, which is still accepted.
Selections on the `npu` backend are exempt.

<Aside type="note">
The capability layer is a convenience, not a separate runtime. Underneath, every
capability resolves to an ordinary [slot](/docs/concepts/slots) that the
SlotManager runs as a podman container.
</Aside>

## Profiles: the whole tune

A **profile** is a reusable, device-agnostic tune. It holds everything that
decides *how* a model runs in a slot, and nothing about *where*:

| Field | Meaning |
|---|---|
| `flags` | Free llama-server flags: KV-cache types, batch and ubatch size, sampling, reasoning, `--parallel`. |
| `ctx_size` | The context window in tokens (128 to 16,777,216). Unset means the model's native window, capped at 32768, or 8192 when the model reports none. |
| `enable_thinking` | The request-time reasoning default for requests the slot serves. A request can always override it; unset means off unless the request asks. |
| `vision` | `auto` loads the model's multimodal projector when it has one; `off` never does. |
| `mtp` | `auto` drafts with the model's MTP heads when it has them and the runner supports it; `off` never does. |
| `runner` | Optional runtime, a `RUNNER_IMAGES` registry key. See "Profiles can carry a runtime" below. |
| `intent`, `cloned_from` | Informational: the card headline, and the profile this one was copied from. |

A profile carries no container image ref and no placement: no device, GPU
index, thread count or layer count. All of that lives on the
[slot](/docs/concepts/slots#who-owns-what-slot-model-profile). The context
window is the profile's `ctx_size` field, not a flag: `--ctx-size` is on
hal0's managed-args denylist and can never appear in a profile's `flags`.

The model holds only facts about its file (path, architecture, native
context, chat template, projector, whether it has MTP heads). A slot names
exactly one profile. To run one model with different tuning — another
context size, other sampling, a different KV-cache type — make a second
profile and point another slot at it. No tune lives on the model, so two
slots that share a file never conflict.

```sh
hal0 profile create agent-32k --from agent --ctx-size 32768
hal0 profile edit agent-32k --flags "-fa auto -b 2048 -ub 512 --temp 0.6" --thinking
hal0 slot edit scratch --profile agent-32k
hal0 slot restart scratch
```

`hal0 profile list` and `hal0 profile show <name>` read the catalog.
`hal0 profile create <name> --from <profile>` duplicates a seed or a custom
profile and applies any other options on top; `hal0 profile edit <name>`
changes a custom profile (`--flags`, `--ctx-size` / `--clear-ctx-size`,
`--thinking` / `--no-thinking` / `--clear-thinking`, `--vision`, `--mtp`,
`--runner`, `--intent`). Slots running an edited profile pick the change up
at their next restart. A profile that a slot still names can't be deleted
(`profiles.in_use`); the dashboard's Profiles tab shows which slots use each
one.

The seed catalog is organized by **workload**, so the same profile works
regardless of which device a slot targets:

| Profile | Purpose |
|---|---|
| `chat` | Minimal generic chat — fallback for unknown models |
| `agent` | The agent workload: deterministic sampling, reasoning off, vision off, 64K context (`ctx_size` 65536 — the bundled Hermes agent needs at least 64,000) |
| `utility` | The utility workload: generic chat flags, 64K context |
| `coding` | Code generation: higher temperature, reasoning off, vision off |
| `embedding` | Pooled embeddings (`--embedding`, wide ubatch), 4096 context |
| `reranking` | Reranking (`--reranking`), 4096 context — always a separate instance from `embedding` |
| `cpu-chat` | CPU-safe chat |
| `flm` | FLM inference on the NPU (chat/embed/STT), 16384 context |
| `kokoro` | Text-to-speech (Kokoro), CPU |
| `qwen3-tts` | Text-to-speech (Qwen3-TTS), GPU |
| `moonshine` | Speech-to-text (Moonshine), CPU |
| `comfyui` | Image generation (ComfyUI) |
| `brain` | The hal0-brain steward workload (small tool-routing model), 64K context |

`embedding` and `reranking` are deliberately separate profiles/slots rather than
one server handling both — combining `--embedding` and `--reranking` on a
single llama-server instance produces all-zero scores.

Every slot hal0 ships names one of these seeds. Further workload variants
(`chat-long-context`, `dense`, `moe`, `thinking`) are published as addons that
you can import as custom profiles — see [Profile
addons](/docs/reference/profile-addons).

### Seed profiles are virtual

Seed profiles live in **code**, not in `/etc/hal0/profiles.toml`. On every
load, hal0 overlays the code definition of each seed name over whatever is on
disk — the code definition always wins, even over a stale on-disk copy — and
if `profiles.toml` is absent entirely, the seeds are still returned in memory,
so the profile catalog is never empty. Saving the catalog back out strips
every seed-named key before writing, so a seed can never accidentally get
pinned to a stale on-disk copy.

Seed profiles are immutable through the API too — updating or deleting a
profile whose name matches a seed is rejected outright. **The only way to
customise one is to clone it**: `hal0 profile create <new-name> --from
<seed>`, the dashboard's slot drawer ("Duplicate & edit" beside the profile
picker), or the Profiles tab, where "Edit" becomes "Edit a copy" for a seed
and forks a `<seed>-custom` profile (with `cloned_from` recording the
original) that you're then free to tune. Delete stays disabled on the seed
itself.

Each profile is also classified into a **runtime family** (llama-server,
FLM, Kokoro, Qwen3-TTS, or ComfyUI) that determines which slot types it can
serve — a coarser, code-derived classification, not to be confused with the
optional `runner` **runtime** key described below, which names one specific
registry entry *within* the llama-server family. Profiles are portable: any
profile can be exported to a self-contained, checksummed `.hal0profile.json`
envelope (which round-trips the `runner` key too) and imported on another
host — the same sharing model [stacks](/docs/concepts/stacks) use. An
envelope naming a runtime this host does not carry still imports: the unknown
key is stripped and the profile lands with no runtime pinned, reported as
`runner_stripped` on both the dry run and the commit. Importing never blocks
on hardware or registry differences. Envelopes use profile schema 2; an
envelope exported before profile-centric config (schema 1) is refused whole
rather than imported with fields silently dropped.

## Where hardware placement lives: the slot

A slot carries its own **device** field — `gpu-rocm`, `gpu-vulkan`,
`gpu-cuda`, `cpu`, or `npu` — plus `gpu_index`, `n_gpu_layers`, `threads`, and
`binary` (a `RUNNER_IMAGES` registry key — the dashboard calls this the
slot's **Runtime**; `image_pin` is a debug-only escape hatch for a full
image override, not a normal way to reach a shipped runtime). This "hardware
grid" is what the slot owns exclusively, validated at config-load time so a
typo fails fast. Which physical GPU device nodes get mapped into the
container is decided from the slot's `device` alone.

<Aside type="tip">
If you're auditing a config: the slot's `device` is authoritative, and a
profile never contributes hardware. The only placement-adjacent thing a
profile can carry is its optional `runner`, described below.
</Aside>

## The Runtime registry

Every image hal0 ships is registered as a `RUNNER_IMAGES` entry — a
first-class runner reachable from the slot drawer's Runtime select, never
only through the `image_pin` escape hatch. A pin-only image, catalogued for
discovery but not offered anywhere a slot's Runtime is picked, is retired as
a shipping shape (ADR-0006).

| Runtime (title) | Registry key | Tier | Lane(s) | Notes |
|---|---|---|---|---|
| Standard | `standard` | default | ROCm + Vulkan | llama.cpp for AMD GPUs; the only runtime allowed both lanes. Runs plain GGUF models. |
| CPU | `cpu` | default | — | llama.cpp on the processor, no GPU needed; a slow fallback. |
| NVIDIA CUDA | `cuda` | optional | CUDA | llama.cpp for NVIDIA GPUs. |

The tier is the registry's `Runner.tier` (ADR-0027): default runtimes are
the set every box is expected to have and are listed first; optional ones
are opt-in. (The non-llama-server runtimes — NPU (FastFlowLM), Kokoro
speech, Moonshine transcription and ComfyUI, all default, and the optional
Qwen3 TTS — are `RUNNER_IMAGES` entries too, but each is fixed to its own
slot type rather than offered as a pick in the Runtime select.)

In the slot drawer's Hardware group, this registry drives one **Runtime**
select — each option showing its title, a one-line blurb, and an
install-state chip, filtered to what the slot's type and this host's
hardware can actually run — plus a **Lane** pill row (Auto / ROCm / Vulkan)
that only appears when the selected runtime supports more than one backend
(today, only Standard). Picking a single-lane runtime derives the slot's
device directly; picking a lane on a dual-lane runtime does the same thing
the CLI's `hal0 slot edit <name> --hardware <rocm|vulkan>` does. Either way,
switching restarts the slot on save. An "Advanced — image & version"
disclosure holds the read-only effective image ref (pinned-by-release, or
"debug pin" when one is set), a pointer to [Manage runner
images](/docs/guides/manage-runner-images) for version/rollback management,
and the debug `image_pin` field — which never widens or narrows the Runtime
options above it.

### Profiles can carry a runtime

A profile's optional `runner` field names one runtime from this box's
registry. In the profile form this is the **Runtime** select, with "— Auto ·
no runtime pinned —" clearing it. The list is every runtime the registry
carries — the single-purpose ones (Kokoro, ComfyUI, …) included, since a
profile has no slot type to narrow it to a family — minus any whose every
lane the host has explicitly probed as infeasible. Options read the same as
the slot drawer's: title · lane(s) · install state. A runtime key the profile
already carries but this box's registry no longer knows keeps its own option
and a warning rather than being silently rewritten. None of the shipped seed
profiles set a runtime, and the select renders disabled on a seed (forking it
via "Edit a copy" is what unlocks it). A profile carrying a runtime shows a
runtime badge chip on its card.

Applying a runtime-carrying profile to a slot is **profile wins**: on save,
the slot's `binary` switches to the profile's runtime key, and — for a
single-lane runtime — its `device` follows to the matching lane (a
multi-lane runtime like Standard only flips `binary` and leaves
the current lane alone). The slot drawer's Profile row previews this before
you save, and `hal0 slot create --profile <profile>` applies the same rule at
create time. Swapping the slot's model keeps its profile, so it never changes
the runtime. The apply is blocked only when it's physically impossible — e.g.
picking a ROCm-only runtime on a host with no `/dev/kfd` — which fails with a
plain-language error before anything is written, rather than partially
applying.

### Unsupported quantizations

hal0 ships no llama.cpp fork, so no runtime loads ROCmFPX-family, IU4 or
ActiveFPX GGUFs. Rather than warn at assignment and crash at load, hal0
refuses them up front: adding such a file or pulling it answers 422
`models.unsupported_quant`, a library scan skips it (`unsupported_quant:<label>`),
and launching a slot whose model is one answers 422 `slot.unsupported_quant`.
Use a plain GGUF build of the same model. Reference:
[Providers, profiles & devices](/docs/reference/providers-profiles-devices/#unsupported-quantizations).

## Flag precedence: how a launch command is assembled

A container slot's actual launch command is built from four layers,
concatenated in a fixed order and then deduplicated **last-wins** per flag
(short and long spellings of the same flag — `-b`/`--batch-size`,
`-ngl`/`--n-gpu-layers`, `-ctk`/`--cache-type-k`, and friends — are treated as
the same key; `--lora`, `--draft-model`, and `--override-kv` are appended,
never deduped, since llama-server treats repeats of those additively):

1. **base** — `--host`/`--port`/`--model`/`--alias`/`--ctx-size`, always
   present. The context size is the profile's `ctx_size`, else the model's
   native window capped at 32768, else 8192 — see "The context window comes
   from the profile" in [Slots](/docs/concepts/slots#who-owns-what-slot-model-profile).
2. **model** — facts about the file: family quirks, `--jinja` (added when the
   runner supports it, unless the model's `jinja` fact is `false` or the
   profile is an embedding or reranking one), `--chat-template-file`, and
   `--mmproj` (only when the profile's `vision` is `auto`).
3. **profile** — the MTP draft bundle when MTP is in effect, then the
   profile's `flags`. Because the flags come second, a profile's own
   `--spec-draft-*` values win over the bundle.
4. **slot** — the hardware grid: `-ngl` and `--threads` from
   `n_gpu_layers`/`threads`, `--metrics`, and, when MTP is in effect,
   `--spec-draft-device` derived from the slot's own device.

The slot Edit drawer's **resolved command** panel shows the fully assembled
argv with a per-flag provenance badge (`base`, `model`, `profile` or `slot`),
backed by `GET /api/slots/{name}/resolved` — the same resolver drives both
this preview and the actual launch, so what you see is what runs.

Each layer owns its flags. A profile's `flags` are screened when the profile
is saved and again at launch: hardware flags, hal0-managed flags, model-fact
flags, host-owned flags and bare positional arguments are refused, in every
spelling llama.cpp accepts. See [Edit
configuration](/docs/guides/configure#launch-flags-are-screened-on-the-profile)
for the list.

### Family quirks

Some model architectures need flags no profile should reasonably have to know
about. The model layer carries a code-shipped table of per-family overrides
(`config/data/family_defaults.toml`, keyed by architecture) that is prepended
to the model layer. It ships empty today, so no family currently adds flags;
a family-specific recipe is a profile you pick.

## MTP: the model has heads, the profile decides

MTP (multi-token prediction / speculative decoding) takes two inputs:

1. **Model: does the file have MTP heads?** An explicit `mtp` fact on the
   model row wins in either direction. Left unset, the registry `mtp` tag
   decides. There is no filename-based sniff.
2. **Profile: `mtp = "auto"` or `"off"`.** `auto` (the default) drafts when
   the model has heads *and* the launching runner declares MTP support; `off`
   never drafts. MTP is also never used in embedding or reranking mode.

A slot has no MTP setting. To stop one slot drafting, give it a profile with
`mtp = "off"`. Under `auto`, a model without heads launches without a draft
(hal0 logs `mtp.auto_off_model_ineligible`), so there is no way to force
llama-server into the "model doesn't contain MTP layers" refusal.

<Aside type="tip">
When MTP is in effect, hal0 merges a tuned speculative-decoding flag
bundle into the profile layer as **defaults only** — any `--spec-draft-*`
flag in the profile's own `flags` wins over the bundle. The bundle's draft
device (`--spec-draft-device`) is set by the slot layer from the slot's own
device, and a profile may not set it.
</Aside>

In the dashboard, the MTP choice is the **MTP** row of the profile form
(Auto or Off). The model drawer shows only the **MTP heads** file fact, and
the slot drawer and stack rows have no MTP control.

## The NPU trio

The AMD XDNA NPU is driven by FastFlowLM (FLM), and one detail shapes how hal0
uses it: a **single `flm serve` process serves three modalities at once** —
chat, speech-to-text, and embeddings. hal0 calls this the **NPU trio**.

There is one containerized NPU slot. Its chat role routes through the slot's
upstream like any other slot. The other two modalities ride as **shadow slots**
— `stt` and `embed` — whose requests are posted straight to the same
container's port when their slot records are enabled. There's no second process
and no separate model server: the three endpoints are the same FLM process
answering on one static port.

Because the XDNA hardware context admits only one NPU LLM at a time, hal0
enforces NPU exclusivity: you can't enable a second `device=npu` chat slot. When
the NPU container isn't dispatchable, trio requests degrade with a clear
`npu.trio_unavailable` error rather than failing obscurely.
