hal0 can give your platform a persistent **memory** — a store of facts that both
the operator surfaces and the bundled agent can write to and recall from. It's a
deliberate, gated subsystem behind a single config flag: powerful when it's on, and
completely absent when it's off. A fresh install turns it on for you; it stays
a conscious, revertible choice rather than something that silently accumulates
data on an existing box.

The dashboard shows memory in one place, the Memory area (Health, Facts,
Knowledge, Operations and Agents), over the same engine-neutral backend
described on this page. See [The Memory area](/docs/guides/memory-workspace)
for the UI tour.

## What memory is

The memory subsystem is an engine-neutral layer behind two surfaces: the
`/api/memory/*` REST routes (which the dashboard's Memory view uses) and the
`/mcp/memory` MCP server, which agents and external tools use. Both speak to
the same provider, so a fact written by an agent over MCP is the same fact
the dashboard shows.

Open WebUI is a third, read-only consumer when its global
`hal0_hindsight_rag` Filter is enabled. `POST /api/memory/context` retrieves
only the `shared` namespace as an anonymous caller, returns the raw chunks
behind visible recalled facts and then the facts they do not cover, and
contributes them to Open WebUI's existing RAG sources and citations. It cannot
request private or project scope; use MCP for those explicit operations. The
Filter fails open when memory is unavailable. See [Open WebUI — chat companion
wiring](/docs/guides/open-webui#shared-hindsight-memory-in-rag).

The MCP surface covers the full read/write/curate/synthesize lifecycle:

- **Core**: `memory_add`, `memory_search`, `memory_list`, `memory_delete`,
  `memory_recall` — the token-budgeted, observation-aware retrieval path
  (preferred over `memory_search`), with native per-result relevance scores
  and optional entity/chunk/source-fact enrichment.
- **Reflect**: `memory_reflect` — ask a question and get an LLM-written
  answer grounded in recalled facts, instead of a raw fact list. Answers
  `{status: "unsupported"}` on an engine without the capability (the
  pgvector fallback) instead of erroring.
- **Curation**: `memory_curate` edits a fact or soft-invalidates/reverts it
  (reversible, no approval gate) — the non-destructive "this is wrong"
  correction path, as distinct from `memory_delete`. `memory_history` shows
  a fact's revision trail — but only **observation** facts have history;
  world/experience facts 404 there by design — see Fact types below.
- **Mental models**: `memory_mental_model_list` / `_get` / `_create` /
  `_update` / `_delete` / `_refresh` — standing questions ("what does the
  operator prefer for X") whose answer is kept refreshed from memory.
- **Directives**: `memory_directive_list` / `_get` / `_create` / `_update` /
  `_delete` — standing instructions injected into an agent's prompt every
  turn.
- **Async operations**: `memory_operation_list` / `_get` / `_cancel` /
  `_retry` — retain is async by default, so these are the poll target for
  `memory_add`'s `operation_id` and for mental-model refreshes and bank
  consolidation.
- **Bank introspection**: `memory_tags_list`, `memory_bank_stats`,
  `memory_bank_consolidate` — read-only counts plus an early-trigger for
  consolidation. No destructive bank operations (delete/clear a whole bank)
  are exposed over MCP; those stay operator-only under `/api/memory/*`.

Every write/destructive tool goes through the same namespace ACL and
approval-gate pattern as `memory_add`/`memory_delete` — `memory_curate`'s
`state` toggle is reversible so it stays autonomous, while
`memory_mental_model_delete` and `memory_directive_delete` gate for operator
approval the same way a bulk `memory_delete` does. The full tool-by-tool
schema lives in [MCP tools: hal0-memory](/docs/reference/mcp-tools-memory) — this page covers the
concepts those tools operate on.

![The Memory area's bank tab in list mode — the stored facts with their sources, and the filters that narrow them](/screenshots/memory-bank.png)
*The fact workspace on the Memory area's bank tab (list mode)*

The engine is **Hindsight** — a memory service that powers the shared operator
and agent "brain." When configured, hal0 builds a Hindsight client and wraps
it with a second-pass reranker so recall surfaces the most relevant facts. If
the Hindsight daemon is unreachable at boot, hal0 degrades to an in-memory
PgVector fallback rather than failing — the subsystem stays usable, but that
fallback is volatile (every write is lost on restart) and exists to keep the
tools answering, not as a durable substitute. Once the daemon comes back,
hal0 swaps the durable engine back in on its own (no restart required) — but
writes accepted while degraded are gone; they were never on the durable side.

<Aside type="note">
The memory layer is engine-neutral by design — a `MemoryProvider` interface is
the explicit anti-lock-in seam. `[memory].engine` accepts `hindsight` (the
default and the only fully-implemented engine), `pgvector` (the volatile
fallback, selectable directly), or `mem0` — but `mem0` is **accepted by
config validation and not implemented**: selecting it logs a warning and
silently runs Hindsight instead. The legacy `cognee` engine was retired in
v1.0.0 and now fails config validation outright; there is no automated
migration path off a Cognee-era store, and Cognee itself has been dark since
v0.4.
</Aside>

## Memory is gated by one config flag

This is the most important thing to know: hal0 only constructs a memory
provider when `[memory].enabled` is `true`, and it **defaults to `true`** —
no shipped `hal0.toml` and no installer step writes the key, so a box with no
`[memory]` section at all comes up with memory *on*. This replaces the older
`HAL0_MEMORY_ENABLED` environment variable — the toggle is now a persisted
config value, editable from `hal0 memory enable`/`disable` or the dashboard's
Settings without an env edit. Set `enabled = false` and memory is off:

- No memory provider is built.
- Every downstream caller degrades to a no-op or a clean error — the
  `/api/memory/*` routes, the `/mcp/memory` server, the agent's memory provider,
  and the per-agent memory stats all handle the absent provider gracefully.
- The dashboard hides the Memory navigation.

Flipping the flag is the *entire* toggle — no code change required either way.
A fresh install leaves memory on (the default) and stands up the local
Hindsight daemon automatically. An upgrade never rewrites an existing config,
so a box that already had `enabled = false` written by hand keeps memory off
across the upgrade — but a box with no `[memory]` key at all picks up the
`true` default and comes up with memory on, upgrade or not.

<Aside type="caution">
The flag is the whole toggle, but the flag's *absence* means on, not off:
memory is inert only once you (or the installer) have written
`[memory].enabled = false` to `hal0.toml` and restarted `hal0-api`.
</Aside>

## Namespaces and banks: who a fact belongs to

Every memory operation is scoped to a namespace, and the grammar is a closed
two-value set: `shared` or the caller's own `private:<client_id>`
([ADR-0005](/docs/adr/0005-memory-namespace-shared-private)). `shared` is the
default for every write; `private:<agent>` is for memories an agent — or the
operator — explicitly wants scoped to one identity. Scoping *within* `shared`
is done with tags (the agent identity cards carry `agent-identity`; a
project is a `project:<slug>` tag, which no read hides), and coding-agent
clients write through `/api/memory/compat` into the same shared bank. The
retired `agents` and `project:<id>`
namespaces are rejected on write with a pointed remedy. A write with no
explicit namespace defaults to `shared`. Setting the `X-hal0-Private` header over REST (or `private=true`
over MCP) promotes the write to `private:<client_id>` and **wins over an
explicit `dataset` field in the request body** — so a private-mode client
can't smuggle data into `shared` by naming it directly in the payload. An
unknown namespace on write raises an error. A read naming
several namespaces drops just the unknown ones and still answers from
whichever are valid — but if *every* named namespace is unknown, the read
now raises rather than silently falling back to `shared`: an earlier version
collapsed "nothing addressable" into "nothing requested," which let an
approval-gated `memory_delete` scoped to a bank the caller couldn't even
name execute against `shared` instead.

Callers identify themselves via the `X-hal0-Agent` header, and the same
identity resolves the same memory namespace whether it arrives over REST or
MCP.

Namespaces map onto Hindsight **banks**. On a new install `shared` is
`hal0:shared` (`[memory] bank`) and every `private:<agent>` is `hal0:private`
(`[memory] private_bank`), one bank where the `agent:<id>` tag scopes each
agent to its own memory. A store from before keeps its old banks until it is
folded in. [Memory banks](/docs/concepts/memory-banks) has both layouts and
who reads what.

## Write envelope

A write bound for the Hindsight engine is normalised on its way there,
whichever surface it came through: REST, MCP, the Hermes memory plugin or Hal0
Brain (ADR-0058). The envelope never rejects a write. It rewrites the tag list
and moves a few values into the document's metadata. The volatile `pgvector`
fallback does not apply it: a write that provider accepts keeps its tags as
given.

Two tags are required, and hal0 adds them when the caller did not:

- `agent:<id>`, the caller's resolved identity. A caller-supplied `agent:`
  tag is replaced. A write with no identity is tagged `agent:unknown`.
- Exactly one of `kind:durable` or `kind:ephemeral`. The default is
  `kind:durable`. A caller can send either tag to choose, and an explicit
  choice wins; if both are sent, `kind:ephemeral` wins.

Two kinds of tag are moved out of the tag list:

- **Session ids** go to metadata as `session_id`, or as the list
  `session_ids` when a write carries several. A tag counts as a session id
  when it is `session:<id>` (also `session_id:`, `session-id:` or
  `sessionid:`) or a bare UUID in the 8-4-4-4-12 form. Any bare UUID is
  moved, whatever it identifies. A bare run of hexadecimal digits, such as an
  MD5 checksum, a commit hash or a digest, stays a tag. A session id taken
  from a tag does not change the document id.
- **Lifecycle words** go to metadata as `lifecycle` (comma-separated when a
  write carries several). The words are `checkpoint`, `session-end`,
  `pre-compress`, `continuity`, `bootstrap` and `chat`, matched as whole
  tags. A write that sends no kind and carries one becomes `kind:ephemeral`.
  A write you mark `kind:durable` keeps these words as ordinary tags: you
  have said it is durable content, so `chat` there is a topic.

A metadata key the caller already set is left as the caller set it; an empty
`session_id` counts as not set. Every other tag passes through unchanged:
namespaced tags such as `source:`, `knowledge:`, `origin:` and `harness:`, and
your own bare words.

A `project:<name>` tag is not stored as sent: hal0 normalises it and drops a
denied name, and a durable write with no project gets `scope:global`.
[Memory projects](/docs/concepts/memory-projects) has the rules.

The reason is how the engine consolidates. It builds observations per scope,
and by default a scope is one distinct set of tags. A tag that changes with
every session gives each session a scope of its own, so related facts never
consolidate together and anything that reads by tag sees very little. With
session ids and lifecycle words out of the tag list, the tag sets stay few and
stable.

For the same reason, hal0 chooses the observation scope of each write rather
than leaving it to the tag set:

- A write with no `project:` tag is sent with `observation_scopes: "shared"`,
  which consolidates it into one untagged scope whatever its tags are.
- A write that carries a `project:<slug>` tag is sent with the explicit scope
  `[["project:<slug>"]]`, one scope per project tag. Its observations carry
  that project tag and nothing else, so what is learned in one project does
  not become a belief about another.
- A coding client's write with no project (`project:unresolved`) is sent with
  `[["project:unresolved", "agent:<id>"]]`, a scope of its writer's own.
- A private write is sent with its writer's own scope,
  `[["agent:<id>", "visibility:private"]]` (plus its project), on a new
  install; on an older unified bank it keeps the engine's default scoping.
  Either way its observations keep `visibility:private`.

Pass another value in the `observation_scopes` argument of the MCP
`memory_add` tool to override the first two. Because hal0 now always sends a
scope on a non-private write, a bank-level default observation scope
(`default_observation_scopes` in the bank's config) no longer applies to those
writes; it still applies to private writes in the unified bank.

The envelope applies to new writes. Memories stored before it keep the tags
they were written with.

## Fact types: world, experience, observation

Every stored fact carries a `fact_type`:

- **world** — a stable fact or configuration detail.
- **experience** — something that happened.
- **observation** — a noticed pattern, derived by Hindsight's own
  consolidation pass over world/experience facts.

Only `world` and `experience` are operator- or agent-authored — `memory_add`
and the dashboard's Add-fact form only offer those two, and `memory_curate`
only accepts `"world"`/`"experience"` as a *new* `fact_type` value. History
runs in reverse of what you'd expect from the name: `memory_history` is
*only* available for observations (their revision trail comes from
consolidation re-runs). Curation (edit text, soft-invalidate) has no such
backend restriction — `memory_curate` over MCP accepts an observation's id
and will edit or invalidate it; it's the dashboard inspector that hides the
Curate/Invalidate buttons for observation facts, as a UI convenience rather
than an engine rule. Either fact type can be deleted outright.

Facts relate to each other through typed links, surfaced in the dashboard's
graph views: `temporal` (near in time), `semantic` (related meaning),
`entity` (shared entity), and `caused_by` (led to). `causal` and
`cooccurrence` are legacy/prototype spellings that don't appear in real
Hindsight payloads — the dashboard still renders them if it ever sees them,
but don't expect to.

## Directives and mental models

Two concepts sit alongside plain facts:

<CardGrid>
  <Card title="Directives" icon="document">
    A standing instruction injected verbatim into an agent's prompt every
    turn it uses a bank — "shape behaviour, not memory." Created with a
    `name`, `content`, `priority`, and `is_active` flag; toggled on/off
    without deleting them. Deleting a directive is destructive and gated for
    operator approval.
  </Card>
  <Card title="Mental models" icon="brain">
    A standing question ("what does the operator prefer for X") whose
    answer is kept refreshed from memory rather than re-derived on every
    ask. Created with a `name` and `source_query`; the first answer builds
    as an async operation, and later refreshes are triggered manually with
    `memory_mental_model_refresh`. Each row in the dashboard shows when the
    model last refreshed. Hindsight's `is_stale` only means the bank was
    written since then, which on a busy bank is nearly always true, so it is
    a quiet dot ("new memories since"), not a warning; the warning and a
    "refresh failed" chip are kept for a refresh that failed after the last
    success. Each bank has a refresh floor
    (`mental_model_min_refresh_interval_seconds`: after every consolidation,
    or at most hourly, every 4 h, every 12 h or daily) set from the bank bar
    or with `hal0 memory bank profile set <bank> --min-refresh-interval
    <seconds>`; a model with its own `trigger.min_refresh_interval_seconds`
    keeps that instead.
  </Card>
</CardGrid>

## Reranking

Recall unions results across banks under one token budget, then re-ranks
that union so the most relevant facts surface first. Configured under
`[memory.embedding]` in `hal0.toml`:

- `rerank_gateway_url` (default `http://127.0.0.1:8080`) — the
  OpenAI-compatible gateway the reranker POSTs `/v1/rerankings` to (hal0-api
  itself by default, whose dispatcher routes to the `rerank` capability
  slot).
- `rerank_model` (default `builtin.jina-reranker-v1-tiny-en-q8`) — the model
  id sent to the gateway.
- `rerank_connect_timeout_s` / `rerank_read_timeout_s` (defaults `1.0` /
  `8.0`) — HTTP budgets. A timeout or an unreachable reranker never blocks
  recall: it fails soft back to the fused vector ordering.

The dashboard's Settings → Data → Memory page has a picker for `rerank_model`: the
schema default is offered as "builtin", plus every model in the
capabilities catalog tagged for reranking (labelled with its serving
backend), plus whatever is currently saved if it's outside both lists. Free
text isn't offered — an id the gateway can't resolve just makes every recall
fail soft to vector-only ordering. The picker links out to Settings →
Capabilities, where the underlying `rerank` slot itself is configured.

## Memory mode and priority settings

`GET /api/memory/graph/status` reports one configured `mode`:

- `dedicated`: `[memory.graph].extraction_slot = "memory"`, with a model bound
  to the memory slot and no upstream `extraction_model`.
- `shared`: the memory slot has no model bound, or extraction explicitly targets
  `agent`, even if memory still has a model bound.
- `custom`: extraction targets any other slot (including `utility`) or an upstream
  `extraction_model`. Reading status never rewrites these settings.

Binding defines dedicated mode independently of whether the slot is ready.
`slot_resolves` and memory write-health checks also recognize the memory-to-agent
fallback, so an empty memory slot with a bound agent is routable.

`[memory.priority]` declares `enabled = true`, `quiet_gap_s = 30`, and
`max_defer_s = 300` for fresh configurations. Config migration v4 disables
priority on upgrades when `enabled` is absent, including a partially configured
table, and preserves explicit values. These are configuration keys only in
this stage; chat-priority admission and cancellation are follow-up work.
See [ADR-0053](https://github.com/Hal0ai/hal0/blob/main/docs/adr/0053-memory-slot-and-chat-priority.md) for the accepted
design and remaining validation.

## What memory powers

When enabled, memory becomes the shared brain that ties the platform together:

  <Card title="Hermes's durable memory, by default" icon="comment">

    with no manual config, backed by Hindsight via the hal0-api REST front
    door. Hermes' private writes and session captures land in
    `hal0:private` tagged `agent:hermes`, and its recall reads `hal0:shared`
    plus its own private memory. Recalled context is injected automatically
    every turn, and the agent can also call the MCP tools directly.

    search, browse the graph, and curate facts directly — across banks,

  <Card title="Namespaced writes" icon="setting">

  </Card>
  <Card title="Destructive ops are audited" icon="approve-check">
    Bank deletes and every memories / config / document / directive /
