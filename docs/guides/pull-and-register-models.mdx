hal0 keeps a **local model registry** — a record of every model it knows
about, where its bytes live, and what it can do. You populate it several
ways: pull from Hugging Face, register a file you already have on disk,
or scan a directory.

## Pull from Hugging Face

```sh
hal0 model pull qwen3-4b
```

The argument is either a **curated alias** (see
[Choose models](/docs/guides/choose-models)) or a model id already in the
registry. The CLI starts a background pull on the daemon, then polls and
renders a progress bar until the job finishes. Cancel an in-flight pull
with:

```sh
hal0 model pull qwen3-4b --cancel
```

The downloader streams the GGUF into a tempfile, computing SHA-256 as it
goes, then atomically moves it into place and upserts the registry entry.
Before it streams a multi-GB file, hal0 runs a disk-space preflight
against what's still left to fetch, so a resumed pull only needs room for
the remainder.

<Aside type="note">
Gated or private repos return `401`/`403`. Set `HF_TOKEN` (or
`HUGGING_FACE_HUB_TOKEN`) in the API environment and the pull adds the
`Authorization: Bearer …` header automatically.
</Aside>

### NPU (FastFlowLM) models

FLM tags such as `qwen3:0.6b` are pulled with FastFlowLM's own `flm pull`,
not the Hugging Face downloader. hal0 runs it in a one-shot container of the
`flm` runner image, the same image the NPU slot serves with, with the FLM
model store mounted where the slot mounts it. The weights therefore match
the FastFlowLM version the slot runs, whatever version of the host `.deb`
is installed. The `flm` runner image must be downloaded first (see
[Manage runner images](/docs/guides/manage-runner-images/)); until it is,
an FLM pull fails and says so.

### Resuming an interrupted pull

If a pull is interrupted — network drop, `hal0-api` restart, an OOM kill
— it leaves a deterministic `.part` file plus a resume sidecar. The next
pull for that model id picks the partial back up with an HTTP `Range`
request instead of starting over. If the upstream object changed in the
meantime, hal0 detects it via the sidecar's ETag and restarts the
download clean rather than splicing mismatched bytes.

### Pull by Hugging Face coordinates

To pull a file that isn't in the curated catalogue, supply the repo and
filename in the body:

```sh
curl -X POST http://localhost:8080/api/models/my-qwen-build/pull \
  -H 'content-type: application/json' \
  -d '{"hf_repo":"unsloth/Qwen3.8-27B-GGUF","hf_filename":"Qwen3.8-27B-UD-Q4_K_XL.gguf","labels":["chat"]}'
```

The dashboard's **Add by HF coords** dialog does the same thing. It
inspects the repo and lists one row per quant. To pull a vision model, add
`"mmproj_filename"` (a projector file in the same repo) and the label
`"vision"`. The projector is downloaded into the model's directory and
paired with the model.

#### Split models

Large quants are often uploaded as a split GGUF: several files named
`…-00001-of-00003.gguf`, `…-00002-of-00003.gguf` and so on, usually in a
folder named after the quant. Pull a split model by its **first part**,
for example
`"hf_filename":"UD-Q4_K_XL/Model-UD-Q4_K_XL-00001-of-00003.gguf"`. hal0
downloads every part into one directory and keeps the part-numbered names,
because llama.cpp opens a split model from its first part and finds the
other parts by name. Naming any part other than the first returns `422`.

## Drafters

A drafter is a small file that guesses the next few tokens so the main model
can check them in one pass. The answer is the same; only the speed changes.
A drafter pairs with one model, the way a vision projector does, and the
slot uses it when the profile's `speculation` is `auto`.

| Kind | What it is | Needs a file |
|---|---|---|
| `dflash` | A drafter trained for one model (DFlash, DFlash2, DSpark and LiLiCorr all land here; the variant is shown in the drawer) | Yes |
| `eagle3` | An EAGLE3 drafter trained for one model | Yes |
| `simple` | Any small model that shares the main model's tokenizer | Yes |
| `mtp` | The main model's own MTP heads | No, unless the heads ship as a separate `mtp-*.gguf` file |

hal0 reads the kind from the drafter's GGUF header; you never set it by hand
(a `draft_kind` in a model write is `422 model.draft_kind_readonly`). A model
with a drafter uses it before its embedded MTP heads. The profile's
`speculation: ngram` needs no file at all.

### Add a drafter from Hugging Face

In **Add from Hugging Face**, Inspect lists drafter files beside the quants
and the projector. The list holds files in the repo itself and files in
companion repos by the same author whose name is the model's name plus a
suffix such as `-LiLiCorr`, `-DFlash`, `-DFlash2`, `-DSpark`, `-EAGLE3` or
`-draft`. If nothing turns up, paste a repo into the **Drafter** row and choose
**Find drafters**. Pick one, or leave it on **None**.

Before anything downloads, hal0 reads the headers of the quant and the drafter
over HTTP range requests (tens of megabytes, not the files) and shows whether
they fit. A drafter that does not fit, or whose header cannot be read, holds
the Pull button until you set the row back to **None**. The same check is
available to scripts:

```sh
curl -s -X POST http://127.0.0.1:8080/api/models/inspect-draft \
  -H 'Content-Type: application/json' \
  -d '{"hf_repo":"org/Model-GGUF","hf_filename":"Model-Q4_K_M.gguf",
       "draft_repo":"org/Model-LiLiCorr-GGUF","draft_filename":"drafter-Q8_0.gguf"}'
```

`hf_*` name the target model and `draft_*` the drafter. The response carries
`kind`, `variant`, `fit` (`ok` and `reasons`), and the two headers' facts. A
file that does not fit is still a `200` with `fit.ok` false; a header that
cannot be read is `422 hf.header_unreadable`. The result is cached for about
five minutes.

`POST /api/models/inspect` also returns `drafts` (each with `id`, `repo`,
`kind_hint`, `variant_hint`, `size_bytes` and `source` of `repo`, `companion`)
and `companion_repos`, the repos that held drafters.

### Pull with a drafter

The pull body takes `draft_filename` and, when the drafter lives in another
repo, `draft_repo` (it defaults to the model's own):

```sh
curl -s -X POST http://127.0.0.1:8080/api/models/my-model/pull \
  -H 'Content-Type: application/json' \
  -d '{"hf_repo":"org/Model-GGUF","hf_filename":"Model-Q4_K_M.gguf",
       "draft_repo":"org/Model-LiLiCorr-GGUF","draft_filename":"drafter-Q8_0.gguf"}'
```

```sh
hal0 model pull my-model --draft drafter-Q8_0.gguf --draft-repo org/Model-LiLiCorr-GGUF
```

A drafter you name is fit-checked before anything downloads; one that does not
fit refuses the pull with `422 model.draft_mismatch`. The drafter lands in the
model's directory and is paired when the pull finishes, and its bytes count
toward the model's size.
A pull without `draft_filename` leaves an existing pairing alone.

### Pair or unpair a model you already have

- **Dashboard.** The model drawer has a **Drafter** field beside **MMProj**:
  choose a drafter from the repo's list or type an absolute path, and use
  **Pull drafter** when the chosen file is not on disk yet.
- **CLI.** `hal0 model set <id> --draft <path>` pairs a file that is already
  on disk and runs the same fit check; `hal0 model set <id> --draft none`
  unpairs it and keeps the file. `hal0 model add --draft <path>` pairs while
  registering.
- **API.** `PUT /api/models/<id>` with `{"draft": "<path>"}` pairs and
  `{"draft": null}` unpairs and keeps the file. `DELETE /api/models/<id>/draft`
  unpairs and deletes the drafter file; it answers `404 model.draft_not_found`
  when none is paired.

A drafter that fails the check is refused with `422 model.draft_mismatch`
(the two values that differ are in `details`), `model.draft_not_a_drafter`
(the file is not a drafter, or is a plain model whose tokenizer is not this
model's), `model.draft_not_found` (the path is not on disk) or
`model.draft_outside_store` (the path is not absolute, or lies outside the
model store and the model's own directory, where a slot could not open it).

A rescan pairs a drafter it finds in a model's directory when it fits. A
drafter it cannot pair is listed as skipped with a reason:
`drafter_without_target` (no model beside it), `drafter_unpaired` (it fits a
model that already has a drafter), `drafter_mismatch` (it fits none of them)
or `drafter_unreadable` (its header cannot be read). A drafter you unpaired on
purpose is not paired again by a later scan; pairing a path lifts that.

### See whether it is in use

The slot's metrics carry a `spec` block: `active`, `mode` (`draft`, `mtp`,
`ngram` or `none`), `kind`, `variant`, `draft_tokens`, `accepted_tokens`,
`acceptance` (accepted over drafted), `mean_accepted_len`, `live_acceptance`
and `unavailable_reason`. `active` comes from the server itself, so a drafter
that loaded but never drafts shows as inactive. When the runner image cannot
run the paired drafter (a LiLiCorr file needs llama.cpp build b11669 or newer),
`unavailable_reason` says so and the slot falls back to the model's MTP heads
if it has them, else to no speculation.

The Slots list shows a bolt after the model name, with a hover title:

| Bolt | Title |
|---|---|
| Lit | `drafting · <drafter or MTP heads or n-gram> · <n>% accepted` (the percentage appears once the slot has drafted) |
| Grey | `drafter paired · speculation off` when the model has a drafter (or MTP heads) and the profile's `speculation` is `off`; `<drafter paired, MTP heads or n-gram> · not running` when the plan uses one but the slot is not drafting right now |
| Amber | `drafter unavailable on this runner: <reason>` |

A model with nothing to draft with shows no bolt. The slot drawer carries the
full line, `Speculation: <what is in use> · <n>% accepted · <x> tok/step`, or
`Speculation: off`, or `Speculation: drafter unavailable — <reason>`. In the
model catalog a model with a paired drafter carries a **Drafter** chip
(hover: `Paired drafter · <variant>`), and the filter chips include **Drafter**.

hal0 does not estimate a speed-up from the acceptance rate. A with and
without comparison through the benchmark queue is planned for a later
release.

## Check for and apply weight updates

```sh
hal0 model update --check           # every model: compares recorded sha256 vs HF Hub, no download
hal0 model update qwen3-4b --check  # one model
hal0 model update qwen3-4b          # re-pull that model in place
hal0 model update --refresh         # force a fresh check, ignoring any cache
```

## Register a file already on disk

If the bytes are already on the host — say you dropped a GGUF into the
model store — register it without re-downloading:

```sh
hal0 model add /path/to/qwen3-4b-instruct-q4_k_m.gguf \
  --id qwen3-4b-q4_k_m \
  --name "Qwen3 4B Q4_K_M" \
  --license Apache-2.0
```

The path is the positional argument; `--id` is optional (omit it and the
registry derives one). `hal0 model add` reads the file's header to
auto-detect capabilities and backends — when the header doesn't carry
enough signal (no `pooling_type`, say) it falls back to a filename guess
and prints a confidence/warning line; fix a wrong guess with
`PUT /api/models/{id}` (`{"capabilities": [...]}`). Pass `--overwrite` to
replace an existing entry at the same id. The API also
exposes a directory scan that registers every new file it finds:

```sh
hal0 model scan
```

<Aside type="note" title="Fork-only quantizations are refused">
ROCmFPX-family (ROCmFP4, …), IU4 and ActiveFPX GGUFs need a llama.cpp fork
that hal0 does not ship, so no runner can load them. `hal0 model add` and a
pull answer 422 `models.unsupported_quant`; a scan skips the file with reason
`unsupported_quant:<label>`; and a slot bound to one fails to launch with 422
`slot.unsupported_quant`. Use a plain GGUF build of the same model (for
example a `Q4_K_M` or `UD-Q4_K_XL` file).
</Aside>

<Aside type="note" title="Moonshine streaming bundles are refused">
The Moonshine runner loads `encoder_model.ort` and `decoder_model_merged.ort`
(the `tiny-en` and `base-en` ids). The streaming layout (`encoder.ort`,
`frontend.ort`, ...) is not supported. `hal0 model add` answers 422
`models.unsupported_moonshine_layout`, a scan skips the file with reason
`unsupported_moonshine_layout`, and a slot pointed at one fails to launch
with `slot.weights_missing` instead of silently running other weights.
</Aside>

## Generate a draft profile from a model

Picking a runtime [profile](/docs/concepts/capabilities-and-profiles) by hand
means guessing which seed template fits a model's architecture and this
host's hardware. `POST /api/profiles/generate` does that guessing for
you — from a model already in the registry, or straight from a HuggingFace
repo you haven't pulled yet — and hands back a draft to review, not
something already written to the catalog.

```sh
# From a registered model
curl -s -X POST http://localhost:8080/api/profiles/generate \
  -H 'content-type: application/json' \
  -d '{"model_id": "qwen3-4b-q4_k_m"}' | jq

# From a HuggingFace repo you haven't pulled yet
curl -s -X POST http://localhost:8080/api/profiles/generate \
  -H 'content-type: application/json' \
  -d '{"hf_repo": "unsloth/Qwen3-8B-GGUF", "name": "my-qwen3"}' | jq
```

Exactly one of `model_id` / `hf_repo` is required (`422` otherwise). The
endpoint classifies the model's capability (chat, embed, rerank, stt, tts,
or image), fits it to *this host's* cached hardware snapshot the same way
slot creation's device auto-pick does, and clones the closest seed
profile.
A HuggingFace repo also picks up the recommended GGUF variant and, when HF
reports parsed GGUF metadata for the repo, its architecture and native context
length; they feed the draft's `intent` headline.

The response wraps a portable `.hal0profile.json` envelope (the same shape
a profile export produces) plus `warnings` (anything it had to fall back
on) and `sources` (where each fact came from):

```json
{
  "profile": {
    "kind": "hal0.profile",
    "name": "qwen3-4b-q4_k_m",
    "profile": {
      "flags": "-fa auto -b 2048 -ub 512",
      "vision": "auto",
      "speculation": "auto",
      "cloned_from": "chat",
      "intent": "Qwen3 4B · qwen3 · 32K ctx · chat · gpu-rocm"
    }
  },
  "warnings": [],
  "sources": ["registry:qwen3-4b-q4_k_m"]
}
```

<Aside type="note">
This call is **compute-only** — nothing is written to the profile catalog.
Take the inner `profile` object and hand it to `POST /api/profiles`
(unwrap the envelope's own `.profile` body) or `POST /api/profiles/import`
(pass the whole envelope as `envelope`) once you've reviewed it.
</Aside>

Pass `"use_llm": true` to have the platform's `hal0/utility` slot write the
draft's headline (`intent`) from the model card instead of the heuristic
one. If the utility slot isn't loaded, unreachable, or the call times out,
the draft still comes back — with the heuristic headline in place and a
warning explaining why the LLM pass was skipped, never a failed request.

## Change or inspect the model store

```sh
hal0 model store              # show the current model-store directory
hal0 model store /mnt/models  # point hal0 at a different directory
hal0 model store /mnt/models --migrate  # move existing files there too
```

There's exactly one directory hal0 pulls to, scans, and bind-mounts into
containers — this is how you point it somewhere with more room.

## List, inspect, and remove

<Tabs>
<TabItem label="List">

```sh
hal0 model list
hal0 model list --json
```

Aggregates the local registry with everything advertised by configured
upstreams. Local files win on id collision and are flagged `installed`.

</TabItem>
<TabItem label="Show">

```sh
hal0 model show qwen3-4b
hal0 model show qwen3-4b --json
```

</TabItem>
<TabItem label="Remove">

```sh
hal0 model rm qwen3-4b               # remove the model and its files
hal0 model rm qwen3-4b --keep-files  # remove only the registry entry
```

Removes the registry row and the model's files on disk: the model file,
any shards, and its vision (`mmproj`) sidecar. There is a confirm prompt;
`--force` skips it. hal0 leaves some files alone and prints each one with
the reason:

- files outside the configured model roots and the model store
- files another registered model also uses
- directories, including FLM model directories

A file with other hardlinks is removed, but its space is not freed.

`--keep-files` leaves every file where it is. hal0 also hides those files
from future scans, so the model does not come back on the next restart.
`hal0 model add <path>` brings one back.

If a slot has this model as its default, the API cascades: it unloads the
slot and clears the default. See [ADR-0026](/docs/adr/0026-model-delete-removes-files)
for the full rules.

</TabItem>
</Tabs>

## One-shot: get a model serving

```sh
hal0 model run qwen3-4b --slot agent --timeout 120
```

Assigns the model to a slot, loads it, and polls until it's ready — the
fastest path from "I have an id" to "it's serving." To only set a
slot's default model without loading it, use `hal0 slot edit agent --model qwen3-4b`.

## A leftover `registry.toml`

The registry lives in SQLite (`/var/lib/hal0/hal0.db`). Releases before the
SQLite registry kept it in `/var/lib/hal0/registry/registry.toml`. If that
file is still there, the post-update migrations (and the same pass at every
`hal0-api` start) retire it without importing it — every supported release
already imported it into SQLite on first boot. They copy it to
`/var/lib/hal0/backups/registry-toml-<UTC>/` and rename it to
`registry.toml.retired-<UTC>`. hal0 never reads the renamed file. If the
service user cannot read or rename the file (a root-owned `0600` file left
by an old `sudo` export, say), the file stays put, nothing fails, and
`hal0 doctor all` shows a `registry-toml` warning with the reason. Nothing
reads it, so delete it: `sudo rm /var/lib/hal0/registry/registry.toml`.

`hal0 model list --json` prints the catalog. To keep a copy of it, snapshot
`hal0.db` with SQLite's online backup. The database runs in WAL mode, so a
plain file copy of a live `hal0.db` can miss committed changes still in the
`-wal` file:

```sh
sudo sqlite3 /var/lib/hal0/hal0.db ".backup '/root/hal0-db-backup.db'"
```

Without the `sqlite3` CLI, Python's built-in module does the same:

```sh
sudo python3 -c "import sqlite3
s = sqlite3.connect('/var/lib/hal0/hal0.db')
d = sqlite3.connect('/root/hal0-db-backup.db')
s.backup(d); d.close(); s.close()"
```

## The registry on disk

Registry entries are metadata records — id, display name, path, size,
SHA-256, capabilities, and facts about the file (chat template, whether it has
MTP heads, whether its template works with `--jinja`). A model row holds no
tuning: the context window, flags and thinking default live on a profile — see
[Choose models](/docs/guides/choose-models).
The registry is the source of truth the dispatcher resolves model ids
against; the actual weights live in your configured model store.
