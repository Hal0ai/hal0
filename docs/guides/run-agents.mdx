hal0 can run a **bundled agent** — Hermes — provisioned into a
hal0-managed virtualenv and driven through the `hal0 agent` CLI. The agent
gets a persona (system prompt + tool gating), an approvals queue for
gated/destructive actions, and an optional per-persona spending budget.

![The dashboard Agents view — the agent library as collectible cards](/screenshots/agents-overview.png)

<Aside type="note">
Only one bundled agent is active at a time (single-pick). `hal0 agent`
lifecycle commands are thin clients over the API; provisioning Hermes runs
locally in the foreground because the venv build can't fit in one HTTP
request.
</Aside>

## Install Hermes

```sh
sudo hal0 agent install hermes
```

Installing Hermes runs a three-step foreground pipeline: ensure the
toolchain (Python ≥3.11, venv stdlib, pip/pipx), provision the managed
venv and register the agent, then enable and start the systemd unit
(`hal0-agent@hermes`).

Run it as root — provisioning writes under root-owned `/var/lib/hal0` and
then chowns the provisioned trees to the shared agent runtime user. As a
normal user it aborts cleanly up front with a `sudo` hint.

Pass `--switch` to atomically uninstall whatever agent is currently
installed before installing this one.

## Hermes' terminal tool — off by default

Hermes ships **without** a terminal tool. It can read your box through the
hal0 MCP tools, but it cannot run shell commands unless you say so.

That is a deliberate default. The only terminal backend that works on a hal0
box is Hermes' `local` one, which runs commands as the `hal0` service user —
and on this box that user is root-equivalent (rootful podman plus the
`hal0-systemctl` / `hal0-agentenv` sudo wrappers). Hermes also reads content
it did not write: web pages, stored memories, MCP tool output. Turning the
tool on therefore means anything that can talk to your agent can, in
principle, get a root-equivalent command run on the machine.

There is no sandboxed middle ground. Hermes' other backends are
`docker | singularity | modal | daytona | ssh`: hal0 ships podman rather than
docker, singularity is not installed, modal and daytona are paid cloud
services, and a containerised shell could not reach the host or the local API
on `127.0.0.1:8080` — which is exactly what the host-management skills need.
So the choice is on or off.

Turn it on when you want it:

```sh
sudo hal0 agent install hermes --terminal-tool     # opt in
sudo hal0 agent install hermes --no-terminal-tool  # opt back out
```

The installer also asks once, on an interactive install. A piped
(`curl … | bash`), headless, or `HAL0_NONINTERACTIVE=1` install is never
asked and always leaves it off; set `HAL0_HERMES_TERMINAL=1` to opt in
unattended.

Your answer is recorded at `/etc/hal0/agents/hermes-terminal-tool`, so
re-provisioning, `--repair` and updates all keep it. That file is root-owned on
purpose: it sits outside the agent's own writable home, so nothing the agent
writes can present itself to a later provision as your decision.

`hal0 agent status hermes` prints the current posture on its own line.

**Upgrades keep your setting.** Every hal0 release that provisioned Hermes
wrote both `terminal.backend: local` and a `terminal.cwd` of its own — first
`/etc/hal0`, then `$HERMES_HOME/scratch`. An update recognises any of those
shapes, and any `cwd` you set yourself, as your answer and leaves the terminal
enabled. Only Hermes' own untouched default (backend `local` with no `cwd`, or
`cwd: "."`, which `hermes config migrate` writes on a box hal0 never finished
provisioning) is not read as consent — those boxes start off, like a fresh
install. Run `sudo hal0 agent install hermes --no-terminal-tool` if you would
rather an upgraded box were off.

### What you lose with it off

These bundled skills drive the host through shell commands and stop working
when the terminal tool is off:

| Skill | What it does |
|---|---|
| `hal0-service-management` | Restart / inspect hal0 units and slot services |
| `hal0-bench` | Run benchmark sweeps against loaded slots |
| `hal0-bench-autopilot` | The weekly judgment pass over the benchmark dataset |
| `hal0-tune` | Apply and measure runtime/tuning parameter changes |
| `hal0-quantize` | Produce quantised model variants on the box |

Hermes' `delegation` toolset (`delegate_task`, which spawns subagents) goes off
with them. A subagent's tools are chosen in the call that creates it and the
parent's disabled toolsets are not inherited, so leaving `delegate_task`
reachable would let anything that can talk to your agent ask for a child
*with* a terminal — the shell you declined, one hop away. Turning the terminal
on brings delegation back with it. What you give up in the meantime is
parallel fan-out for subagent work that needs no shell; no bundled skill or
persona uses it.

Everything else — chat, memory, personas, the kanban board (its workers are
spawned by hal0's own dispatcher, not `delegate_task`), and the hal0 MCP tools
(slot state, model management, hardware readouts) — is unaffected: those go
through the hal0 API, not a shell.

## Manage the lifecycle

<Tabs>
<TabItem label="List / status">

```sh
hal0 agent list                 # installed bundled agents
hal0 agent list --json
hal0 agent status hermes        # provisioning checkpoint, per phase
hal0 agent peers                # every published agent identity card
```

`list` only shows agents installed on this host; `peers` searches the
memory store for every identity card any host has published (needs the
memory API reachable).

</TabItem>
<TabItem label="Logs">

```sh
hal0 agent log hermes
hal0 agent log hermes --phase provision
```

Per-phase provisioning logs — these are flat files under the agent's
state directory, not a systemd journal. See
[Logs and activity](/docs/guides/logs-and-activity) for how this differs
from a slot's runtime logs.

</TabItem>
<TabItem label="Re-run / upgrade">

```sh
hal0 agent reprovision hermes          # idempotent re-converge
hal0 agent reprovision hermes --repair # force every phase
hal0 agent upgrade hermes              # bump the version pin + repair
hal0 agent upgrade hermes --to 0.15.3  # pin a specific version
```

`reprovision` is a stable wrapper over the same state machine `install`
runs. For finer control — skipping a phase, staging the agent wheel
offline, or a dry run that doesn't persist the checkpoint — drop to the
underlying command directly:

```sh
hal0 agent bootstrap hermes --dry-run
hal0 agent bootstrap hermes --repair --verbose
```

To restart the running Hermes process without re-provisioning anything:

```sh
sudo systemctl restart hal0-agent@hermes
curl -X POST http://localhost:8080/api/agents/hermes/restart
```

</TabItem>
<TabItem label="Uninstall">

```sh
hal0 agent uninstall hermes
hal0 agent uninstall hermes --keep-memory
```

Default uninstall tears down the agent's private memory namespace too;
`--keep-memory` preserves it so a re-install reuses the identity card.

</TabItem>
</Tabs>

## Personas

A persona is a TOML file pairing a system prompt with tool gating:

```sh
hal0 agent personas list                 # list + mark the active one
hal0 agent personas show <id>            # print a persona's TOML (good template)
hal0 agent personas activate <id>        # switch active + nudge a hot-reload
```

Activating writes the active pointer atomically and best-effort nudges a
running Hermes to hot-reload; if Hermes isn't running, the next restart
picks up the new active persona. To author your own, copy `personas show`
output, change the persona id, and save it under the persona store.

## The approvals queue

Destructive or gated tool calls don't execute immediately — they land in
an approvals queue you review:

```sh
hal0 agent approvals list                # pending requests
hal0 agent approvals approve <id>        # let it run
hal0 agent approvals deny <id>           # reject it
```

Each pending row shows the request id, the tool, the requesting agent,
when it was enqueued, and a one-line summary of the primary argument. The
dashboard's Agent → Approvals tab renders the same queue. See
[Connect MCP servers](/docs/guides/connect-mcp) for the full list of
gated admin tools.

## Spending budget

Each persona can carry spending caps so an autonomous loop can't drain a
paid provider pool. Caps live in the persona's `[persona.budget]`
sub-table:

```toml
[persona.budget]
daily_usd = 5.0
monthly_usd = 50.0
lifetime_usd = 200.0
per_call_max_usd = 0.50
hard_cap = true
```

Every cap is optional — omit one to leave that window uncapped, or set it
to `0.0` to block every paid request. `hard_cap = true` (the default)
denies requests that would overshoot; `hard_cap = false` lets them
through but still reports the breach.

```sh
curl http://localhost:8080/api/agents/hermes/personas/hermes/budget
```

The same route accepts a `PUT` with a `{"daily_usd": ..., ...}` body to
change the caps without hand-editing the persona TOML.

## Chatting directly

Outside of Hermes's own agent loop, `hal0 chat` is a terminal REPL over
the local `/v1/chat/completions` endpoint, defaulting to the `agent`
model alias. It supports `/think on|off|default` as an in-REPL command
and `--no-stream` for non-streaming output.

## Audit trail

Every gated tool invocation is journaled. Pull an agent's recent MCP
activity:

```sh
curl 'http://localhost:8080/api/agents/hermes/activity?limit=50'
```

Each row carries `tool`, `args`, `gated`, `outcome`, `timestamp`, and the
`client_id` the action was attributed to.
