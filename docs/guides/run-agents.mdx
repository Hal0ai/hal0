hal0 can run a **bundled agent** — Hermes — provisioned into a
hal0-managed virtualenv and driven through the `hal0 agent` CLI. The agent
gets a persona (system prompt + tool gating), an approvals queue for
gated/destructive actions, and an optional per-persona spending budget.

![The dashboard Agents view — the agent library as collectible cards](/screenshots/agents-overview.png)

<Aside type="note">
Only one bundled agent is active at a time (single-pick). `hal0 agent`
lifecycle commands are thin clients over the API; provisioning Hermes runs
locally in the foreground because the venv build can't fit in one HTTP
request.
</Aside>

## Install Hermes

```sh
sudo hal0 agent install hermes
```

Installing Hermes runs a three-step foreground pipeline. First it ensures
the OS toolchain: git, plus python3 with venv and pip, and pipx. Then it
builds a Hermes release and registers the agent. Last, it enables and
starts the systemd unit (`hal0-agent@hermes`).

The Hermes venv runs on the Python minor the pinned commit admits: 3.12
for today's pin, 3.14 once the pin moves to a commit that requires it. By
default the uv that ships with hal0 fetches a managed interpreter, which
needs the network; a system one is used only when uv cannot fetch one and
it links SQLite 3.51.3 or newer. See the
[interpreter policy](/docs/operate/services#hermes-interpreter-policy).

Run it as root — provisioning writes under root-owned `/var/lib/hal0` and
then chowns the provisioned trees to the shared agent runtime user. As a
normal user it aborts cleanly up front with a `sudo` hint.

Pass `--switch` to atomically uninstall whatever agent is currently
installed before installing this one.

### Hermes version, session history and linger

hal0 installs one reviewed Hermes release: v0.22.2 (commit `d923a5eb`) from
hal0 1.6.0. Moving from the previous pin (0.19.0) changes two things you may
notice:

- **Session history is kept.** From 0.22, Hermes deletes ended sessions that
  have been idle for 90 days, at startup. hal0 writes `sessions.auto_prune:
  false` into Hermes's config, so nothing is pruned. To prune anyway, set
  `sessions.auto_prune: true` in `/etc/hal0/agents/hermes/overrides.yaml` and
  run `hal0 agent reprovision hermes`.
- **The `hal0` user lingers.** Installing the Hermes gateway turns on systemd
  linger for `hal0`. Hermes's scheduled jobs and kanban workers run through
  `hal0`'s own systemd manager, which only runs while the user lingers.
  `hal0 doctor all` reports it on the `hal0_linger` row, and
  `hal0 agent uninstall hermes` turns it off.

`hal0 update` does not regenerate the gateway unit. On a box that ran Hermes
before 1.6.0, run `sudo hal0 agent install hermes` once after the update: it
rewrites the gateway unit and turns linger on. Until then Hermes's kanban
workers do not start and cron jobs run outside their own scope, and
`hal0 update`, `hal0 update status` and `hal0 doctor all` print the command.

## Hermes' terminal tool — off by default

Hermes ships **without** a terminal tool. It can read your box through the
hal0 MCP tools, but it cannot run shell commands unless you say so.

That is a deliberate default. The only terminal backend that works on a hal0
box is Hermes' `local` one, which runs commands as the `hal0` service user —
and on this box that user is root-equivalent (rootful podman plus the
`hal0-systemctl` / `hal0-agentenv` sudo wrappers). Hermes also reads content
it did not write: web pages, stored memories, MCP tool output. Turning the
tool on therefore means anything that can talk to your agent can, in
principle, get a root-equivalent command run on the machine.

There is no sandboxed middle ground. Hermes' other backends are
`docker | singularity | modal | daytona | ssh`: hal0 ships podman rather than
docker, singularity is not installed, modal and daytona are paid cloud
services, and a containerised shell could not reach the host or the local API
on `127.0.0.1:8080` — which is exactly what the host-management skills need.
So the choice is on or off.

Turn it on when you want it:

```sh
sudo hal0 agent install hermes --terminal-tool     # opt in
sudo hal0 agent install hermes --no-terminal-tool  # opt back out
```

The installer also asks once, on an interactive install. A piped
(`curl … | bash`), headless, or `HAL0_NONINTERACTIVE=1` install is never
asked and always leaves it off; set `HAL0_HERMES_TERMINAL=1` to opt in
unattended.

Your answer is recorded at `/etc/hal0/agents/hermes-terminal-tool`, so
re-provisioning, `--repair` and updates all keep it. That file is root-owned on
purpose: it sits outside the agent's own writable home, so nothing the agent
writes can present itself to a later provision as your decision.

`hal0 agent status hermes` prints the current posture on its own line.

**Upgrades keep your setting.** Every hal0 release that provisioned Hermes
wrote both `terminal.backend: local` and a `terminal.cwd` of its own — first
`/etc/hal0`, then `$HERMES_HOME/scratch`. An update recognises any of those
shapes, and any `cwd` you set yourself, as your answer and leaves the terminal
enabled. Only Hermes' own untouched default (backend `local` with no `cwd`, or
`cwd: "."`, which `hermes config migrate` writes on a box hal0 never finished
provisioning) is not read as consent — those boxes start off, like a fresh
install. Run `sudo hal0 agent install hermes --no-terminal-tool` if you would
rather an upgraded box were off.

### What you lose with it off

These bundled skills drive the host through shell commands and stop working
when the terminal tool is off:

| Skill | What it does |
|---|---|
| `hal0-service-management` | Restart / inspect hal0 units and slot services |
| `hal0-bench` | Run benchmark sweeps against loaded slots |
| `hal0-bench-autopilot` | The weekly judgment pass over the benchmark dataset |
| `hal0-tune` | Apply and measure runtime/tuning parameter changes |

Hermes' `delegation` toolset (`delegate_task`, which spawns subagents) goes off
with them. A subagent's tools are chosen in the call that creates it and the
parent's disabled toolsets are not inherited, so leaving `delegate_task`
reachable would let anything that can talk to your agent ask for a child
*with* a terminal — the shell you declined, one hop away. Turning the terminal
on brings delegation back with it. What you give up in the meantime is
parallel fan-out for subagent work that needs no shell; no bundled skill or
persona uses it.

Everything else — chat, memory, personas, the kanban board (its workers are
spawned by hal0's own dispatcher, not `delegate_task`), and the hal0 MCP tools
(slot state, model management, hardware readouts) — is unaffected: those go
through the hal0 API, not a shell.

### Command approvals: smart or manual

With the terminal tool on, Hermes stops before a dangerous shell command or an
`execute_code` script and asks for approval. The command approvals setting
(Hermes' own `approvals.mode`) decides who answers first:

- **Smart** (the default): a call to your `hal0/agent` model approves the
  command. If that call fails, or answers anything but APPROVE, Hermes falls
  back to asking you.
- **Manual**: you approve every flagged command yourself.

Switch it in the dashboard (Settings ▸ Security ▸ Hermes command approvals) or
from the CLI:

```sh
hal0 agent command-approvals          # show the setting and what is in effect
hal0 agent command-approvals manual   # always ask me
hal0 agent command-approvals smart    # let the approval model answer first
```

The change re-renders Hermes' config and restarts `hal0-agent@hermes` if it is
running. If any step fails, the previous setting is restored and the command
reports the error. While the terminal tool is off, the setting has no effect.

This is not [the approvals queue](#the-approvals-queue). That queue holds gated
hal0 MCP tool calls. Command approvals gate the shell commands Hermes runs.

The setting is stored as `command_approvals` in the `[hermes]` table of
`/etc/hal0/agents/hermes.toml`. That file is root-owned, so the agent cannot
change the stored setting, and a later re-provision always renders your choice
rather than one the agent wrote. An `approvals.mode` in
`/etc/hal0/agents/hermes/overrides.yaml` wins over the setting. The dashboard
and `hal0 agent command-approvals` then show the override's value as the one in
effect.

If Hermes' `config.yaml` no longer holds the value hal0 rendered, the dashboard
and `hal0 agent command-approvals` say so, and `hal0 doctor all` shows a
warning row. Pick the mode again (or, when overrides.yaml sets it, run
`hal0 agent reprovision hermes`) to re-apply it.

<Aside type="caution" title="Known limits">
The setting is not a boundary against an agent that has the terminal tool on.

- Hermes reads `approvals.mode` from its own `config.yaml` under
  `/var/lib/hal0/.hermes`, which the `hal0` user owns, and the agent runs as
  that user. With a shell it can edit that file directly (for example to
  `off`) without any API call. This stays true after
  [ADR-0024](/docs/adr/0024-agent-credential-tier). hal0 restores your choice
  at the next re-provision, and the drift warning above is how you notice it
  in the meantime.
- Until ADR-0024 ships, agents authenticate with the box admin key, so a
  Hermes agent with the terminal tool on can also call the admin API that
  changes the setting itself, just as it can approve its own queued MCP calls.
  The admin MCP tools never expose the setting, and the API refuses a request
  that identifies itself as an agent, but neither stops a prompt-injected
  agent with a shell.
</Aside>

### Delegation slot

When Hermes hands work to `delegate_task` children, they run on the `agent`
slot by default, the same slot as the parent. On a single-parallel
llama-server the children then queue behind the parent. To run them on another
slot, such as `utility`, set `delegation_slot` in the `[hermes]` table of
`/etc/hal0/agents/hermes.toml`:

```toml
[hermes]
delegation_slot = "utility"
```

There is no CLI or dashboard writer for this yet, so edit the root-owned file.
The choice survives `hal0 agent reprovision hermes`, which renders it as
`delegation.model = "hal0/utility"`. It is applied only while that slot is
ready. If the slot is down at provision time, nothing is rendered and a value
from an earlier run stays, so start the slot and re-provision.
`hal0 doctor all` warns while the chosen slot is not ready.

## Manage the lifecycle

<Tabs>
<TabItem label="List / status">

```sh
hal0 agent list                 # installed bundled agents
hal0 agent list --json
hal0 agent status hermes        # provisioning checkpoint, per phase
hal0 agent peers                # every published agent identity card
```

`list` only shows agents installed on this host; `peers` searches the
memory store for every identity card any host has published (needs the
memory API reachable).

</TabItem>
<TabItem label="Logs">

```sh
hal0 agent log hermes
hal0 agent log hermes --phase provision
```

Per-phase provisioning logs — these are flat files under the agent's
state directory, not a systemd journal. See
[Logs and activity](/docs/guides/logs-and-activity) for how this differs
from a slot's runtime logs.

</TabItem>
<TabItem label="Re-run / upgrade">

```sh
hal0 agent reprovision hermes          # idempotent re-converge
hal0 agent reprovision hermes --repair # force every phase, building a fresh release
hal0 agent upgrade hermes              # build and activate a fresh release of the pin
hal0 agent upgrade hermes --to <sha>   # build a vetted commit other than the pin
```

`reprovision` is a stable wrapper over the same state machine `install`
runs. Plain `reprovision` re-converges the agent, including its managed
virtualenv, so it is the command to reach for when the agent is running
but its MCP tools are missing. `--repair` forces every phase instead of
converging: it builds a fresh Hermes release, re-writes the persona seeds
and re-renders the config.

Every build lands in its own release directory under `/var/lib/hal0/hermes`
and is checked before anything switches. Activating it stops the agent and
the gateway (only the ones that were running), moves the `current` link,
runs `hermes config migrate` from the new release, starts the units again
and re-checks them. If that re-check fails, hal0 switches back to the
previous release and restores `config.yaml` by itself.

`upgrade --to` takes only a full commit sha listed in hal0's vetted refs.
A version string such as `0.15.3` or an `==X.Y.Z` spec is refused. A ref
other than the pin lasts until the next `hal0 update`, which builds the pin
again.

To watch each phase as it runs, or to re-run provisioning without the
network, drop to the underlying command directly. With `--offline` it never
builds: if a build is needed, the install step fails and names the step
that needs the network, and a running host keeps its live release. It is one linear pass: there is no
preview mode and no way to skip a phase, and it refuses `--dry-run` and
`--skip-phase` rather than run a real install.

```sh
hal0 agent bootstrap hermes --offline
hal0 agent bootstrap hermes --repair --verbose
```

To restart the running Hermes process without re-provisioning anything:

```sh
sudo systemctl restart hal0-agent@hermes
curl -X POST http://localhost:8080/api/agents/hermes/restart
```

Restart the Hermes gateway with `sudo systemctl restart hermes-gateway`, not
with `hermes gateway restart` or `hermes gateway start`. Upstream's commands
regenerate the unit when it differs from what they would write, which turns
hal0's stable `/var/lib/hal0/hermes/current/` paths back into the paths of
one release under `/var/lib/hal0/hermes/releases/<id>/`. The gateway then
stays on that release when hal0 builds a newer one, and `hermes gateway status`
reports the unit as outdated. `sudo hal0 agent install hermes` regenerates and
normalises the unit again.

</TabItem>
<TabItem label="Uninstall">

```sh
hal0 agent uninstall hermes
hal0 agent uninstall hermes --keep-memory
```

Default uninstall tears down the agent's private memory namespace too;
`--keep-memory` preserves it so a re-install reuses the identity card.

Uninstalling Hermes also runs `loginctl disable-linger hal0`, which undoes the
linger the Hermes gateway turned on. Run the uninstall as root for that step;
otherwise it prints the command to run.

</TabItem>
</Tabs>

## Running `hermes` as root

Upstream `hermes` resolves its state from `~/.hermes`, so a bare root
invocation would read `/root/.hermes` — an empty tree the agent never
uses — and commands like `hermes mcp list` would falsely report
"No MCP servers configured" on a healthy install. hal0's `hermes`
wrapper prevents that: run as root, it re-executes as the `hal0`
service user (via the run-as-hal0 guard), so you see the same config
the running agent uses. If the guard can't drop privileges, the
wrapper points `HOME` at the service home instead and prints which
`~/.hermes` tree it resolved on stderr. `HAL0_ALLOW_ROOT=1` opts out
for deliberate root debugging — the wrapper then leaves root's
environment alone but still names the tree it is reading. The
euid-aware fix inside the hermes CLI itself is an upstream
(NousResearch/hermes-agent) matter; the wrapper is hal0's seam.

## Personas

A persona is a TOML file pairing a system prompt with tool gating:

```sh
hal0 agent personas list                 # list + mark the active one
hal0 agent personas show <id>            # print a persona's TOML (good template)
hal0 agent personas activate <id>        # switch the active persona
```

Activating writes the active pointer atomically. The persona's prompt reaches
Hermes as `agent.system_prompt` in its `config.yaml` the next time hal0
provisions the agent, so run `hal0 agent reprovision hermes` after switching.
A restart alone does not apply it. To author your own, copy `personas show`
output, change the persona id, and save it under the persona store.

## Connect accounts for OAuth skills

Skills that act on a third-party account — Google Workspace, Spotify, GitHub —
need an OAuth grant. hal0 runs the consent flow itself: you open a consent
link, the provider redirects back to hal0-api, and hal0 exchanges the code for
a token server-side, using PKCE where the provider supports it. Nobody copies
an authorization code, and the agent never sees a client secret.

<Steps>

1. Register an OAuth app in the provider's developer console with this
   redirect URI:

   ```
   <base>/api/oauth/<provider>/callback
   ```

   `<base>` is `HAL0_DASHBOARD_URL`, else `HAL0_API_URL`, else
   `http://hal0.local:8080`, read from hal0-api's environment — never from the
   request's `Host` header. It must be reachable from your browser and match
   the console entry exactly.

2. Put the app's client ID in `/etc/hal0/oauth-providers.toml`. hal0 seeds this
   file from its shipped defaults (`google`, `spotify`, `github`) the first
   time the registry is read and never overwrites it afterwards. Every shipped
   entry has an empty `client_id`. Add your own `[[providers]]` entry the same
   way.

3. If the provider needs a client secret (`google` and `github` do; `spotify`
   is PKCE-only), store it — you are prompted for the value:

   ```sh
   hal0 oauth set-client-secret google
   ```

4. Connect, then poll until the account reports connected:

   ```sh
   hal0 oauth list               # configured, connected, expiry per provider
   hal0 oauth connect google     # prints the consent URL
   hal0 oauth status google
   ```

   A consent link is single-use, expires after 10 minutes, and does not
   survive a `hal0-api` restart — run `connect` again if it goes stale.

5. Restart the agent so it loads the token:
   `sudo systemctl restart hal0-agent@hermes`.

</Steps>

The dashboard covers steps 3 and 4 too: **Settings ▸ Integrations ▸ Connected
Accounts** lists each provider's status, stores a client secret, opens the
consent link in a new tab, and disconnects.

Tokens and client secrets are stored in `/etc/hal0/api.env` as
`HAL0_OAUTH_<PROVIDER>_TOKEN` and `HAL0_OAUTH_<PROVIDER>_CLIENT_SECRET` — never
in the TOML registry, never returned by an endpoint. hal0 does not refresh
tokens: when `hal0 oauth status` reports the token expired, connect again.
`hal0 oauth disconnect <provider>` asks the provider to revoke the token where
the registry names a `revoke_url`, and deletes hal0's copy even if that call
fails.

A Hermes provisioned on 1.3.0 or later has a persona section describing this
flow — send the consent link, poll `status`, confirm — which it runs through
`hal0 oauth` shell commands, so it needs the terminal tool (see above); with
the tool off, run the steps yourself. On a box provisioned before 1.3.0, run
`hal0 agent reprovision hermes` first.

## The approvals queue

Destructive or gated tool calls don't execute immediately — they land in
an approvals queue you review. This queue covers hal0 MCP tool calls; the
shell commands Hermes runs are gated separately by
[command approvals](#command-approvals-smart-or-manual).

```sh
hal0 agent approvals list                # pending requests
hal0 agent approvals approve <id>        # let it run
hal0 agent approvals deny <id>           # reject it
```

Each pending row shows the request id, the tool, the requesting agent,
when it was enqueued, and a one-line summary of the primary argument. The
dashboard's Agent → Approvals tab renders the same queue. See
[Connect MCP servers](/docs/guides/connect-mcp) for the full list of
gated admin tools.

## Spending budget

Each persona can carry spending caps so an autonomous loop can't drain a
paid provider pool. Caps live in the persona's `[persona.budget]`
sub-table:

```toml
[persona.budget]
daily_usd = 5.0
monthly_usd = 50.0
lifetime_usd = 200.0
per_call_max_usd = 0.50
hard_cap = true
```

Every cap is optional — omit one to leave that window uncapped, or set it
to `0.0` to block every paid request. `hard_cap = true` (the default)
denies requests that would overshoot; `hard_cap = false` lets them
through but still reports the breach.

```sh
curl http://localhost:8080/api/agents/hermes/personas/hermes/budget
```

The same route accepts a `PUT` with a `{"daily_usd": ..., ...}` body to
change the caps without hand-editing the persona TOML.

## Chatting directly

Outside of Hermes's own agent loop, `hal0 chat` is a terminal REPL over
the local `/v1/chat/completions` endpoint, defaulting to the `agent`
model alias. It supports `/think on|off|default` as an in-REPL command
and `--no-stream` for non-streaming output.

Open WebUI can also chat with each Hermes profile directly, through hal0's
`/v1`. See [Talking to Hermes](/docs/guides/open-webui#talking-to-hermes).

## Audit trail

Every gated tool invocation is journaled. Pull an agent's recent MCP
activity:

```sh
curl 'http://localhost:8080/api/agents/hermes/activity?limit=50'
```

Each row carries `tool`, `args`, `gated`, `outcome`, `timestamp`, and the
`client_id` the action was attributed to.

## When the agent has no memory tools

An otherwise healthy Hermes that answers chat but cannot recall anything
usually has a broken MCP client rather than a broken memory service. There
are two independent causes, and both are repaired automatically now.

The first is the wiring: the `X-hal0-Private` header has to be a YAML
string, and a version that wrote it unquoted left the client unable to
connect. The second is the managed virtualenv itself. A venv that drifted
off its vetted pin — no `mcp` package installed at all — used to survive
every upgrade untouched, because nothing outside provisioning re-converges
the venv and `hal0 update` never provisions. The symptom is a client that
fails to import with `mcp.client.streamable_http is not available` while
the config header reads correctly.

`hal0 update` now checks both on every upgrade and repairs what it finds.
A venv repair builds a fresh release of the live commit and activates it,
switching back on its own if the result does not check out. Verification
is a re-probe of the import, not the installer's exit code, so a repair
that silently produces an unusable venv is reported as a failure rather
than a success. If a repair cannot run — no venv on the box, no network,
another build holding the builder lock — the update logs the fault and the
remedy and carries on rather than failing; the next update retries.

`hal0-api` also probes this on every start, including crash-restarts, but
that path only diagnoses: it will not build during the startup of a box
that is already unhealthy. It logs the remedy, and the next real update
performs the repair.

To fix a box by hand:

```sh
hal0 agent reprovision hermes           # re-converges the venv; usually enough
hal0 agent reprovision hermes --repair  # builds and activates a fresh release
```
