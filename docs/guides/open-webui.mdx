hal0 ships **Open WebUI** as a companion container (`hal0-openwebui.service`,
LAN `:3001`) and writes its environment file
(`/etc/hal0/openwebui.env`) for you — there is nothing to configure inside
Open WebUI's own settings for any of this to work. What gets wired depends
on what you have actually enabled through hal0's own capability slots:

| Open WebUI feature | Wired when | Always on? |
| --- | --- | --- |
| Chat | — | Yes — points at hal0's own `/v1` |
| Voice (Call mode) | — | Yes — STT/TTS point at hal0's `/v1/audio/*` |
| Document uploads (RAG) | An **embed**-capable slot is enabled | No |
| Shared Hindsight memory | You installed the `hal0_hindsight_rag` Filter (see below) | No |
| Image generation | The **img** capability has an installed model the API can render | No |
| Web search | A search provider is installed | No — none ships today |
| hal0's tools (MCP) | `[bridge].enabled` is on and hal0 has minted the `openwebui` bridge client | No |

<Aside type="note">
Chat and voice are unconditional because hal0 always exposes a `/v1`
gateway and voice endpoints — there is no "off" state for those to be
gated on. Documents and images are real capability slots you turn on
yourself; hal0 never tells Open WebUI a feature exists unless there is a
real backend behind it, so an unwired button fails honestly instead of
silently doing nothing.
</Aside>

## Chat and voice (always wired)

`OPENAI_API_BASE_URLS` points Open WebUI's chat at hal0's own `/v1`
gateway, and `AUDIO_STT_*` / `AUDIO_TTS_*` point Call mode's transcription
and synthesis at hal0's own `/v1/audio/transcriptions` and
`/v1/audio/speech`. See [Speech to text and text to
speech](/docs/guides/voice-stt-tts) for the underlying `stt`/`tts` slots
Call mode actually dispatches to.

## Document uploads (RAG)

Open WebUI's upload button embeds every document you attach through
whichever model backs its `RAG_EMBEDDING_MODEL` setting. hal0 points that
at its own `/v1` and the model id bound to the **embed** capability's
`embed` child — enable it the same way you'd enable any other capability:

```sh
hal0 capabilities set embed embed --model <your-embed-model>
```

Until an embed-capable slot is enabled, `RAG_EMBEDDING_ENGINE` and its
siblings are left unset — Open WebUI falls back to its own bundled
sentence-transformers model rather than a broken hal0 route. See [Enable
memory](/docs/guides/enable-memory) and [Choose
models](/docs/guides/choose-models) for picking an embed model.

## Shared Hindsight memory in RAG

hal0 can add relevant shared Hindsight memory to every chat with one of its own
slot models as another native Open WebUI source. It does not copy memory into Open
WebUI's vector database: a global inlet Filter calls
`POST /api/memory/context` and adds the returned raw chunks and facts to the
same list of sources uploads use. Uploaded documents and Hindsight memory
therefore share Open WebUI's normal source and citation UI.

Automatic recall is deliberately **shared-only**. The endpoint accepts no
bank, dataset, private toggle or caller-controlled agent identity. Private and
project memory stays with the explicit hal0-memory tools.

Only a model listed with `owned_by` `hal0` gets this, so raw memory never goes to
a cloud model. Turns to a remote upstream or a Hermes profile (which recalls for
itself) skip the Filter, and so does a workspace model you built over a slot,
because Open WebUI does not say where it runs. All of them can still call the
memory tools.

Open WebUI 0.13 turned the file/RAG path that carries this memory off by
default: it now runs only for a model whose `file_context` capability is on.
hal0 pins that capability on in the Open WebUI environment file
(`DEFAULT_MODEL_METADATA={"capabilities":{"file_context":true}}`), so recall
keeps reaching the model. A model whose own settings say otherwise still wins,
and a hand edit to that line in `/etc/hal0/openwebui.env` survives every
re-render — see [ADR-0059](/docs/adr/0059-openwebui-file-context-capability-pin).

<Aside type="caution">
Do not enable this on a box with Open WebUI users you do not trust. Any user's
`memory_add` lands in shared memory (`user:<name>` is a tag, not a permission),
and the Filter then injects that note into other users' turns, in chats that can
also hold `agent_run`. The reminder hal0 adds to the system message tells a model
not to obey retrieved text. It cannot make the model comply.
</Aside>

Each turn waits for recall before the model starts. Against a large bank that
is several seconds. If recall takes longer than the Filter's `timeout_seconds`
valve (10 seconds), or Hindsight is down, the chat continues without memory
context and says nothing about it.

The Filter is not installed by default. To have hal0 manage it, add an Open
WebUI admin token to `/etc/hal0/api.env` and converge the component; hal0
creates and globally enables only its own Function ID:

```sh
# add HAL0_OPENWEBUI_ADMIN_TOKEN=<Open-WebUI-admin-token> to /etc/hal0/api.env
sudo systemctl restart hal0-api.service
hal0 update component openwebui
```

Without a token, import it once under **Admin → Functions** from this URL, keep
the ID `hal0_hindsight_rag`, save it, and turn on both **Active** and **Global**:

```text
http://host.docker.internal:8080/api/memory/openwebui-function/hal0_hindsight_rag.py
```

hal0 never uses Open WebUI's bulk Function sync, never touches other Functions,
and will not overwrite a user-owned Function that happens to use the same ID.
To stop recall, turn the Function off in that same screen. hal0 leaves it
installed and off. Clearing the token does not stop it: the Function keeps
running, and hal0 only stops updating it. A token Open WebUI refuses shows as
`hindsight_rag: auth_rejected` in the component's converge result.
Without a token hal0 cannot update a Function you imported by hand, so import it
again if a release note says the Filter changed.

## Image generation

The image button in the chat composer generates through hal0's own
`/v1/images/generations`, the endpoint any OpenAI client uses, so a render
goes through the same model resolution, template, step count, size default
and GPU switch, including the `img` slot's `[image].default_size` and
`default_steps` (see [Generate images](/docs/guides/generate-images) for the
underlying capability and [the image defaults](/docs/guides/image-workflows-troubleshooting#the-image-settings)).
Pick the model in hal0:

```sh
hal0 capabilities set img img --model <your-image-model>
```

hal0 sets Open WebUI's image engine to OpenAI, with its base URL at hal0's
`/v1`, the box client key (the same key chat and voice use, so it keeps
working with auth on), the model selected for `img`, and an empty image size
so that hal0 picks the size. Image settings are written only while the
selected model is installed and the API can render it. Changing the `img`
selection, installing an image model or removing one re-renders them, and a
running Open WebUI restarts to pick them up.

Open WebUI's image settings page lists OpenAI's model names, which hal0 does
not serve, so choose the model in hal0 rather than there. A change made on
that page lasts only until Open WebUI restarts, because hal0 turns off Open
WebUI's persistent config. Open WebUI no longer connects to ComfyUI; ComfyUI's
editor stays on the dashboard's Image Gen tab.

Each image render from Open WebUI puts the GPU in image mode for as long as
the image takes. A chat request for a GPU slot that arrives during the render
waits for the render to finish and for hal0 to reload the chat models (up to
120 seconds in all) instead of being refused, so Open WebUI's reply in the same
turn, right after the image, arrives later than usual by the time the chat
model takes to load. hal0 answers `503 gpu.image_mode` with `Retry-After: 15`
only when image mode is pinned, when ComfyUI's queue cannot be read, or when
the 120 seconds run out. When the last render is done, hal0 frees ComfyUI's
models and reloads the GPU slots it unloaded about 10 seconds later, or at once
when a chat request is waiting. If you pinned image mode (see
[Image mode and the GPU gate](/docs/guides/image-mode-and-gpu-gate#how-long-image-mode-lasts)), it holds until you unpin it
or force a switch back to inference, and chat on GPU slots is refused until
then. Chat on NPU and CPU slots is not affected.

Every render passes ComfyUI's GPU gate node (see
[Image mode and the GPU gate](/docs/guides/image-mode-and-gpu-gate#comfyuis-editor-and-the-gpu-gate)).
After updating hal0, run `hal0 slot restart img` once, so the running ComfyUI
container loads the current gate.

## Talking to Hermes

Open WebUI's model picker lists every Hermes profile that has an API key,
next to your slot models: `hermes-agent` for the default profile, and
one entry named after each additional profile. Picking one sends the turn to
that profile's own OpenAI-compatible API through hal0's `/v1`, so the profile
answers with everything it already has: its skills and toolsets, and the
hal0-admin and hal0-memory tools. Picking a slot model works exactly as it
did before. The same entries appear in `/v1/models` for any other OpenAI
client of hal0.

- **Tools and memory in every profile.** hal0 writes its hal0-admin and
  hal0-memory servers into each profile's own `config.yaml`, as that profile's
  identity with shared memory (private only if the profile sets
  `hal0: {memory_private: true}`), and keeps whatever else the profile
  configures. A profile you create later gets them within two minutes. To
  keep hal0 out of a profile, put `hal0: {wire_mcp: false}` in its
  `config.yaml`: hal0 then neither adds nor removes anything there, so to
  revoke the tools from a profile that already has them, delete the
  `hal0-admin` and `hal0-memory` entries yourself. `hal0 doctor` reports the
  wiring on its `hermes_profiles_mcp` row, including what an opted-out
  profile still carries.
- **Approvals** for gated hal0-admin tools land in the hal0 dashboard inbox,
  as they do from any other Hermes channel. The turn does not wait on them.
- **History** is resent by Open WebUI on every turn; hal0 holds no Hermes
  session state. Clients that send `X-Hermes-Session-Id` or
  `X-Hermes-Session-Key` have both forwarded to Hermes.
- **`/v1/responses` is not available** through hal0. Use chat completions.
- **Titles, tags and follow-ups do not use the Hermes profile.** New installs
  set `TASK_MODEL_EXTERNAL=hal0/agent`, so those calls use the agent slot.
  Existing `openwebui.env` files keep their task model, including `utility`
  on older boxes. To use another model, edit `TASK_MODEL_EXTERNAL` in
  `/etc/hal0/openwebui.env`: hal0 keeps a hand edit across re-renders.
  `hal0 doctor all` warns if that value names a slot that no longer exists.
  A task model chosen on Open WebUI's admin
  screens does not survive a restart, because hal0 runs it with
  `ENABLE_PERSISTENT_CONFIG=False`.
- **One chat is one Hermes session.** hal0 turns Open WebUI's chat id
  (`X-OpenWebUI-Chat-Id`, sent because hal0 sets
  `ENABLE_FORWARD_USER_INFO_HEADERS=True`) into `X-Hermes-Session-Id:
  owui-<chat id>` when it sends a turn to a Hermes profile, unless your
  client already sent a session header. The Hermes dashboard then lists the
  chat as a session, and Hermes memory scopes to it. A chat id with anything
  other than letters, digits, `_` and `-` (at most 64) is ignored. Turn this
  off with `[openwebui] hermes_session_from_chat_id = false`
  ([config reference](/docs/reference/config-schema#openwebui)).
- **Do not enable tools on a `hermes-*` model.** A Hermes profile already
  has hal0's memory and admin tools, so hal0 drops the `tools` and
  `tool_choice` Open WebUI would send along with a turn to one; without that,
  Open WebUI would answer the profile's tool calls itself and loop. Slot
  models keep the tools you attach. This is the same setting as above.
- **Keys.** Hermes gives each profile its own API key. hal0 reads them from
  Hermes's own `.env` files and keeps them in its process only. It never
  writes a key into `api.env`, the Open WebUI container or the vault. It
  writes a missing key into a named profile's own `.env`, and it mirrors the
  default profile's key into `$HERMES_HOME/.env` when it provisions Hermes.
  It does so at every hal0-api start (so after every `hal0 update`), every
  two minutes after that, on `hal0 agent reprovision hermes`, on
  `POST /api/agents/hermes/reconcile-upstreams` and after the Hermes
  component converge job, and the profile appears in the picker after that.
- **`hermes-agent` missing from the picker?** On a box where Hermes was
  installed before 1.6.0, the default key sits only in hal0's root-only
  vault, which hal0-api cannot read. Run
  `sudo hal0 agent reprovision hermes --repair` once; it mirrors that key
  into `$HERMES_HOME/.env` and the entry appears on the next reconcile.
  `hal0 doctor` reports this on the `hermes-api` row.
- **When Hermes is down** or still starting, its entries stay in the picker
  and a turn to one fails at once with `dispatch.upstream_unavailable`. It is
  never answered by a slot model instead. hal0 re-checks the gateway every two
  minutes. A long agent turn is allowed up to 600 seconds of silence on the stream and 1800 seconds in total. A named profile is dropped only when the running gateway answers 404 for it. Hermes entries are registered and removed on `hal0 agent install` and `uninstall`, so an uninstall removes them.

To hide a profile from the picker, change it on the Hermes side: run
`hermes -p <profile> gateway stop` to park it, or set `gateway.standalone:
true` in that profile's config. Hermes then stops serving it, and hal0 removes
its entry on the next reconcile that finds the gateway running: within two
minutes, at a hal0-api restart, or on
`POST /api/agents/hermes/reconcile-upstreams`. hal0's entries for these
models are read-only on the providers page. `hermes-agent`, the default
profile, cannot be hidden this way and always stays.

The Agents chip on the Services page (below) lists these entries, and the
`hermes-api` row in `hal0 doctor` checks each one. A green row means the API
path answers; it does not prove the gateway has its tools installed. The design is
recorded in [ADR-0035](/docs/adr/0035-hermes-openai-api-as-v1-upstreams).

## hal0's tools in every chat

When the agent bridge is on (`[bridge].enabled`, the default), Open WebUI
gets hal0's own tools as MCP tool servers, so any model you chat with can
remember and recall through hal0 and hand work to Hermes. They show up in
Open WebUI as tool-server connections you did not add:

| Connection | Tools Open WebUI may call |
| --- | --- |
| hal0 memory (`/mcp/memory/mcp`) | `memory_add`, `memory_search`, `memory_recall`, `memory_list` |
| Hermes, delegate (`/mcp/agents/mcp`) | `agent_run`, `agent_run_wait`, `agent_run_status`, `agent_run_answer`, `agent_run_stop`, `agent_memory_search`, `agents_list` |
| hal0 admin (`/mcp/admin/mcp`) | Only if you grant it, see below |

Both are reached with one bridge key, held by a client named `openwebui`.
hal0-api creates that client the first time it starts with the bridge on and
the Open WebUI unit installed, writes the key into `TOOL_SERVER_CONNECTIONS`
in `/etc/hal0/openwebui.env` (mode `0600`), and restarts Open WebUI only if
the file changed. It never creates the client from a root-run command, and
never takes over an `openwebui` client you made yourself: with one of those,
hal0 renders nothing and `hal0 doctor` says so. The key lives in the env file
and in `bridge.db` as a hash; it is not shown anywhere else.

- **Rotate or re-scope it** with `hal0 bridge rotate openwebui` or
  `hal0 bridge scopes openwebui <scope>…`. hal0 re-renders the env file and
  restarts Open WebUI once. The old key stops working at once.
- **Revoking is final.** A revoked bridge client keeps its name, so hal0 does
  not create a new `openwebui`. Open WebUI keeps running without hal0's tools,
  and `hal0 doctor` reports the revoked client.
- **The admin connection is an opt-in** with
  `hal0 bridge scopes openwebui agents memory admin`. Open WebUI runs with
  sign-in off by default, so it hands every person who can reach port 3001 a
  chat model that can call hal0's admin tools (gated ones still wait in the
  approval inbox). Several admin tools return very large answers. Leave it off
  unless you are the only person who reaches Open WebUI, and treat it as an
  operator credential.
- **Memory writes say where they came from.** A note a model saves through
  Open WebUI is stored as shared memory tagged `agent:openwebui` and
  `user:<the Open WebUI user's name>`, with the chat id in its metadata
  (`chat_id`). Each note is its own document, so a second note in the same chat
  does not replace the first. Open WebUI's own memory store is off
  (`ENABLE_MEMORIES=False`), so there is one memory, hal0's.
- **Writers share one bank.** Notes from Open WebUI, Hermes and the brain land
  in the same bank, so the memory engine has more to extract and consolidate.
  Point that work at a slot or model that is not your chat model with
  `[memory.graph] extraction_slot` or `extraction_model`.
- **The key only goes to hal0.** The connections always point at hal0's own
  address, `http://host.docker.internal:8080`, whatever
  `OPENAI_API_BASE_URLS` lists: an address you added there for another
  provider never receives the bridge key, and `hal0 doctor` fails the
  `openwebui_mcp` row if a connection in the file points anywhere else.
- **The container must reach hal0 as `host.docker.internal`.** The installed
  `hal0-openwebui.service` needs `--add-host=host.docker.internal:host-gateway`.
  `hal0 update` does not rewrite an installed unit, so a box installed before
  that line existed lacks it; `hal0 doctor` reports the `openwebui_mcp` row as
  a warning then.
If the connections are missing in Open WebUI, run `hal0 doctor all` and read
the `openwebui_mcp` row: it names the first link that is broken (bridge off,
no client yet, a client you made, a revoked client, an env file without the
block or with a key the client no longer accepts, a unit without `--add-host`). After changing `[bridge].enabled`, restart
hal0-api. The design is in [ADR-0043](/docs/adr/0043-agent-bridge-and-bridge-keys).

## Web search

No search provider ships with hal0 today, so hal0 has nothing to point
Open WebUI's search at and renders no `ENABLE_WEB_SEARCH`. That is a seam
for a future extension (e.g. a SearXNG addon), not a switch you are locked
out of: while no provider exists hal0 leaves the five web-search keys
(`ENABLE_WEB_SEARCH`, `ENABLE_SEARCH_QUERY_GENERATION`, `WEB_SEARCH_ENGINE`,
`SEARXNG_QUERY_URL`, `WEB_SEARCH_RESULT_COUNT`) alone, so a self-hosted
SearXNG you wire up by hand in `/etc/hal0/openwebui.env` survives every
re-render and never restarts the container on its own (see below).

## Checking what's actually wired

The Services page's Open WebUI card shows a chip per feature — Chat,
Voice, Documents, Images, Web search, Agents, MCP — each lit only when hal0
actually has a backend behind it. Hover a chip for the specific slot or model it's
routed to (or why it isn't wired yet). The same information is available
over the API:

```sh
curl http://localhost:8080/api/services | jq '.services[] | select(.id == "openwebui") | .wired'
```

```json
{
  "chat": true,
  "voice": true,
  "documents": true,
  "images": false,
  "agents": ["hermes-agent"],
  "web_search": false,
  "mcp": true,
  "embed_model": "nomic-embed-text-v1.5",
  "image_model": null
}
```

The Images chip follows the same rule as Open WebUI's image settings: it is lit
only when the `img` selection names a model that is installed and that the API
can render, and `image_model` is `null` otherwise, even with a model selected.

The Agents chip is lit while hal0 has Hermes profiles registered; `agents`
lists the model ids each profile advertises, which may include Hermes
`model_routes` aliases as well as the profile's own id, and is an empty list
when there are none. It stays lit while the gateway is down, because the entries stay
registered then (see "When Hermes is down" above).

The MCP chip is lit when `[bridge].enabled` is on and a bridge client named
`openwebui` exists. It does not prove the env file carries the key or that the
container can reach hal0; the `openwebui_mcp` row in `hal0 doctor all` checks
both.

## Running next to Docker

Open WebUI's port 3001 is published by podman, and Docker can set the kernel's
`FORWARD` chain policy to `DROP`. That policy would leave port 3001 answering on
the box itself but timing out from every other host on the LAN. The
`hal0-podman-forward` unit prevents this: each time Docker starts, it adds an
`ACCEPT` for the `podman0` bridge to Docker's `DOCKER-USER` chain. The installer
enables it, and `hal0 update` refreshes and enables it after switching to the new
release, then runs it once. It does nothing on a box without Docker.

If port 3001 only answers locally, check the rules as root:

```sh
iptables -S FORWARD | head -1
iptables -S DOCKER-USER | grep podman0
```

With `-P FORWARD DROP` and no `podman0` rules, run
`systemctl restart hal0-podman-forward` and look at
`journalctl -u hal0-podman-forward` if the rules still don't appear. A Docker
installed from the snap has a different service name and doesn't trigger the
unit, so run that restart after each Docker start.

The rules go at the top of `DOCKER-USER`, so they take effect ahead of any rules
of your own there and allow all traffic to and from `podman0`. If you filter that
traffic yourself, opt out by masking the unit, which the installer and
`hal0 update` both leave alone, and then remove the rules it added. A plain
`systemctl disable` is not enough, because the next update enables the unit again.

```sh
systemctl mask hal0-podman-forward
iptables -D DOCKER-USER -i podman0 -j ACCEPT
iptables -D DOCKER-USER -o podman0 -j ACCEPT
```

## When the env file re-renders

`/etc/hal0/openwebui.env` re-renders automatically — you never edit it by
hand for any of this. It re-renders (and a running Open WebUI container
restarts **only if the rendered file actually changed**; a stopped or skipped
one is never started by this, and reads the new file at its next start)
whenever:

- You apply a capability change to `embed` or `img`
  (`hal0 capabilities set …` or the dashboard's Capabilities page).
- You create or delete the `embed` or `img` slot directly.
- You rotate, re-scope or revoke the `openwebui` bridge client, or hal0-api
  starts and has to create it.
- hal0 runs its regular component convergence pass: `hal0 update`, the
  Services page's Retry button on Open WebUI's version row, or the
  boot-time convergence check.

Hand edits are preserved across every re-render, with one exception: the
RAG / image-generation / web-search / MCP keys listed in the file's own
header. hal0 owns one of those keys only while it has something to point
Open WebUI at — an enabled `embed` slot, an enabled `img` slot, an installed
search provider, a live `openwebui` bridge client. While it does, it writes
the keys and replaces a hand edit to them; when that backend goes away it removes only the keys it wrote itself
(recorded on the `# hal0-managed:` line in the header). A value you set by
hand while hal0 has nothing to claim for that block — a SearXNG pointed at
by hand, say — is never touched. The exposure knobs documented in the
installer (`HAL0_BIND_HOST`, `HAL0_OWUI_TRUSTED_EMAIL_HEADER`) and every
other key are always preserved.
