hal0 updates itself. The `hal0 update` CLI is a thin client over the
daemon's `/api/updates/*` surface, so the same code path runs whether you
trigger an update from the shell or the dashboard. The actual swap is a
**cosign-verified, atomic symlink swap** of `/usr/lib/hal0/current` — your
config (`/etc/hal0`) and state (`/var/lib/hal0`) are untouched.

## Check for an update

```sh
hal0 update --check
```

Fetches the release manifest for your channel and diffs it against the
running version. It shows `current → latest (channel)` plus whether an
update is available, and (when present) the release date, notes URL,
digest, and signer identity. A revoked (yanked) release is never reported
as available even if it's newer — the response still carries
`revoked_reason` so `--check` and the Settings → Updates panel can explain
why nothing was offered.

<Aside type="note">
Version comparison uses [PEP 440](https://peps.python.org/pep-0440/)
(`packaging.version.Version`) in both the updater and the API route, so a
pip-normalized installed beta (`0.8.0b3`) and a tag-form manifest version
(`0.8.1-beta.1`) compare correctly. A digit-tuple parser used to misread the
installed beta number as a patch component, so every box on a `0.8.0bN`
beta saw the newer release as "not newer" and `hal0 update` reported
nothing to apply — fixed in v0.8.1-beta.2. Non-PEP-440 nightly tags still
fall back to the digit-tuple comparator for their timestamp ordering.
</Aside>

## Apply an update

```sh
hal0 update
```

This checks, then applies if a newer version exists. The actual flow runs in
two stages: **prepare** (downloads, cosign-verifies, extracts the release
without touching the running system) and **commit** (performs the atomic
swap). After the prepare stage completes, the CLI renders the release notes
(highlights, breaking changes, migrations) and on an interactive terminal
prompts `Apply hal0 <version>?` before proceeding. Declining leaves the
staged tree in place (harmless) and tells you to re-run `hal0 update` to
apply it later. The `--yes` / `-y` flag skips the confirmation prompt — useful
for scripts, cron jobs, and unattended updates. Non-interactive or piped
invocations also skip the prompt automatically so updates never block.

After a successful apply the **daemon try-restarts hal0-api itself** — the CLI
never touches systemd. If the restart didn't complete, the result says so (the
new tree stays in place regardless).

To pin a specific version instead of the latest:

```sh
hal0 update --target v0.8.4b1
```

## Channels

Three release channels are available: **`stable`**, **`preview`**, and
**`nightly`**. Set your updater channel (it persists in `hal0.toml`), which
also runs a check:

```sh
hal0 update --channel preview
# or
hal0 update --channel nightly
```

For a new preview-channel bootstrap, pass the channel to the receiving shell:

```sh
curl -fsSL https://hal0.dev/install.sh | HAL0_CHANNEL=preview bash
```

The manifest URL contract is `https://releases.hal0.dev/<channel>.json`
(overridable via `HAL0_RELEASES_URL` for dev / air-gapped installs). Availability
still depends on the separately operated external release service publishing
that exact pointer and sibling bundle; this repository does not make those
external pointers operational. Preview is strictly opt-in: stable clients
accept only stable pointer contents and never consume preview artifacts. A
stable artifact may be promoted through the preview pointer without changing
its `release_kind`.

## Update from git (local dev)

For development or local testing, you can update hal0 directly from a git checkout:

```sh
hal0 update --source git
```

This clones or fetches the GitHub repository and pip-installs the newer version
directly, without downloading or verifying a release tarball. On an interactive
terminal it prompts to confirm before applying — `--yes` has no effect on this
path (it's only wired for the release path above); to skip the prompt, run
`hal0 update --source git` from a non-interactive or piped invocation instead.

To check for an update via git without applying it:

```sh
hal0 update --source git --check
```

Unlike the release path, a git-based update does **not** automatically restart
`hal0-api` — the CLI prints `Restart hal0-api to apply: systemctl restart
hal0-api` and leaves that to you. The post-update slot-drift banner still
appears, so you can restart drifted slots with `hal0 update --restart-slots`
when convenient. This code path skips the cosign signature and digest
verification described in the next section; it is intended for development and
testing, not production.

## How the atomic update works

<Steps>

1. **Fetch and authenticate** the exact release-manifest bytes and sibling
   `<channel>.json.bundle` with `cosign verify-blob`, using the updater's
   client-pinned release-workflow identity and issuer. No artifact URL is
   trusted before authentication succeeds. A missing `cosign`, missing bundle,
   or failed verification aborts closed.

2. **Download** the release tarball plus its Sigstore bundle into a per-version
   cache under `/var/lib/hal0`.

3. **Verify** the SHA-256 digest against the authenticated manifest, then
   verify the tarball signature against the GitHub Actions OIDC identity
   declared in the trusted manifest (`signer_identity` / `signer_issuer`).
   This artifact verification remains defense-in-depth; failure aborts the
   update and nothing is swapped.

4. **Extract** the tarball and run any forward config migrations the
   release needs, plus three self-healing passes over on-disk state:
   pruning any materialized seed profiles back to the code-defined
   catalog, clearing crash-only `mtp = true` slot overrides that no longer
   match their model, and retagging slot/custom-profile `image` pins that
   exactly match a *former* default runner image to the current default
   (a deliberate operator override — any other ref — is left alone; the
   new image is pulled by podman on the slot's next start).

5. **Swap** the `/usr/lib/hal0/current` symlink atomically using the POSIX
   `symlink(tmp) + os.replace(tmp, current)` pattern, then reinstall the
   code into the venv. A failed re-install rolls the symlink back so
   `current` and the venv never diverge.

6. **Re-render every slot's systemd unit** through the newly installed
   code, plus one `daemon-reload`. A slot's unit bakes its launch flags in
   at load time, so without this step a slot kept serving — or restarting —
   with pre-update flags until an operator restarted it *through hal0*.
   This step never bounces a running slot itself; the dashboard's drift
   indicator still flags any slot serving stale argv until its next start.

7. **Record** the prior symlink target in `/var/lib/hal0/hal0.previous`
   for rollback.

</Steps>

<Aside type="note">
After an update applies, the CLI checks whether any slots are still running
pre-update launch flags (printed as a drift banner). Since step 6 re-renders
unit files but never bounces a running container, a slot may keep serving
the older command until you restart it. When the CLI detects drift, it names
the affected slots and tells you to run `hal0 update --restart-slots`. This
flag is deliberately opt-in — a slot might be mid-inference — and it restarts
only the drifted slots, reporting which succeeded and which failed per-slot.
If nothing is drifted, no action is needed.
</Aside>

<Aside type="caution">
`hal0 update` verifies every release with `cosign verify-blob` before
swapping anything in. There is an escape hatch — `HAL0_UPDATE_SKIP_COSIGN=1`
— but it's only honored while the installed hal0 is itself on a pre-1.0
(0.x or pre-release) version, which covers every current release line.
Once hal0 reaches
a v1.x tag the variable is silently ignored and verified releases become
truly mandatory. A missing `cosign` binary always aborts the update unless
that skip hatch is active.
</Aside>

<Aside type="note">
The **initial one-line installer** uses the same signed-manifest trust
contract. It requires jq and cosign, verifies the sibling channel-manifest
bundle against the same pinned release-workflow identity and issuer before
parsing, then applies a strict `hal0.releases.v1` channel policy. It requires
the artifact `bundle_url`; detached signature/certificate fallback is not
accepted. Digest and bundle verification remain defense-in-depth.
</Aside>

## Roll back

If an update misbehaves, revert to the previously installed tree:

```sh
hal0 update --rollback
```

Rollback reads `/var/lib/hal0/hal0.previous`, atomically swaps the
`current` symlink back to it, then reinstalls that prior tree into the
venv — mirroring the apply-side reinstall — so it's what actually runs.
Unlike an apply, a rollback does **not** try-restart `hal0-api` for you:
the running process keeps serving the newer code until you restart it
yourself (Settings → Advanced's restart button, or `systemctl restart
hal0-api`). It warns (without erroring) if the previous tree is gone on
disk, and if the current config's `meta.schema_version` is ahead of what
the previous tree understands — migrations are forward-only, so the older
tree just parses what it can. If no previous-version record exists,
there's nothing to roll back to.
