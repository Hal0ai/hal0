hal0 updates itself. The `hal0 update` CLI is a thin client over the
daemon's `/api/updates/*` surface, so the same code path runs whether you
trigger an update from the shell or the dashboard. The actual swap is a
**cosign-verified, atomic symlink swap** of `/usr/lib/hal0/current` — your
config (`/etc/hal0`) and state (`/var/lib/hal0`) are untouched by the swap
itself.

## Check for an update

```sh
hal0 update --check
```

Fetches the release manifest for your channel and diffs it against the
running version. It shows `current → latest (channel)` plus whether an
update is available, and (when present) the release date, notes URL,
digest, and signer identity. A revoked (yanked) release is never reported
as available even if it's newer.

## Apply an update

```sh
hal0 update
```

Checks, then stages the update, shows you the release notes (highlights,
breaking changes, migrations — pulled from the release manifest), asks
for confirmation, and applies. Skip the confirmation prompt for scripted
runs:

```sh
hal0 update --yes
```

The CLI polls the apply job until it reaches `applied` or `failed`. After
a successful apply the **daemon try-restarts hal0-api itself** — the CLI
never touches systemd.

To pin a specific version instead of the latest:

```sh
hal0 update --target v1.0.0
```


<Aside type="note">
`hal0 update` refuses outright on an editable/dev install (`pip install
-e`), with an actionable message to install from a release wheel instead.
</Aside>

## Channels

Three release channels are available: **`stable`**, **`preview`**, and
**`nightly`**. Set your channel (it persists in `hal0.toml`), which also
runs a check:

```sh
hal0 update --channel preview
```

![The Settings → Updates panel showing current version, available update, and channel selector](/screenshots/settings-page.png)
*Settings → Updates: current version, available release, and channel selector.*

### How a channel resolves to a release

A channel is resolved at check time. It is not a pointer file someone
maintains by hand.

The updater fetches `https://releases.hal0.dev/<channel>.json`. That host
scans the project's GitHub releases newest-first and serves the manifest
from the first release that publishes an asset of that name, together with
its detached `<channel>.json.bundle` signature from the same release. A
release therefore joins a channel by carrying that channel's manifest
asset — nothing else promotes it.

Which manifests a release carries follows from its tag:

| Tag shape | Manifests published |
| --- | --- |
| `v1.2.3` | `stable.json` and `preview.json` |
| `v1.2.3-rc.1`, `v1.2.3-alpha.1`, `v1.2.3-beta.1` | `preview.json` |
| `v1.2.3-nightly.20260829120000` | `nightly.json` |

The separator before the sequence number is a dot, and it is not optional.
`v1.2.3-rc.1` parses; `v1.2.3-rc1` does not and the release tooling rejects
it outright rather than publishing nothing quietly. A nightly tag carries a
14-digit timestamp.

A stable release also enters `preview`, so `preview` is never behind
`stable`. The reverse does not hold: only a final tag publishes
`stable.json`, so every preview and nightly cut afterwards pushes the
current stable release further down the release list. That is why the
channel host scans more than the first page of releases — a stable release
that falls off page one must still resolve. If a channel looks stuck, check
for a release cut without its manifest asset before suspecting the updater.

<Aside type="note">
The channel host is served by the website, not by this repository, so its
scan depth is a property of that deployment rather than of the hal0 tree.
</Aside>

Set `HAL0_RELEASES_URL` to point the updater at a different endpoint. It
wins over the default; when the override is an `http`/`https` URL and the
channel is not `stable`, the channel is appended as a `?channel=`
parameter instead of as a filename.

An active override is disclosed wherever the channel is named.
`hal0 update --check` labels the channel `— overridden`, prints the override
URL with a note that the configured channel is ignored, and reports
`pinned by HAL0_RELEASES_URL` instead of `up to date` when nothing newer is
found. `GET /api/updates/check` and `GET /api/updates/state` carry a
`releases_url_override` field (`null` when no override is set), which the
Settings → Updates page shows next to the channel.

## How the atomic update works

<Steps>

1. **Fetch** the release manifest for the channel.

2. **Download** the release tarball plus its detached cosign signature
   into a per-version cache under `/var/lib/hal0`.

3. **Verify** the SHA-256 digest against the manifest, then the signature
   with `cosign verify-blob` against the exact GitHub Actions OIDC
   identity declared in the manifest. A missing `cosign` binary or a
   failed verification aborts the update — nothing is swapped.

4. **Extract** the tarball into a versioned tree beside the running one.

5. **Swap** the `/usr/lib/hal0/current` symlink atomically, then reinstall
   the code into the venv. A failed re-install rolls the symlink back so
   `current` and the venv never diverge. The activation then re-installs the
   root-owned `hal0-*` sudo wrappers, re-asserts the `/usr/local/bin/hal0`
   and `/usr/local/bin/hal0-agent` PATH links from the new tree, and removes
   root-owned files older releases installed and nothing replaces (the
   `hal0-slotctl` wrapper, the `hal0-slotctl` and `hal0-comfyui` sudoers
   grants, and a pre-quadlet `hal0-slot@.service` template). The new code
   then runs the config migrations the release needs.

6. **Re-render every slot's systemd unit** through the newly installed
   code. The re-render itself never bounces a running slot. Afterwards the
   CLI restarts every slot whose drift includes a new runner image, because
   a stale image keeps serving the build the release replaced; a slot that
   is mid-request is skipped and listed as "could not be restarted
   automatically: in use". Slots with argv-only drift are left running and
   shown in the "N slots need restart" banner; pass `--restart-slots` to
   bounce them. Pass `--no-restart-slots` to skip the automatic image
   restart too. While an image restart is still pending, `hal0 update`
   says so and exits **2** instead of reporting a clean success.

7. **Record** the prior symlink target in `/var/lib/hal0/hal0.previous`
   for rollback.

</Steps>

## Profile-centric config conversion

Slot files carry placement only; every tune (flags, context window, thinking
default, vision, speculation) lives on a profile ([ADR-0029](/docs/adr/0029-profile-centric-config)).
`hal0 update` converts an older install once, automatically, after the
runner-system conversion; `hal0 serve` also runs it when it starts `hal0-api`,
before config is validated. The conversion gives every slot the profile that
keeps what it launches today, generating one where needed, and reports every
value that never reached a launch (those are dropped, never applied). Before it
writes anything it backs up every file it changes, plus the model tuning rows,
to `/var/lib/hal0/backups/profiles-<ts>.tar.gz`. A run with nothing to write
makes no backup, and a rerun converts nothing that is already in the new shape.

Preview the plan without changing anything, or run it by hand as the service
user:

```sh
hal0 profile migrate                         # preview: profiles to generate, slots to re-point, dropped values
sudo -u hal0 hal0 profile migrate --apply    # convert (backs up first)
```

Run `--apply` as `hal0`, not as root, so the backup stays readable by
`hal0-api` and `hal0 update --rollback`.

Four launch changes are reported rather than applied silently:

- a slot without a usable profile gets its type's seed (`embedding`, `reranking`);
- `--jinja` is no longer added in embedding or reranking mode;
- the MTP draft device follows the slot's own device;
- forced MTP stops on a runner without MTP support.

If a slot, stored profile or stack cannot be converted, `hal0 update` prints
each blocker with its reason and the fix, and exits **2** (applied, not
converged); `hal0 profile migrate` also exits 2 while anything is blocked. A
blocked slot launches with its recorded pre-conversion tune only while its
file is unchanged and still carries the old tuning keys; the recorded tune
covers the launch flags and context window, while host, port, model, chat
template, projector and placement come from the current slot and model.
Editing the slot file drops the record. If tuning keys remain, the slot then
refuses to launch (`slot.unconverted`) until the conversion succeeds or you
remove them; once they are gone it launches under its profile (or its type's
seed). Every other slot still converts. To go back, see "Rolling
back past the profile-centric conversion" below.

## Upgrading to 1.3.0

The config schema version is unchanged and nothing needs a manual migration
pass, but a few things are worth doing or checking. The full list is in the
`1.3.0` Migrations and Breaking sections of `CHANGELOG.md`.

- **Refresh the PATH link once, when coming from 1.2.0 or earlier.** 1.3.0's
  updater re-asserts `/usr/local/bin/hal0` on every activation, but the
  activation that installs 1.3.0 still runs the outgoing version's code. If
  `hal0 --version` keeps reporting the old version while the dashboard and API
  report 1.3.0, run:

  ```sh
  sudo hal0 doctor wrappers --fix
  ```

  It re-installs the sudo wrappers, their sudoers drop-ins and the
  `/usr/local/bin/hal0` (+ `hal0-agent`) links from the active tree. Without
  `--fix` it only reports which tree it would refresh from. A later
  `hal0 update` also fixes the link.
- **Reprovision Hermes before using OAuth-connected skills.** The agent's
  half of the OAuth connect flow lives in its persona file, which `hal0 update`
  does not rewrite. On an already-provisioned box run
  `hal0 agent reprovision hermes`. Each shipped OAuth provider also has an
  empty `client_id`, so configure the provider's own app credentials before
  connecting an account.
- **Off-box admin calls may now need a credential.** On a box with an admin key
  configured and `hal0-api` bound past loopback, mutating (ADMIN-class) routes
  answer `401 auth.required` to off-box callers even with `require_auth` off.
  See [Authentication](/docs/operate/auth/).
- **Check a pinned `img` slot.** A ComfyUI slot's `image_pin` is now honoured,
  so an `img` slot carrying a pin that never took effect can start a different
  container image. Check `/etc/hal0/slots/img.toml` before upgrading and clear
  `image_pin` if you want the resolver default.
- **Pull before enabling a capability.** `POST /api/capabilities/{slot}/{child}`
  with `enabled: true` for a model whose weights are not on disk now returns
  `409 capability.model_not_downloaded`. Pull first
  (`POST /api/models/{id}/pull`), or stage the selection with
  `enabled: false`.
- **Hard-refresh an open dashboard tab** if layout saves start failing:
  `PUT /api/user/dashboard-layout` now accepts only the v3 body and answers an
  older cached bundle with `422 layout.invalid`.
- **Rolling back to 1.2.0 after writing an MCP server record.** 1.3.0 writes
  installed-server records in a new shape (a `[tools]` policy table, with the
  old tool count moved to `tools_count`), and 1.2.0 cannot validate it: the
  server disappears from `hal0 mcp list` and a direct read answers
  `400 mcp.record_malformed`. A record is rewritten whenever 1.3.0 saves it —
  installing a server, or changing its config, enabled flag, tool policy
  (`hal0 mcp allow`/`gate`/`block`) or exposure (`hal0 mcp expose`) — never on
  load, so a box that upgrades and rolls back without touching MCP servers is
  unaffected.
- **Skipping 1.2.0 from 1.1.0** still applies 1.2.0's automatic
  `profiles.toml` migration, and the migrated file does not parse on 1.1.0.
  Back up `/etc/hal0/profiles.toml` first if you may downgrade.

## Upgrading to 1.6.0

The first `hal0 update` to 1.6.0 changes how Hermes is installed. One step is needed on a box that had Hermes before 1.6.0 (the Open WebUI repair below); expect the following. The full list is in the Breaking section of the `## [1.6.0]` entry in `CHANGELOG.md`.

- **Hermes moves from 0.19.0 to v0.22.4 (`4d043038`) and from Python 3.12 to a uv-managed Python 3.14.** The update builds a release next to the live one under `/var/lib/hal0/hermes/releases/`, checks it, then switches. `/var/lib/hal0/venvs/hermes` becomes a symlink to `current/venv`. The build needs the network; an offline host refuses it and stays on 0.19.0. `/etc/hal0/hermes-python.env` is rewritten to the 3.14 interpreter and the old value is discarded with a `hermes-python-discarded` warning. A box already on v0.22.2 rebuilds onto v0.22.4 at its next `hal0 update`.
- **Expect a short Hermes outage** while the agent and gateway restart on the new release.
- **The gateway unit is regenerated and linger is enabled for `hal0` automatically.** Run `sudo hal0 agent install hermes` only if the update says it could not.
- **Hermes cannot be moved back to v0.22.2 once v0.22.4 is live.** v0.22.3 and later write gateway runtime state into Hermes's `state.db` that v0.22.2 cannot run over, so `hal0 update component hermes --target d923a5eb487a17c0a68801bba9ef0f56c81040a8` is refused as a downgrade. v0.22.2 stays in hal0's vetted refs for the automatic flip-back after a failed activation.
- **Session history is kept** (`sessions.auto_prune: false`) and the persona prompt is written to `agent.system_prompt` before the new Hermes first starts.
- **Open WebUI gets the default Hermes profile after one repair.** If the default profile is missing from the picker on a box that had Hermes installed before 1.6.0, run `sudo hal0 agent reprovision hermes --repair` once; `hal0 doctor` flags this on the `hermes-api` row. See [Talking to Hermes](/docs/guides/open-webui#talking-to-hermes).
- **The agent chat proxy is removed.** `/api/agents/{id}/events`, `/submit` and `/session/*` return 404.
- **Key rotation now ends open sockets and streams** (WebSocket close code `4401`, SSE `event: revoked`).

## Upgrading to 1.7.1

- **The upgrade floor is 1.5.0.** `hal0 update` on a 1.3.x or 1.4.x box
  stops before it downloads anything and prints the installer command that
  steps the box through 1.5.0; run that, then update again. See
  [Upgrading from an older release](#upgrading-from-an-older-release).
- **Run `hal0 slot restart img` once for the LAN editor.** The running
  ComfyUI container keeps the loopback bind it started with, so
  `http://<host>:8188` stays refused from other machines until the engine
  restarts. To keep the editor fenced to the box, set
  `[network].comfyui_listen = "loopback"` in `/etc/hal0/hal0.toml` before the
  restart. See [Reaching the editor](/docs/guides/generate-images#reaching-the-editor).
- **The GPU's controls are in the dock.** Hold, keep, unpin and stop image
  mode live in the dock's GPU segment and **gpu** tab on every page; the
  Engine tab keeps Restart engine and Logs, and the Slots page's Activity
  sidebar became the dock's **events** tab. See
  [The dock](/docs/guides/dashboard-and-settings#the-dock).
- **ComfyUI drops to the `hal0` account.** The same `hal0 slot restart img`
  switches the running container from root to the hal0 identity. If the
  ComfyUI data root (`/var/lib/hal0/models/comfyui` by default) was laid down
  by hand under another account or on a share, make its `output`, `input`,
  `user` and `custom_nodes` directories writable by `hal0` first, as root:
  `chgrp -R <hal0 group> <dir> && chmod -R g+ws <dir>`. A data root hal0
  created is already `hal0:hal0 2775`. Until then a render fails at
  `SaveImage` with `Permission denied`, and `hal0-api`'s journal logs
  `comfyui.data_dir_not_writable` with the command.

## Upgrading to 1.7.0

- **Run `hal0 slot restart img` once after the update.** ComfyUI loads its
  GPU gate node (`hal0_gpu_gate`) when the `img` container starts, and
  `hal0 update` does not restart slots. Until you restart it, the running
  container keeps the gate from the release before, which lets a prompt
  through when `hal0-api` is unreachable and after its own 120 seconds, and
  such a prompt can render next to the LLM slots. See
  [ComfyUI's editor and the GPU gate](/docs/guides/image-mode-and-gpu-gate#comfyuis-editor-and-the-gpu-gate).
- **With auth enforcement on, the same restart gives the gate its
  credential.** The new gate authenticates with a token of its own, which hal0
  mounts into the container when `img` starts. Until you run `hal0 slot
  restart img`, the 1.6.x gate the container still runs cannot authenticate
  on a box with `hal0 auth require on` (or a specific `HAL0_BIND_HOST` and an
  admin key). hal0 refuses its status request, and the 1.6.x gate then lets
  the prompt through without a GPU switch, so every editor prompt can render
  next to the LLM slots. See
  [ComfyUI's GPU gate credential](/docs/operate/auth#comfyuis-gpu-gate-credential).
- **Image models come from the image catalog.** `hal0 comfyui models list`
  shows each catalog model's install state, the GB it still has to download
  and the pick recommended for this box, and
  `hal0 comfyui models install <id>` installs one. `hal0 comfyui
  orchestrate-models` and the image ids in `hal0 model pull` are gone, and the
  GGUF image models `SD-Turbo-GGUF` and `Flux-2-Klein-9B-GGUF` cannot be
  installed again. See [Generate images](/docs/guides/generate-images).
- **Image mode no longer holds after the last render.** The update removes
  `[image].idle_restore_minutes` from slot files; the GPU returns to the LLM
  slots about ten seconds after the last render. Pin image mode to hold it for
  ComfyUI's editor. See
  [Image mode and the GPU gate](/docs/guides/image-mode-and-gpu-gate).
- **Toggle the Discovery card once** on the Services page if the box announced
  services on an earlier version. That removes ComfyUI's old mDNS
  announcement, which hal0 no longer writes and does not delete by itself.

## Upgrading from an older release

Upgrades start at **1.5.0** in the releases after 1.7.0 (1.4.0 from 1.6.0
through 1.7.0; 1.3.0 before that). Every release manifest declares the window
it upgrades from (`upgrade_from: ">=1.5.0"`), and both upgrade paths enforce
it:

- `hal0 update` on an older box stops before it downloads anything, with
  `system.update_upgrade_path_unsupported` and both versions named.
- Re-running the installer over an older install stops before it changes
  anything.

A nightly counts as a prerelease of its base version, so a `1.5.0` nightly is
below the floor and a `1.6.0` nightly is inside it.

From a 1.3.x or 1.4.x box, step through 1.5.0 with its installer, which
upgrades in place and keeps `/etc/hal0` and `/var/lib/hal0`, then update
again. This is the command the installer prints when it refuses a box below
the floor:

```sh
curl -fsSL https://hal0.dev/install.sh \
  | sudo env HAL0_RELEASES_URL=https://github.com/hal0ai/hal0/releases/download/v1.5.0/stable.json bash
hal0 update -y
```

`hal0 update --target` cannot make this hop. It is an exact pin against the
manifest the channel serves now, so once the channel has moved past a release,
`--target` with that release's version fails with `UpdateManifestInvalid`
before it downloads anything.

From 1.2.x or older, step through 1.3.0 the same way first, then follow the
1.3.x path:

```sh
curl -fsSL https://hal0.dev/install.sh \
  | sudo env HAL0_RELEASES_URL=https://github.com/hal0ai/hal0/releases/download/v1.3.0/stable.json bash
curl -fsSL https://hal0.dev/install.sh \
  | sudo env HAL0_RELEASES_URL=https://github.com/hal0ai/hal0/releases/download/v1.5.0/stable.json bash
hal0 update -y
```

Read "Upgrading to 1.3.0" above before you start from 1.2.x.

Or reinstall from scratch: `sudo bash installer/uninstall.sh --purge` deletes
`/etc/hal0` and `/var/lib/hal0`, models included, and the normal one-liner
then installs the current release.

## Component updates

Four components carry their own release-pinned version alongside hal0
itself: OpenWebUI (the companion container), runner images, Hermes, and
Hindsight. None of them float independently — each pin travels *inside*
the hal0 release, so a normal `hal0 update` converges all four as part of
applying. Reach for `hal0 update status` and `hal0 update component <id>`
for a narrower view, or to retry just the piece that's stuck.

```sh
hal0 update status
```

Prints the same hal0 version/channel check as `hal0 update --check`, plus
a table of installed / pinned / status for each component. `status` is
`converged` once the box matches the release pin; anything else
(`pending`, `stale`, or a failure status) still needs to catch up. Exits
**2** when a component is outstanding — useful for scripting a gate on
full convergence, not just "hal0 itself is current."

```sh
hal0 update component runner-images
hal0 update component hermes --check
```

Re-runs one component's converge arm without a full `hal0 update` — a
retry surface for a component that's stuck (e.g. `build_failed` after a
transient pull failure). `--check` prints the status row without
converging.

Hermes converges through its release builder. The first `hal0 update` after
upgrading to a release with the Hermes release layout migrates every host:
it builds a new release under `/var/lib/hal0/hermes`, stops the agent and
the gateway (only those that were running), moves the old venv aside as the
`legacy` release, switches, runs `hermes config migrate`, and starts the
units again. Expect a short Hermes outage during that step. On an offline host the build is refused, the update names the step that needs the network, and Hermes stays on its live release. If the new
release fails its re-check, hal0 switches back to the old venv, restores
`config.yaml`, and reports `activation_failed` with the
`sudo hal0 agent reprovision hermes --repair` remedy. The component row
also shows `busy` for a pass that found another Hermes build running; that
is not a failure, and the next update retries. The update also regenerates the gateway unit and enables linger for the `hal0` user; it shows a component note such as "Hermes config keys applied; restart hal0-agent@hermes to load agent.system_prompt" in `hal0 update` and `hal0 update status` when a restart is still pending.

<Aside type="note">
An apply that leaves a component unconverged, or a slot blocked by the
profile-centric conversion, still reports the update as applied, but exits **2** —
distinct from a failed update (exit 1). `hal0 update` prints the same
convergence report and component table inline after an apply, so you
don't need a separate `hal0 update status` call to see what's left.
</Aside>

## Roll back

If an update misbehaves, revert to the previously installed tree:

```sh
hal0 update --rollback
```

Rollback reads `/var/lib/hal0/hal0.previous`, atomically swaps the
`current` symlink back to it, then reinstalls that prior tree into the
venv and re-renders every slot unit. Unlike an apply, a rollback does
**not** try-restart `hal0-api` for you — the running process keeps
serving the newer code until you restart it yourself; the CLI names the
version it reverted to, shows what the previous-version slot now holds,
prints any schema warning as its own callout and, while the running version
still disagrees, prints the `systemctl restart hal0-api` remedy.
`POST /api/updates/rollback` returns the same facts as `rolled_back_to`,
`previous_now`, `schema_warning`, `running_version` and a
`restart_required` flag. It warns (without
erroring) if the previous tree is gone on disk, or if the current
config's schema version is ahead of what the previous tree understands —
migrations are forward-only, so the older tree just parses what it can.
If no previous-version record exists, there's nothing to roll back to.

Rollback swaps the code tree only. It does not restore `profiles.toml`,
slot files or any other config: that is config state, deliberately decoupled
from the code tree. The one exception is the profile-centric conversion below.

Rolling back from 1.6.0 to 1.5.x leaves Hermes running on the release 1.6.0 built, and leaves the Hermes build failing until you update again. 1.6.0 records a Python 3.14 interpreter in `/etc/hal0/hermes-python.env`, and 1.5.x accepts only 3.12, so its Hermes converge stops with `Hermes Python must be exactly 3.12: <path> reports 3.14`. The 1.5.x MCP probe also fails against the mcp 2.0 client in the new venv, so every `hal0 update` on 1.5.x reports the Hermes venv as broken and `hal0 agent reprovision hermes` and `hal0 agent reprovision hermes` fail at `mcp_wire`. Do not edit `hermes-python.env` to point 1.5.x at a 3.12 interpreter: 1.5's builder then replaces the release symlink at `/var/lib/hal0/venvs/hermes` with a 0.19.0 venv and leaves a stray `/var/lib/hal0/venvs/hermes.rollback-<pid>` behind. Update back to 1.6.0 instead, which clears these errors.

Rolling back from 1.7.0 to 1.6.x needs no step for image generation: the
1.7.0 GPU gate left in ComfyUI's `custom_nodes` directory reads 1.6.x's
`/api/comfyui/status` when `/api/comfyui/arbiter` is missing, and waits for
and asks for image mode as the 1.6.x gate did while that hal0 answers. Unlike
the 1.6.x gate, it still refuses a prompt when hal0 is silent or slow to
answer, where 1.6.x let it through. Two exceptions. On a box that enforces auth, the
gate refuses image prompts, because 1.6.x does not know the gate's token. And
once `img` restarts under 1.6.x, the gate refuses image prompts on a box whose
`hal0-api` does not answer on `127.0.0.1:8080` (another port, or
`HAL0_BIND_HOST` set to a specific address), because 1.6.x's unit no longer
passes the gate hal0's address or `HAL0_COMFYUI_GATE_FAIL_OPEN`.

### Rolling back past the profile-centric conversion

The release that moves to profile-centric config
([ADR-0029](/docs/adr/0029-profile-centric-config)) converts the slot,
profile and stack files on its first start. An older release cannot read the
converted files. So when `hal0 update --rollback` targets a release from before
the conversion, it puts every conversion backup back first
(`/var/lib/hal0/backups/profiles-<ts>.tar.gz`, newest first) and then swaps:

- the slot files, `profiles.toml` and `stacks.toml` return to the state the
  older release left them in;
- the model tuning returns to the `model` columns, which the conversion left
  in place;
- the conversion's database bookkeeping (migration 012) is forgotten.

The rollback response lists what was restored under
`profile_conversion_restored`. Restart `hal0-api` as usual.

If a backup is missing, the rollback refuses before it changes anything and
prints the steps to do it by hand:

```sh
sudo systemctl stop hal0-api
sudo -u hal0 hal0 profile migrate --restore /var/lib/hal0/backups/profiles-<ts>.tar.gz   # each backup, newest first
sudo systemctl start hal0-api   # the restore marker keeps it from converting again
hal0 update --rollback
```

Updating forward again converts the files again.

### Rolling back past per-slot tune overrides

A release before per-slot tune overrides
([ADR-0045](/docs/adr/0045-slots-carry-a-sparse-tune-override-table)) refuses
keys it does not know. So when `hal0 update --rollback` targets one, it removes
them first:

- `[tune]` from each slot file;
- `reasoning_effort` and `reasoning_budget` from `profiles.toml`;
- `tune` from each stack's slot entries, and the two reasoning keys from each
  stack's embedded profiles, in `stacks.toml`.

Each changed file is first copied to `<file>.bak-<stamp>` beside it, and a file
with none of these keys is not rewritten. If the swap fails or is cancelled, the
files go back as they were, except one edited since the strip, which keeps your
edit and its backup. The rollback response lists the changed files under
`tune_stripped`.

Updating forward again does not put the keys back. To restore an override, copy
it from the backup or set it again.

### Rolling back past the speculation rename

The release that adds speculative-decoding drafters renames the profile field
`mtp` to `speculation` (`auto`, `off` or `ngram`). `hal0 update` rewrites
`profiles.toml` once: `mtp = "off"` becomes `speculation = "off"`, `mtp = "auto"`
is dropped (auto is the default), and a `--spec-type` found in a profile's
`flags` is removed (an `ngram-*` value becomes `speculation = "ngram"`). Before
it writes, it copies the file beside itself as `profiles.toml.bak-<UTC
stamp>`, in the same directory as `profiles.toml`.

An older release does not know `speculation`, so it quarantines every profile
that carries the field (a slot that names one fails with `profiles.invalid`). Before `hal0 update --rollback`
to such a release, put the backup back:

```sh
sudo systemctl stop hal0-api
sudo cp /etc/hal0/profiles.toml.bak-<UTC stamp> /etc/hal0/profiles.toml
hal0 update --rollback
```

Profiles you created or edited after the update are lost with the copy. After
the update, the API and CLI refuse `mtp` on a profile (`422
profiles.field_renamed`, `hal0 profile ... --mtp` exits 2); there is no alias.

## Repin the OpenWebUI companion container

```sh
hal0 update component openwebui --check
hal0 update component openwebui --yes
hal0 update component openwebui --target <digest> --yes
hal0 update component openwebui --clear-override --yes
```

This is the same `hal0 update component <id>` every release-pinned component
uses (see [Component updates](#component-updates) above). Plain, it converges
the bundled OpenWebUI container to whatever pin hal0 carries for it, as a
plain `hal0 update` would. There is no `--tag` float-to-upstream flag; the pin
rides hal0 releases like every other component. `hal0 update owui` no longer
exists.

`--target <digest>` (`sha256:…` or bare 64-hex) pins an explicit digest
override instead, for holding OWUI outside the release cadence. The
override persists across future converges — including a plain `hal0
update` — until you drop it with `--clear-override`, which converges the
container back to the release pin. `--check` prints the status row only;
`--yes`/`-y` skips the confirmation prompt.
