A **slot** is one inference endpoint: a podman container, backed by the
`hal0-slot@<name>.service` systemd unit, serving a model on a loopback
port. The `hal0 slot` CLI is a thin client over the API — every command
hits the local daemon at `http://localhost:8080`, so the CLI and the
dashboard always agree.

<Aside type="note">
The CLI talks to a running hal0-api. If the daemon is down, commands exit
non-zero with an "API unreachable" message rather than acting on disk
directly.
</Aside>

The dashboard's slot edit drawer has its own page,
[Manage slots: the dashboard drawer](/docs/guides/manage-slots-dashboard/).

## List and inspect

```sh
hal0 slot list              # every configured slot: state, model, backend, port, kind
hal0 slot list --json
hal0 slot status <name>     # quick human-readable state/model/port check
hal0 slot show <name>       # full status + on-disk TOML as JSON
hal0 slot metrics <name>    # live throughput/latency for the slot
hal0 slot capacity          # aggregate memory/port headroom across all slots
```

![Slot list showing configured slots with state badges, model names, device, and port](/screenshots/slots-inference.png)
*The slot list view shows live state, assigned model, device, and port for every configured slot.*

`status` also prints a `WARN config drift: ...` line when the container's
*actual* running launch flags no longer match what hal0 would render
today — see Config drift after an update, below.

![Slot detail panel showing state, model, port, and on-disk TOML config as formatted JSON](/screenshots/slot-detail.png)
*The slot detail panel combines live status with the persisted TOML config in a single view.*

The dashboard's per-slot cards (Inference pane) carry a metric row —
**tok/s**, **ttft**, and **mem** (resident memory in GB, from the slot's
`mem_mb`) — plus a footer strip of chips: a **context** chip (`Nk ctx`,
shown on a full-size card whenever the slot's `ctx_effective` is a positive
number — MiniCards never show it; TTS, STT and image slots have no context
window and omit it), an **image status** chip when
hal0 could not read the container image store (label "image ?" — not a claim
the image is missing, see [Slot lifecycle reference](/docs/reference/slot-lifecycle)),
and a **crash-loop breaker** chip whenever a slot is backing off or parked
after repeated load failures (see the same reference page). Drag a card's grip
handle (or use the arrow keys on it) to reorder the grid — that ordering is a
per-browser preference stored locally, not slot config, so it needs no Save
step.

On an `llm` slot's full card, the model name is a picker: each row shows the
model's quantisation and modality tags, its size, other slots bound to it, and a
GTT fit chip (`fits` / `tight` / `won't fit`, from one
`POST /api/models/feasibility` fired the first time the menu opens — advisory
only). Picking a model swaps it immediately. The `[ device | PROFILE ]` pill is a
profile picker filtered to the slot's type: a pick writes nothing until you
confirm, then applies `PUT /api/slots/{name}/config` followed by a background
`POST /api/slots/{name}/restart`. Its last row, "✎ Edit slot…", opens the full
editor and is the only way to clear a profile.

<Aside type="note">
`primary` and `chat` are retired slot names — neither is accepted as
an alias anymore. The canonical LLM slots are `agent` (the capable
default/fallback anchor) and `utility` (the cheap helper seeded for
memory extraction); a slot is reachable only by its own name.
</Aside>

## Create a slot

```sh
hal0 slot create embed \
  --type embedding \
  --model nomic-embed-text-v1.5-q8_0 \
  --hardware rocm
```

<Steps>

1. **`name`** (positional) — the slot id, e.g. `agent`, `embed`, `stt`.

2. **`--type` / `-t`** — how the dispatcher routes requests. One of
   `llm` (default), `embedding`, `reranking`, `transcription`, `tts`,
   `image`.

3. **`--model` / `-m`** (required) — the initial model ref to assign.

4. **`--hardware`** — the compute backend: `rocm`, `vulkan`, or `cpu`.
   When omitted it reads the cached hardware probe: `rocm` on an AMD GPU with
   ROCm compute reachable (and if no probe has run yet), `vulkan` on an AMD or
   Intel GPU without it, `cpu` if neither lane is available. `rocm` is the
   lane hal0 seeds on AMD and requires the `/dev/kfd` compute node. `vulkan`
   needs only a render node, which makes it the lane for a box where
   `/dev/kfd` was never forwarded; an LLM slot on it must also resolve a
   Vulkan-validated runner image, or slot load refuses it by name. Either way
   the refusal is loud and immediate rather than a slot that serves nonsense.
   Which lane is faster depends on the model; `hal0 bench` measures both on
   your box. This sets the slot's
   `device` field directly (`vulkan → gpu-vulkan`, `rocm → gpu-rocm`,
   `cpu → cpu`) — as of v1.0, **the slot owns its hardware grid**
   (`device`, `n_gpu_layers`, `threads`, `binary`, `image_pin`), not the
   profile it references. The profile supplies the tune: flags, context
   window, thinking default, vision and MTP.

5. **`--port` / `-p`** — the slot's port. Omit it and hal0 auto-assigns
   the next free port.

6. **`--profile`** — the profile: the slot's whole tune (flags, context
   window, thinking, vision, MTP). Omit it and hal0 infers the profile the
   slot's `--type` implies: `embedding` → `embedding` (`--embedding`),
   `reranking` → `reranking` (`--reranking`), `tts`/`transcription` → the
   engine hal0 ships for the chosen device (Kokoro on CPU, Qwen3-TTS on ROCm,
   Moonshine for CPU speech-to-text), `image` → `comfyui`. Nothing is inferred
   where hal0 has no engine for that pairing — a `tts` slot on a Vulkan
   device, for instance, keeps the CPU Kokoro runtime rather than being
   pinned to the ROCm-only Qwen3 image. That inference is what makes a
   capability slot actually serve its endpoint — an `embedding` slot with no
   `--embedding` flag loads to `ready` and returns HTTP 501 from
   `/v1/embeddings`. An `llm` slot is the one type that infers nothing: no
   mode flag is at stake, so with no `--profile` it runs the `chat` seed.
   Change a slot's profile later with `hal0 slot edit <name> --profile
   <profile>` or the slot drawer.

   There is no `--ctx-size`: the context window is the profile's `ctx_size`.
   For a window other than the seed's, create a profile first and name it
   here:

   ```sh
   hal0 profile create chat-16k --from chat --ctx-size 16384
   hal0 slot create scratch --model qwen3.5-9b --profile chat-16k
   ```

   A profile can also pin a **runtime** — one of hal0's runner-registry
   entries (Standard, NVIDIA CUDA,
   CPU, …) — instead of just flags.
   Naming such a profile at create time sets the new slot's `binary` (and, for
   a single-backend runtime, its `device`) to match, so the profile decides
   the runtime and not only the tune. A ROCm-only runtime profile on a host
   with no `/dev/kfd` is rejected at create time with a plain-language error
   rather than writing a slot that can never spawn.

</Steps>

Creating a slot writes its config and systemd drop-in but does **not**
start it — follow with `hal0 slot load`.

<Aside type="note" title="Pinning a GPU on multi-GPU hosts">
Multi-GPU hosts can pin a slot to one card via the `gpu_index` key in the
slot's TOML — there's no `--gpu-index` CLI flag and no dashboard field for
it, so set it by editing the slot's TOML directly (`gpu_index = 1`), then
`hal0 slot restart <name>`. The file is `/etc/hal0/slots/<name>.toml` on a
box that's still name-keyed, or `/etc/hal0/slots/<id>.toml` (the slot's
numeric id) after running `migrate-id-keying` — `ls /etc/hal0/slots/` shows
which stem this box uses.
</Aside>

<Aside type="caution">
`--provider` is the runtime label (e.g. `llama-server`/`flm`/`kokoro`) — it
does **not** mean compute hardware. Use `--hardware` for the device.
</Aside>

## Load, restart, unload, rename

<Tabs>
<TabItem label="Load">

```sh
hal0 slot load agent
# or assign a model at load time:
hal0 slot load agent --model qwen3.8-27b
```

Loads the slot's container and waits for it to go healthy. A bad
`--model` is rejected against the registry up front, so you don't wait
out the health timeout on a typo.

</TabItem>
<TabItem label="Restart">

```sh
hal0 slot restart agent
```

Unloads then reloads — used after editing config that the running
container baked in (ports, hardware grid, or the profile's flags and context size).

</TabItem>
<TabItem label="Unload">

```sh
hal0 slot unload agent
```

Stops the container gracefully and returns the slot to `offline`.

</TabItem>
<TabItem label="Rename">

```sh
hal0 slot rename agent primary-llm
```

The slot's internal id is stable across a rename — only the label
changes, so references from stacks and activity history stay intact.

<Aside type="caution">
Rename requires the slot to be **offline** first (`hal0 slot unload <name>`) —
the on-disk TOML and the systemd unit are still name-keyed, so renaming a
running slot would orphan its unit. The API rejects a rename attempted while
the slot is anything but offline. In the dashboard's slot drawer the Rename
field is disabled with this same reason while the slot is up.
</Aside>

</TabItem>
</Tabs>

### While a lifecycle command is waiting

`load`, `unload`, `restart`, and `swap` all block until the slot converges —
a cold load can legitimately take minutes (health poll, then the
output-sanity check). On a terminal, the CLI now shows an elapsed counter and
the slot's live state, refreshed every couple of seconds:

```sh
$ hal0 slot load agent
⠋ Loading agent… 42s elapsed — state=starting
```

With stdout redirected, it prints one line up front instead and stays quiet
until the result. With `--json` it prints nothing but the final JSON:

```sh
$ hal0 slot load agent > load.log
Loading agent (up to 2139s)…
```

If the wait itself times out — every `systemctl`/podman call the server
makes on your behalf is now bounded, so this means a specific wedged
command, not an indefinite hang — the CLI prints the seam's own error and
where to look next:

```
Error: POST http://127.0.0.1:8080/api/slots/agent/load → HTTP 504: `<seam command>` did not return within 180s
still converging? check `hal0 slot logs agent` or `journalctl -u hal0-slot@agent`.
```

The slot itself lands in `error` with that same message (`hal0 slot status
agent`, or `/api/slots/agent`), carrying the typed code `slot.seam_timeout` —
a load in this state is safe to retry once the stuck command clears (a
wedged `systemctl`/podman invocation on the host, or a genuinely oversized
model that needs a wider `[server]` timeout upstream).

## Swap the model

```sh
hal0 slot swap agent --model qwen3.5-9b
```

A swap does two things by default, as two separate calls:

1. **Hot-swap** the running slot to the new model (`POST
   /api/slots/{name}/swap`).
2. **Persist** the new default to the slot's on-disk config so it
   survives a restart (`PUT /api/install/slots/{name}/model`).

Pass `--no-persist` to try a model briefly without changing the default —
it reverts on the slot's next restart:

```sh
hal0 slot swap agent --model phi3-mini --no-persist
```

If the hot-swap succeeds but the persist step fails, the runtime swap is
left in place and the failure is surfaced so you can retry.

## No `enabled` flag — a default model is the activation signal

A slot has no separate `enabled` boolean. A non-empty `[model].default`
on the slot **is** what makes it active; clearing the default (or never
setting one) is how you take a slot out of rotation without deleting it.

## Edit slot config

```sh
hal0 slot edit agent --profile agent-32k
hal0 slot edit embed --hardware rocm
hal0 slot edit rerank --profile reranking
```

Pass any subset of `--model`, `--port`, `--provider`, `--hardware`,
`--profile`. At least one is required. Changes the container baked in (port,
hardware grid, profile) take effect on the next `restart`. A slot has no
flags or context size of its own to edit; to change them, edit the profile it
runs (`hal0 profile edit <name> --ctx-size N`) or point the slot at another
one. Editing a profile affects every slot that runs it, and each picks up
changed flags, context window, vision or MTP at its next restart. A changed
profile `runner` does not reach a slot that way: re-apply the profile to each
slot with `hal0 slot edit <slot> --profile <name>`, then restart it.

## Switching a slot to the Vulkan lane

On AMD, an LLM slot runs one of two GPU lanes and always names it explicitly —
`gpu-rocm` or `gpu-vulkan`. Moving between them is a normal, supported
operation:

```sh
hal0 slot edit agent --hardware vulkan     # gpu-rocm -> gpu-vulkan
hal0 slot restart agent

hal0 slot edit agent --hardware rocm       # and back
```

In the dashboard, open the slot's drawer and change **Device** — same effect,
same checks.

### Why you might

The Vulkan lane needs only a render node, so it is the only GPU lane available
on a box where `/dev/kfd` was never forwarded — an unprivileged LXC, typically.
Measure both lanes on your own box with `hal0 bench` before switching for
speed.

hal0 still *seeds* `gpu-rocm` where the box can run it. That is a maturity
preference, not a performance one: the ROCm lane carries hal0's release
validation history, and MTP / speculative-decode profiles are tuned against
it. A slot leaning on speculative decode may well do better staying put. The
seeded default is revisited at GA against a broader matrix.

### What has to pass before it serves

Two gates, and both are the point:

1. **Preflight.** The target lane's devices must be present — `/dev/kfd` for
   ROCm, `/dev/dri/renderD*` for Vulkan — and, for Vulkan, the slot's runner
   image must be one whose digest has passed the hardware gate's Vulkan lane
   (`"vulkan"` in its `lanes_gated` pin in `manifest.json`). An ungated Vulkan
   backend can emit invalid tokens for every model while every health surface
   reads green, so such an image is refused by name with the reason. If you
   see that refusal, clear the slot's `image_pin` so it runs the pinned
   Standard image, or move the slot to ROCm; don't work around it.
2. **Output sanity.** After preflight, the slot must answer a fixed prompt
   correctly before it is marked ready. A lane that emits nonsense fails in
   about a second instead of serving it for hours.

<Aside type="caution" title="`HAL0_ALLOW_VULKAN_FALLBACK`">
This environment variable downgrades the preflight refusals above to a warning.
It exists so a broken box can be *inspected*, not run: on an unvalidated runner
image it will let a slot start on a Vulkan backend that can emit invalid tokens
for every model. There is no supported configuration in which it is the right
answer.
</Aside>


## Editing multiple slots at once: Stacks

The dashboard's **Stacks** view (there's no `hal0 stack` CLI command — it's
dashboard/API only, `GET/POST/PUT/DELETE /api/stacks[/{slug}]`) lets you
edit several slots as one named, portable bundle instead of one at a
time. **Apply** (`POST /api/stacks/{slug}/apply`) creates any slot named
in the stack that doesn't exist yet, then *converges* the live slot set —
applying a stack is a declarative replace of what's currently running,
not a merge. A stack row goes through the same slot-write checks as a direct
`hal0 slot edit`: a row the checks refuse fails that one slot's convergence
without aborting the rest of the apply.

See [Stacks](/docs/concepts/stacks) for the full concept — row fields,
plan/converge phases, drift states, export/import/snapshot.

## Config drift after an update

A slot's systemd unit bakes its launch flags in **at load time** —
updating hal0 changes the code that *would* render that unit, not the
unit file itself. `hal0 update` re-renders every existing slot unit
afterward, but never bounces a container for an argv change — a slot that
was serving when the update landed keeps running its old argv until its
*next* load, swap, or restart. The one exception is a runner-image change:
`hal0 update` (and `hal0-api` at start) restarts idle slots whose running
image differs from the one a fresh render would pick, and skips slots with a
request in flight — see [Manage runner images](/docs/guides/manage-runner-images-lifecycle/#what-happens-to-a-running-slot-when-its-image-changes).

`hal0 slot status <name>` is how you check whether a running slot is in
that stale window — it prints `WARN config drift: ...` when the
container's live argv no longer matches what hal0 would render today. If
you see it, `hal0 slot restart <name>` (or a dashboard restart) clears it.

## Delete a slot

```sh
hal0 slot delete scratch
```

Stops the unit and removes the config. You'll be asked to confirm; pass
`--force` / `-f` to skip the prompt — for a seeded slot, `--force` also
bypasses the delete protection described below.

<Aside type="note">
Seeded slots (`flm`, `tts`, `rerank`, `utility`, `img`, `agent`, `brain`,
`qwen3tts`, `coder`, `embed`) are protected: deleting one without
`--force` is rejected. `hal0 slot delete <name> --force` (or
`DELETE /api/slots/{name}?force=true`) deletes a seeded slot anyway — but
an install or update reconcile may re-seed it later. Clearing the slot's
default model is the way to take it out of rotation without deleting it.
</Aside>

## Stream logs

```sh
hal0 slot logs agent               # last 200 lines
hal0 slot logs agent --follow      # -f, live SSE tail
hal0 slot logs agent --lines 1000  # -n, more history
```

Logs come from the slot's `hal0-slot@<name>.service` journal.

## Migration helpers

Slot runtimes and image pins are converted onto the current runner system by
`hal0 runner-images migrate`, which `hal0 update` runs for you before it validates
config; see [Manage runner images → Upgrading an older
install](/docs/guides/manage-runner-images-lifecycle/#upgrading-an-older-install).

Slot tuning, profiles and stacks are converted onto the profile-centric model
by `hal0 profile migrate`, which `hal0 update` also runs for you; see [Update
and roll back](/docs/guides/update-and-rollback#profile-centric-config-conversion).
Run `hal0 profile migrate` to preview the plan, and
`sudo -u hal0 hal0 profile migrate --apply` to convert by hand.

One manual slot migration remains: `hal0 slot migrate-id-keying`, which
flips name-keyed slot files, state directories and units to id-keyed ones. It
is **operator-run only** — nothing in `hal0 update` runs it. It previews by
default; `--apply` writes, after writing a tar backup of `/etc/hal0/slots`,
`/var/lib/hal0/slots` and `/var/lib/hal0/hal0.db` to `/var/lib/hal0/backups/`.
It refuses to run while `hal0-api` or any `hal0-slot@*` unit is active, since
renaming slot artefacts under a live runtime risks a split-brain config; pass
`--stop-services` to stop those units first. They are started again if the run
refuses or fails, and stay stopped after a successful run, so restart hal0
yourself afterwards (after `systemctl daemon-reload` where the command says
so).
