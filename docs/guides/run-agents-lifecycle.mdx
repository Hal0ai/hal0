These are the operational commands for the bundled agents — what is installed,
what it is doing, how to rebuild it, how to take it away and how to move pi
to a new pin. Installing Hermes for the first time, its personas and the
approvals flow live in [Run agents](/docs/guides/run-agents/).

## Manage the lifecycle

<Tabs>
<TabItem label="List / status">

```sh
hal0 agent list                 # installed bundled agents
hal0 agent list --json
hal0 agent status hermes        # provisioning checkpoint, per phase
hal0 agent peers                # every published agent identity card
```

`list` only shows agents installed on this host; `peers` searches the
memory store for every identity card any host has published (needs the
memory API reachable).

</TabItem>
<TabItem label="Logs">

```sh
hal0 agent log hermes
hal0 agent log hermes --phase provision
```

Per-phase provisioning logs — these are flat files under the agent's
state directory, not a systemd journal. See
[Logs and activity](/docs/guides/logs-and-activity) for how this differs
from a slot's runtime logs.

</TabItem>
<TabItem label="Re-run / update">

```sh
hal0 agent reprovision hermes          # idempotent re-converge
hal0 agent reprovision hermes --repair # force every phase, building a fresh release
hal0 update component hermes                       # build and activate a fresh release of the pin
hal0 update component hermes --target <sha>        # build a vetted commit other than the pin; stays until cleared
hal0 update component hermes --clear-override      # return to the pin
```

`reprovision` is a stable wrapper over the same state machine `install`
runs. Plain `reprovision` re-converges the agent, including its managed
virtualenv, so it is the command to reach for when the agent is running
but its MCP tools are missing. `--repair` forces every phase instead of
converging: it builds a fresh Hermes release, re-writes the persona seeds
and re-renders the config.

Every build lands in its own release directory under `/var/lib/hal0/hermes`
and is checked before anything switches. Activating it stops the agent and
the gateway (only the ones that were running), moves the `current` link,
runs `hermes config migrate` from the new release, starts the units again
and re-checks them. If that re-check fails, hal0 switches back to the
previous release and restores `config.yaml` by itself. A failed activation is
reported as `activation_failed`, and a flip-back that fails too says so in the
same message. The plugin trees hal0 mirrors into `$HERMES_HOME/plugins/` are re-synced on `hal0 update` and on a repair whose build fails, so a stale plugin manifest does not survive an update.

`hal0 update component hermes --target` takes only a full commit sha listed in
hal0's vetted refs. A version string such as `0.15.3` or an `==X.Y.Z` spec is
refused. The override persists across `hal0 update` until you run
`hal0 update component hermes --clear-override`, and `hal0 update status` shows
the row as overridden while it is set. If a later hal0 release no longer lists
that commit as vetted, `hal0 update` refuses to keep or rebuild it and names
`--clear-override`. The command also refuses a vetted commit older than the live release, as long as the live release is itself one of hal0's vetted refs: once v0.22.4 is live, `--target d923a5eb487a17c0a68801bba9ef0f56c81040a8` (v0.22.2) fails as a downgrade, because v0.22.3 and later write gateway runtime state into Hermes's `state.db` that v0.22.2 cannot run over. The automatic flip-back after a failed activation is not affected.

To watch each phase as it runs, or to re-run provisioning without the
network, use the flags below. With `--offline` it never
builds: if a build is needed, the install step fails and names the step
that needs the network, and a running host keeps its live release. It is one linear pass: there is no
preview mode and no way to skip a phase, so it has no `--dry-run` or
`--skip-phase`.

```sh
hal0 agent reprovision hermes --offline
hal0 agent reprovision hermes --repair --verbose
```

To restart the running Hermes process without re-provisioning anything:

```sh
sudo systemctl restart hal0-agent@hermes
curl -X POST http://localhost:8080/api/agents/hermes/restart
```

Restart the Hermes gateway with `sudo systemctl restart hermes-gateway`, not
with `hermes gateway restart` or `hermes gateway start`. Upstream's commands
regenerate the unit when it differs from what they would write, which turns
hal0's stable `/var/lib/hal0/hermes/current/` paths back into the paths of
one release under `/var/lib/hal0/hermes/releases/<id>/`. The gateway then
stays on that release when hal0 builds a newer one, and `hermes gateway status`
reports the unit as outdated. `sudo hal0 agent install hermes` regenerates and
normalises the unit again.

The Hermes card in the dashboard has buttons for restart, upgrade and repair:
**Restart agent** and **Restart gateway** on its Controls tab, and **Upgrade**
or **Repair** on its Lifecycle tab. See [The Agents view](/docs/guides/agents-view).

</TabItem>
<TabItem label="Uninstall">

```sh
hal0 agent uninstall hermes
hal0 agent uninstall hermes --keep-memory
```

Default uninstall tears down the agent's private memory namespace too;
`--keep-memory` preserves it so a re-install reuses the identity card.

Uninstalling Hermes also runs `loginctl disable-linger hal0`, which undoes the
linger the Hermes gateway turned on. Run the uninstall as root for that step;
otherwise it prints the command to run.

The Hermes card also has an **Uninstall** button on its Lifecycle tab, behind a
type-to-confirm dialog. It has no `--keep-memory` option; see
[The Agents view](/docs/guides/agents-view#upgrade-repair-and-uninstall).

</TabItem>
</Tabs>

## Update pi

If you installed the pi coding agent with `sudo hal0 agent install pi`, re-pin it without an uninstall:

```sh
sudo hal0 update component pi
```

Run it as root, the same way you installed pi. It reruns the pinned installer, redeploys hal0's two extensions and refreshes the hal0-memory MCP entry, and leaves the extensions you added under `~/.pi/agent/extensions` and your default provider, model and theme in `settings.json` alone. It refuses, and changes nothing, when pi is not installed, when pi's profile is in a different home than the one it runs in (run it as the user who installed pi), and when `settings.json` or `mcp.json` is not a JSON object. `hal0 update` never re-pins pi; it only reports it.

A fresh `hal0 agent install pi` from a git checkout seeds a name-keyed `banks` alias in `~/.hindsight/coding-agent.json` (`coding-agent::hal0` to `coding-agent::hal0-mono`); the update adds it to an existing file and leaves every other key alone. Other Hindsight tools read that file.

## Running `hermes` as root

Upstream `hermes` resolves its state from `~/.hermes`, so a bare root
invocation would read `/root/.hermes` — an empty tree the agent never
uses — and commands like `hermes mcp list` would falsely report
"No MCP servers configured" on a healthy install. hal0's `hermes`
wrapper prevents that: run as root, it re-executes as the `hal0`
service user (via the run-as-hal0 guard), so you see the same config
the running agent uses. If the guard is installed but cannot drop
privileges — no `runuser`, `setpriv` or `sudo` on the box — the wrapper
refuses to run as root and exits. On a box where the guard is not installed
at all (a dev or partial install), or where the `hal0` service user does not
exist, the wrapper points `HOME` at the service home instead and prints which
`~/.hermes` tree it resolved on stderr. `HAL0_ALLOW_ROOT=1` opts out
of the guard for deliberate root debugging — the wrapper then leaves root's
environment alone but still names the tree it is reading. The
euid-aware fix inside the hermes CLI itself is an upstream
(NousResearch/hermes-agent) matter; the wrapper is hal0's seam.
