hal0 generates images through **ComfyUI**, a node-graph Stable-Diffusion
runtime, running as one containerized generation engine tuned for the AMD
iGPU. Image generation is one of the four capability slots — `embed`,
`voice`, `img`, `vision` — alongside chat.

Because there is exactly one iGPU, image generation is **mutually
exclusive** with the LLM stack: only one of them can hold GPU memory at a
time. hal0 models this as a switchover driven by the GPU arbiter — the
ComfyUI container stays resident, only its model memory is freed and
reloaded.

<Aside type="caution">
Switching the iGPU to generation **stops the LLM stack** (chat bots and
memory extraction go dark) for as long as generation holds the GPU: while a
render runs and for about 10 seconds after the last one, or until you unpin a
pinned image mode. See [How long image mode lasts](#how-long-image-mode-lasts).
</Aside>

## Enable the img capability

Install an image model first. On a box that can run ComfyUI the installer
offers a starter model and picks the one that suits the box's memory (see
[Starter image model](/docs/getting-started/install/#starter-image-model));
skip it and install later. `hal0 comfyui models list` shows the catalog, what
each model still has to download, and the pick recommended for this box:

```sh
hal0 comfyui models list
hal0 comfyui models install sdxl-lightning
```

`install` follows each download until it finishes, one model at a time when you
name several. It treats an already-installed model as done and exits 1 if an
install fails, is cancelled or is refused; the same install is
`POST /api/comfyui/models/{model_id}/install`. An install is refused up front
(409 `comfyui.models_dir_not_writable`) when a directory it must write into is
not writable by the hal0 user, so a permissions problem shows before the
download starts, not after it; the same 409 is returned when the models tree
cannot be read by the hal0 user. `list` marks the pick
recommended for this box with `*` and shows the state of each model (`none`,
`partial`, `complete`, or `installing`). `hal0 comfyui models remove <id>`
deletes a model's weights and workflow (a file another installed model uses
stays and is listed with the models that hold it, unless you pass
`--include-shared`, which deletes it and names the models it uninstalls, workflows
included; a file
that cannot be deleted stops the removal with 409 `comfyui.remove_failed`, which
lists what had already gone), and `hal0 comfyui files` lists the weight files on
disk, grouped by kind. A file no catalog model loads, such as a checkpoint you
copied in by hand, is deleted from the Models view's **Image / ComfyUI** tab or
with `DELETE /api/comfyui/files/{subdir}/{relpath}` (MCP `comfyui_file_delete`);
the call refuses a file a catalog model loads (409 `comfyui.file_catalog_owned`),
a symlink, a hidden path part and any file that is not a weight file.

hal0 writes a model's ComfyUI workflow when its install finishes. A model whose
weights you copied into the models folder by hand reads as installed, so hal0
writes its workflow when the API starts. A removal is remembered: a model you
removed whose files stay on disk (another model still uses them) does not get
its workflow back at the next start, and installing it again restores it. After
an install or a removal hal0 re-renders Open WebUI's image settings, so the
image button follows the models you have. A running Open WebUI restarts to pick
them up; one you stopped or skipped stays down.

On a box with a ROCm lane, the first image model you install that the API can
render becomes the `img` selection by itself when nothing is selected, and
selecting it starts the `img` slot. Install a model first with
`hal0 comfyui models install <id>` (`hal0 comfyui models list` shows the ids):
picking one that is not downloaded yet is refused with 409
`capability.model_not_downloaded`. To pick or change the model, use the
**Model** row of AI Capabilities → Image in the dashboard (it lists the catalog
models the API can render, marking those not downloaded yet, and your own
`ckpt/<path>` checkpoints), or point the `img` capability at one you installed:

```sh
hal0 capabilities set img img --model sdxl-lightning
```

This is the same pattern as every other capability — set the child
(`img`) under its parent (`img`), pointing at an installed image model.
Every installed catalog model the API can render works through
`/v1/images/generations`: `sdxl-turbo`, `sd-1.5-pruned-emaonly`,
`sdxl-lightning`, `qwen-image-lightning` and `qwen-image`. So do your own SDXL
and SD 1.5 checkpoints, addressed as `ckpt/<path>`: put the file under the
ComfyUI `checkpoints/` folder and `GET /api/comfyui/files` lists its id as
`api_id`. Video, edit and upscale models stay in ComfyUI's editor.

## Read the generation-engine status

```sh
curl http://localhost:8080/api/comfyui/status
```

Key fields:

- `mode` — `generation` (ComfyUI owns the iGPU) or `inference` (the LLM
  stack owns it). The GPU arbiter is the source of truth.
- `engine` — `running`, `generating` (a render is in flight), `starting`
  (container up, port not bound yet), or `stopped`.
- `reachable` — whether ComfyUI's HTTP API answers.
- `container` — the `img` slot container's state (`running` / `exited` /
  `absent`).
- `queue` — `{running, pending}` job counts.
- `switchover` — the in-flight switch tracker (`active`, `target`,
  `error`).
- `arbiter` — the GPU arbiter's own block: `mode` (`img` or `llm`),
  `pinned`, `saved_llm_slots` (the slots it will reload), `switching` (true
  while it holds its switch lock), `image_jobs` (the `/v1/images/generations`
  requests in flight) and `phase`, what the GPU is doing right now:
  `draining`, `unloading`, `starting_engine` or `reloading` during a switch or
  restore, and `handoff`, `rendering` or `grace` in image mode, else `null`.
  The whole block is `null` when the arbiter cannot report.
- `progress` — the step of the render hal0 submitted that ComfyUI is running:
  `model`, `step` out of `total`, `node` and `elapsed_s`; `null` when none is
  live. A render queued from ComfyUI's editor has no entry; read `queue` for it.
- `gate`, `gate_refusal` — whether the engine runs the current GPU gate, and
  the latest prompt the gate refused (see
  [ComfyUI's editor and the GPU gate](#comfyuis-editor-and-the-gpu-gate)).

The status carries no memory figures. Read the `memory` block of
`GET /api/stats/hardware` ([Memory budget API
reference](/docs/reference/api/memory-budget/)) for the GPU pool and RAM.

Every probe degrades to a safe default: a dead engine surfaces as
`stopped`, never a 500.

## Switch the iGPU between modes

The `img` slot runs as the `hal0-slot@img.service` systemd unit. To hand
the iGPU to ComfyUI (drains and unloads the LLM GPU slots, then ensures
the resident container is up):

```sh
curl -X POST http://localhost:8080/api/comfyui/switchover \
  -H 'Content-Type: application/json' \
  -d '{"mode": "generation"}'
```

To hand it back to inference:

```sh
curl -X POST http://localhost:8080/api/comfyui/switchover \
  -H 'Content-Type: application/json' \
  -d '{"mode": "inference"}'
```

Body fields:

| Field   | Type   | Notes |
|---------|--------|-------|
| `mode`  | string | `generation` or `inference` (required). |
| `force` | bool   | Switching to `inference` drops any running/pending render. Without `force`, a busy queue is refused with **409**. |
| `pin`   | bool   | `generation` only — hold image mode until you unpin it (`POST /api/comfyui/pin` with `{"pinned": false}`) or switch to `inference` with `force`. Without a pin, image mode ends about 10 seconds after the last render, as it does for every image request. |

Responses: **202** (`switching`, poll `/status`), **200** (`noop`,
already in the target mode), **409** (switch already in flight, or a busy
queue without `force`), **503**
(`comfyui.arbiter_unavailable` — the GPU arbiter isn't wired on this
host; requires a configured `img` slot). Pin or unpin while image mode is
on (pinning while the GPU serves LLMs answers **409**
`comfyui.not_image_mode`; pass `pin` on the switchover instead):

```sh
curl -X POST http://localhost:8080/api/comfyui/pin \
  -H 'Content-Type: application/json' \
  -d '{"pinned": true}'
```

## How long image mode lasts

Image mode lasts only while image work runs: a `/v1/images/generations`
request, from before the switch until its render returns, or a render in
ComfyUI's queue from its editor. About 10 seconds after the last render, hal0
frees ComfyUI's models (`POST /free`) and reloads the LLM slots it had
unloaded. This holds however image mode began: a switch to `generation`
without `pin`, such as the dashboard's Start button, also ends about 10
seconds after the switch when nothing renders. To keep image mode, pin it.

- **A chat request ends the wait.** A request for a GPU LLM slot that arrives
  while image mode is on waits for the render to finish and for the saved
  slots to reload, up to 120 seconds in all, and is then served. It gets
  `503 gpu.image_mode` (with `Retry-After: 15`) only when image mode is
  pinned, when ComfyUI's queue cannot be read, or when the 120 seconds run
  out. Requests for NPU and CPU slots are never affected.
- **hal0 never restores under a render.** While a render runs or waits in
  ComfyUI's queue, the reload waits. Switching to `inference` by hand while
  one runs needs `force`, which drops it.
- **A hand-off follows each request for image mode.** For about 3 seconds
  (a render sent to `/v1` on a GPU already in image mode starts one too)
  hal0 does not restore, so a prompt sent from ComfyUI's editor can reach
  ComfyUI's queue, where hal0 sees it.
- **A pin lasts until you end it.** `POST /api/comfyui/pin` with
  `{"pinned": false}` unpins it, and a switch to `inference` with `force`
  ends image mode and clears the pin. Pinning needs image mode: pass `pin` on
  the switchover that enters it, because `{"pinned": true}` while the GPU
  serves LLMs answers 409 `comfyui.not_image_mode`.
- **A ComfyUI queue that never drains holds image mode.** hal0 restores LLM
  mode only while ComfyUI's queue shows nothing running or pending, so a
  wedged job keeps the GPU in image mode until you switch to `inference` with
  `force`.

### ComfyUI's editor and the GPU gate

Prompts from ComfyUI's own editor do not pass through hal0, so ComfyUI loads
a custom node, `hal0_gpu_gate`, that asks hal0 for image mode before each
prompt is queued. hal0's own `/v1` renders pass through it too. The node
reaches `hal0-api` on the port and address it binds (`HAL0_PORT` and
`HAL0_BIND_HOST` in `/etc/hal0/api.env`), which hal0 writes into the `img`
slot's unit. The prompt waits while hal0 switches the GPU, up to 180 seconds
(the switch itself waits for running chat requests to finish). When the GPU
is already in image mode, the node first tells hal0 the prompt is coming, and
hal0 holds image mode for it for about 3 seconds, until ComfyUI's queue shows
it.

The node refuses the prompt and queues nothing, answering it with a 503 that
carries the reason, when:

- hal0 rejects the switch request;
- hal0 stops answering while it switches the GPU;
- hal0 still holds the GPU for the LLM slots after three switch requests;
- the switch has not finished after 180 seconds;
- hal0 is unreachable, or does not say which mode holds the GPU, for 5
  seconds after the prompt is submitted;
- hal0 answers 401 or 403, at once: the gate's credential is missing or no
  longer current (see below).

Queue the prompt again once the reason is gone. The node also tells hal0 why it
refused, and `GET /api/comfyui/status` reports the latest as `gate_refusal`
(`at` and `reason`). Its `gate.state` says whether the engine runs the current
gate: `current`; `stale`, an older gate, so run `hal0 slot restart img`;
`unknown`, because the gate has not called since `hal0-api` started; or
`no_credential`, because hal0 requires the gate to authenticate and it has no
token it can send.

To let prompts through while `hal0-api` is down or refuses the gate's
credential, as the gate did in v1.6.5, set `HAL0_COMFYUI_GATE_FAIL_OPEN=1` in
`/etc/hal0/api.env`, restart `hal0-api`, then run `hal0 slot restart img`.
hal0 writes the setting into the slot's unit when it loads the slot, so a bare
`systemctl restart` of the unit does not pick it up. The setting covers only
those two cases: a prompt that hal0 answered and refused stays refused. A
prompt it lets through is unguarded: with `hal0-api` down the GPU most likely
still holds the LLM slots, so it renders next to them.

With auth enforcement on (`hal0 auth require on` or `HAL0_REQUIRE_AUTH=1`),
or on a box whose `HAL0_BIND_HOST` is a specific address and that has an
admin key, the gate authenticates with a token of its own, never the admin
key. hal0 mints it when the `img` slot first starts and mounts it read-only
into the container; it opens the gate's four requests and nothing else (see
[ComfyUI's GPU gate credential](/docs/operate/auth#comfyuis-gpu-gate-credential)).
An `img` container started before the update has no token, so on such a box it
refuses every image prompt (the editor's, hal0's own `/v1` renders, Open
WebUI's and the omni loop's) until you run `hal0 slot restart img`.

**After updating hal0, run `hal0 slot restart img` once.** A running `img`
container keeps the gate it started with, and `hal0 update` does not restart
slots. hal0 keeps that older gate waiting while it switches or restores the
GPU, but the older gate lets a prompt through when `hal0-api` is unreachable or
after its own 120 seconds, and such a prompt can render next to the LLM slots.
Restarting the slot loads the gate described here. Until you do, the older
gate does not report why it refused a prompt, and `gate.state` on
`/api/comfyui/status` reads `stale` once it has called, with one exception: on
a box that requires authentication, hal0 mints the gate's token only when the
`img` slot loads, so a box updated from v1.6.5 reads `no_credential`, which
ranks above `stale`, until you restart the slot.

## The `[image]` slot config

The `img` slot's `[image]` table carries `default_size`
(`""` by default, meaning the model's native size, such as `1024x1024` for SDXL
and `512x512` for SD 1.5) and `default_steps` (`0` means the workflow's own
step count). A request's own `size`, or `steps` in `extra_body`, wins. Set
these from the dashboard's Settings → Image-gen panel or edit the slot's TOML
directly — see [Edit configuration](/docs/guides/configure). Image mode has no
setting: it ends when generation stops (see
[How long image mode lasts](#how-long-image-mode-lasts)).

Once ComfyUI is up, hal0 leaves its container running: idle-timeout,
memory-pressure and pre-load eviction never unload the `img` slot, whatever
its `idle_timeout_s` says, so a ComfyUI editor session is never cut off. Idle,
ComfyUI holds next to no GPU memory, and switching back to inference frees its
models. `hal0 slot unload img` still stops it by hand.

### Which container image the `img` slot runs

The `img` slot resolves its image in this order: `image_pin` (top-level or
`[slot]`-nested, honored verbatim), then `[slots].default_images.comfyui` in
`hal0.toml` (the operator's choice of launch image for ComfyUI, set from the
Runner Images page — see
[Manage runner images](/docs/guides/manage-runner-images)), then the
`comfyui` runner's resolved image (`HAL0_RUNNER_IMAGE_COMFYUI`, then the
`manifest.json` pin for `comfyui`). A bare `image` string left in an older
`img` slot file is moved to `image_pin` by the profile-centric conversion that
`hal0 update` runs. Clear `image_pin` in `/etc/hal0/slots/img.toml` if you
want the resolved default.

## Generate an image

```sh
curl -X POST http://localhost:8080/v1/images/generations \
  -H 'Content-Type: application/json' \
  -d '{
    "model": "sdxl-lightning",
    "prompt": "a cat in a hat, studio lighting",
    "n": 1,
    "size": "1024x1024",
    "response_format": "url"
  }'
```

The route flips the GPU to image mode before dispatching, so a single
call also performs the switchover when needed. The request holds image mode
until its render returns. hal0 then hands the GPU back to the LLM slots about
10 seconds later, or as soon as a request for one of them arrives. A request
for a GPU LLM slot that arrives during the render waits for the render and the
reload (up to 120 seconds) instead of being refused. The route also starts the
`img` slot when image mode finds it down, for example after it crashed or was
unloaded by hand. `model` is an installed
catalog model or a `ckpt/<path>` checkpoint; leave it out to use the model
selected for `img`. Any other id returns **404** (`image.model_unknown`, with
the ids that work), a catalog model that is not installed **409**
(`image.model_not_installed`, naming the install call), and a video, edit or
upscale model **422** (`image.model_not_renderable`). A `size` that is not
a string gets **422** (`image.invalid_size`), and a render the box cannot hold
gets **422** (`image.wont_fit`; see [Will it fit?](#will-it-fit)). A hal0
extension `extra_body` accepts `seed`, `steps`, `cfg`, `negative_prompt` and
`hal0_skip_fit_check`. See
[OpenAI-compatible API reference](/docs/reference/api/openai-compat/) for the
resolution order and how `size` and `steps` default.

The response is the OpenAI image shape:

```json
{
  "created": 1716000000,
  "data": [
    { "url": "/api/images/cache/<uuid>.png" }
  ]
}
```

With `response_format: "b64_json"` each `data` entry carries a base64 PNG
instead of a `url`.

To cancel an in-flight or queued render:

```sh
curl -X POST http://localhost:8080/api/comfyui/render/cancel
```

## Will it fit?

Image models are large, and a render draws on two budgets that are different
resources: the GPU pool and this box's RAM. hal0 judges each catalog model
against both, with the same figures the memory screens show
([Memory budget API reference](/docs/reference/api/memory-budget/)), and says
so before it unloads anything.

`GET /api/comfyui/models` gives every model a `fit` at its native size, and
`GET /api/comfyui/models/{model_id}/fit?size=1536x1536` gives the verdict at
another size:

- `fits` — the model fits both budgets.
- `tight` — it fits, but the need is above 90% of what is free in one of them.
- `wont_fit` — the need is above what is free. `reason` says which budget:
  "needs ~47.9 GB of RAM to load, 45.8 GB free (48.0 GB container limit)".
- `null` — hal0 cannot tell, because the box has no GPU pool reading or its
  RAM cannot be read. Unknown is never `wont_fit`.

The two budgets are never added together. The GPU budget is the pool a render can use
once image mode has unloaded this box's GPU slots; the RAM budget is what is
free under this box's RAM limit, which inside a container is the container's
limit. That second budget is why a model can fail on a large GPU: Qwen-Image
Lightning needs about 48 GB of RAM to load, so a guest limited to 48 GB reads
`wont_fit` however large its GPU pool is.

`POST /v1/images/generations` checks the same verdict at the size it will
render and refuses a `wont_fit` render with **422** `image.wont_fit` before
any slot is unloaded: the LLM slots stay loaded and nothing about the GPU
changes. `error.details` carries the figures. If the box misreads its own
memory, skip the check for one request:

```json
{
  "model": "qwen-image-lightning",
  "prompt": "a cat in a hat",
  "extra_body": { "hal0_skip_fit_check": true }
}
```

A `fits` built on an estimated figure (`need.gpu_estimated`,
`need.ram_estimated`) can still run out of memory, which then fails the render
as it did before. The fields are in the
[Image readiness API reference](/docs/reference/api/image-readiness/).

## Quick-launch workflows

The Image-Gen tab ships a **workflow quick-launch strip** — curated chips
that deep-link straight into ComfyUI's own UI. Any workflow JSON dropped
into the bind-mounted workflows directory shows up as a "custom" entry:

```sh
curl http://localhost:8080/api/comfyui/workflows
curl -X POST http://localhost:8080/api/comfyui/workflows/my-workflow/launch
```
