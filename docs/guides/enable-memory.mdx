hal0's memory subsystem gives agents a persistent recall store —
**Hindsight** — plus an optional knowledge-graph extraction layer. As of
v1.0 it's toggled with the `hal0 memory` CLI rather than an environment
variable — the old `HAL0_MEMORY_ENABLED` flag is gone.

<Aside type="note">
A fresh install turns memory on for you and stands up the local Hindsight
daemon automatically. The steps below are for the cases the installer
doesn't cover: re-enabling memory after you turned it off, a manual
install, or tuning the engine/graph/reranker after the fact. Every
downstream caller — the MCP tools, the `/api/memory/*` routes, the agent
memory provider — degrades to a no-op or `503` when memory is off.
</Aside>

## Turn it on or off

```sh
hal0 memory status
hal0 memory enable
hal0 memory disable
```

Toggles `[memory].enabled` in `hal0.toml`; enabling requires a
`hal0-api` restart to actually construct the memory provider.
`hal0 memory status` also reports the retain pipeline's health once memory
is on — whether writes are landing, waiting on a chat model to be loaded, or
failing, plus the engine's own failed/pending/processing operation counts.

When enabled, hal0 builds the memory provider from your config. The
engine is **Hindsight**; if the Hindsight daemon is unreachable at
startup, hal0 logs a warning and degrades to an in-memory PgVector
fallback rather than failing startup. hal0-api keeps re-probing in the
background and swaps the durable engine back in on its own once Hindsight
answers — no restart needed — but any writes accepted while degraded are
gone; they were never on the durable side.

<Aside type="caution">
The PgVector fallback is **volatile** — every write is lost on restart.
It exists so the tools and dashboard keep answering (empty results
instead of a crash) while Hindsight is down, not as a durable substitute.
Check `GET /api/memory/engine` — `"engine": "hindsight"` and
`"reachable": true` means you're on the real store.
</Aside>

<Aside type="caution">
`[memory].engine` accepts `hindsight` (default), `pgvector`, or `mem0` at
config validation time, but `mem0` **is not implemented** — selecting it
just logs a warning and runs Hindsight anyway. The dashboard's engine
picker only offers `hindsight`/`pgvector` for this reason. The legacy
`cognee` engine is **retired as of v1.0.0** and fails config validation
outright. There is no automated migration path off a Cognee-era store —
Cognee has been dark since v0.4.
</Aside>

## Two banks: hal0:shared and hal0:private

A new install keeps all of hal0's memory in two Hindsight banks:
`hal0:shared` for every agent's durable memory and `hal0:private` for private
notes and raw session captures, where each agent's `agent:<id>` tag scopes it
to its own. `[memory] bank` and `[memory] private_bank` name them. A box
upgraded from before keeps the banks it has (`shared`, and `private__<agent>`
if it ran with `unified_bank = false`) until its memory is folded in. Which
layout a box is on is recorded in `/var/lib/hal0/state/memory-layout.json`;
see [Memory banks](/docs/concepts/memory-banks).

## The dashboard's Settings → Memory page

Everything below this section is also available from the dashboard —
`#settings/memory` — as three panels: **Engine**, **Memory graph
extraction**, and **Reranker**. Engine and reranker changes save through the
generic settings API; graph changes go through a dedicated endpoint (see
below) because it validates the extraction slot against the live slot set
and propagates the change to `hindsight-api` itself. Changing the engine
needs a `hal0-api` restart to take effect; graph and reranker changes apply
live.

## The graph-extraction gate

Storing recall items is one thing; running an LLM over them to extract a
knowledge graph is heavier and separately gated — **off by default** even
on a fresh install.

Hindsight builds its graph natively from whatever model you point it
at. By default that is a local `llm` slot, `[memory.graph].extraction_slot`
in `hal0.toml` (default `"utility"`). You can instead run the engine on an
upstream model — anything your configured upstreams advertise, such as an
OpenRouter or MiniMax id — with `[memory.graph].extraction_model`; the
local slot stays configured as the way back. Either way hindsight-api
calls the one virtual id `hal0/memory`, which hal0's `/v1` resolves to your
choice on every call, so switching applies at once with no engine
restart, and an upstream target uses hal0's own upstream credentials (the
engine never holds a cloud key). `[memory.graph].llm_timeout_s`
(default `300`, 30–3600) sets how long Hindsight will wait on its own
extraction/consolidation/reflect calls — raise it if a cold slot start
regularly times out. The **Extraction limits** on the same panel (Settings →
Data → Memory) cap how hard Hindsight may drive that slot: one extraction call
in flight, 16384 completion tokens per call, and a bounded retry ladder by
default. On a slow box they are what keeps a single stuck extraction from
wedging the whole retain queue; see `[memory.graph]` in the config reference
for each knob.

`--slot` names a local `type=llm` slot; it must already be enabled — the

retries a provider that is offline at most once a minute. The dashboard's **Engine model** picker (Settings → Data →

extraction inside `[memory.graph].llm_timeout_s`. hal0 reads the slot's

timed completion (at most 512 prompt and 32 decode tokens, capped at 30 s),
and projects `~3500 / prompt tok/s + min(extraction_max_tokens, 4096) / decode tok/s`.
When that exceeds the timeout, the enable still goes through and prints a
warning that names the measured rates. Point extraction at a faster slot,
or raise `llm_timeout_s`.

If extraction operations are failing (an unreachable or too-small
extraction slot, for example), the dashboard's graph panel shows a "Retry N
failed" button that requeues every failed extraction/consolidation
operation once the underlying problem is fixed. The CLI equivalent is
`hal0 memory ops retry --all-failed` (below), which covers the same
operations from the terminal.

<Aside type="note">
A memory write is refused outright — not silently dropped — if the
extraction slot's model can't clear an ~8192-token context-window floor
(a conservative estimate of the extraction prompt's own footprint).
Override the floor with `HAL0_MEMORY_EXTRACTION_FLOOR` on the hal0-api
service if it's wrong for your engine. Chat is unaffected; only memory
writes are gated on this check.
</Aside>

## Reranking

Recall from more than one bank goes through a second-pass reranker before
it's returned, configured under `[memory.embedding]`:

```toml
[memory.embedding]
rerank_gateway_url = "http://127.0.0.1:8080"
rerank_model = "builtin.jina-reranker-v1-tiny-en-q8"
rerank_connect_timeout_s = 1.0
rerank_read_timeout_s = 8.0
```

`rerank_model` must resolve to a model the `rerank` capability slot serves.
The dashboard's Reranker panel gives you a picker instead of free text: the
schema default labelled "builtin", every model the capabilities catalog
tags for reranking (with its serving backend), and — if you've saved
something outside both — that value labelled "(saved)" so you can see and
move off it. A model id the gateway can't resolve doesn't error; it just
makes every recall fall back to fused vector ordering, so pick from the
list. The panel links to Settings → Capabilities, where the underlying
`rerank` slot itself lives.

## Manage banks

```sh
hal0 memory bank list
hal0 memory bank stats <bank>
hal0 memory bank profile get <bank>
hal0 memory bank profile set <bank> --skepticism 4 --retain-mission "..."
hal0 memory bank export <bank> [--out <file>]
hal0 memory bank import <bank> --file <file> [--dry-run]
hal0 memory bank delete <bank> --confirm <bank>
hal0 memory bank consolidate <bank> [--scope <tag>]
```

Deleting a whole bank requires `--confirm <bank>` to exactly match the
target bank id — the CLI refuses before the request even reaches the
server if it doesn't, and the server enforces the same check independently.

A bank id starts with a letter or digit and continues with letters, digits, `.`, `_`, `:` or `-`, up to 128 characters in all. Dots are legal inside an id, so a bank the hindsight coding-agent plugin named after a repository (`coding-agent::ultrareview-1.4`) can be managed and deleted through hal0: its stats, profile, config and delete routes under `/api/memory/banks/{bank_id}` accept it. A leading dot, a dot-only segment and any `..` run are refused. The dashboard's new-bank form accepts the same grammar.

`bank profile set` writes every flag as a bank-config override in one
config PATCH: `--skepticism`/`--literalism`/`--empathy` (1–5 disposition
traits) and `--retain-mission`/`--observations-mission`/`--reflect-mission`.
Pass any combination — only the fields you name are changed. `bank profile
get` shows the bank's name, mission and effective disposition. The memory
engine's own `/profile` endpoint answers `410 Gone` from Hindsight 0.10.0 on;
hal0's `/api/memory/banks/<bank>/profile` keeps working by composing the same
answer from the bank list and the bank config.

`--reflect-mission` is the text the Memory area's Facts tab shows in the bank bar as the bank's description. You can also edit it there in place; see [The bank bar](/docs/guides/memory-workspace#the-bank-bar).

## Async operations and mental models

```sh
hal0 memory ops list [--bank <bank>] [--failed]
hal0 memory ops retry --all-failed [--bank <bank>]
hal0 memory ops retry --bank <bank> --id <operation_id>
hal0 memory mm list <bank>
hal0 memory mm refresh <bank> <model_id>
hal0 memory mm history <bank> <model_id>
hal0 memory recall <query> [--bank <bank>] [--tags ...] [--types ...]
```

`ops list`/`ops retry --all-failed` fan out across every bank when `--bank`
is omitted — Hindsight's operations API has no cross-bank listing endpoint,
so hal0 merges the per-bank results itself. `ops retry --id` needs `--bank`
too, since operation ids are bank-scoped. `mm` (mental model) commands
always take the bank as the first argument. `hal0 memory recall` hits the
same namespace-scoped recall path an agent uses at runtime (not the admin
bank console) — use it to see exactly what an agent would get back for a
query.

## Move the platform memory to a named bank

`[memory] bank` in `hal0.toml` names the Hindsight bank behind the `shared`
namespace (for example `Hal0::Platform`). The namespaces callers use do not
change, only the engine bank behind `shared`. A box from before the two-bank
layout uses the bank its store already had, `shared` unless the key was set.
To move it to a named bank:

```sh
hal0 memory migrate platform --target Hal0::Platform            # dry run: the plan
hal0 memory migrate platform --target Hal0::Platform --apply    # clone + fold + verify
```

The command clones `shared` into the new bank with the engine's clone call
(no LLM, so no consolidation queue), folds a leftover `agents` bank
(identity cards tagged `agent-identity`) into it, and exits 1 if the new bank
holds fewer facts than the sources. Then set the key and restart:

```toml
[memory]
bank = "Hal0::Platform"
```

```sh
sudo systemctl restart hal0-api
```

Run the migration first: a box that sets `bank` before cloning starts with an
empty memory. The old `shared` and `agents` banks stay untouched until you
delete them with `hal0 memory bank delete`. See ADR-0052.

<Aside type="caution">
This is a bank-consolidation tool (private banks → one unified bank), not
a Cognee migration path — there is no CLI command for migrating a
Cognee-era store. See the engine note above.
</Aside>

## Change the embedding model

The embedding model belongs to the store, not to the config. hal0 records the
provider and model a store was built with and keeps the engine on that pair,
because the engine does not re-embed stored vectors: started on another model
it raises no error and recall over older memories quietly gets worse. Editing
`[memory.models]` therefore changes nothing by itself. One command moves a
store:

```sh
sudo hal0 memory embedder switch hindsight-ai/hs-embed-1            # dry run: checks and the plan
sudo hal0 memory embedder switch hindsight-ai/hs-embed-1 --apply    # do it
```

Run it on the box, as root. The dry run lists every bank with its fact,
observation, mental-model, directive and document counts, the free disk
space, and an estimate of the duration. It writes nothing: no export, no
pause, no file.

### Memory is out of service while it runs

`--apply` is your consent to this, so read it first.

- **The engine is taken away from every other client.** For the whole run it
  listens only on a private loopback port that the switch picks. That is the
  only way to keep a client that writes to the engine's own port (the
  Hindsight coding-agents plugin, the Pi coder's plugin) from changing a bank
  while it is being rebuilt. Such a client simply fails to connect.
- **Recall does not work**, for the whole run and not only during restarts.
  hal0 sees the engine as down: recall, search and reflect answer
  `503 memory.engine_unavailable`.
- **Writes are refused**: `503 memory.writes_paused` with `Retry-After: 30`.
  Nothing queues them. The Hermes memory plugin logs a failed turn capture
  and drops it, so conversation turns captured during the switch are lost.
- **`hal0 update` refuses to start**, and the switch refuses while an update
  is queued or running.

A run restarts the engine three times (15 to 30 seconds each on the reference
box), exports every bank and restores it twice, and re-embeds at about 60
facts per second on CPU, so every fact is embedded twice. A small store takes
about two minutes. Pick a quiet moment.

### What `--apply` does

1. Pauses memory writes and waits for the engine's queues to drain.
2. Restarts the engine on its private port, still on its original model, and
   lists the banks. That list is what the run rebuilds.
3. Exports every bank to
   `/var/lib/hal0/backups/memory-embedder-switch-<time>-<run>/` and checks
   each archive against the bank.
4. Records the new embedder, rewrites the engine's managed drop-in from that
   record, restarts the engine (still private) and confirms from its
   environment that it runs the new model.
5. Restores each archive into a temporary bank named `<bank>.switch-<run>`,
   which re-embeds every fact with the new model and makes no LLM call, and
   compares it with the original as it was archived: its counts, every
   document id and the length of its stored text, every fact's text and
   tags, and each mental model's content. A restore that loses content is
   found here, while every original is still untouched.
6. Only when every bank matches: for each bank, checks the original and its
   rebuilt copy one more time, deletes the original, restores its archive
   again into the bank's own id, checks that the same way (its
   knowledge-page and directive ids too), and only then deletes the rebuilt
   copy.
7. Returns the engine to its normal address and then lets writes through.

The engine is isolated with one drop-in for its unit,
`hindsight-api.service.d/zzzz-hal0-embedder-switch.conf`, which the switch
writes and removes. It keeps the command your unit already runs, your own
`ExecStart` drop-in included, and changes only the address. The preflight
reads the unit with `systemctl cat hindsight-api.service` and refuses, before
anything changes, when:

- `ExecStart` is not a direct command line it can rewrite: a shell wrapper
  (`/bin/sh -c '…'`), a prefix other than `-` or `:` (`@`, `+`, `!`, `!!`),
  a `%` specifier or `$VAR` in the `--host` or `--port` value, or a
  backslash escape. Make it a plain command line that names the engine's
  binary with literal `--host` and `--port` values, run
  `sudo systemctl daemon-reload`, and run the switch again;
- a drop-in whose name sorts after `zzzz-hal0-embedder-switch.conf` sets
  `ExecStart`, so it would win. The refusal names the file and its
  `ExecStart`; rename it so it sorts earlier;
- an `ExecStartPre`, `ExecStartPost`, `ExecCondition` or `ExecReload` line
  names the engine's normal port (a health probe, say). It would fail at
  every restart while the engine is private. The refusal names the line.

After each restart onto the private port the switch confirms that the
process listening there belongs to `hindsight-api.service` and that
`/version` reports the engine version the preflight saw. Anything else on
that port stops the run at once, naming the process. If anything still
answers at the normal address (a refused connection is the only "nothing
there"), the run stops before it has exported anything.

Nothing else writes the engine's banks or drop-ins while a run is unfinished:
the default banks are not seeded, a new install's first-start step skips, and
hal0-api's replay of boot-time writes waits for the pause to lift.

### Ids after the switch

Each bank keeps its knowledge-base folder and page ids (`kf-…`, `kp-…`), its
directive ids, its mental-model ids and its document ids. That is why step 6
restores a second time: the engine keeps those ids only on a restore into the
bank's own id once the original is gone, never on the rebuilt copy beside it.
Agents that hold a page id (the coding-agents plugin's
`relates_to_page_id` and its initiative markers), Memory page links to a
knowledge page, and bindings to a mental model keep working.

Fact ids are not kept: the engine gives every restored fact a new id. A fact
id written down before the switch, such as a link to an open fact on the
Memory page or an id saved for `memory_delete`, no longer resolves. The dry
run says this too.

### If it fails or is interrupted

Before step 6 (an import fails, a count differs, the engine does not come up
on the new model, Ctrl-C): the command deletes the temporary banks, returns
the engine to its normal address on the original model, lifts the pause and
exits non-zero naming the bank and what differs. The original banks were
never touched.

Step 6 cannot be undone, so it can be resumed instead. If it stops part-way,
**the engine stays on its private port and writes stay paused**. That is on
purpose, and nothing ends it by itself: the banks are half replaced. The
`memory_embedder` row of `hal0 doctor all` warns for as long as that lasts,
naming the run and its archive directory.

```sh
sudo hal0 memory embedder switch --status    # where it stands and what --resume would do
sudo hal0 memory embedder switch --resume    # finish it
```

If the very last restart fails, after the isolation drop-in is gone, the
engine is back at its normal address (recall works) while writes stay paused.
`--status` and the doctor row say exactly that, and `--resume` isolates the
engine again before it finishes the run.

`--resume` never cancels a restore. The engine marks a cancelled restore
as cancelled straight away but lets it go on writing, so a resume that finds
one still running waits for it, and if it is still running after twice its
expected time, stops without deleting or restoring anything and asks you to
run `--resume` again later. A restore that someone else cancelled stops the
resume until the engine has been restarted, which ends it. The switch tells a
restart by the engine's process and by the unit's systemd `InvocationID`; if
it can read neither, the message says so, and stopping the engine
(`sudo systemctl stop hindsight-api.service`) before `--resume` works: the
resume starts it again itself.

If a bank restored into its own id fails its check, `--resume` restores it
once more. If that fails the same way, the switch stops retrying and tells
you to stop running `--resume`: it will not delete or restore that bank
again. Its rebuilt copy, which matched before the original was deleted, and
its archive are kept. Report it with the output of `--status`.

`--resume` also stops, changing nothing, when the run stopped while it was
deleting an original and that original is still there (the delete may have
taken part of it), and when the journal was written by a different hal0
version. Both messages name the archive directory.

`--status` changes nothing, never waits, and runs the same checks a resume
would, each on one read of the bank. For each bank it says what `--resume`
will do; where the switch cannot repair something by itself it says exactly
what you do, down to the command. It lists the operations running on each
bank by type, bank and id (also in `--json`), and a check made while the
engine was still working on a bank says so: `--resume` waits for that work.

`--resume` looks at which banks the engine has now, not only at its journal.
What it can repair it repairs: a rebuilt bank that no longer matches is
rebuilt from the original, a bank missing from its own id is restored from
its archive, and a restore into the own id that was cut short is deleted and
done again. Run after a stop that happened before step 6, the same command
undoes the run instead. The journal is kept in two places
(`/var/lib/hal0/state/` and the archive directory), so losing one copy does
not lose the run. You never edit it by hand.

`--clear-gate` returns the engine to its normal address and lifts the pause
by hand. It is for one case only, a pause or a private engine that no journal
explains, and it is refused while any switch is unfinished. It checks no
bank, so look at `--status` first.

### Before you start

- The preflight refuses while any bank has queued or running operations.
  The engine's export does not carry them, so a queued retain would be lost
  with the old bank. Wait for them (`hal0 memory ops list` shows them) or
  cancel them (`DELETE /api/memory/banks/<bank>/operations/<id>`).
  `--allow-pending` goes ahead anyway: what those operations have not written
  when a bank is exported is not carried over.
- The engine's own work is waited for, not refused: a mental-model refresh
  (which the engine queues after a restore or a restart), a consolidation,
  or vector-index or graph maintenance. Before the run starts the switch
  waits up to 15 minutes for it, for all banks together, and each time it
  compares or deletes a bank, up to 15 minutes for that bank. If it does not
  finish, the switch stops and names the operation by type, bank and id. A
  dry run lists such work as a warning, and refuses parked work the way
  `--apply` would (below).
- The engine can park its own work: an automatic mental-model refresh due
  within the model's minimum refresh interval (30 minutes in hal0's seed
  banks) waits, queued, until that interval is over. When parked work is due
  later than the switch would wait, the switch does not wait: it stops at
  once, names the operation and when it is due, and tells you to run it
  again after that time.
- A refresh or a consolidation on an original bank while the engine runs the
  new model embeds with the new model. If the run is then undone, any refresh
  or consolidation activity on an original after the switch to the new model,
  whether it finished, failed, was cancelled or is still queued, records the
  store as mixed (see below), as does an original bank the undo cannot check,
  including one an interrupted undo never reached. This holds across
  `--resume`, and activity after the undo returns the engine to the old model
  counts too. The engine's records cannot show whether such work wrote anything, so the
  switch counts it all. The only cost of a mixed record is running the switch
  again. Vector-index and graph maintenance embed nothing and never count.
- The export carries only facts that belong to a document. A bank holding any
  other fact does not match its archive, and the switch stops at step 3
  saying so. Observations whose source facts are gone are not exported
  either; that is reported in the result, not refused.
- It needs free space of about the size of the engine's data directory on
  that filesystem (the rebuilt banks sit beside the originals until the swap)
  and half of that again for the archives.
- The archives are kept. The command prints their directory and the `rm -r`
  line that deletes them. They hold your memories in plain text; the
  directory is `0700`.
- The audit log and LLM request traces of a bank are not carried over.
- A store flagged as mixed (it may hold vectors from two models) is repaired
  the same way: switch it to the model it is already recorded on.
- The switch does not edit `hal0.toml`. If `[memory.models]` names another
  model afterwards, that is fine: the engine runs what the store was built
  with, and `hal0 doctor all` says so without a warning. Set
  `embeddings_provider` and `embeddings_model` there to the new pair when you
  want the two to agree.

## Destructive ops are audited

Every destructive call under `/api/memory/*` — bank delete, and the
memories/config/document/directive/operation/mental-model delete routes
— records a durable audit row (actor, target, and outcome) so a memory
wipe is attributable after the fact.
