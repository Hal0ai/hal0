A fresh hal0 install boots with its services up — the dashboard and
OpenWebUI on `:3001`, Hermes, and the control-plane API on `:8080` — but
with **zero models and zero model-serving slots configured**. The
installer seeds the first-run sentinel and extension wiring only
(`hal0 setup --auto --no-slots`); it does not select or download a model.
Every model is something *you* obtain afterward, and this page is the map
for doing that.

If you just want the fastest path from a blank box to a working chat, run
the [setup TUI](/docs/getting-started/setup/) or follow
[Load your first model](/docs/getting-started/first-model/). This guide is
the reference behind those flows: what the registry is, where bytes land,
and every real way to get a model into it.

## The registry is the source of truth

hal0 keeps a **local model registry** — a record of every model it knows
about: its id, display name, on-disk path, size, SHA-256 digest,
capabilities, launcher defaults, and (for pulled models) the Hugging Face
coordinates it came from. The dispatcher resolves model ids against this
registry; the actual weights live in your [model store](#the-model-storage-directory).

A registry row can be **local** (bytes are on this host — pulled,
registered, or scanned) or **upstream** (only advertised by a configured
remote provider, never pulled). `hal0 model list` shows both, and every
row carries an explicit `origin` so the dashboard can badge upstream-only
rows distinctly.

<Aside type="note" title="NPU/FLM models are the exception">
FastFlowLM (NPU) models are **not** stored in the registry — they're owned
by the host `flm` cache and surfaced into the model list straight from the
FLM probe. See [NPU / FastFlowLM models](#npu--fastflowlm-models).
</Aside>

## The model storage directory

Every downloaded model file lives under a single **model store** — the
directory hal0 reads from and writes pulls into, and the path each slot
container bind-mounts to find its weights.

| | |
|---|---|
| **Default** | `/var/lib/hal0/models` |
| **Set at install** | `hal0 setup --storage-dir <path>` |
| **Show / change at runtime** | `hal0 model store [<path>] [--migrate]` |
| **Set in config** | `[models].store` in `hal0.toml` (an absolute path, e.g. `/mnt/ai-models`) |
| **Env override** | `HAL0_MODEL_STORE` |
| **Conventional mount** | `/mnt/ai-models` — the default slot bind-mount root |

`[models].store` is the single source of truth for where models are read
and written; when it's set the pull engine writes there and slots
bind-mount it. It supersedes the older `[models].pull_root` field, which is
retained only so pre-existing installs round-trip without a manual edit —
clearing `store` falls back to `pull_root`, which itself defaults to
`/var/lib/hal0/models`.

Inspect or change the store without hand-editing `hal0.toml` using
**`hal0 model store`**:

```sh
hal0 model store                       # show the effective store + candidate dirs
hal0 model store /mnt/ai-models        # point the store at a new path
hal0 model store /mnt/ai-models --migrate   # ...and move existing weights into it
```

A store/registry mismatch — weights on one path, the registry or a slot
pointing at another — is the single most common "the file exists but the
slot dies with `No such file or directory`" failure. `hal0 model store`
(and [`hal0 doctor models`](#verifying-and-troubleshooting)) exist to catch
and fix exactly that. Running slots pick up a changed store on their next
restart.

<Aside type="note" title="NPU/FLM has its own store">
FastFlowLM (NPU) weights live under a **separate** store, `[models].flm_store`,
not the GGUF store above — see [NPU / FastFlowLM models](#npu--fastflowlm-models).
</Aside>

hal0 also scans a set of **roots** (`[models].roots`, plus the effective
store) for model files — see [Scan an existing directory](#scan-an-existing-directory).
Files with a `[models].file_extensions` suffix (`.gguf`, `.safetensors` by
default) are treated as candidate models.

<Aside type="tip" title="ComfyUI image/video models land elsewhere">
Image and video models don't live in the per-id store layout — they're
placed into ComfyUI's own models tree (`checkpoints`, `loras`, `vae`,
`upscale_models`, …) so ComfyUI's loaders pick them up directly. See
[Capabilities: ComfyUI image and video models](#capabilities-comfyui-image-and-video-models).
</Aside>

See [Paths and files](/docs/reference/paths-and-files/) for the full
store-resolution precedence.

bytes (or a registration) on *this* host; the fourth is remote.

### Pull from Hugging Face

The most common path. The pull argument is either a **curated alias**
(from hal0's built-in catalogue, e.g. `qwen3-4b`) or a model id already in
the registry.

<Tabs>
<TabItem label="Dashboard">

Open the **Models** tab. The **Catalog** section renders each curated pick
as a card with size, license, and minimum-memory badges — click **Pull**
on a card to start the download; a progress bar tracks it inline.

To pull something off-catalogue, use the **HuggingFace search** box (it
proxies HF's public search) to find a repo, then the **Add by HF coords**
modal inspects the repo, lists its pullable `.gguf` variants (and any
`mmproj` vision sidecar), and pulls the one you pick.

</TabItem>
<TabItem label="CLI">

```sh
# curated alias or a registered id
hal0 model pull qwen3-4b
```

The pull runs as a background job on the daemon; the CLI polls
`/api/models/<id>/pull/status` every 500 ms and prints a progress bar
until the job reaches a terminal state, then reports the final path and
SHA-256. A vision pick's `mmproj` projector downloads automatically in the
same job.

To pull an off-catalogue file, supply the HF coordinates in the request
body (there's no CLI flag for this yet — use the API directly):

```sh
curl -X POST http://localhost:8080/api/models/my-qwen-build/pull \
  -H 'content-type: application/json' \
  -d '{"hf_repo":"unsloth/Qwen3-8B-GGUF","hf_filename":"Qwen3-8B-UD-Q4_K_XL.gguf","labels":["chat"]}'
```

You can search and inspect HF without leaving the host:

```sh
# free-text HF search (capped at 20 rows)
curl 'http://localhost:8080/api/hf/search?q=qwen3+gguf&type=text-generation'

# list a repo's GGUF variants + license
curl -X POST http://localhost:8080/api/models/inspect \
  -H 'content-type: application/json' \
  -d '{"hf_repo":"unsloth/Qwen3-8B-GGUF"}'
```

</TabItem>
</Tabs>

For the full pull lifecycle — resume, checksum verification, the mmproj
sidecar, cancel — see [Pull and register models](/docs/guides/pull-and-register-models/).
For the curated catalogue itself, see [Choose models](/docs/guides/choose-models/).

### Register a local file

If the bytes are already on the host — you dropped a GGUF into the model
store, or copied one over — register it without re-downloading. hal0
records metadata only; it never copies or `chown`s the file, so it must be
readable by the `hal0-api` process.

<Tabs>
<TabItem label="Dashboard">

In the **Models** tab, use the **Add by path** action: type or paste the
absolute path to a `.gguf` / `.safetensors` file, confirm the detected
capabilities, and **Register**. The input pre-fills with your configured
scan root so the path is easy to complete.

</TabItem>
<TabItem label="CLI">

The quickest path is **`hal0 model add <path>`** — it reads the file
header to auto-detect the id, capabilities, and backends, and leaves the
file where it is (no copy, no `chown`):

```sh
hal0 model add /mnt/ai-models/local/qwen3-4b-instruct-q4_k_m.gguf
# optional: --id <explicit-id>  --name "Display Name"  --overwrite
```

It prints the detected capabilities and the exact next command
(`hal0 model run <id>` / `hal0 model assign <id> --slot <slot>`). Under the
hood it posts to `POST /api/models/add-from-path`, the same
capability-detecting flow the dashboard's **Add by path** modal uses.

If you'd rather set the metadata explicitly instead of auto-detecting it,
`hal0 model register` takes the fields as flags and posts to `POST /api/models`:

```sh
hal0 model register qwen3-4b-q4_k_m \
  --path /mnt/ai-models/local/qwen3-4b-instruct-q4_k_m.gguf \
  --name "Qwen3 4B Q4_K_M" \
  --license Apache-2.0
```

</TabItem>
</Tabs>

### Scan an existing directory

When you already have a folder full of models (a shared NAS mount, an HF
cache, a previous install's store), scan it and bulk-register everything
hal0 detects. The scan walks the directory, auto-detects each file's
backends and capabilities, and skips accessory files (mmproj sidecars,
shards, HF/ComfyUI accessory dirs).

<Tabs>
<TabItem label="Dashboard">

Use the **Scan directory** action in the **Models** tab. Enter an absolute
path (it defaults to your first configured `[models].roots` entry), toggle
recursive on/off, and **Scan**. hal0 returns a preview table of every
candidate with detected capabilities and an *already-registered* badge;
tick the rows you want and **Register** them. Registration runs one row at
a time so a single bad path doesn't poison the rest.

</TabItem>
<TabItem label="CLI">

**`hal0 model scan`** walks the configured `[models].roots` **plus the
effective store**, auto-detects each new file, and registers it — use it
right after hand-placing files or mounting a drive of them:

```sh
hal0 model scan
# → Scanned: /mnt/ai-models, /var/lib/hal0/models
#   + qwen3-4b-instruct-q4_k_m
#   1 added, 3 skipped.
```

It reports the roots it walked, so if nothing new turns up the printout
tells you whether your files even live under a scanned root. Two adjacent
tools for the cases scan doesn't cover:

- A file **outside** the scanned roots → register it directly with
  [`hal0 model add <path>`](#register-a-local-file) (any path).
- Files are under the wrong root → move the store with
  [`hal0 model store <dir> --migrate`](#the-model-storage-directory).

hal0 also runs this scan **automatically at startup** when
`[models].auto_scan_on_start` is `true` (the default), so files dropped
into a root are picked up on the next `hal0-api` start. The underlying
endpoint is `POST /api/models/scan`; `POST /api/models/scan/preview`
returns the candidate table without mutating the registry (the dashboard's
preview uses it).

</TabItem>
</Tabs>

### Upstream-advertised models

If you've [connected an external provider](/docs/guides/connect-external-providers/),
the models it advertises through its `/v1/models` endpoint show up in
`hal0 model list` with `origin: upstream`. These are **not** downloaded —
they're served remotely by the provider — so there's nothing to pull;
point a slot (or a request) at the id and hal0 routes to the upstream. On
an id collision, a local model wins over an upstream one.

## Initial model pulls: list → pull → assign → start

The end-to-end flow to go from a blank box to a serving slot is **list →
pull → assign → start the slot**.

<Aside type="tip" title="Smoke-test first">
`qwen3.5-0.8b` is the recommended first pull on a fresh install — it
verifies the whole slot lifecycle (pull → load → serve) in seconds before
you commit to a 20+ GB pick.
</Aside>

<Tabs>
<TabItem label="Dashboard">

<Steps>

1. Open the **Models** tab and review the **Catalog** cards (or search HF).
2. Click **Pull** on a pick and watch the progress bar to completion.
3. When it lands, **assign** it to a slot as that slot's default model.
4. Go to the **Slots** view and **load** the slot to start serving.

</Steps>

</TabItem>
<TabItem label="CLI">

<Steps>

1. **List** what's available — registry rows plus upstream-advertised
   models:

   ```sh
   hal0 model list
   ```

2. **Pull** a model:

   ```sh
   hal0 model pull qwen3.5-0.8b
   ```

3. **Assign** it as a slot's default (this does *not* start the slot).
   `agent` is the always-seeded anchor slot:

   ```sh
   hal0 model assign qwen3.5-0.8b --slot agent
   ```

4. **Start** (load) the slot:

   ```sh
   hal0 slot load agent
   ```

</Steps>

</TabItem>
</Tabs>

Assigning writes `model.default` into the slot's config; loading starts
the container. See [Manage slots](/docs/guides/manage-slots/) for creating
slots, choosing device/profile, and the load/unload lifecycle.

<Aside type="tip" title="One command: hal0 model run">
`hal0 model run <ref>` collapses pull → assign → load → wait-ready into a
single step. It pulls the model if it isn't registered yet, assigns it to a
compatible slot (`--slot` to pick one), loads it, and blocks until the slot
is serving (`--timeout`, default 300 s):

```sh
hal0 model pull qwen3.5-0.8b   # or drop a file + hal0 model add
hal0 model run  qwen3.5-0.8b
```
</Aside>

## NPU / FastFlowLM models

On an AMD Strix Halo box with the XDNA2 NPU, hal0 can serve models through
**FastFlowLM (FLM)** on the `npu` slot. FLM models are obtained
differently from GGUFs:

- They're identified by an **Ollama-style `family:size` tag** (e.g.
  `gemma4-it:e4b`, `llama3.2-3b`), not HF coordinates.
- They're **not** stored in hal0's registry — the host `flm` binary owns
  them, downloading into a cache it also serves from. hal0 surfaces
  installed FLM models into the model list straight from the FLM catalog
  probe, flagged `backend: flm` / `upstream: npu`.
- Serving needs the host FLM binary (`/usr/bin/flm`), the NPU device node
  (`/dev/accel/accel0`), and a slot whose provider is `flm`.

<Tabs>
<TabItem label="Dashboard">

Installed FLM models appear in the **Models** list as NPU rows. Assign one
to a slot configured with the `flm` provider (the NPU slot), then load it.
The NPU **occupancy** and **swap-status** panels reflect what's resident.

</TabItem>
<TabItem label="CLI">

The pull endpoint auto-routes an FLM `family:size` tag through the host
`flm pull` (validated against the FLM probe, so a stray `foo:bar` still
falls through to the HF resolver):

```sh
# routes to `flm pull gemma4-it:e4b` on the host — no HF coords needed
hal0 model pull gemma4-it:e4b
```

Provision the NPU slot with [`hal0 setup`](/docs/getting-started/setup/) —
it opts the NPU in automatically when the hardware is present — then
assign the FLM model to it and load:

```sh
hal0 model assign gemma4-it:e4b --slot npu
hal0 slot load npu
```

The `npu` slot uses the `flm` provider; `hal0 slot create --provider flm`
exists, but the NPU device is wired by the setup flow rather than a
`--hardware` flag (which only covers `vulkan`/`rocm`/`cpu`).

</TabItem>
</Tabs>

<Aside type="caution">
FLM download and serving are only available where the NPU driver and host
`flm` binary are present. On a box without XDNA2 passthrough, `flm pull`
(which only downloads files) can still run, but the `npu` slot can't
serve. See [Providers, profiles, and devices](/docs/reference/providers-profiles-devices/).
</Aside>

#### Relocating the FLM store (`[models].flm_store`)

By default FLM weights sit in FLM's cache under the hal0 HOME
(`/var/lib/hal0/.config/flm/models`). To keep them off the root filesystem
— e.g. on a data pool — set an absolute `[models].flm_store` in `hal0.toml`:

```toml
[models]
flm_store = "/mnt/ai-models/flm/models"
```

The NPU slot container bind-mounts that directory over FLM's hardcoded
cache. hal0 creates it (writable by the container uid) at slot-spec build
time and orders the generated unit **after** the backing mount, so a reboot
with a late or missing mount no longer kills the slot with `podman exit 125`
(`statfs … no such file or directory`). Empty falls back to the
`HAL0_FLM_MODELS_DIR` env var, then to the default cache — if both the env
var and `flm_store` are set, the **env var wins**.

## Capabilities: ComfyUI image and video models

Image and video generation runs through ComfyUI, which uses a
**capability-based** model system rather than the GGUF registry. Each
capability — `txt2img`, `img2img`, `txt2video`, `img2video`,
`image_upscale` — maps to a family (e.g. `qwen-image`, `sdxl`, `ltx2`,
`esrgan`) with a default variant and alternatives. The installer records
your default capability picks but downloads nothing; you trigger the
fetches afterward.

<Tabs>
<TabItem label="Dashboard">

Open the **Models** tab and switch to the **Image / ComfyUI** segment
(dispatcher-routable text models and image models live on separate tabs).
Trigger the deferred downloads for your capability picks from there; the
weights land in ComfyUI's models tree, not the per-id store.

</TabItem>
<TabItem label="CLI / API">

Trigger the deferred fetch via `POST /api/comfyui/models/fetch`. Fetch the
default variant for **every** capability, or name specific ones — the
endpoint returns `202` with background job ids:

```sh
# fetch the default variant for every capability
curl -X POST http://localhost:8080/api/comfyui/models/fetch \
  -H 'content-type: application/json' \
  -d '{"auto": true}'

# or fetch specific capability/family selections
curl -X POST http://localhost:8080/api/comfyui/models/fetch \
  -H 'content-type: application/json' \
  -d '{"selections":[{"capability":"txt2img","family":"sdxl"}]}'
```

</TabItem>
</Tabs>

See [Generate images](/docs/guides/generate-images/) for the full ComfyUI
workflow, and the image picks in [Choose models](/docs/guides/choose-models/#image-picks).

## Verifying and troubleshooting

- **Audit the whole pipeline in one pass.** `hal0 doctor models` checks
  every registry entry's file still exists, flags model files sitting in
  the store that were never registered, and verifies the FLM (NPU) store
  dir exists and is writable by the container uid. It exits non-zero (and
  prints the exact fix — `hal0 model scan`, `hal0 model store <dir>`, or an
  `rm`/re-register) when it finds any of them — including the classic
  registry-points-at-a-missing-file case that makes a slot die with
  `gguf_init_from_file: … No such file or directory`.

  ```sh
  hal0 doctor models
  ```

- **Where did the file land?** A completed pull reports its final path and
  SHA-256. `hal0 model show <id>` (add `--json`) prints the full registry
  row including `path` and `size_bytes`; GGUFs live under your
  [model store](#the-model-storage-directory).

- **Pull status.** A pull job moves through `queued → running →
  completed`, or `failed` / `cancelled`. On failure the CLI exits non-zero
  and prints the daemon's error; the registry row stays so you can retry.
  Re-issuing a pull for the same id reuses an in-flight job rather than
  starting a second download. The dashboard's **Models** view shows the
  same state inline with a **Retry** button.

  ```sh
  curl http://localhost:8080/api/models/<id>/pull/status
  ```

- **Gated or large models.** Pulls that need a Hugging Face token read
  `HF_TOKEN` (or `HUGGING_FACE_HUB_TOKEN`) from the API environment; a
  gated repo returns `401`/`403` without one. The easiest path is the
  dashboard: **Settings → Secrets → HuggingFace token** applies live
  without a restart.

- **Out of disk.** Before a multi-GB pull, hal0 runs a disk-space
  preflight against the staging filesystem and fails fast with
  `model.insufficient_disk` (`507`) rather than filling the disk.

- **Slot won't load a model it can't find.** If a slot's configured
  default no longer resolves locally, `hal0 slot load` falls back to the
  best matching locally-registered model for that capability instead of
  crash-looping, and logs the substitution. Fix the slot's default when
  you see this.
