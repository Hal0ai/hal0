hal0 ships an in-tree benchmark engine (`hal0.bench`, since v0.9.6): a
planner that works out which measurements are stale, a runner that executes
them against the same container images your production slots serve, and a
durable result store the **Benchmarks** dashboard page (roster / runs /
evals / run-queue) reads through `/api/benchmarks/*`.

```sh
hal0 bench plan            # what's stale and why (no GPU, no writes)
hal0 bench run             # execute the plan (or a slice)
hal0 bench status          # recent records / session state
hal0 bench results         # current values from bench.db
hal0 bench history         # trend for a cell/model over time
hal0 bench eval            # agentic task eval: score a model as a real agent
hal0 bench devices         # GPU device nodes benchmark containers will use
```

## GPU device nodes are probed, never assumed

Benchmark containers get their GPU passthrough from the same resolution the
production slot containers use — hal0's hardware probe plus live enumeration
of the real device nodes — so a benchmark runs wherever a slot runs:

| Hardware tier | What the container is given |
| --- | --- |
| AMD (Strix Halo iGPU, AMD dGPU) | `/dev/kfd` plus the actual `/dev/dri` nodes (`card1`, `renderD128`, … — whatever the kernel named them) and the real render/video group IDs |
| NVIDIA dGPU | the CDI device `nvidia.com/gpu=all` (no device paths, no group IDs — CDI injects them) |
| CPU | nothing: a CPU-tier run does not require a DRI device |

`hal0 bench devices` prints what a run on this host would get. If a device
setting cannot be honoured, the sweep fails **before** any container starts and
names the paths it checked, rather than falling back to a guess.

Each tier has a matching sweep lane. The GPU lanes (`rocm`, `vulkan_radv`) run
the unified ROCmFPX runner with full offload; the `cpu` lane runs the lean
CPU toolbox with `-ngl 0` and no device flags at all. The default sweep picks
the lanes for the tier it resolved — `cpu` alone on a GPU-less box, the two GPU
lanes otherwise. To measure the CPU baseline on a machine that also has a GPU,
pin the tier: `HAL0_BENCH_TIER=cpu`, or ask for the lane by name with
`hal0-benchctl sweep <model.gguf> cpu`. Results record the tier they ran on, so
a CPU number is never published under the iGPU's name.

For unusual passthrough layouts, `HAL0_BENCH_GPU_DEVICES` (or the per-node
`HAL0_BENCH_KFD_DEVICE` / `HAL0_BENCH_CARD_DEVICE` /
`HAL0_BENCH_RENDER_DEVICE`), `HAL0_BENCH_GPU_GROUPS`, and `HAL0_BENCH_TIER`
override the probe. Each override is validated as a real character device.

## What the installer sets up

<Steps>

1. **State store** — `/var/lib/hal0-bench` (override with
   `HAL0_BENCH_STATE`): an append-only `records.jsonl` (the source of
   truth), a derived `bench.db`, and an `artifacts/` directory. Kept on
   uninstall unless `--purge`.

2. **Operator-owned config** — suite definitions seeded no-clobber to
   `/etc/hal0/bench/suites/*.toml` (`smoke`, `roster`, `lane-matrix`,
   `concurrency`) plus `/etc/hal0/bench/window.toml`, the politeness
   policy for scheduled runs.

3. **Three systemd units** —
   `hal0-bench.timer` fires `hal0-bench.service`
   (`hal0 bench run --suite roster --scheduled`) weekly, Sunday 03:00
   local with a randomized delay; `hal0-bench-worker.service` drains the
   dashboard's run queue. The worker is **inert by default** — it touches
   the GPU only after you press Start on the dashboard (or POST to
   `/api/benchmarks/queue`).

4. **A scoped sudo seam** — `/etc/sudoers.d/hal0-benchctl` lets the
   `hal0` user stop/restart GPU consumers through the `hal0-benchctl`
   helper only. The bench units are deliberately *not* sandboxed with
   `NoNewPrivileges` because that would block this seam.

</Steps>

## Scheduled runs are polite

A `--scheduled` run only proceeds inside the `[window]` defined in
`/etc/hal0/bench/window.toml` (default Sun 03:00–07:00 local) and only
when the box looks idle: minimum idle minutes, battery and thermal checks.
Any failed check makes the tick exit cleanly and try again next week —
a scheduled run never preempts live inference.

<Aside type="note">
The bench runner records the **observed** engine image from the running
slot, so results are always attributed to the exact container your slots
serve — there is no separate bench runner image to keep in sync.
</Aside>

## Where results go

- `hal0 bench results` / `history` query the local `bench.db`.
- `hal0 bench publish` regenerates `roster.json` for consumers.
- The dashboard's **Benchmarks** page shows the roster, individual runs,
  agentic eval scores, and the run queue, live from `/api/benchmarks/*`.
- `hal0 bench reindex` rebuilds `bench.db` from `records.jsonl` if the
  derived store is ever lost — the JSONL is the durable record.
