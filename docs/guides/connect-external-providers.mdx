hal0 can route requests to **external upstreams** — third-party
OpenAI-compatible APIs like OpenAI, Anthropic, OpenRouter, Google AI
Studio, DeepSeek, MiniMax, Ollama, or any custom endpoint. Manage them
in the dashboard under **Models → Providers**, or with `hal0 upstream`, a
thin client over `/api/upstreams` / `/api/providers` backed by a built-in
catalogue of provider templates. Both manage the same providers; the dashboard
sections come first, the CLI follows.

## Add a provider in the dashboard

Open **Models → Providers** and choose **Add provider**. One dialog does the
whole job:

<Steps>

1. **Pick a provider.** Each tile is a template with the base URL and sign-in
   style filled in. Choose **Custom OpenAI-compatible** for anything that is
   not listed, and enter its address yourself.

2. **Check the name, the address and the key.** The name becomes the prefix
   you and your agents use, for example `deepseek/model-id`. Paste the key
   into the key box. It is stored on the hal0 box only and is never shown
   again.

3. **Choose Check connection.** hal0 asks the provider for its model list
   without saving anything. A rejected key, a wrong address or an unreachable
   provider is reported in the dialog, and nothing is saved. A good answer
   shows how many models the provider offers.

4. **Tick the models to switch on.** The ones the template recommends are
   ticked for you. Use **Select all**, **Recommended only**, or the search box
   (shown when the list is long) to change the picks. You can also correct a
   model's type, such as chat or embedding, before adding it. Only ticked
   models can be called; the rest stay in the list, switched off.

5. **Choose Add provider.** hal0 creates the provider, then stores the key,
   and selects the new provider in the list.

</Steps>

Each provider gets its own key slot, named after the provider: a provider
called `deepseek` keeps its key as `DEEPSEEK_API_KEY`, and a second one called
`deepseek-2` keeps its own as `DEEPSEEK_2_API_KEY`. Two providers made from the
same template never share or overwrite a key. If the name would clash with a
reserved variable, or the variable is already in use, hal0 adds a prefix or a
number.

If the key cannot be saved, the dialog stays open and says that the provider
was added but the key was not. Fix the key and choose **Try saving the key
again**, or close the dialog and add the key later from the provider's page.
**Add without checking** adds the provider with no models on, for a provider
that is not reachable yet; refresh its model list once it is.

## Switch models on and off

Each provider is a section of the list. Select its header to open it. Models
that are on come first, then the ones that are available. Every row has a
switch: flipping it takes effect at once, and a model that is off cannot be
called. A long list shows 25 available models at a time; choose **Show 25
more** for the next page. The search box looks through every provider, even
the closed ones, and the **Show** and **Type** filters narrow the list.

Select a model's name to see its details on the right: the name to call it by
(`<provider>/<model>`), its type, context size and price. **Edit** lets you
correct the context size and the prices stored for the model.
A **gone** tag means the provider answered and no longer offers that model; a
**recommended** tag marks the template's suggestion. A provider without a key
cannot load its model list, so nothing is tagged gone there and the panel says
the model's status is unknown. Add a key, then choose **Refresh model list**.
When two providers come from one template, the header shows the template name
followed by the provider's own name.

Select a provider's header to act on the whole provider. Its facts and actions
appear in the panel on the right:

- **Test connection** checks that the address and key still work.
- **Refresh model list** asks the provider again. New models arrive switched
  off, so nothing starts being routed without you. If the provider cannot be
  reached, hal0 says so and keeps showing the last known list. **Refresh model
  lists** at the top of the tab does this for the providers that are switched
  on, use per-model switches, and have a key stored or need none. It says how
  many lists it refreshed and how many could not be reached; a provider that
  is switched off, still awaiting **Choose models**, missing its key or managed
  by an agent is skipped.
- **Replace key** (or **Add key** when none is stored) writes a new key under
  the provider's own key slot. A banner on the provider's section offers
  **Add key** too when no key is stored.
- **Remove** deletes the provider. Its models stop being callable; the stored
  key stays on the box.
- **Routes requests** switches the whole provider on or off for routing (the
  `enabled` field, the same as `hal0 upstream update` with `--enabled` and
  `--disabled`). A provider that is switched off is not called at all, and its
  section shows an **off** chip, "switched off" instead of the count of models
  that are on, and a **Switch on** button. Its model switches keep their state,
  so switching the provider back on restores what you had.
- **Shown in app model pickers** controls whether the provider's models appear
  in the model lists inside hal0's apps.

### A provider added before per-model switches

Providers created by an older hal0 route every model the provider lists. Their
section says so, with a **Choose models** button, and their switches are
locked. **Choose models** asks the provider for its list and converts it: every
model it offered is switched on, except any that your old filters hid, and you
switch off the ones you do not use. If the
provider cannot be reached or lists nothing, hal0 leaves the provider as it was
and tells you why; fix the address or key and try again.

### Providers managed by an agent

Providers that an agent creates, such as the Hermes profiles, are listed at the
end of the tab as read-only. Change them from the agent.

### Where the Endpoints panel went

**Slots → Endpoints** now shows only your local endpoints, with a link to
**Models → Providers**. The panel that added and edited remote providers moved
into the Providers tab, and the old address (`#models/upstream`) forwards
there. The pinned-id, include and exclude filter editor is gone from the
dashboard: switch models on and off instead. The CLI filters below still work
for a provider that has not been converted.

## The CLI in short

Create the upstream, store its key, check it, then enable the models you want
routed.

1. `hal0 upstream create openrouter --catalog openrouter --auth-env OPENROUTER_API_KEY --api-key ...`
2. `hal0 upstream test openrouter`
3. `hal0 upstream refresh openrouter` — fetch the provider's model list and store one row per model.
4. `hal0 upstream enable openrouter <model>` — route a model; `hal0 upstream models openrouter` shows the rows.

## See what's available

```sh
hal0 upstream list                 # your configured upstreams
curl http://localhost:8080/api/providers/catalog
```

The catalogue is a static reference of known provider templates —
`openai`, `anthropic`, `openrouter`, `google_ai_studio`, `deepseek`,
`minimax`, `groq`, `mistral`, `ollama` (local), `hal0_peer` (another hal0
box; you enter its URL) and a generic `custom` OpenAI-compatible
entry — each carrying its default base URL and auth style, plus suggested
models. The full table is in
[Providers, profiles & devices](/docs/reference/providers-profiles-devices/#b-remotecloud-upstream-provider-catalog).

## Create an upstream from the CLI

```sh
hal0 upstream create openrouter \
  --catalog openrouter \
  --auth-env OPENROUTER_API_KEY \
  --api-key sk-or-...
```

<Steps>

1. **`name`** (positional) — a unique id you'll reference everywhere else.

2. **`--catalog`** — the catalogue id to seed defaults from (base URL,
   auth style). Omit for a fully custom entry and pass `--url` /
   `--auth-style` yourself.

3. **`--url`** — override the base URL.

4. **`--auth-style`** — `bearer` (`Authorization: Bearer <key>` — the
   default for most OpenAI-compatible endpoints, including OpenRouter and
   Ollama), `header` (custom header), or `none` (unauthenticated, e.g. a
   local Ollama).

5. **`--auth-header`** — the header name, when `--auth-style header`.

6. **`--auth-env`** — the **name** of the environment variable that will
   hold the secret. The key itself never lands in TOML — only the
   env-var name does.

7. **`--api-key` / `-k`** — write the credential in the same call. This
   posts to `/api/providers/{name}/credentials` and binds it to the
   upstream's declared `auth_value_env`, so you can't accidentally write
   a key the upstream won't read.

8. **`--timeout`** — request timeout in seconds (default `300`).

9. **`--advertise-models` / `--hide-models`** — whether this upstream's
   models appear in the aggregated model list.

10. **`--enabled` / `--disabled`**.

</Steps>

<Aside type="note">
The `anthropic` preset points at Anthropic's OpenAI-compatible endpoint
(`https://api.anthropic.com/v1`, bearer auth), so it needs no proxy. That
layer is meant for testing and comparison: thinking output and prompt caching
are not available through it.
</Aside>

A new upstream registers live, with no restart. Without a `models` list it is
*uncurated* and keeps routing whatever the provider advertises until you run
`hal0 upstream refresh` (see [Choose which models are routed](#choose-which-models-are-routed)).
In the dashboard, **Add upstream** on Slots → Endpoints (also reachable from
Models → Upstream Models) does the same create; enabling individual models is
done with the CLI, the API or the MCP tools below, not from the dashboard.

## Check a provider before saving it

`hal0 upstream probe` tests a base URL and key and lists what the provider
offers, without writing anything:

```sh
export OPENROUTER_API_KEY=...
hal0 upstream probe --catalog-id openrouter --key-env OPENROUTER_API_KEY
hal0 upstream probe --url http://localhost:11434/v1 --auth-style none
```

It prints whether the provider answered (HTTP status and latency), any
rate-limit headers the preset knows about, and a table of models. Pass
`--catalog-id` or `--url`; the key is read only from the environment variable
named by `--key-env`, never from an argument, and is not stored or printed.
The command exits `1` when the provider does not answer. Over the API this is
`POST /api/providers/probe`, which accepts JSON only.

## Update, test, and remove

```sh
hal0 upstream update openrouter --timeout 120
hal0 upstream test openrouter
hal0 upstream show openrouter
hal0 upstream advertise openrouter on # required on|off — set /v1/models visibility
hal0 upstream delete openrouter
```

`test` probes the upstream's `/models` endpoint and returns a
reachability report: `{ok, status, latency_ms, models_count, error?}`. If
the declared env var is empty, the probe fails fast without making an
HTTP call.

hal0 also registers upstreams for you. When Hermes is installed, each Hermes profile with an API key appears in **Models → Providers** and in `GET /api/upstreams` as `hermes` or `hermes.<profile>`, with `managed_by` set to `agent:hermes`. These entries are pinned and read-only: an update or delete request is refused with `400 upstream.protected`. Change them on the Hermes side; see [Talking to Hermes](/docs/guides/open-webui#talking-to-hermes).

## Choose which models are routed

Once an upstream has per-model rows (it is *curated*), only the rows that are enabled
route; everything else the provider lists is reachable only after you enable it.

```sh
hal0 upstream models openrouter                       # table: id, enabled, type, context, prices
hal0 upstream enable openrouter qwen/qwen3-coder      # route a model
hal0 upstream disable openrouter qwen/qwen3-coder     # stop routing it
hal0 upstream refresh openrouter                      # refetch the list; store new models (off)
export OPENROUTER_API_KEY=...                         # a probe reads its key from the environment
hal0 upstream probe --catalog-id openrouter --key-env OPENROUTER_API_KEY
```

An upstream created without `models` is uncurated: it routes whatever the provider lists,
as before. `refresh` converts it once the provider answers, writing one row per model. If
the provider cannot be reached or lists nothing, the row is left as it is and the `warning`
in the response (printed by the CLI) says why; fix the URL or key and refresh again. Over
the API, `POST /api/upstreams` with a `models` array (even `[]`) creates a curated upstream
directly. On a curated upstream, `refresh` stores each model the provider newly offers as a
switched-off row, so it shows in `hal0 upstream models` ready to enable; hal0 does the same
once at every start.

Request a model by its canonical id, `<provider>/<id>`, which splits on the first `/`
(`openrouter/qwen/qwen3-coder` is provider `openrouter`, model `qwen/qwen3-coder`). A bare id
works when exactly one enabled model has it. When `<provider>/<id>` has no enabled row on that
provider, the whole string is tried as a bare id first, so `openai/gpt-5` still reaches an
OpenRouter that lists it. A slot or an upstream that has not been converted keeps serving the
ids it advertises. Routing reads only the stored rows, never the provider's live list. The
full order is in
[How a model id is routed](/docs/reference/providers-profiles-devices/#how-a-model-id-is-routed).

| Response | Code | What to do |
|---|---|---|
| 404 | `upstream.model_not_enabled` | Nothing else serves the request, and either you named `<provider>/<id>` and that provider has no enabled row for it, or a bare id is stored switched off on a curated provider. Enable it under **Models → Providers** or with `hal0 upstream enable <name> <model>`. A bare id on embeddings, rerank, speech, transcription or images, or a hal0 alias such as `tts-1`, is not refused this way: a local slot serves it. |
| 400 | `upstream.model_ambiguous` | A bare id is enabled on several providers: the message lists the canonical ids; send one of them. |

A key you type may start with `Bearer `: hal0 strips it only for `bearer` auth on the
`Authorization` header, where it adds the prefix itself. For a custom header (`--auth-style
header`) the key is sent exactly as typed.

## Curate which models are advertised

<Aside type="note">
Filters apply only to an uncurated upstream. A curated upstream lists exactly
its enabled models, and a filter on it is refused; use
`hal0 upstream disable` instead.
</Aside>

`[upstream.model_filters]` narrows which of an upstream's models show up
in the aggregated `/v1/models` catalog, without touching dispatch — a
model can be filtered out of the catalog and still be reachable by its
explicit id.

```sh
hal0 upstream update openrouter --include 'anthropic/*' --exclude '*:free'
hal0 upstream update openrouter --model gpt-4o-mini
hal0 upstream update openrouter --clear-filters
```

- **`--model`** (repeatable) — allowlist one exact model id.
- **`--include`** (repeatable) — an fnmatch glob; a model is advertised if
  it's in `--model` or matches any `--include` glob (both empty means
  everything is included).
- **`--exclude`** (repeatable) — an fnmatch glob that always wins over
  `--model`/`--include`.
- **`--clear-filters`** — drop all filters and advertise everything again.

`hal0 upstream list` shows a **Filters** column summarizing what's
active per upstream. Like `--advertise-models`/`--enabled`, filter
changes apply live — no restart.

## Write a credential without recreating the upstream

```sh
hal0 upstream credentials set openrouter --key sk-or-new-key
```

`credentials set` posts to `/api/providers/{name}/credentials` and binds
the key to the upstream's declared `auth_value_env` — pass `--env-var` to
target a different env-var name instead of the upstream's default. Omit
`--key` to be prompted for it securely.

Or directly over the API:

```sh
curl -X POST http://localhost:8080/api/providers/openrouter/credentials \
  -H 'content-type: application/json' \
  -d '{"key":"OPENROUTER_API_KEY","value":"sk-or-..."}'
```

The `key` must match the upstream's declared env-var name exactly. The
endpoint writes the value atomically to the API's env file with `0600`
permissions, updates the running process environment immediately, and
**never echoes the secret back** — the response carries
`"value": "***REDACTED***"`.

The dashboard's Settings → Secrets panel writes the same file with
presets for the common providers plus a paired AWS Bedrock entry, but it
doesn't check the name against any upstream's declared env var — type the
exact name your upstream expects.

<Aside type="caution">
The hal0 API ships with optional key auth (`hal0 auth status` /
`hal0 auth require`): with auth off it binds LAN-open and the credential
file is LAN-writable. Enable auth on any shared network — the secrets
surface requires the admin key once it is on — and reverse-proxy the host
if it needs to be exposed beyond the LAN.
</Aside>

## Troubleshooting

| Symptom | Cause and fix |
|---|---|
| `refresh` prints a `warning` and the row stays uncurated | The provider returned no models. Check the URL and key (`hal0 upstream test <name>`), then refresh again. |
| `404 upstream.model_not_enabled` | The model's row is off, or no row exists. `hal0 upstream models <name>` shows the rows; `hal0 upstream enable <name> <model>` routes it. |
| `400 upstream.model_ambiguous` | A bare id is enabled on several providers. Send `<provider>/<id>`. |
| A new model the provider released is missing | Run `hal0 upstream refresh <name>`; it appears as a switched-off row. |
| `probe` says the environment variable is not set | Export the variable in the same shell that runs the command. |
| `409 upstream.protected` on a model or refresh call | The upstream is managed by an agent, backed by a slot, or reserved. Change it at its source. |

## Picking up changes

Credential writes, and every `hal0 upstream create` / `update` / `delete`
/ `advertise` / `enable` / `disable` / `refresh` call, apply to the running `hal0-api` process immediately —
no restart needed. Creating an upstream registers it live; patching one
(visibility flags, auth, URL, timeout, model filters) applies live too. A
patch that flips `advertise_models` or `enabled` punches only that
upstream's entry in the per-upstream model cache (and only if it's
already cached), so the next `/api/upstreams` or `/v1/models` request
refetches it. The composite `/v1/models` catalogue itself is served from
a separate, module-level TTL cache that per-upstream visibility patches
do not touch — it's refreshed by its own TTL (default 5s) and by slot
readiness events, not by upstream PATCH calls.

The one case that still needs a restart is a **hand-edit** of
`upstreams.toml` outside the CLI/API — nothing watches that file for
changes, and `hal0 config reload` only re-reads `hal0.toml`, not
`upstreams.toml`. Run `hal0 config validate` after a hand-edit, then
`sudo systemctl restart hal0-api` to pick it up.
