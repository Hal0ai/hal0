# Model handling: ODS vs. hal0

Scope: selection, storage, download, switching, rollback, and discovery. ODS paths are relative to `/home/user/ods/ods/` unless given in full; hal0 paths are absolute under `/home/user/hal0/`.

## A. ODS mechanism

### A.1 Catalog + selection

`config/model-library.json` (schema `"version": 2`, 56 entries) is the single versioned catalog. Each entry carries `id`, `family`, `gguf_file`/`gguf_url`/`gguf_sha256`, `size_bytes`/`size_mb`, `vram_required_gb`, `context_length`/`max_context_length`, `quantization`, `specialty`, `tokens_per_sec_estimate`, `llama_server_image`, and — the distinctive part — an `app_compatibility` block per consumer app (`openai_chat`, `hermes_talk`, `perplexica`, `agent_viability`, …) with `status`, `label`, `reason`, `evidence` (a path into a fleet-test run directory), `recordedAt`, `productSha`/`harnessSha`, sometimes `hostScope`. This is real fleet-test provenance, not hand-written metadata: `qwen3.5-2b-q4`'s `hermes_talk.status` is `verified` across six named hosts while `openai_chat` is `unsupported_until_revalidated` because two consumers truncated output on one host (`config/model-library.json:9-63`). Some entries also carry `publisher_evidence`, `quality_evidence`, `source_evidence`, `rejected_artifacts`, and `runtime_profiles` (VRAM/arch-gated alternate launch recipes).

`scripts/select-model.py` (562 lines) is a deterministic, offline selector invoked by the installer and by `ods model swap`. It loads only `source ∈ {"", "curated"}` records (`load_catalog`, `:121-131`) — HF imports in `data/model-imports.json` are excluded from auto-selection. `usable_memory_gb()` (`:134-144`) computes a memory envelope: unified-memory hosts get `max(ram_gb*0.55, 2.0)` GB, CPU/no-GPU hosts get `min(max(ram_gb*0.35,3.0),8.0)` GB, else raw VRAM/1024. `selector_required_memory_gb()` (`:177-182`) adds an estimated KV-cache footprint on top of on-disk size: `estimated_param_billions()` (`:151-167`) infers B-params from declared fields or a regex on id/name/gguf filename, then `estimated_context_kv_gb()` (`:170-174`) scales `params_b*0.12` (clamped 0.35–3.5 GB) by `context/32768`. `score_model()` (`:237-259`) ranks by specialty weight (`Code=4.4 > Quality=4.1 > General=3.8 > … > Bootstrap=1.0`), a family-affinity bonus, a context bonus, a size term, and a headroom penalty above 92%/98% memory utilization. `MODEL_PROFILE` is `qwen | gemma4 | auto` (`:38-44`), `auto` resolving to `qwen` on `CLOUD/0` tier and `gemma4` elsewhere (`:68-73`); `family_allowed()` (`:230-234`) filters the catalog to one family.

**Unified-memory routing** (`arch_policy_model`, `:326-364`): on the `qwen` profile, when the tier is `NV_ULTRA` on `arm64` (Spark/GB10) **or** `memory_type == "unified"` and the otherwise-selected model is `qwen3-coder-next` (`is_spark_aarch64_excluded_model`, `:367-372`), the selector force-substitutes `qwen3.6-35b-a3b-ud-q4` under policy tag `unified-memory-coder-next-a3b-v1`, because "qwen3-coder-next produces all-`?` tokens on every chat completion" on those backends (`:24-31,100-108`). Output is JSON or `--env` shell assignments (`LLM_MODEL`, `GGUF_FILE`, `GGUF_URL`, `GGUF_SHA256`, `MAX_CONTEXT`, `LLM_MODEL_SIZE_MB`, `MODEL_RECOMMENDATION_*`, and, when a `runtime_profile` matched, `MODEL_RUNTIME_PROFILE*`/`LLAMA_SERVER_IMAGE`).

`installers/lib/tier-map.sh` (393 lines) is the **static**, non-catalog tier table actually used for install-time defaults and `ods model swap`: `set_qwen_tier_config()`/`set_gemma4_tier_config()` hard-code `LLM_MODEL`/`GGUF_FILE`/`GGUF_URL`/`GGUF_SHA256`/`MAX_CONTEXT`/`LLM_MODEL_SIZE_MB` per tier (`CLOUD, ARC, ARC_LITE, NV_ULTRA, SH_LARGE, SH_COMPACT, 0-4`). Two in-source incident notes matter: the `NV_ULTRA` block (`:92-118`) documents the same coder-next bug on Blackwell-aarch64, and the `SH_LARGE` block (`:119-138`) documents a live 2026-05-19 Strix Halo repro ("bootstrap-upgrade downloaded the 48.5GB coder-next-Q4_K_M.gguf, stalled at 91%, and the model would not have worked on this hardware even if the download completed") and the fix (substitute `Qwen3.6-35B-A3B-UD-Q4_K_M`, ~21.1 GB). `tier_to_model()` (`:333-393`) is what `ods model swap <tier>` uses to resolve a tier without re-running detection.

`config/backends/{amd,nvidia,apple,cpu}.json` are small per-backend service contracts (engine, API port/path, provider URL, runtime image) — `amd.json:1-21` pins `llm_engine: lemonade`, `lemonade-server:v10.2.0`, `linux_backend: rocm` / `windows_backend: vulkan`. `config/hardware-classes.json` maps `(platform_id, gpu_vendor, memory_type, vram_mb range)` → `{backend, tier, compose_overlays}`; `strix_unified_large` matches AMD unified memory ≥ 92160 MB → `SH_LARGE`+`docker-compose.amd.yml` (`:3-18`). `docs/CAPABILITY-PROFILE.md` documents the derived `CAP_*` env contract install-core consumes for tier/backend/overlay normalization.

`installers/lib/llama-memory-budget.sh` (56 lines) is narrower than its name: it reads Docker-visible memory, takes min(host, Docker) RAM, and derives the NVIDIA llama-server container memory *limit* — reserve 3 GiB under 16 GiB RAM else 4 GiB, clamp usable to [1,64] GiB (`:33-56`). Context/batch sizing itself lives in `tier-map.sh`'s static `MAX_CONTEXT`, not a separate budgeting module.

`docs/MODEL-SWITCHBOARD.md` (938 lines) is a **PR plan**, not all-implemented status: its header says the state store/data-plane/reconciler/consumer-migration work "are not implemented" as of its audit date (`:5-7`), but `extensions/services/model-router/app/main.py` (PR 3's target) exists and is wired into every non-cloud compose file (A.4) — the doc is architecture rationale/roadmap; cite code for current truth.

`docs/ENGINE-PROVIDER-MODES.md` defines four provider modes — `local`, `cloud` (LiteLLM → remote APIs), `hybrid` (local-first + cloud fallback), `lemonade` (ODS-managed or external) — with a shared env contract (`ODS_MODE`, `LLM_BACKEND`, `LEMONADE_EXTERNAL`, `LEMONADE_BASE_URL`/`LEMONADE_CONTAINER_BASE_URL`, `LEMONADE_API_BASE_PATH=/api/v1`) and a capability-proof contract (liveness/chat/embeddings/STT/TTS/rerank/stats must each pass through the app-visible route or the mode fails readiness) (`:14-60`). LiteLLM (`config/litellm/{local,lemonade,hybrid,cloud,switchboard}.yaml`) is the OpenAI-compatible front door in every mode.

### A.2 Storage + download

Models live at `data/models/*.gguf` (one file per model, flat). `scripts/pre-download.sh` (425 lines) is **legacy/independent**: its own `nano/edge/pro/cluster` tiers map to *non-GGUF* HF repo ids (e.g. `Qwen/Qwen2.5-32B-Instruct-AWQ`) via `huggingface_hub.snapshot_download` (`:162-176`) — it shares no tiers/ids/filenames with `config/model-library.json` and has no SHA256 check. Not the production path.

The real download path is `installers/phases/11-services.sh`: checks an existing file's SHA256 against `GGUF_SHA256` and deletes-and-redownloads on mismatch (`:697-722`); downloads with `curl -fSL -C - --connect-timeout 30 --max-time 3600 --retry 3 --retry-delay 5 --retry-all-errors` into a `.part` file so an interrupted install resumes (`:751-762`); on curl failure falls back to `scripts/download-hf-artifact.py` (89 lines), which parses a `/resolve/<rev>/<file>` URL and calls `huggingface_hub.hf_hub_download` — the documented `hf_xet` fallback for Xet-backed HF files plain curl can fail against (`:1-7,36-56`); re-verifies SHA256 after either path and hard-fails the install if it never passes (`:791-829,894-897`). `scripts/download-hf-snapshot.py` (74 lines) is the same helper for whole-repo snapshots.

`installers/lib/bootstrap-model.sh` pins the fast-start model as constants (`BOOTSTRAP_GGUF_FILE=Qwen3.5-2B-Q4_K_M.gguf`, sha, `LLM_MODEL=qwen3.5-2b`, `MAX_CONTEXT=65536`, `:16-24`); `bootstrap_needed()` (`:34-52`) gates on tier>0, full model absent, no `--no-bootstrap`, not offline/cloud/external-Lemonade. `.env` gets `GGUF_FILE`/`LLM_MODEL`/`MAX_CONTEXT`/`MODEL_RECOMMENDATION_*` from `select-model.py --env`. `config/llama-server/models.ini` is a plain per-model INI stanza (`installers/phases/11-services.sh:929-939`):
```ini
[${LLM_MODEL}]
filename = ${GGUF_FILE}
load-on-startup = true
n-ctx = ${MAX_CONTEXT}
```
Background hot-swap: phase 11 backgrounds `scripts/bootstrap-upgrade.sh` (3412 lines) with the full model's file/url/sha/name/context (`installers/phases/11-services.sh:1328-1362`); it downloads, re-verifies sha (`:242-275`), and hot-swaps llama-server with minimal downtime, safely re-triggerable by `ods start`/`ods restart`/re-install on failure.

No mmproj/vision-projector handling exists anywhere in ODS's model catalog, download scripts, or `models.ini` generation — ODS's local models are text-only.

### A.3 Switching + rollback

`ods model {current,list,swap}` (`ods-cli:3584-3710`): `current` reads `.env`'s `LLM_MODEL`/`TIER`; `list` prints the static tier table; `swap <tier>` resolves the tier via `tier-map.sh`, looks up the catalog `id` for that tier's `GGUF_FILE` via `jq`, requires the file already downloaded (`:3623-3625`), then POSTs `{model_id, tier, context_length}` to the **host agent's** `POST /v1/model/activate` (bearer-authed, key fed over stdin so it never appears in argv), treating anything but HTTP 200 + `status:"activated"` as failure (`:3635-3697`).

The activation transaction, `_do_model_activate()` in `bin/ods-host-agent.py` (12,834 lines total; handler at `:7635`), snapshots every file it's about to touch before mutating — `.env`, `models.ini`, `config/litellm/{lemonade,local,switchboard}.yaml`, `config/model-router/endpoints.json`, the activation receipt, Hermes/OpenCode/Perplexica config, plus container state (`:7836-7876`). `restore_backups()`/`restore_previous_runtime()`/`rollback_and_prove()` (`:7878-8020`) implement rollback: on any failure past the mutation point, every snapshot is restored, the previous runtime relaunched, and — critically — the **previous** model must itself re-pass identity+completion proof before rollback is reported successful (`:7967-8020`); a rollback that can't re-prove the old model is reported as a failed restoration, not a silent success. `installers/lib/model-lifecycle-lock.sh` is a `flock`-based, per-install-dir advisory lock so a background bootstrap-upgrade and a foreground `ods model swap`/install can never race on the same files (`:15-83`).

`docs/MODEL-MANAGEMENT.md` (466 lines) documents the six-verb dashboard flow (discover → download → load → use-through-every-app → restore → delete): multi-GPU reassignment re-runs the topology planner when a target model's VRAM envelope exceeds the current GPU subset (`:137-160`); context above a model's declared max is allowed with a warning but must pass runtime identity+context proof or roll back (`:101-131`); HF imports pin an immutable revision and reject projectors/adapters/split files (`:38-70`); the `.env`/`models.ini` fields ODS's activation transaction owns are read-only in the Dashboard settings editor specifically so a manual edit can't bypass verification/rollback (`:194-199`).

### A.4 The model-router service

`extensions/services/model-router/app/main.py` (1126 lines) is fully implemented, not just planned. It is the Switchboard's "PR 3" data plane: a public stable alias (`ods/current`, `default`) every ODS app can hardcode, decoupling app config from the concrete model. Key mechanics: reads `data/model-state.json` with strict shape validation and only trusts an `active` route with completed identity+completion proof and a monotonic `seq`/`routeSeq` (`_has_verified_active_route`, `:493-538`) — regressed/mutated-at-same-sequence state is rejected; `endpointId` resolves only through a read-only, install-generated allowlist so state can never name an arbitrary upstream (`:317-347,541-562`); forwards only `/v1/chat/completions|completions|responses` (`:84-88`), stripping client-auth headers and injecting its own upstream credential; rewrites `model` back to the requested alias on every response and every SSE chunk (`_SSERewriter`, `:680-786`) while emitting `X-ODS-{Request-Id,Requested-Model,Routed-Model,Backend,Route-Seq}` headers; bounded queue-during-reload returns HTTP 503 `model_swap_in_progress` with `Retry-After` on timeout (`:894-935`); signed fleet-probe route evidence (HMAC-SHA256 over a UUID, `:605-620`) is recorded in a bounded TTL'd map behind an internal bearer-authed endpoint, never prompts/generations/credentials.

It exists **alongside** LiteLLM, not instead of it: at design time LiteLLM's alias-to-model mapping was a static YAML mount with no DB-backed management plane, so changing `ods/current` would otherwise mean rewriting LiteLLM's YAML and restarting it on every swap (`docs/MODEL-SWITCHBOARD.md:94-98`). model-router is the small, ODS-owned, hot-reloadable indirection layer; LiteLLM keeps owning auth/OpenAI-compat/multi-provider policy and always points `ods/current`/`default`/`"*"` at `http://model-router:9099/v1` (confirmed live in `config/litellm/switchboard.yaml`, `docker-compose.base.yml:225,299-303,328`).

`extensions/services/llama-server/` ships only a manifest (no `compose.yaml` — its compose lives in `docker-compose.base.yml` as a core service); the manifest declares `aliases: [llm]` (so `ods restart llm` works), `port: 8080`, `health: /health`, `gpu_backends: [amd, nvidia]`.

### A.5 AMD Strix Halo specifics

`config/backends/amd.json` pins the Lemonade runtime: `ghcr.io/lemonade-sdk/lemonade-server:v10.2.0`, `linux_backend: rocm`, `windows_backend: vulkan`, health at `/api/v1/health`. `config/gpu-database.json` has exact device matches: `strix_halo_395` (`device_ids: ["0x1586"]`, "Radeon 8060S"/"RYZEN AI MAX+ 395"/"Strix Halo", `memory_mb: 98304`, `rdna-3.5`, `bandwidth_gbps: 256`, `compute_units: 40`) → tier `SH_LARGE`; `strix_halo_390` (RYZEN AI MAX 390, `memory_mb: 65536`) → `SH_COMPACT` (`:29-68`). `config/hardware-classes.json` gates `SH_LARGE` at `min_vram_mb: 92160`, `SH_COMPACT` at `65536` (both AMD, unified, linux/wsl).

`SH_COMPACT` ships `qwen3-30b-a3b` (18.6 GB, 128K ctx); `SH_LARGE` ships `qwen3.6-35b-a3b` (21.1 GB UD-Q4_K_M, 128K ctx) — **not** `qwen3-coder-next`, per the routing note in A.1/A.3 (`installers/lib/tier-map.sh:119-146`). `docs/LEMONADE-SDK-COMPAT.md` documents wrapping an already-running Lemonade SDK install (`--use-existing-lemonade`) without ODS managing that process or downloading its own GGUF, auto-detecting the first non-image model from Lemonade's `/api/v1/models` unless `LEMONADE_MODEL` is set, with Phase 12 proving the model via a real chat completion (`:90-118`). `docs/AMD-ODS2-GAMMA-BRIEF.md` is a go-to-market/appliance-onboarding deck (QR setup, magic-link auth, mDNS) with Strix Halo as flagship demo hardware and no model-selection content of its own; it self-flags "code present, packaged appliance images need end-to-end validation."

**The one fact hal0 most needs from this domain**: ODS's own fleet testing found `qwen3-coder-next` (an 80B-A3B MoE, ~48.5 GB Q4_K_M) produces garbage output ("all-`?` tokens on every chat completion") specifically on unified-memory backends — verified independently on Strix Halo (AMD, `gfx1151`) and NVIDIA Grace-Blackwell aarch64 (Spark/GB10) — and now hard-routes both away from it to `Qwen3.6-35B-A3B-UD-Q4_K_M` (`installers/lib/tier-map.sh:100-138`; `scripts/select-model.py:24-31,326-372`). The model stays in the catalog (`install_recommendation: true`) for manual/discrete-GPU use; it's excluded only on unified memory.

## B. hal0 today

**Registry** (`src/hal0/registry/`): `store.py` (624 lines) is mid-cutover — `TomlModelRegistry` is the original atomic-tmpfile+fsync+`os.replace` implementation (`_atomic_write`, `:305-341`) plus a cross-process `flock` on a stable-inode sidecar (`registry_write_lock`, `:101-134`) and an mtime-cache, but the public name `ModelRegistry` is rebound at the bottom of the file to `SqliteModelRegistry` (`:594-612`) — SQLite is the actual runtime source of truth since the "ML-1" migration, TOML kept alive only for `export`/`import-sqlite`. `gguf_header.py` (379 lines) mmaps up to 8 MiB and walks the real GGUF v1-v3 KV block rather than trusting the filename, extracting `general.architecture`, `general.embedding_length`, `general.tags`, `<arch>.context_length`, `<arch>.pooling_type`, `<arch>.attention.causal` (`:1-36,85-90`). `detect.py` (579 lines) layers capability inference cheapest-first: header `pooling_type` (high confidence) → tag heuristics → filename tokens (medium/low), extracts quantization from `general.file_type` or a filename regex, and `_hf_repo_name_from_path()` (`:214-229`) walks up a path looking for a `models--ORG--REPO` HF-cache dir to recover `org/repo` when scanning blob-hash-named cache files directly. `discover.py` (717 lines) is the filesystem scanner (`POST /api/models/scan` + startup auto-scan), skipping HF-cache internals and non-standalone accessory dirs (`mmproj`, `vae`, `clip`, `controlnet`, …).

**model_fit / capacity**: `model_fit.py` (118 lines) — `evaluate_model_fit()` is a pure, reason-bearing verdict (`allowed|blocked|degraded`) combining model classification, slot-type match, registry resolvability, and profile/device-class compatibility (NPU/image mismatches hard-block, GPU/CPU degrade). `slots/capacity.py`'s `gtt_feasibility_verdict()`/`estimate_file_size_kv_mb()` (`:177-282`) is a **live** memory-fit check: it reads AMD `amdgpu` sysfs GTT counters at request time, explicitly because on a UMA/LXC host `/proc/meminfo` can lie ("the actual weight allocation fails with `cudaMalloc failed: out of memory`", `:222-228`), returning `fits|tight|exceeds|exceeds_total|unknown` — advisory only, never blocking. `POST /api/models/feasibility` (`src/hal0/api/routes/models.py:604-692`) batches this per (model, ctx) pick for the picker UI, degrading any bad row to `"unknown"` rather than 500ing the batch.

**profiles/**: profiles are device-agnostic "logical tune" templates (chat template, sampler, KV type, batch sizes) — explicitly not hardware flags (NGL/threads/tensor-split live on the slot). 10 shipped seeds cover one profile per runtime family plus generic `chat`/`cpu-chat`/`embedding`/`reranking`; 8 workload variants (long-context, dense, MoE, named family recipes like `chadrock-dense` with `--no-mmproj`/`mtp=true` toggles tuned to a real model card) are demoted to `legacy_seed_profiles.toml`, auto-migrated once into an existing install as editable custom entries, never re-injected fresh. `-fa auto` (never `-fa on`) is a deliberate policy so a generic profile never forces an unschedulable fused-attention kernel.

**capabilities/**: a UX overlay grouping flat slots into "capability cards" (`embed`=embed+rerank, `voice`=stt+tts, `img`) via a `_CHILD_TO_SLOT` bridge; selections persist in `capabilities.toml`, and `CapabilityOrchestrator.apply()` reconciles against `slots/*.toml` through `slot_config.SlotConfigStore` (compute-only `apply()` → `ChangeSet`, atomic `commit()`/`revert()` across *both* files). NPU picks (`device=npu`) don't spawn a standalone slot — they drive one shared `flm serve` anchor serving chat+embed+ASR coresident ("NPU trio"), a multiplexing model ODS's single-llama-server design has no equivalent of. **slot_config/** is the single reconciled-write owner for both files.

**API routes**: `models.py` exposes `GET /api/models`, `GET /api/models/catalogue`, `POST /api/models/scan{,/preview}`, `POST /api/models/add-from-path`, `POST /api/models` (register), `POST /api/models/validate`, `GET /api/models/pulls`, `GET /api/models/updates/check` + `POST /api/models/{id}/update` (HF LFS-sha diffing against the stored sha, `src/hal0/registry/update_check.py:1-17` — "is a newer upstream build available," which ODS's pinned-revision catalog doesn't offer), `POST /api/models/feasibility`, `GET/PUT/DELETE /api/models/{id}`, `POST .../{seed-profile,default}`, `POST .../pull` + `GET .../pull/{status,stream}` (SSE) + `POST .../pull/cancel`, `POST /api/models/inspect`. `hf.py` adds `GET /api/models/huggingface/search` (thinner than ODS's — see D).

**Download** (`src/hal0/registry/pull.py`, 2169 lines): per-file streaming SHA256 (computed while downloading, `:739`), true HTTP `Range` resume via a `.part`+`.part.json` sidecar keyed by model id *and* filename (`:546-610`), and — where curl-based ODS only verifies when a hash is pre-pinned in its own catalog — hal0 extracts HF's own advertised LFS sha256 off `X-Linked-ETag` (`:659-684`) so an unpinned community pull still gets verified against what HF claims to serve. `PullFile.kind: "model"|"mmproj"` and a documented two-file pull shape (`:128-152,973-1111`) give hal0 **first-class mmproj/vision support ODS has none of**; `CuratedModel.mmproj_file` (`src/hal0/registry/curated.py:107-116`) lets an entry declare a companion projector downloaded alongside the main file and stamped onto `Model.mmproj` directly.

**Curated catalog** (`curated.py`, 1299 lines, 41 entries): code-shipped, not remote-fetched, "so users can't end up on an outdated pick list," sized for "Strix Halo's 100 GB unified pool." Its own header is candid about gaps: STT/TTS curated picks are blocked because Moonshine/Kokoro/VibeVoice weights don't fit the single-file pull shape yet (`:17-58`) — the wizard's STT/TTS dropdowns are empty on a fresh install. Entries carry `tool_calling: bool|None` ("verified, not aspirational") plus free-text `notes`, but no cross-app, cross-host pass/fail ledger like ODS's `app_compatibility`.

**UI** (`ui/src/dash/`): tests for `model-filters`, `model-usage`, `model-drawer` — a drawer/picker pattern rather than ODS's dedicated `Models.jsx` page, consistent with the flatter "everything is a slot" surface.

**Brain steward install-time download** (`src/hal0/install/brain_model.py`, 573 lines): provisions the dashboard sidebar-chat "steward" model (`hal0/brain`) at install time, defaulting to a hardware-blind `LFM2.5-2.6B Q8_0` GGUF loadable by both the FPX runner and stock llama.cpp. **Never fatal** (a failed pull leaves the slot model-less, not the install broken), reuses the same `run_pull_and_activate` gate as every model activation, idempotent via `already_pulled()`. A long in-source postmortem (`:53-70`) documents a real 0.9.8→1.0.0 upgrade regression where scaffold/seed-loop ordering silently reverted a successful bind — the same "write the incident, then the invariant" style as ODS's tier-map.sh notes.

## C. Better / worse / equivalent

**ODS ahead:**
1. **Fleet-verified catalog metadata** — `app_compatibility` (real run evidence, per-consumer pass/fail, host scope, product/harness SHAs) has no hal0 analogue; hal0's `tool_calling` flag + free-text `notes` cover a fraction of the same signal.
2. **HF discovery + verified import UX end to end** — `routers/models.py`'s pipeline (`_hf_gguf_artifacts`, `_hf_llm_runtime_compatibility`, Hub-parsed context length, revision pinning, projector/adapter/split-file rejection, gated-repo `HF_TOKEN` handling) is more complete than hal0's `hf.py` search endpoint plus the general pull path.
3. **Automatic rollback with re-proof of the old model** — `rollback_and_prove` requires the restored *previous* model to itself pass identity+completion proof before rollback counts as successful. hal0 has no equivalent transactional multi-file-snapshot + app-config-fanout + verified-rollback path; a failed slot load is a state-machine transition, not a snapshot/restore across config plus every downstream consumer.
4. **Stable-alias routing layer (model-router)** decoupling every app from the concrete model — hal0 has no equivalent; each slot binds to a concrete model id, and a swap is a reconfigure+restart, not an atomic alias flip behind a shared gateway.
5. **Static, pre-flight memory-envelope selection with documented hardware exclusions** (the unified-memory coder-next routing) — hard-won hardware knowledge hal0's selection logic doesn't encode anywhere (see F).
6. **Bootstrap-then-hot-swap fast start** — tiny model first, full model swapped in transparently in the background, resumable independent of the foreground install; hal0's brain-model install is "never fatal" but a single pull, not a fast-start/upgrade pair.

**hal0 ahead:**
1. **Multi-slot architecture** — ODS runs one `llama-server` process; hal0 runs N independent `hal0-slot@<name>` containers (chat/embed/rerank/stt/tts/img, plus an NPU trio) with per-slot lifecycle.
2. **Registry as real infrastructure, not a catalog** — atomic writes, cross-process `flock`, mtime-cache, one-level-deep merges with explicit null-clears, and (ML-1) a SQLite-backed store behind the same interface. ODS has nothing playing this role for locally-discovered/imported models beyond flat `data/model-imports.json`.
3. **GGUF magic-byte + KV-header parsing** for capability/context/quant, vs. ODS's filename/catalog-declared metadata only.
4. **Live, hardware-truth memory-fit check** (`gtt_feasibility_verdict` against real `amdgpu` sysfs counters) per-request, vs. ODS's static, install-time-only envelope math.
5. **mmproj/vision as a first-class, documented two-file pull shape** — ODS has none.
6. **HF update-checking** for already-pulled models (LFS sha diff) — ODS's pinned-revision catalog doesn't offer this (and arguably shouldn't — see E).
7. **Capability cards + NPU multiplexing** — a richer UX/runtime model for grouping embed/voice/image slots and sharing one NPU process across chat+embed+ASR.

**Roughly equivalent:** both do atomic-write+fsync+rename config persistence; both have real streaming-SHA256 verification with resume; both classify GGUF-vs-non-GGUF; both fall back to a sane on-disk model when the configured one is missing (ODS's `rank_models` pool vs. hal0's `fallback_local_model` heuristic) — hal0's is arguably more careful (explicit `looks_diffusion_or_nontext` guard after a real incident where a 25 GB video model was picked for a chat slot).

## D. Port candidates

## E. Do-not-copy

- **`scripts/pre-download.sh`** — stale, a different tier vocabulary and non-GGUF HF repos than the rest of ODS, no SHA256 check. Would only confuse hal0's already-cleaner pull model.
- **`docs/MODEL-SWITCHBOARD.md` as a literal process to follow** — a planning artifact whose "not implemented" disclaimer is stale (model-router *is* built); cite the current code (`extensions/services/model-router/app/main.py`) instead of the plan.
- **A single-process, single-model inference server as the target shape** — ODS's one-`llama-server`/tier-swap-the-whole-model design is a worse fit for hal0's multi-slot/capability-card architecture than what hal0 already has. Port the *verification discipline* (D.3/D.6), not the single-process shape.
- **ODS's static memory-envelope heuristics wholesale** (`estimated_param_billions`'s filename regex, `estimated_context_kv_gb`'s flat per-B-param constant) — hal0's live GTT-sysfs check is strictly better evidence where it applies; only worth adapting as a *fallback* for non-AMD/no-live-telemetry hosts.
- **Bundling fleet-evidence JSON paths (`fleet-test/runs/...`) into a public catalog file** — meaningless dead links outside ODS's private harness. If hal0 adopts the schema idea (D.2), populate `evidence` from hal0's own repo/CI.

## F. Owner decisions

1. **Verify or retire `qwen3-coder-next` as hal0's flagship Strix Halo coder pick — the single highest-value finding here.** hal0's `hal0-Max` first-run bundle tier ("100 GB Strix Halo," hal0's own reference hardware class) sets `chat.coder = Qwen3-Coder-Next-80B-A3B` (`ARCHITECTURE.md:844`), and `curated.py:260-275`'s entry is explicitly described as "Sized for a Strix Halo unified memory pool (~100 GB)" / "needs the full Strix Halo pool," pulling the same `unsloth/Qwen3-Coder-Next-GGUF` repo family ODS pulls. ODS's own fleet testing found this exact model produces "all-`?` tokens on every chat completion" on unified-memory backends including Strix Halo, verified on two different unified-memory architectures (`installers/lib/tier-map.sh:100-138`), and now hard-routes every unified-memory host away from it. **Load this model on a real Ryzen AI Max+ 395 box and check for garbled/`?`-only output before shipping `hal0-Max`** — if it reproduces on hal0's llama.cpp/ROCm build, this is a correctness bug in the flagship pick for hal0's own target hardware, not a nice-to-have.
2. **Decide whether hal0 wants a fleet-verification ledger at all.** ODS's `app_compatibility` metadata is expensive (private, six-host harness) but genuinely differentiates its catalog. hal0 could invest in an equivalent (even single-host, CI-driven) pass, or explicitly document that curated entries are unverified beyond "it loads."
3. **Decide the rollback bar for slot/model swaps.** ODS requires the *previous* model to re-prove identity+completion before a rollback counts as successful — meaningfully stronger than "the state machine transitioned back." Worth adopting the same discipline for `chat.primary`/brain slots that gate the dashboard's own usability.
4. **Decide whether mmproj pull failures need a louder story** — with mmproj already a first-class two-file pull (`pull.py:973-1111`), is a partial pull (GGUF landed, mmproj failed) ever left silently vision-less rather than failing loud? Worth a targeted test if one doesn't exist.
5. **Scope any model-router analogue deliberately.** Decide whether the actual pain point is "apps hardcode a concrete model id" (already solved for one slot by the `hal0/brain` virtual-model pattern) versus a genuine need for LiteLLM-style multi-consumer alias indirection — different problems, different right-sized solutions.
