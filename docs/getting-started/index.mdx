**hal0** turns a Linux box into a polished, OpenAI-compatible inference
appliance. It is built for the AMD Ryzen AI Max+ 395 ("Strix Halo") —
iGPU + XDNA NPU + 128 GB of unified memory — and falls back to portable
hardware parsers on every other host.

Every inference workload runs as its own **podman container**, supervised
by a `hal0-slot@<name>.service` systemd unit. A single control plane,
`hal0-api` on port `8080`, owns the slot state machines, dispatches
OpenAI-compatible `/v1/*` requests to the right slot, and serves the
dashboard. There is no shared inference daemon to babysit.

A fresh install seeds slots such as `agent`, `brain`, `memory`, `coder`,
`embed`, `rerank`, `tts` and `img`, plus the NPU `flm` slot where the hardware
allows; each runs in its own dedicated podman container. The slot name is the
routing key (`hal0/<slot>`). `agent` is the capable default/fallback anchor,
`brain` backs the dashboard's steward chat, and `memory` is the extraction
slot for the memory engine. The Recommended setup pulls the small brain model
and, on the setup screens, a chat model picked for this box; Minimal pulls neither.

## Hardware support

hal0 is first-class on AMD Strix Halo — the Ryzen AI Max+ 395 (128 GB) and
the 385 / 390 (64 GB) — with AMD RX 7000-series GPUs also supported. NVIDIA
RTX 30/40/50 (via CDI + the NVIDIA Container Toolkit) is experimental, and
CPU-only x86_64 hosts work as a fallback. There is no minimum-spec gate —
backend selection degrades to CPU rather than refusing to run.

## What you get

- **OpenAI-compatible `/v1/*` API** — chat, completions, embeddings,
  rerank (`/v1/rerankings`, plus the `/v1/rerank` alias for
  llama.cpp/Cohere-style clients), audio transcription, speech, and image
  generation. Point any OpenAI SDK at `http://localhost:8080/v1` and go.
- **Hardware-aware slots** — each capability gets its own container,
  image, flags, port, and lifecycle, sharing only the GPU through an
  arbiter.
- **Profiles** — the whole tune for a slot: llama-server flags, context
  window, thinking default, vision, reasoning and speculation (seeds include
  `chat`, `agent`, `memory`, `coding`, `embedding` and `reranking`). A slot
  names a profile and can override individual keys in its own `[tune]` table;
  to run one model two ways, make two profiles.
- **Stacks** — named, exportable bundles of slot + profile + model
  assignments (built-in `saber`, `forge`, and `pi`) that you can load,
  clone, and re-apply as a single declarative unit.
- **Component-aware install** — `install.sh` probes your hardware, seeds the
  slots, and asks everything once, on a few setup screens at the start; flags
  such as `--no-owui`, `--no-hermes` or `--bare` (inference only) settle a
  choice for you — no separate setup program to run afterward.
- **Prewired chat UI** — Open WebUI on port `3001`, zero config, with hal0's
  memory and agent-delegation tools attached.
- **Agents and memory** — the bundled Hermes agent, an optional Pi coding
  agent, the Hindsight memory engine, and an agent bridge that lets a remote
  coding agent share hal0 memory under its own revocable key.
- **NPU** — FastFlowLM chat, embedding and speech on the XDNA NPU, plus the
  optional `xdna` runner for plain GGUF models.
- **Signed self-update** — cosign-verified tarballs with one-flag
  rollback.

<Aside type="caution" title="Open on the LAN by default, no TLS">
`hal0-api` binds `0.0.0.0:8080` and, until you configure an admin key,
treats every request as authenticated by network reachability — the right
posture for a trusted LAN appliance. hal0's own auth is opt-in (see
[Authentication](/docs/operate/auth/)). If hal0 is reachable from anywhere you
do not control, front it with a reverse proxy that owns TLS.
</Aside>
