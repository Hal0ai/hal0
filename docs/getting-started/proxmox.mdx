Proxmox VE is a common host for hal0, especially on AMD Strix Halo (Ryzen
AI Max+) hardware where an LXC shares the host kernel and the iGPU + XDNA
NPU pass through as ordinary device nodes — no VM, no vGPU shim, near-native
throughput. This guide covers the quick-start script — which creates that
container and forwards the accelerators for you — the manual passthrough
recipe it automates, and running hal0 in a Proxmox VM instead.

## 1. Prepare the PVE host

Everything the accelerators need lives on the **host kernel**, because an
LXC shares it. See the Kernel and firmware section of
[GPU drivers and memory](/docs/getting-started/drivers/)
for the `amdgpu`/`amdxdna` kernel and firmware requirements, and the
Size the GTT pool section for
the GRUB parameters that raise the amdgpu GTT window — both are set on the
**Proxmox host**, not inside the container.

If you only want a CPU-only trial, skip straight to the quick path below
and pass `GPU_PASSTHROUGH=0`; GTT sizing and driver checks only matter once
you attach a GPU.

## 2. Quick path: one command

The fastest way to get hal0 running on Proxmox is the bundled installer
script, run **on the Proxmox host**:

```sh
bash -c "$(curl -fsSL https://raw.githubusercontent.com/Hal0ai/hal0/main/scripts/proxmox-ve/hal0.sh)"
```

It creates a **privileged Ubuntu 26.04** LXC (default CTID from
`pvesh get /cluster/nextid`, 4 cores, 8 GB RAM, 20 GB disk — all
overridable via env vars), forwards every GPU/NPU device node the host
actually has, writes the matching cgroup2 device rules, `memlock` limit and
AppArmor profile, and then runs the standard hal0 bootstrap inside it. The
guest installs its own prerequisites (curl, jq, Python + venv, podman,
cosign) — there is nothing to pre-stage by hand.

Two defaults worth knowing before you run it:

- **Privileged.** hal0's slots are rootful podman containers that open the
  GPU compute node directly, and a privileged CT can repair a mis-mapped
  `/dev/kfd` from inside (see §3). The trade is real: a privileged
  container's root is effectively host root. Pass `UNPRIVILEGED=1` for the
  narrower container. That quick path is validated on Strix Halo (hal0
  1.7.1, Ubuntu 24.04 template via `OS_VERSION=24.04`, default unprivileged
  idmap; the script wrote the devices, cgroup rules, memlock limit and gid
  alignment, then the stable bootstrap ran inside): ROCm and Vulkan slots
  load and serve through the idmap-mapped `/dev/kfd` and `/dev/dri/renderD128`
  (about 57 and 73 tok/s on a 0.8B model, on a GPU shared with another
  workload), `flm validate` passes on the mapped NPU node, and slot
  networking works on the default bridge. Prefer it unless you need to
  repair `/dev/kfd`'s gid from inside the guest: device ownership is
  host-mapped, so repairs must happen on the host. See the unprivileged
  notes in §3.
- **GPU passthrough on by default** (`GPU_PASSTHROUGH=auto`). On a host with
  no accelerator nodes it warns and builds a CPU-only container; set
  `GPU_PASSTHROUGH=0` to skip passthrough deliberately.

<Aside type="tip">
Pass `--advanced` to open `whiptail` prompts for CTID, hostname, cores,
RAM, disk, storage, bridge, static IP, privilege and passthrough instead of
accepting the defaults. Everything is also settable per-run as an env var —
see the [script's README](https://github.com/Hal0ai/hal0/blob/main/scripts/proxmox-ve/README.md).
</Aside>

## 3. Manual GPU/NPU passthrough

The script in §2 does all of this for you; this section is what it
automates, for anyone building the container by hand or retrofitting an
existing one. To get the iGPU and XDNA NPU into a container, create the LXC
and forward the accelerator device nodes from the host (PVE 8.2+ `devN`
syntax). A minimal starting point:

```sh
pct create <CTID> local:vztmpl/ubuntu-26.04-standard_26.04-1_amd64.tar.zst \
  --unprivileged 0 --features nesting=1,keyctl=1,fuse=1,mknod=1 \
  --cores 4 --memory 8192 --rootfs local-lvm:20
```

For the unprivileged container described below, use `--unprivileged 1` and
the same `--features`.

The `devN` gid-mapping mechanism below works on both privileged and
unprivileged containers. The difference is who can repair a wrong mapping
afterwards: on a privileged CT hal0 aligns `/dev/kfd` to the render gid
itself, while on an unprivileged one the node's ownership is host-mapped
and only the host's `devN:` entry can fix it. That is why every `devN`
line below carries a `gid=`, `/dev/kfd` included.

Append this to `/etc/pve/lxc/<CTID>.conf` on the host:

```ini
# /etc/pve/lxc/<CTID>.conf
dev0: /dev/dri/renderD128,gid=<render gid INSIDE this container>
dev1: /dev/kfd,gid=<render gid>            # ROCm compute (optional)
dev2: /dev/accel/accel0,gid=<render gid>   # XDNA NPU (Strix Halo only)

# Device-cgroup rules for the majors above, plus the memlock limit ROCm
# needs to pin buffers (and `flm validate` needs for the NPU).
lxc.cgroup2.devices.allow: c 226:* rwm
lxc.cgroup2.devices.allow: c <kfd major>:* rwm
lxc.cgroup2.devices.allow: c 261:* rwm
lxc.prlimit.memlock: unlimited
```

226 is the DRM major and 261 the accel major on the kernels this was tested
on. The `/dev/kfd` major is assigned dynamically — 234 on some kernels, 509
on the 7.0 Proxmox kernel the unprivileged validation ran on — so don't
copy a number. Read each major from the host, in the decimal number before
the comma:

```sh
ls -l /dev/dri/renderD128 /dev/kfd /dev/accel/accel0
```

(`stat -c %t` also works, but prints the major in hex; the cgroup rules
want decimal.) `lxc.prlimit.memlock: unlimited` is also what lets
`flm validate` pass inside the container: it then reports `Memlock Limit:
infinity`, while a test container without the line failed the check at an
8 MB limit.

<Aside type="note" title="The stock unprivileged idmap is enough">
The unprivileged container that was validated (`unprivileged: 1`, the
`features:` line above, the three `devN` lines, the cgroup rules and the
memlock line) had no `lxc.idmap` lines and no AppArmor override: the default
`0 100000 65536` map and the stock profile were sufficient for GPU and NPU
passthrough. Guest-side notes follow in this section.
</Aside>

Then apply it:

```sh
pct stop <CTID> && pct start <CTID>
```

<Aside type="tip">
The quick-path script resolves this for you: it boots the container once,
reads the guest's `render` gid, re-points every `devN` entry at it, and
restarts. That step exists because the correct gid cannot be known before
the container exists — and on a **privileged** container there is no idmap
to paper over the difference, so a host gid of 993 stays 993 inside a guest
whose render group is 991.
</Aside>

<Aside type="caution" title="gid means the CONTAINER's gid, not the host's">
The `gid=` value must be the render group's id **inside the container**,
not on the host — the two gid spaces can disagree. See the Render-group
gids section of [GPU drivers and memory](/docs/getting-started/drivers/) for
how to read the correct value with `stat -c %g` and why `getent group
render` can silently resolve to the wrong group.
</Aside>

hal0's own preflight checks this device layout inside an LXC and prints the
matching `devN` line for what it finds wrong: the whole `dev0`/`dev1`/`dev2`
block when no render node is visible, the `dev0` line when the render node's
gid is off, and the `dev1` line when `/dev/kfd`'s gid is off. It does not
check the NPU node's gid, so confirm `/dev/accel/accel0` by hand with
`ls -ln` after installing hal0 inside the CT (§4 below); `hal0 doctor` then
confirms the devices are visible.

### PVE keyring sysctls

Podman inside an LXC can fail to start a container with `crun: create
keyring '…': Disk quota exceeded`, even with `nesting=1,keyctl=1` already
set — that's the kernel's session-keyring byte quota, not a missing
feature flag. Raise it **on the Proxmox host**:

```sh
sysctl -w kernel.keys.maxbytes=1000000
```

then re-run `install.sh` inside the container. Persist the value in
`/etc/sysctl.d/` if you don't want to repeat this after a host reboot.

Leave `kernel.keys.maxkeys` alone unless `sysctl kernel.keys.maxkeys` prints
less than 2000; if it does, raise it to 2000. Proxmox defaults to 2000 keys
and 20000 bytes, so setting `maxkeys` to a smaller number such as 1000 would
cut the key-count quota. The byte quota is the one that runs out: with
`brain`, `utility` and Open WebUI running, an unprivileged guest used about
11% of it and never hit the error, so apply the bump if you do.

### AppArmor

GPU/NPU passthrough on a **privileged** container needs an unconfined
AppArmor profile (`lxc.apparmor.profile: unconfined` in the container's
`.conf`) for the container runtime to launch slots inside the LXC — the
quick-path script writes it for you, and the installer detects and repairs
the in-guest half of the same failure (#1563). On an **unprivileged**
container leave the stock profile in place on the host: it is a narrower
trust boundary and the runtime works without the override. The guest has its
own AppArmor profiles, though — see the next subsection.

### Unprivileged Ubuntu 24.04 guests: disable the guest's unconfined AppArmor profiles

An Ubuntu 24.04 guest ships `flags=(unconfined)` AppArmor profiles for
`podman`, `crun`, `buildah`, `runc`, `rootlesskit` and `slirp4netns`. Inside
a nested container on some host kernels those "unconfined" profiles are
still enforced for network access, and every `podman` command fails with
`socket: permission denied`. It was seen on a Proxmox VE 9.2 host on kernel
7.0. The installer then stops at its container-runtime gate, and its hint to
set `nesting=1` is wrong because nesting is already on.

Check podman from inside the CT before you run the installer (Proxmox's
Ubuntu templates already include the `apparmor` package):

```sh
pct enter <CTID>
apt-get update && apt-get install -y podman
podman run --rm quay.io/podman/hello
```

If that prints its greeting, skip the rest of this subsection. If it fails
with `socket: permission denied`, disable the six profiles once:

```sh
for p in podman crun buildah runc rootlesskit slirp4netns; do
  [ -e /etc/apparmor.d/$p ] || continue
  mkdir -p /etc/apparmor.d/disable
  ln -sf /etc/apparmor.d/$p /etc/apparmor.d/disable/$p
  if command -v apparmor_parser >/dev/null; then
    apparmor_parser -R /etc/apparmor.d/$p
  fi
done
podman run --rm quay.io/podman/hello
```

**The installer repairs this itself.** From the release that ships the fix
tracked in [#3234](https://github.com/Hal0ai/hal0/issues/3234), hal0's
installer detects this exact failure — `podman run` failing with `: socket:
permission denied` — but only inside a nested AppArmor policy namespace,
which is what an unprivileged LXC is. It never acts on a bare-metal host or
in a privileged container. It disables only those of the six profiles that
exist and carry `flags=(unconfined)`, retries, and prints what it changed.
Until you are on that release, the check is manual.

The denial depends on the **host** kernel: it reproduced on a Proxmox VE 9.2
host running kernel 7.0 and not on a 6.8 kernel, and Ubuntu 26.04 guests were
unaffected in our runs.

To put a profile back, whether you or the installer disabled it, run this
inside the CT:

```sh
rm /etc/apparmor.d/disable/<name> && apparmor_parser -r /etc/apparmor.d/<name>
```

The trade-off is small. These stub profiles only grant `userns`, so
disabling them does not weaken confinement. On a host with
`kernel.apparmor_restrict_unprivileged_userns=1`, though, it removes that
grant from unprivileged users of those binaries inside the guest. That
includes rootless podman as the `hal0` user, which is already unavailable
inside an unprivileged container (see the rootless podman note below), so
hal0 loses nothing there.

### Unprivileged podman network fix

Unprivileged podman-in-LXC has a known bridge-netns teardown race. The
validation run did not hit it — an Ubuntu 24.04 guest (podman 4.9.3, netavark
1.4) on Proxmox VE 9.2 / kernel 7.0 started and stopped containers five times,
including a slot restart, on the default bridge with no network errors — so
the default is fine to start with. If slots do fail to start with network
errors, set hal0 to render every slot with host networking instead of a
bridge netns:

```toml
# /etc/hal0/hal0.toml
[slots]
network_mode = "host"
```

hal0 still fences each slot's process bind to loopback under
`network_mode = "host"`, so this does not expose slot ports to the LAN.

### Unprivileged containers: rootless podman for the `hal0` user

A default unprivileged container owns only the ids 0–65535
(`0 100000 65536`), so no subordinate uid range fits beside its own users
and rootless podman as `hal0` cannot build a user namespace
([#3236](https://github.com/Hal0ai/hal0/issues/3236)). The installer
detects the nested uid map, skips the `hal0` range and the deferred
`podman system migrate`, and prints an info line instead of a warning.
Slots (rootful quadlets) and dashboard image pulls (the root-owned
`hal0-podman-rw` helper) are unaffected; only running `podman` as the
`hal0` user itself is unavailable.

### Surface true host memory pressure (optional)

Inside an LXC, hal0 only sees its own cgroup memory share — but the GPU's
GTT pool is drawn from the same physical DIMMs every other tenant and the
host kernel use. Give hal0 a **read-only** Proxmox API token so the
dashboard's unified-memory bar shows real host pressure instead of
pretending only this container's bytes exist.

Create a read-only token in the Proxmox UI (Datacenter → Permissions →
API Tokens, with `PVEAuditor` on `/`), then configure it via the dashboard
Settings → Proxmox card, or write `/etc/hal0/proxmox.json` directly:

```json
{
  "proxmox": { "host": "192.0.2.10", "port": 8006, "verify_ssl": false, "service": "PVE" },
  "auth": { "user": "hal0@pve", "token_name": "readonly", "token_value": "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx" }
}
```

hal0 polls `GET /cluster/resources` (cached 30 s) and surfaces host RAM
total/used plus every running tenant's allocation. Non-Proxmox installs
leave the file absent and the feature stays silent.

## 4. Install hal0 in the CT

Open a shell in the container and run the standard bootstrap:

```sh
pct enter <CTID>
apt-get update && apt-get install -y curl ca-certificates
curl -fsSL https://hal0.dev/install.sh | bash
```

No `sudo` needed here — `pct enter` drops you in as root inside the
container, and minimal CT templates often don't even have `sudo`
installed.

See [Install hal0](/docs/getting-started/install/) for the full sequence,
every environment variable, and what the 15-step installer does. On a
GPU/NPU passthrough CT, the hardware probe should now see the iGPU and NPU
through the forwarded device nodes.

<Aside type="note" title="Some !! lines are expected">
A `!!` line is a warning, not a failure. A fresh install into an
unprivileged CT with the GPU and NPU forwarded finished with three:

- `could not create /var/lib/hal0/.config/flm/models as hal0` — appears on
  any fresh install that has an NPU node; hal0 creates the directory later,
  when a model is pulled.
- `podman system migrate (as hal0) failed` — see the rootless podman note in
  §3.
- `memory bank seeding incomplete` — hal0-api had not yet connected to the
  memory engine, which starts after it on a new install. The installer now
  waits up to 45 s for that before seeding. If the engine was not healthy
  at install time, hal0-api seeds the banks when it comes up.

`hal0 doctor all` on the same box reported 31 passes, 5 warnings and no
failures. The five warnings were: no capability slots active, the open-on-LAN
auth posture, the agent uid split, memory extraction speed (the `utility`
slot has no model yet), and `Port DNAT rules` audit unavailable on netavark
1.4. `systemctl --failed` may also list `proxmox-regenerate-snakeoil.service`,
a known container artefact.
</Aside>

<Aside type="note" title="podman inspect is misleading here">
Inside an unprivileged LXC, `podman inspect` prints `Could not locate device
<major>:<minor> on host` warnings and reports `HostConfig.Devices: []` even
though the slot container has its devices. Check with `podman exec
<container> ls -ln /dev/kfd /dev/dri` instead.
</Aside>

## 5. FastFlowLM NPU trio

On an apt-based CT with the NPU device nodes present, the installer's NPU
prerequisites step handles the **FastFlowLM (FLM)** userspace automatically.
On Ubuntu it first adds the `lemonade-team/stable` PPA, which is where
`libxrt-npu2` (the AMDXDNA NPU runtime) ships, then installs it; on Debian 13
it uses the distribution's own sources. It then fetches the pinned,
SHA-256-verified FastFlowLM `.deb` matching the CT's distro (Debian 13 or
Ubuntu 24.04/25.10/26.04) directly from FastFlowLM's GitHub releases.
A single `flm serve` process backs the **NPU trio** — one chat model plus
optional embedding and speech-to-text "passengers" sharing the NPU.

The host `.deb` is used for `flm validate`, the setup-time NPU check. The
NPU slot serves from the `flm` runner image, and FLM model pulls and the NPU
model catalogue run inside that same image, so the FastFlowLM version that
picks the weights is the runner image's, not the host `.deb`'s.

Confirm the NPU runtime is reachable from inside the container:

```sh
flm validate       # → "flm validate ok — NPU runtime reachable"
hal0 doctor        # re-runs preflight; hardware probe records the NPU
```

The seeded `flm` slot serves a chat model on port `8088`. The trio's
embedding and STT passengers are **opt-in** — enable them per slot (the
`asr` / `embed` keys on the slot's `[npu]` table) once the chat slot is
loaded. See [Voice (STT/TTS)](/docs/guides/voice-stt-tts/) and
[Slots](/docs/concepts/slots/) for the trio routing details.

<Aside type="note">
If `flm validate` reports the NPU is unreachable, re-check that
`/dev/accel/accel0` is visible **inside** the container (`ls -l
/dev/accel/`) and that `amdxdna` is loaded on the **host** kernel. The
`.deb` ships only userspace — it never loads the kernel driver.
</Aside>

## 6. Verify

```sh
hal0 status                       # system + slot status
hal0 doctor all                   # evidence roll-up, including units
systemctl status hal0-api         # control plane
journalctl -fu hal0-api           # live logs
```

The API and dashboard listen on `http://<container-ip>:8080`; OpenWebUI on
`:3001`.

## Proxmox VM

hal0 also auto-detects and supports running inside a **Proxmox VM**
(`proxmox-kvm`), CPU-only. iGPU passthrough to a VM is not documented for
1.0 — use an LXC for GPU/NPU acceleration instead. The dashboard's Proxmox
panel (host memory pressure) also stays off inside a VM, since it depends
on the LXC-specific cgroup-vs-host memory split described above.
