Models in hal0 live in a local registry, the single source of truth for
Hugging Face coordinates, SHA-256 digests, and curated filenames. A fresh
install seeds **zero** model slots — you pick the first model yourself,
and the fastest path is two commands.

## Starting from zero — no models yet

Every fresh install boots with services up but nothing to serve — first-run
setup scaffolds slot *structure* only, no model picks (see
[First-run setup](/docs/getting-started/setup/)). Until you pull one, that
shows up in a few places:

- The dashboard shows a passive banner — "No models configured yet" —
  whenever the API reports `first_run: true`. It's dismissible and never
  auto-routes you anywhere.
- The **Models** view has an empty registry (the Inference tab reads "the
  catalog is empty"), and the Downloads panel prompts you to add a model
  from the catalog or via **Add by HF coords**.
- The **Slots** view shows a **no slots configured** hint if no capability
  slots exist yet.
- `GET /v1/models` returns an empty list, and a chat request against an
  unconfigured slot has nothing to dispatch to.

`first_run` is computed from two conditions: `/var/lib/hal0/models/` is
empty **and** the first-run sentinel (`/var/lib/hal0/.first_run_done`)
doesn't exist yet. Either one flips it to `false` — so pulling or adding
any model (or the setup TUI writing the sentinel) is enough to clear the
banner for good in normal use.

Getting out of this state is the rest of this page: the two-command path
right below, the dashboard's **Models** view, or the
[`hal0 setup`](/docs/getting-started/setup/) TUI.

## The two-command path

```sh
hal0 model pull qwen3-4b      # download from Hugging Face (curated alias)
hal0 model run  qwen3-4b      # assign to a slot, load, wait until serving
```

`model run` picks the first compatible slot (or takes `--slot`), loads it,
polls until the server answers, and prints a copy-paste `curl` smoke test
against the slot port. That's a working chat endpoint.

## Already have the files on disk?

Many installs start from a disk full of GGUFs, not a download. Point hal0
at them instead of re-pulling:

```sh
# the whole directory is your model store (persists to hal0.toml,
# registers everything it finds immediately):
hal0 model store /mnt/ai-models

# ...or register files where they already are:
hal0 model scan                              # sweep the configured roots
hal0 model add /any/path/my-model.gguf       # one file, auto-detected

hal0 model run my-model
```

If something doesn't show up, `hal0 doctor models` audits the pipeline —
dangling registry entries, unregistered files, store mismatches — and
prints the exact fix for each finding.

## Via `hal0 setup`

Re-run `hal0 setup` any time for the guided TUI: it can provision slots,
pick curated models sized to your hardware, and kick off the pulls for
you.

## The CLI, step by step

![Models registry](/screenshots/models-registry.png)

*The Models view — registry, pull progress, and curated loadouts.*

The `hal0 model` subcommand is a thin HTTP client to the API.

<Steps>

1. **List what's available** — registry rows plus models advertised by
   configured upstreams:

   ```sh
   hal0 model list
   ```

   Add `--json` to emit the raw `/api/models` payload for scripting.

2. **Pull a model** from Hugging Face. The argument is either a curated
   alias (e.g. `qwen3-4b`) or a registered model id:

   ```sh
   hal0 model pull qwen3-4b
   ```

   The pull runs as a background job on the daemon. The CLI polls
   `/api/models/<id>/pull/status` every 500 ms and prints a progress bar
   until the job reaches a terminal state, then reports the final path
   and SHA-256. If the curated pick is a vision model, its `mmproj`
   projector sidecar downloads automatically alongside the main GGUF —
   no extra step needed.

3. **Run it** — or assign without loading:

   ```sh
   hal0 model run qwen3-4b --slot agent      # assign + load + wait ready
   hal0 model assign qwen3-4b --slot agent   # assign only (slot not started)
   ```

   Both write `model.default` into the slot's configuration. `agent` is the
   always-seeded default/anchor slot (see [Slots](/docs/concepts/slots)); swap
   in `utility` or any other slot name you've created instead. For
   assign-only, start the slot afterward (see
   [Manage slots](/docs/guides/manage-slots/)).

</Steps>

Other `hal0 model` commands: `add` (register an on-disk file,
auto-detected), `scan` (sweep the roots + store), `store` (show/move the
model store), `register` (record an on-disk file with an explicit id),
`show` (inspect metadata), and `rm` (remove a registry row).

<Aside type="note" title="NPU (FLM) models">
On Strix Halo NPU installs, FLM models use Ollama-style tags
(`qwen3:0.6b`, `gemma3:4b`) rather than HF coordinates. `hal0 model pull
<tag>` routes them to the FLM puller automatically, and the loaded tag
serves through the `npu` slot. See the
[Proxmox quick start](/docs/getting-started/proxmox-lxc/) for the NPU
trio setup.
</Aside>

<Aside type="tip" title="Gated or large models">
Pulls that need a Hugging Face token read `HF_TOKEN` from the API
environment. The easiest path is the dashboard: **Settings → Secrets →
HuggingFace token** applies live without a restart.
</Aside>

## When a pull fails

A pull job ends in one of these states: `queued`, `running`, `completed`,
`failed`, or `cancelled`. On `failed`, the CLI exits non-zero and prints
the error message returned by the daemon; the registry row stays in place
so you can retry.

```sh
# retry — an already queued/running pull for the same id is reused,
# not duplicated
hal0 model pull qwen3-4b
```

The dashboard's **Models** view surfaces the same failure inline with a
**Retry** button, and you can always pull later from there or via the CLI.
Re-issuing a pull for a `completed`/`failed`/`cancelled`
job replaces it; a pull already `queued` or `running` returns the
existing job handle rather than starting a second download.
