The installer seeds slots and starts services, and pulls only the small brain
model (skip it with `--no-brain-model`); it does not pick a chat model for you.
Models in hal0 live in a local registry, the single source of truth for
Hugging Face coordinates, SHA-256 digests, and curated filenames. Populate it
from the dashboard or directly from the CLI.

## Via the dashboard

Open the dashboard at `http://<host>:8080` and go to **Models → Inference
Models**. Use **+ Add model** → **Search HF** to find a model on Hugging
Face, pick a quantization, and pull it; progress shows in the Downloads
panel. Then open **Slots**, choose the model in the slot card's model
picker, and start the slot. The fit chip beside each model says whether it
fits this box's memory. Image models live under
**Models → Image / ComfyUI**, and NPU models under **Models → FLM**.

## Via the CLI

![Models registry](/screenshots/models-registry.png)

*The Models view — registry, pull progress, and curated loadouts.*

The `hal0 model` subcommand is a thin HTTP client to the API. The common
flow is **list → pull → assign**.

<Steps>

1. **List what's available** — registry rows plus models advertised by
   configured upstreams:

   ```sh
   hal0 model list
   ```

   Add `--json` to emit the raw `/api/models` payload for scripting.

2. **Pull a model** from Hugging Face. The argument is either a curated
   alias (e.g. `qwen3-4b`) or a registered model id:

   ```sh
   hal0 model pull qwen3-4b
   ```

   The pull runs as a background job on the daemon. The CLI polls
   `/api/models/<id>/pull/status` every 500 ms and prints a progress bar
   until the job reaches a terminal state, then reports the final path
   and SHA-256. If the curated pick is a vision model, its `mmproj`
   projector sidecar downloads automatically alongside the main GGUF —
   no extra step needed.

3. **Assign the model to a slot's default** (this does not start the
   slot):

   ```sh
   hal0 slot edit agent --model qwen3-4b
   ```

   This writes `model.default` into the slot's configuration. `agent` is the
   seeded default/anchor slot (see [Slots](/docs/concepts/slots)); use any
   other slot name you've created instead. Start the slot afterward (see
   [Manage slots](/docs/guides/manage-slots/)).

4. **Verify the slot is up**:

   ```sh
   hal0 status
   ```

   Confirms the slot's state machine reached its running state with the
   assigned model loaded.

</Steps>

`hal0 model run <ref>` does the pull, assignment, load and wait in one
command; pass `--slot <name>` to pick the slot (the default is the first
compatible one). Other `hal0 model` commands: `add` (record an on-disk file
in the registry), `show` (inspect metadata), `default` (promote a model as its
type's default), `update` (check for or apply Hugging Face updates), `scan`,
`set`, `store` (show or change the model store), and `rm` (remove a model and,
unless `--keep-files` is given, its files).

<Aside type="tip" title="Gated or large models">
Pulls that need a Hugging Face token read `HF_TOKEN` from the API
environment. The easiest path is the dashboard: **Settings → Secrets →
HuggingFace token** applies live without a restart.
</Aside>

## When a pull fails

A pull job ends in one of these states: `queued`, `running`, `completed`,
`failed`, or `cancelled`. On `failed`, the CLI exits non-zero and prints
the error message returned by the daemon; the registry row stays in place
so you can retry.

```sh
# retry — an already queued/running pull for the same id is reused,
# not duplicated
hal0 model pull qwen3-4b
```

The dashboard's **Models** view surfaces the same failure inline with a
**Retry** button, and you can always pull later from there or via the CLI.
Re-issuing a pull for a `completed`/`failed`/`cancelled`
job replaces it; a pull already `queued` or `running` returns the
existing job handle rather than starting a second download.
