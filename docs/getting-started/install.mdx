hal0 installs from a single command. The bootstrap script is the trust
boundary: it fetches the release manifest, verifies the tarball, unpacks
it, and hands off to the real installer.

```sh
curl -fsSL https://hal0.dev/install.sh | bash
```

<Aside type="tip" title="The installer is the whole setup">
There is no separate first-run wizard to run afterwards. The installer does
all of it: it asks where models should live, optionally takes a Hugging Face
token, creates every capability slot, downloads the hal0 brain steward model,
and starts the API. When it finishes you open the dashboard and assign models
to slots.
</Aside>

To install from the opt-in preview channel instead:

```sh
curl -fsSL https://hal0.dev/install.sh | HAL0_CHANNEL=preview bash
```

Only `stable`, `preview`, and `nightly` are accepted. The requested channel is
validated before any download, and stable clients never consume preview
artifacts. These URLs describe the client contract; installation also depends
on the external release service publishing the selected pointer and sibling
bundle, which this repository does not operate.

<Aside type="note">
The installer needs root to write to `/etc`, `/usr/lib`, and the systemd
unit directory. When piped through `bash` without `sudo`, it re-execs
itself under `sudo` automatically. You can also run it explicitly:
`curl -fsSL https://hal0.dev/install.sh | sudo bash`.
</Aside>

## Requirements

- **Linux, x86_64** — hal0 ships amd64-only binaries (the FastFlowLM
  `.deb` and the toolbox container images). ARM and macOS/Windows are not
  supported.
- **systemd** — `systemctl` must be on `PATH` (outside `--dev` mode).
- **Python ≥ 3.12** — the package requires 3.12+; the installer is tested
  on 3.11–3.14 and builds a dedicated virtualenv.
- **cosign** — required to authenticate the channel manifest and release
  artifact against hal0's pinned GitHub Actions workflow identity. You do
  **not** have to install it yourself: the bootstrap uses your distro's
  `cosign` when one is on `PATH` (Arch, Fedora, Alpine, openSUSE package it)
  and otherwise downloads the official sigstore build for your architecture
  into its throwaway work directory, verified against a SHA-256 pinned in
  the script. This is what keeps the one-liner working on Debian/Ubuntu,
  which do not package cosign. Nothing is installed persistently, and there
  is no flag to skip verification — an unsupported CPU architecture, a
  failed download, or a digest mismatch aborts the install with
  instructions for installing cosign by hand.
- **jq 1.6 or newer** — required for the authenticated manifest's strict,
  fail-closed schema and channel-policy validation.
- **A container runtime** — every inference slot runs in a container. The
  installer auto-installs **podman** if no runtime is found.
- **~20 GB free disk** under the data directory, plus free ports `8080`
  (API) and `3001` (OpenWebUI).

Supported package managers for auto-installing prerequisites (podman, the
Python venv stdlib): **apt** (Debian/Ubuntu), **dnf**/**yum** (Fedora),
**pacman** (Arch), **zypper** (openSUSE), and **apk** (Alpine).

<Aside type="caution" title="NVIDIA / CUDA">
hal0 is tuned for the AMD Strix Halo iGPU + XDNA NPU; ROCm is AMD-only,
so GPU acceleration on other hardware runs through the generic **Vulkan**
profile (works on AMD/NVIDIA/Intel). An experimental `cuda` profile also
ships (the upstream `llama.cpp:server-cuda` image, needs
`nvidia-container-toolkit`/CDI on the host) — it isn't part of the
one-line installer's automatic hardware seeding, so assign it to a slot
manually from the dashboard after install.
</Aside>

## pip install (convenience only — not the full install)

hal0 is also published to PyPI as a convenience for scripting, tool
discovery, and Python-level imports. The distribution is named `hal0ai`
(PyPI's name-similarity guard rejects `hal0`), but it still installs the
`hal0` command and the `hal0` import package:

```sh
pip install hal0ai
```

This installs the `hal0` and `hal0-agent` console scripts and the
`hal0.*` package namespace — enough to run `hal0 --version`, import
`hal0.*` in your own Python code, or invoke the CLI from a virtualenv.

<Aside type="danger" title="Not the supported production path">
`pip install hal0ai` does **not** set up systemd units, podman containers,
the dashboard UI, OpenWebUI, model registry, or the FHS `/usr/lib/hal0`
layout. It is a lightweight complement for scripting and development.
For a full production deployment, use the bootstrap script above.
</Aside>

## What the bootstrap does

<Steps>

1. **Resolve a verifier** — a `cosign` already on `PATH` is used as-is.
   Otherwise the pinned official sigstore build for the detected
   architecture (`x86_64`/`amd64` → `cosign-linux-amd64`,
   `aarch64`/`arm64` → `cosign-linux-arm64`) is downloaded into the
   temporary work directory and its SHA-256 checked against the digest
   pinned in the bootstrap script. This happens **before** any release
   bytes are requested, so the installer never downloads something it
   could not verify. Pinning the digest adds no new trust root — you
   already trusted those bytes when you piped the script to `bash`.

2. **Fetch and authenticate the channel manifest** — by default from
   `https://releases.hal0.dev/stable.json`, or the selected
   `HAL0_CHANNEL`. The bootstrap downloads the exact sibling
   `<channel>.json.bundle` and verifies the manifest bytes with cosign against
   the client-pinned release-workflow identity and issuer before parsing JSON
   or trusting artifact URLs. Then one jq-compatible policy pass requires the
   exact `hal0.releases.v1` schema, required strings and digest shape, and the
   canonical requested-channel/kind/stage matrix. Missing jq, a missing
   bundle, or failed validation/verification aborts the install.
   `HAL0_RELEASES_URL` still overrides the full manifest URL; its sibling
   `.bundle` must satisfy the same contract.

3. **Download and SHA-256-verify the tarball** against the authenticated
   manifest digest. A mismatch aborts the install.

4. **Cosign keyless verify the tarball** — the mandatory artifact Sigstore
   bundle from `bundle_url` is checked against the workflow OIDC identity
   declared in the now-trusted manifest. Detached signature/certificate
   fallback is not accepted by the bootstrap. This second signature check is
   defense-in-depth.

5. **Unpack and hand off** to `installer/install.sh` — see
   [What the installer does](#what-the-installer-does) below.

</Steps>

## What the installer does

`installer/install.sh` prints a numbered banner per step. In order, it:

<Steps>

1. **Pre-flight** — architecture, systemd, Python ≥ 3.12, a container
   runtime, GPU/NPU device visibility, disk space, and port availability.
   The GPU gate is a hard stop when passthrough is visibly broken (the
   render device is present but its gid maps to no group in the container),
   because every slot would otherwise fall back to CPU silently.

2. **Ask for the two things it can't derive** — the model storage
   directory and, optionally, a Hugging Face token. Both are pre-filled
   and both are skipped entirely on a non-interactive install; see
   [Operator input](#operator-input).

3. **Lay down the platform** — the `hal0` system user, the FHS layout under
   `/usr/lib/hal0`, the Python venv, the dashboard build, `/etc/hal0`
   config, and the systemd units.

4. **Seed the curated container slots** — `agent`, `brain`, `coder`,
   `embed`, `flm`, `img`, `qwen3tts`, `rerank`, `tts`, `utility` are copied
   verbatim from the release's `installer/etc-hal0/slots/`, carrying their
   hand-tuned profile recipes. An existing file is never overwritten.

5. **Scaffold anything left over** — the remaining capability slots (e.g.
   `vision`) get a device, profile, and port derived from the hardware
   probe, with **no model assigned**. Nothing is downloaded here.

6. **Download the brain steward model** — see [The brain slot](#the-brain-slot).

7. **NPU prerequisites, ComfyUI model share, bundled agent skills**, then
   **start the API**.

</Steps>

## Operator input

The installer asks exactly two questions, and only when stdin is a terminal:

| Question | Pre-filled from | If you press Enter |
|---|---|---|
| Where should downloaded models live? | `--models-dir=PATH` / `HAL0_MODELS_DIR` | `/var/lib/hal0/models` |
| Hugging Face token (input hidden) | `HF_TOKEN` / `HUGGING_FACE_HUB_TOKEN` | skipped — open models need none |

A supplied `--models-dir` / `HAL0_MODELS_DIR` is never re-asked. A non-default
store is written to `/etc/hal0/hal0.toml` as `[models].store`, so pulls, scans,
and slot container mounts all resolve through the one value. A token is
validated with `hf auth whoami` (a failure warns, it never aborts the install)
and persisted to `/var/lib/hal0/secrets/hal0-api.env`, root-only `0600` — not
into the world-readable `api.env`. You can add or rotate one later from the
dashboard's **Settings → Secrets** tab, or by re-running the installer with
`HF_TOKEN` in the environment.

<Aside type="note" title="Piped and headless installs never prompt">
The gate tests stdin, so `curl -fsSL https://hal0.dev/install.sh | sudo bash`
(stdin is the script itself) and `ssh host 'sudo bash install.sh'` (no tty at
all) both run completely unattended on the flag/env values. Only a downloaded,
directly-invoked `sudo bash install.sh` prompts. `HAL0_NONINTERACTIVE=1` forces
the unattended path even on a terminal.
</Aside>

## The brain slot

Every slot the installer creates ships **without** a model — no surprise
multi-gigabyte download, no container crash-looping against a file that isn't
there. The `brain` slot is the one exception. It backs the dashboard's sidebar
steward chat (the virtual model `hal0/brain`), so the installer downloads its
weights and binds them, and the steward works the moment the install finishes.

Which build it pulls depends on your hardware, and the difference matters: the
quantised builds use custom tensor types that only hal0's ROCmFPX runner can
load, so a box without a ROCm/Vulkan device gets the portable F16 build
instead. The installer picks for you.

If the download can't happen — no network, no disk, an unreachable repo — the
installer **warns and carries on**. The brain slot is left model-less and the
install still succeeds; the sidebar chat falls back to the `agent` slot
meanwhile. An optional model can never fail a platform install.

Set `HAL0_SKIP_BRAIN_MODEL=1` to skip the download entirely.

## Environment variables and flags

The installer reads several environment variables and accepts a few
flags:

| Variable | Default | Purpose |
|---|---|---|
| `HAL0_PREFIX` | `/usr/lib/hal0` | Installation root (FHS layout with a versioned dir + `current` symlink) |
| `HAL0_PORT` | `8080` | API bind port |
| `HAL0_MODELS_DIR` | `/var/lib/hal0/models` (or `$PWD/.hal0ai/var/lib/hal0/models` under `--dev`) | Where Hugging Face pulls land |
| `HAL0_PYTHON` | `python3` | Python interpreter to build the venv from |
| `HAL0_NONINTERACTIVE` | _(unset)_ | Set to `1` to skip the two operator prompts even on a terminal |
| `HF_TOKEN` / `HUGGING_FACE_HUB_TOKEN` | _(unset)_ | Hugging Face read token; pre-fills the prompt, or supplies it outright on a headless install |
| `HAL0_NO_PROBE` | _(unset)_ | Set to `1` to skip the hardware probe and the capability-slot scaffolding step |
| `HAL0_SKIP_BRAIN_MODEL` | _(unset)_ | Set to `1` to skip the brain steward model download |
| `HAL0_CHANNEL` | `stable` | Bootstrap channel: `stable`, `preview`, or `nightly` |
| `HAL0_RELEASES_URL` | `https://releases.hal0.dev/<channel>.json` | Full manifest URL override; the exact sibling `.bundle` remains mandatory |

| Flag | Effect |
|---|---|
| `--dev` | Local-only editable install under `$PWD/.hal0ai` — no systemd, no host package changes |
| `--no-start` | Set everything up but do not enable/start the units |
| `--models-dir=PATH` | Absolute path where pulls land (same as `HAL0_MODELS_DIR`); suppresses the prompt |

<Aside type="tip">
The model store must be an **absolute** path — pulls run as root, so a relative
path would land somewhere unpredictable. Re-running the installer with a
different `--models-dir` repoints `[models].store` in `/etc/hal0/hal0.toml`;
models already on disk are not moved, so add their directory to
`[models].roots` if you want them to keep being scanned.
</Aside>

## Verify the install

Once the installer finishes, check system and slot status:

```sh
hal0 status
```

Re-run the full pre-flight set (architecture, systemd, Python, container
runtime, disk, ports) any time:

```sh
hal0 doctor
```

Re-run hardware detection (CPU, RAM, GPU, NPU) on its own with:

```sh
hal0 probe
```

The API listens on `http://localhost:8080`. Service-level checks:

```sh
systemctl status hal0-api
systemctl list-units 'hal0-slot@*'
journalctl -fu hal0-api
```

## Uninstall

The CLI wraps `installer/uninstall.sh`:

```sh
hal0 uninstall          # conservative: keep /etc/hal0 + models/registry
hal0 uninstall --purge  # clean slate: also wipe config, data, user, images
```

The **conservative default** stops services and removes code, units,
venvs, binaries, and every hal0 podman container, but keeps `/etc/hal0`
(config) and the data directory (models, registry, OpenWebUI state) so a
re-install reuses them. `--keep-data` is a legacy alias for this same
default — it's kept for back-compat, not because the default changed.

`--purge` (alias `--clean-slate`) additionally removes the config and
data directories, the `hal0` system user and group, and all hal0/toolbox
podman images. It prompts for a typed `DELETE` confirmation unless you pass
`--force` (or set `HAL0_FORCE=1`).

<Aside type="note">
`--purge` deliberately leaves general-purpose host packages installed —
podman itself, `libxrt-npu2`, ffmpeg, and boost — since other software
may depend on them.
</Aside>

## Next steps

The install created every capability slot and bound a model to `brain`. The
other slots are grey — configured, but with no model assigned. From here:

- **Open the dashboard** at `http://<host>:8080/` and assign models to slots.
  This is the intended path: it browses the curated catalogue, shows what fits
  your detected memory, and pulls in the background.
- Prefer the CLI? Pull a model and bind it — see
  [Load your first model](/docs/getting-started/first-model/).
- Chat straight away without leaving the terminal: `hal0 chat --brain` talks to
  the steward model the installer just pulled.
