hal0 installs from a single command. The bootstrap script is the trust
boundary: it fetches the release manifest, verifies the tarball, unpacks
it, and hands off to the real installer (`installer/install.sh`).

```sh
curl -fsSL https://hal0.dev/install.sh | sudo bash
```

<Aside type="note">
The installer needs root to write to `/etc`, `/usr/lib`, and the systemd
unit directory. If you pipe through plain `bash` (no `sudo`), it re-execs
itself under `sudo` automatically — as long as `sudo` is on `PATH`.
</Aside>

## Channels

By default the bootstrap fetches the latest `stable` release manifest.
Pick a different channel with `HAL0_CHANNEL`:

```sh
HAL0_CHANNEL=preview curl -fsSL https://hal0.dev/install.sh | sudo bash
```

Accepted values: `stable` (default), `preview`, `nightly`.

## Requirements

- **curl** and **ca-certificates** — the one-liner needs them to fetch the
  bootstrap at all. Minimal cloud/LXC images, including a stock Ubuntu 24.04
  Proxmox container, ship without curl:
  `apt-get update && apt-get install -y curl ca-certificates` (or the
  equivalent for your distro). The bootstrap then checks for `tar`,
  `sha256sum`, `jq` and `python3`, installs any that are missing with the
  system package manager, and fetches its own pinned `cosign`.
- **Linux, x86_64** — hal0 ships amd64-only binaries (the FastFlowLM
  `.deb` and the runner container images). ARM and macOS/Windows are not
  supported.
- **systemd** — `systemctl` must be on `PATH` (outside `--dev` mode).
- **Python 3.12 to 3.14** — hal0 requires `>=3.12` and is tested on 3.12, 3.13 and 3.14. If the default `python3` is older, the installer uses `python3.14`, `python3.13` or `python3.12` when one is already on `PATH`, and otherwise tries to install `python3.12` through apt or dnf. If none can be found or installed it stops with a remediation hint (`HAL0_PYTHON=python3.12`).
- **Python for the memory engine** — the Hindsight memory engine builds its own venv and accepts Python 3.11 to 3.14. The installer picks one (installing it when it can) before it does anything else, so a host with none finds out up front. If none is usable, the memory engine is skipped for that run and the rest of the install continues; point `HAL0_HINDSIGHT_PYTHON` at a 3.11-3.14 interpreter and re-run to add it.
- **Network for the first Hermes build** — the bundled Hermes agent builds on its own Python 3.14, never on hal0's interpreter. It uses a uv-managed CPython kept under `/var/lib/hal0/hermes/python/`, or a suitable system interpreter. The first build downloads Hermes's dependencies (and the interpreter, when uv-managed), so the host needs internet access when Hermes is provisioned.
- **A container runtime** — every inference slot runs in a container.
  The installer prefers **podman** (auto-installed if neither podman nor
  docker is found); **docker** is accepted if already present.
- **Node.js** — only needed to build the dashboard UI from a source/git
  checkout. Signed release tarballs ship a prebuilt `ui/dist` and skip
  this requirement entirely; the installer auto-provisions Node when it's
  needed and can't find a suitable version.

## What the installer does

The bootstrap hands off to `installer/install.sh`, which runs 16 steps,
in order:

<Steps>

1. **Pre-flight checks** — architecture, systemd, Python, container
   runtime, disk space, free ports.
2. **System user** — creates the `hal0` service account.
3. **Filesystem layout** — creates the FHS directory tree (or the `--dev`
   tree under `$PWD/.hal0ai`).
4. **Python environment** — builds the shared venv and `pip install`s
   hal0 into it.
5. **Node.js toolchain** — provisions Node only if this tree ships the
   dashboard's npm project.
6. **Dashboard UI** — builds `ui/dist` (or reuses a release's prebuilt
   copy).
7. **Configuration** — writes `/etc/hal0/hal0.toml`, `api.env`,
   `upstreams.toml`, `openwebui.env` — never overwriting existing files.
8. **Systemd units** — writes and enables `hal0-api.service` and
   `hal0-openwebui.service` (unless `--no-start`).
9. **Container slot seeds** — copies default slot TOMLs into
   `/etc/hal0/slots/` (never overwriting operator edits).
10. **Hardware probe** — detects CPU/RAM/GPU/NPU and writes
    `/etc/hal0/hardware.json`.
11. **Steward + agent models** — seeds a hardware-recommended slot and
    profile.
12. **NPU prerequisites** — installs the FastFlowLM runtime on
    AMDXDNA/apt hosts (fail-soft elsewhere).
13. **ComfyUI model share** — sets up the image-generation model path.
14. **Bundle picker manifests** — writes the dashboard's first-run bundle
    catalog.
15. **Bundled agent skills** — installs the shipped agent skill set.
16. **Service start** — starts `hal0-api` and `hal0-openwebui` (unless
    `--no-start`), waits up to 60 s for `/api/health` to answer before the post-install checks run, stands up the Hindsight memory engine, then provisions the bundled Hermes agent (skip with `HAL0_SKIP_HERMES=1`; install later with `hal0 agent install hermes`). Hermes provisioning builds a release and can take a few minutes.

</Steps>

The installer is **idempotent** — safe to re-run after a partial failure,
or just to pick up new configuration defaults. Existing config files are
never clobbered, and a unit you disabled or masked (for example
`hermes-gateway.service`) is left off on re-run; the installer prints the
`systemctl` command to turn it back on.

## Flags and environment variables

```sh
curl -fsSL https://hal0.dev/install.sh | sudo bash -s -- --no-start --models-dir=/mnt/ai-models
```

| Flag | Effect |
|---|---|
| `--dev` | Local-only editable install under `$PWD/.hal0ai` — no systemd, no host package changes |
| `--no-start` | Set everything up but do not enable/start the units |
| `--models-dir=PATH` | Absolute path where Hugging Face pulls land (same as `HAL0_MODELS_DIR`) |
| `--summary-json=PATH` | Write a versioned, machine-readable install summary to `PATH` once the install finishes (see below) |

| Variable | Default | Purpose |
|---|---|---|
| `HAL0_PREFIX` | `/usr/lib/hal0` | Installation root (versioned dir + `current` symlink) |
| `HAL0_PORT` | `8080` | API bind port |
| `HAL0_PYTHON` | `python3` | Python interpreter to build the venv from |
| `HAL0_MODELS_DIR` | `/var/lib/hal0/models` | Where Hugging Face pulls land |
| `HAL0_NONINTERACTIVE` | _(unset)_ | Set to `1` to force flag/env values everywhere instead of prompting on a terminal |
| `HAL0_NO_PROBE` | _(unset)_ | Set to `1` to skip the hardware probe / first-run seeding |
| `HAL0_SKIP_HINDSIGHT` | _(unset)_ | Set to `1` to skip installing the Hindsight memory service |
| `HAL0_PY_AUTOINSTALL` | _(unset)_ | The installer already sets this itself when the default Python is below 3.12, so you rarely need it; it allows installing `python3.12` via apt or dnf when no 3.12-3.14 is on `PATH`. Other distros need `HAL0_PYTHON` pointed at a newer interpreter |
| `HAL0_HINDSIGHT_PYTHON` | _(auto)_ | Interpreter (Python 3.11-3.14) for the Hindsight memory engine venv; use it when the installer reports none usable |
| `HAL0_SKIP_HERMES` | _(unset)_ | Set to `1` to skip provisioning the bundled Hermes agent; install it later with `hal0 agent install hermes` |

### Install log and failure reports

Every run tees its full output to `/var/log/hal0/install-<ts>-<random>.log`
(`/tmp/hal0-install-<random>.log` when not root) — the path is printed at the
start and end, and `hal0 doctor bundle` includes the latest one. If the
installer aborts, it also writes a redacted `hal0-install-report-<ts>-<random>.txt`
next to the log (environment, failed units, Podman state, port owners, unit
status, redacted config, hardware summary, log tail, hal0-api journal) and
prints its path. Secret values are masked throughout the report, not only
where their key names them. See `installer/README.md` for the full
breakdown of what each report contains.

### `--summary-json`

```sh
sudo bash installer/install.sh --summary-json=/tmp/hal0-install-summary.json
```

Writes a `schema: "hal0.install-summary.v1"` JSON document — hal0 version,
`--dev`/`--no-start` flags, models dir, network bind info, the detected
hardware class, which brain model was pulled, a warning/error count, and
measured per-step durations — atomically, so a script polling for the file
never reads a half-written one. Full field reference and an example payload
are in `installer/README.md`.

## Production filesystem layout

```
${HAL0_PREFIX}/hal0-<version>   # versioned code tree
${HAL0_PREFIX}/current          # symlink hal0 update swaps atomically
/etc/hal0                       # config: hal0.toml, slots/, profiles.toml
/var/lib/hal0                   # state: models, registry, slots, openwebui, cache
```

Under `--dev`, all of the above lands under `$PWD/.hal0ai/` instead.

## Verify the install

```sh
hal0 status
hal0 slot list
curl http://localhost:8080/api/health
journalctl -fu hal0-api
```

`hal0 status` reports system + slot + memory health; `hal0 slot list`
shows configured slots; the `/api/health` curl is a lightweight liveness
probe (200 the moment the API is serving); `journalctl -fu hal0-api`
tails the control-plane log if something looks wrong. The installer itself
waits up to 60 s for `/api/health` after starting `hal0-api`. For the full
six-step "did it work" checklist — health, model list, first chat,
dashboard, logs, and `hal0 doctor verify` — see
[Verify the install](/docs/getting-started/verify/).

## Uninstall

```sh
hal0 uninstall              # conservative: keep /etc/hal0 + models/registry
hal0 uninstall --purge      # clean slate: also wipe config, data, user, images
```

The conservative default stops services and removes code, units, venvs,
binaries, and every hal0 podman container, but keeps `/etc/hal0` (config)
and the data directory (models, registry, OpenWebUI state) so a re-install
reuses them. `--purge` additionally removes the
config and data directories, the `hal0` system user and group, and all
hal0 runner and OpenWebUI podman images — it prompts for a typed `DELETE` confirmation
unless you pass `--force` (or set `HAL0_FORCE=1`).
