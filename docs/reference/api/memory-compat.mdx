`/api/memory/compat` speaks the memory engine's own REST protocol
([ADR-0058](/docs/adr/0058-memory-v3-one-surface-guarded-embedder), decision 4b). It exists for
one client: the Hindsight coding-agents plugin that Claude Code, Codex and Pi use, which talks to
the engine directly and so bypasses everything hal0 does to a memory write. Pointed here instead,
its writes go through the same write envelope as every other hal0 writer, and its reads are held
to one project.

It is not a proxy. hal0 answers a fixed list of routes, parses each request, and forwards only
the fields it names. Everything else is refused or ignored as described under
[What is refused or ignored](#what-is-refused-or-ignored).

Two hal0 commands point a client here, each in that harness's own section of
`~/.hindsight/coding-agent.json` (`harnesses.<harness>.apiUrl` and `apiToken`, which the plugin
lays over the file's flat keys): `hal0 agent install pi` and `sudo hal0 update component pi`, with
the hal0-managed bridge client `pi-coder`, and `hal0 memory agents install <harness>
--bridge-key-file <path>` for the other harnesses ([CLI reference](/docs/reference/cli-operator/)).

## Base URL and auth

The plugin builds every URL as `apiUrl` + the engine's path, so its `apiUrl` is hal0's origin
plus the prefix:

```
http://<hal0 host>:8080/api/memory/compat
```

The whole prefix is **BRIDGE** class, for every method: it is never open, whatever
`[security] require_auth` says and from loopback too. A request needs one of:

| Credential | Result |
|---|---|
| A bridge key that holds the `memory` scope (`Authorization: Bearer hal0bk_…`) | Admitted. The caller's identity is the bridge client's name. |
| The admin key, or a dashboard session | Admitted. The identity is `admin`. |
| A bridge key without the `memory` scope | `403 memory.compat_scope_required` |
| A bridge key whose client name hal0 has since reserved (`unknown`, `unresolved`, ...) | `403 bridge.client_name_reserved` (from the auth layer, on every bridge surface) |
| The box client key | `403 auth.forbidden` |
| Nothing, or a revoked key | `401 auth.required` |

`hal0 bridge add <name>` mints a key with the `agents` and `memory` scopes by default
([Agent bridge API reference](/docs/reference/api/bridge/)). The `X-hal0-Agent` and
`X-hal0-Private` headers are not read here.

## What a client can and cannot do

Every client of this endpoint shares one bank with every other client and with hal0's own
agents. These rules hold whatever a client sends:

| A client… | How |
|---|---|
| writes only as itself | every write is tagged `agent:<client name>`; `agent:` and `visibility:` tags it sends are dropped |
| writes into one project, or none | the project is resolved by hal0 from the bank name; `project:` tags it sends are replaced |
| never writes global memory | `scope:` tags it sends are dropped. A write here carries a project, or `project:unresolved` |
| cannot replace, extend or delete another client's document | [document ids](#document-ids) are stored in the client's own namespace |
| reads one project plus global memory | [the read filter](#what-a-read-sees) is built by hal0 and can only be narrowed |
| never reads another agent's private memory | same filter |
| sees only its own operations | [operation ids](#operations) are derived from the client's name |
| cannot change or delete the bank | template imports are ignored, bank deletes refused |
| sees and changes only its project's [knowledge pages](/docs/reference/api/memory-compat-knowledge-base), and changes only its own | one folder per project; the writer's `agent:` tag decides |

What clients of one project do share: the project's non-private memory (all of them read it),
and the documents whose ids start with a shared prefix (any of them may rewrite one).

## The bank, and the project it carries

Every engine route is addressed to a bank: `…/v1/default/banks/{bank}/…`. Whatever bank a request
names, hal0 sends the engine call to the **platform bank** (`[memory] bank`). No bank is created,
and a client cannot reach any other bank through this endpoint.

The bank name is still read, because it is the only place the plugin can say which project it is
working in. Its default bank id is `coding-agent::<directory>`, where `<directory>` is the
directory name of the repository's main worktree. hal0 takes the part after `::` and resolves it
through `[memory.projects]` ([Projects in memory](/docs/concepts/memory-projects/)):

| The bank in the URL | Project |
|---|---|
| `coding-agent::widgets` | `widgets` |
| `coding-agent::widgets-monorepo`, with the alias `widgets-monorepo = "widgets"` | `widgets` |
| `coding-agent::tmp` (a name on the deny list) | none: the caller is *unresolved* |
| `claude-code`, `Team::Agents`, `coding-agent::unknown` (no project part) | taken from the request's own `project:` tags; with none, or with several, *unresolved* |

A response to a bank-scoped route carries `X-hal0-Project` with the resolved slug, or
`unresolved`.

## Document ids

The engine replaces or extends a document when a retain names an id that already exists, and the
plugin picks its ids as if it had a bank to itself (`conversation:<session>`, a slug of a
document's title, `git:<sha>`). So hal0 stores a client's document under a longer id and gives
the client its own id back:

| The client sends | Stored as |
|---|---|
| `readme`, working in project `widgets` as client `cc` | `widgets::cc::readme` |
| `git:4f2a9c1` (an id with a shared prefix) | `widgets::shared::git:4f2a9c1` |
| `readme`, with no project | `unresolved::cc::readme` |

- The prefix is added to every id a client sends, on a retain and on a delete, and removed from
  every id it gets back. An id that itself contains `::` is still the client's id, whole.
- A client can only address its own namespace and its project's shared one. Any other document,
  another client's or one hal0's own agents wrote, does not exist as far as this endpoint can
  tell.
- The shared prefixes are `[memory.compat] shared_document_prefixes`
  ([config reference](/docs/reference/config-schema/)), by default `git:`, `gitlog:` and
  `survey-baseline:`: the ids the plugin derives from the repository itself, which a second
  agent on the same repository should find already ingested. A prefix is at least three
  characters and ends with `:`. A client with no project has no shared namespace.
- A stored id must stay usable in hal0's own bank routes: at most 256 characters of
  `a-z A-Z 0-9 . _ : -`, with no `..`. An id that would not fit is stored as
  `<project>::<owner>::sha256-<hex>` and the client's id is kept in the document's metadata as
  `client_document_id`, from which the client that wrote it is shown it back.
- A shared id that would not fit keeps its shared prefix: `git:<300 characters>` is stored as
  `<project>::shared::git:sha256-<hex>`. Another client of the project sees it as
  `git:sha256-<hex>`, which is itself a shared id and names the same document when sent back.
- A retained item that names no `document_id` gets a new one in the client's namespace.

### Retain

Body: `{items: [...], async?, operation_id?}`, at most 32 items and 48 MiB.

Each item is written as a coding client's memory, by `HindsightProvider.retain_items`:

| Item field | What happens |
|---|---|
| `content` | passed as sent; at most `[memory.compat] max_item_bytes` (16 MiB) of UTF-8, else `413 memory.compat_item_too_large` |
| `context`, `timestamp`, `entities`, `update_mode` | passed to the engine as sent |
| `document_id` | stored in the client's namespace, see [Document ids](#document-ids) |
| `tags` | any `agent:` tag is replaced by `agent:<caller>`; any `visibility:`, `scope:` and `source:bridge:` tag is dropped; every `project:` tag is replaced by the one resolved project tag (`project:unresolved` when there is none); a session id (`session:<id>`, a bare UUID) and a lifecycle word (`checkpoint`, `session-end`, …) move to metadata; `kind:durable` is added unless the caller sent a `kind:` or a lifecycle word (then `kind:ephemeral`). Everything else, `harness:` and `source:` included, is kept |
| `metadata` | kept, plus `bridge_client` (the caller), `project` and `project_source`. `source` becomes the caller's name and the value the client sent is kept as `client_source`. A client cannot set `bridge_client`, `project`, `project_source`, `client_source` or `client_document_id` |
| `observation_scopes` | ignored. hal0 chooses: the project's scope, or for an unresolved write `[project:unresolved, agent:<caller>]`, so its observations stay the caller's own |
| `strategy` | kept only when the platform bank defines a retain strategy of that name; otherwise dropped, and the bank's default applies. The bank's configuration is read at most every 5 minutes |

`async` is passed on as sent, and all items go to the engine in one call. An asynchronous retain
is an operation: the engine is given an operation id derived from the client's name and the
`operation_id` the client sent, and the answer carries the client's own id. A resend with the
same id is therefore still the same operation, and one client's id can never name another
client's. A client that sends no `operation_id` is given one. A synchronous retain has no
operation.

An asynchronous retain is accepted at once and processed later, so each client is held to a
quota of unfinished ones: `[memory.compat] max_outstanding_operations` (64) operations and
`max_outstanding_bytes` (256 MiB) of request bodies. Beyond either, an asynchronous retain is
`429 memory.compat_busy` with `Retry-After: 30` until earlier ones finish. hal0 learns that an
operation finished from the client's own status polls, and reads the oldest from the engine
itself before it refuses (at most once every 5 seconds per client). A resend of an operation
already counted, a synchronous retain, and a single retain while nothing is outstanding are
never refused by the quota. The count is kept in the hal0-api process: after hal0-api restarts,
operations submitted before the restart are not counted.

### What a read sees

A reflect, a recall and a documents listing are all held to two rules, and both go to the engine
as a tag filter:

1. **Visibility.** A memory another agent marked private is never returned. The caller's own are.
2. **One project.** With a project: memories tagged with that project, global memories
   (`scope:global`) and memories with no tags at all. For an unresolved caller: global memories,
   untagged memories, and the caller's own `project:unresolved` writes.

There is no way to read across projects through this endpoint. A request's own `tags`,
`tags_match` and `tag_groups` are added to the filter and can only narrow it.

A reflect forwards `query`, `budget`, `max_tokens` and `response_schema`. Mental models are left
out of it while the bank holds other agents' private memories, as on
`POST /api/memory/reflect`. If the client disconnects while the engine is still working, hal0
closes its request to the engine, and the engine stops the reflect.

### Recall

Forwards `query`, `types`, `budget`, `max_tokens`, `query_timestamp`, `min_scores`,
`prefer_observations`, and `chunks` / `source_facts` under `include`. The answer has the engine's
shape (`{results, …}`), with these changes:

- `entities` is always `null`. An entity's state is built from the whole bank.
- `trace` is never requested or returned.
- **A result the caller wrote** (it carries `agent:<caller>`) is returned whole, with its
  `document_id` as the client knows it and its chunk id rewritten the same way.
- **Any other result**, another client's or one of hal0's own agents', is reduced to an
  allow-list: `id` (the engine's id for the memory), `text`, `type`, `occurred_start`,
  `occurred_end`, `mentioned_at`, and of its `tags` only the project tag, `scope:global` and
  the `kind:`, `knowledge:` and `source:` tags (never `source:bridge:`). Its `document_id` is
  `null` and its `chunk_id` an opaque value. Its `metadata`, `context`, `entities`, scores,
  `agent:` tag and any field not named here are not returned: they name the client that wrote
  it, its session and its document.
- `source_facts` are kept where one of the caller's own results refers to them, each reduced
  the same way when it is not the caller's. `chunks` are kept only for the caller's own results.

### Documents

The engine's listing takes one flat set of `tags` and one `tags_match`, not `tag_groups`, so the
strictest filter it can express is "carries all of these". hal0 sends the caller's project tag
(plus, for an unresolved caller, its own `agent:` tag) together with the request's own tags, with
`tags_match=all_strict`, and then keeps only the rows whose stored id is in one of the client's
namespaces and that are not private to another agent. The consequences:

- The listing shows the client's own documents and its project's shared ones, under the client's
  ids. Documents another client or hal0's own agents wrote into the project under ids of their
  own are not in it, and neither are global documents.
- A shared document another client wrote last is listed as `id`, `created_at`, `updated_at`
  and its descriptive tags (the same tag rule as in [Recall](#recall)), and nothing else: not
  its metadata, its retain parameters or its writer's tags.
- `tags_match` on the request must be `all` or `all_strict`, or anything over at most one tag.
  `exact`, and `any` over several tags, are `400 memory.compat_filter_unsupported`.
- A `project:` tag in the request is replaced by the resolved one. `q` and `offset` are
  forwarded; `limit` is at most 500. Other parameters are not forwarded.
- When rows were left out, hal0 reads up to three more pages from the engine to fill the page,
  so a page is shorter than `limit` only when the engine has no more rows. Rows read that way can
  appear again on the next page. `X-hal0-Listing-Incomplete: 1` marks the rare page that is
  short although the engine had more.
- `total` counts only what the client can see: `offset` plus the rows returned, plus one when
  the page is full. Neither the engine's count nor the number of rows left out is passed on,
  because with a chosen `q` or `tags` either would confirm another agent's private document.

`DELETE …/documents/{document_id}` looks the id up in the client's namespaces only. A document
that is not there is `404 memory.compat_document_not_found`, whether or not something else by
that name exists elsewhere. The document must carry `agent:<caller>`; a shared document another
client wrote last is `403 memory.compat_document_not_owned`. A delete is recorded in the activity
log with the actor `bridge:<caller>`.

### Operations

An operation is the client's own or it does not exist:
`GET …/operations/{operation_id}` asks the engine for the operation derived from this client and
that id, so an id the client did not start, another client's included, is
`404 memory.compat_operation_not_found`. This needs no bookkeeping and answers the same after
hal0-api restarts.

`GET …/operations` lists the client's own operations, newest first. The engine's own list covers
every client and does not say who started what, so hal0 does not read it: the list is the
operations this hal0-api process has seen the client start, and each unfinished one is read from
the engine by its id. `limit` (at most 100) and `offset` index into the client's own operations
and are not sent to the engine; `status` and `type` filter them; `total` counts them. After a
restart the list is empty until the client retains again.

`X-hal0-Listing-Incomplete: 1` is set when the list may be missing operations: hal0 remembers
2000 operations per client and drops the oldest finished ones beyond that, and it reads at most
the 64 newest unfinished operations per request.

Both routes return statuses and nothing a client submitted: `id`, `operation_id` (the client's
own id), `task_type`, `operation_type`, `status`, `items_count`, `created_at`, `updated_at`,
`completed_at`, `retry_count`, `next_retry_at`, `error_message` cut to 500 characters, the
`stage`, `at`, `processed` and `total` of `progress`, and each child operation's status and item
count. Payloads, result metadata, document ids and engine ids are not returned, and the client's
stored-id prefixes are removed from `error_message`.

## Limits

| Limit | Value | Beyond it |
|---|---|---|
| Retain body | 48 MiB | `413 memory.compat_body_too_large` |
| Items per retain | 32 | `413 memory.compat_too_many_items` |
| One item's `content` | `[memory.compat] max_item_bytes`, 16 MiB | `413 memory.compat_item_too_large` |
| Reflect or recall body | 1 MiB | `413 memory.compat_body_too_large` |
| Knowledge-base write body | 256 KiB | `413 memory.compat_body_too_large` |
| `budget` | `low`, `mid` or `high` | `400` |
| `max_tokens` | 8192 on a reflect, 16384 on a recall | lowered to the limit |
| Documents `limit` | 500 | lowered to the limit |
| `operation_id` | 200 characters | `400` |
| Operations `limit` | 100 | lowered to the limit |
| Retains in flight, per client | 4 | `429 memory.compat_busy`, `Retry-After: 2` |
| Retain bodies over 1 MiB in flight | 2 across all clients, 1 per client | `429 memory.compat_busy`, `Retry-After: 2` |
| Unfinished asynchronous retains, per client | `[memory.compat] max_outstanding_operations`, 64, and `max_outstanding_bytes`, 256 MiB | `429 memory.compat_busy`, `Retry-After: 30` |
| Reflects in flight, per client | 1 | `429 memory.compat_busy`, `Retry-After: 15` |
| Reflects in flight, all clients | `[memory.compat] max_concurrent_reflects`, 2, and never more than one fewer than the engine runs | `429 memory.compat_busy`, `Retry-After: 15` |
| Recalls in flight, per client | 2 | `429 memory.compat_busy`, `Retry-After: 5` |
| Recalls in flight, all clients | `[memory.compat] max_concurrent_recalls`, 4 | `429 memory.compat_busy`, `Retry-After: 5` |

The item limit is sized for the largest thing the plugin sends, a whole session transcript.

A retain body of at most 1 MiB is read at once. A larger one, or one that does not declare its
size, takes one of two slots shared by all clients, which keeps the memory hal0-api spends on
retain bodies near 300 MiB however many clients send at once. A body that declares a small size
and turns out larger is cut off at 1 MiB with `413`.

The engine runs `[memory.lanes] llm_max_concurrent` language-model calls at once (one, as
shipped), and a reflect's at most `[memory.lanes.reflect] max_concurrent` of them when that is
set. Reflects through this endpoint always leave one of those slots to hal0's own agents and the
dashboard, so with the shipped lanes one reflect runs here at a time whatever
`max_concurrent_reflects` says.

All of these are counted in the hal0-api process and start empty when it restarts.

## What is refused or ignored

| Request | Answer | Why |
|---|---|---|
| A field the route does not name | dropped; listed in `X-hal0-Ignored-Fields` | A field hal0 has not examined never reaches the engine |
| `scope:`, `agent:`, `visibility:`, `project:`, `source:bridge:` tags on a retain | dropped or replaced | See [What a client can and cannot do](#what-a-client-can-and-cannot-do) |
| `observation_scopes` on a retain | ignored | hal0 chooses the scope |
| `POST …/import` (a bank template) | `200`, not applied | hal0 owns the platform bank's missions, strategies and directives. The plugin sends its template on every configure pass and raises on a refusal |
| `DELETE …/banks/{bank}` | `403` | Every bank name is the shared platform bank |
| Knowledge-base routes for a client with no project | `404` | The plugin reads this as "no pages on this server" and carries on without them |
| An engine `404` on a knowledge-base write | `502` | The plugin would read a `404` as "no pages" and stop writing them |
| Any other read | `404`, with the served routes in `error.details.supported` | |
| Any other write | `405` | A `404` would be treated by the plugin as done |
| An engine `404` on a retain | `502` | The same reason: a write must never answer `404` |

## Errors

A failure hal0 raises is the standard envelope `{"error": {"code", "message", "details"}}`.

| Status | Code | When |
|---|---|---|
| 400 | `request.invalid_json`, `validation.invalid` | The body is not a JSON object, or a field has the wrong type or value |
| 400 | `memory.compat_filter_unsupported` | A documents listing with a `tags_match` that cannot be combined with the project |
| 400 | `memory.compat_document_id_reserved` | A retain in a project literally named `private`, whose stored ids the bank reserves |
| 401 | `auth.required` | No credential, or a key that does not verify |
| 403 | `auth.forbidden` | The box client key |
| 403 | `memory.compat_scope_required`, `bridge.client_name_reserved` | A bridge key without the `memory` scope, or under a reserved name |
| 403 | `memory.compat_document_not_owned` | Deleting a shared document another client wrote last |
| 403 | `memory.compat_bank_delete_refused` | `DELETE` on a bank |
| 403 | `memory.compat_knowledge_parent_refused` | See [Knowledge pages](/docs/reference/api/memory-compat-knowledge-base) |
| 404 | `memory.compat_document_not_found`, `memory.compat_operation_not_found` | A document or operation that is not the client's own |
| 404 | `memory.compat_knowledge_base_unsupported` | A knowledge-base route this endpoint does not serve, or any for a client with no project |
| 404 | `memory.knowledge_page_not_found`, `memory.compat_knowledge_page_not_owned`, `memory.compat_knowledge_node_refused` | A page the client's tree does not show, or may not change |
| 404 | `memory.compat_route_unsupported` | A read this endpoint does not serve |
| 405 | `memory.compat_mutation_unsupported` | A write this endpoint does not serve |
| 413 | `memory.compat_body_too_large`, `memory.compat_too_many_items`, `memory.compat_item_too_large` | See [Limits](#limits) |
| 429 | `memory.compat_busy` | Too many retains, reflects or recalls in flight, or the client's quota of unfinished retains is used up; `Retry-After` says when to retry |
| 502 | `memory.compat_engine_error` | The engine answered `5xx`, refused hal0's own credential, or answered `404` to a retain. `error.details.upstream_status` has its status |
| 503 | `memory.engine_unavailable`, `memory.unavailable` | The engine cannot be reached, or hal0 is running on its volatile fallback store |
| 503 | `memory.writes_paused` | `POST .../memories`, `DELETE .../documents/{id}` and the three knowledge-base writes while `hal0 memory embedder switch` holds the memory write gate, checked before any engine call; `Retry-After: 30`, the same answer as `POST /api/memory/add`. Reads are not gated |
| 503 | `memory.extraction_ctx_too_small` | The extraction model's context window is too small to process any retain |
| 504 | `memory.compat_engine_timeout` | The engine did not answer within the route's timeout |

Any other `4xx` from the engine is passed through with the engine's own status and body, and its
`Retry-After` header: a `422` for a value the engine rejects, a `429`. Stored-id prefixes are
removed from such a body first.
