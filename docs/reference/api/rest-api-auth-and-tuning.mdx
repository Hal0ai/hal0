## Auth tiers

Every route resolves to one of five classes in `src/hal0/security/exposure.py`
(`hal0.security.exposure.classify`), evaluated first-match-wins against an explicit
rule table:

- **OPEN** — no auth ever. A deliberately tiny, enumerated allowlist (the `/v1/models`
  probe, the Prometheus scrape, the two liveness checks, the dashboard bootstrap-urls
  endpoint, the login/status/logout routes themselves, the static SPA shell — same
  HTML/JS bundle for every visitor, no server data — and the Hermes
  dashboard-plugin static asset proxy at
  `/dashboard-plugins/{plugin_name}/{file_path}`).
- **BOOTSTRAP** — open only until an admin key is configured (`/api/install/*`).
- **CLIENT** — the `/v1/*` inference/writer surface plus a short list of genuinely
  read-only introspection `GET`s.
- **BRIDGE** — the agent bridge's own surfaces (ADR-0043): `GET /api/bridge/me`, the
  `/mcp/agents` mount and `/api/memory/compat`, open to a bridge client key (`hal0bk_…`) or
  the admin key and never to the dev-open bypass.
- **ADMIN** — everything else, including every mutating route and every route that can
  return secrets or config. **Unclassified paths fall back to ADMIN** (deny-by-default).

These classes are fully enforced once `[security].require_auth` is on. While it's off,
the surface is trusted-LAN-open with one exception (since v1.3.0): with an admin key
configured and the API bound past loopback, ADMIN-class requests from a non-loopback
peer still need an admin credential (`_lan_admin_gate` in `src/hal0/api/auth.py`; see
[Authentication](/docs/operate/auth/)). The table below states
each group's class as enforced by `exposure.py`, not as a claim about the current
default posture.

<Aside type="note">
`src/hal0/api/routes/events.py`, `activity.py`, and `journal.py` each carry a
module docstring claiming "no auth dependency" / "no auth gate" for first-run UX
reasons (the dock's events pane must render before any credential
exists). `exposure.py`'s own module docstring names eight routes not spelled out
in either explicit OPEN/CLIENT bucket list — `/api/status`, JSON `/api/metrics`,
`/api/features`, `/api/logs`, `/api/events`, `/api/activity`, `/api/journal`, and
the dashboard-plugin manifest — as an "UNSURE — please review" bucket that
defaults to ADMIN except where a close analogy to an existing CLIENT bucket
argued otherwise: `/api/status` and JSON `/api/metrics` were reasoned across to
CLIENT (and `/api/features` GET separately resolves CLIENT via its own exact-match
rule). That leaves `/api/logs`, `/api/events`, `/api/activity`, `/api/journal`,
and the dashboard-plugin manifest as the UNSURE items that actually landed
ADMIN. If `require_auth` is ever turned on, the events/activity/journal panels
will 401 during first-run before a credential exists — contradicting the
rationale their own route files state. Flagging this as a real discrepancy
between route-level intent and the enforced classification, not a doc error to
silently paper over.
</Aside>

## Slot tune API

`PUT /api/slots/{name}/config` accepts `{"tune":{"vision":"off"}}`.
Only supplied keys change. A null key removes one override; `{"tune":null}`
removes all. Slot creation applies the same type/device and thinking guards.

Slot snapshots (`GET /api/slots`, `GET /api/slots/{name}`) expose
`model_id`, which follows the slot's state: a serving slot (`ready`,
`serving`, `idle`) names the model it is serving, even if the slot's binding
was cleared after the load; a cold slot (`offline`, `error`) names its
configured `[model].default` binding; a loading slot (`pulling`, `starting`,
`warming`) names the model it is actually pulling or warming; and it is
`null` for any non-serving slot whose binding is empty and whose provider
requires an explicit model.

Slot snapshots also expose
`tune_effective`: `ctx_size`, `enable_thinking`, `reasoning_effort`,
`reasoning_budget`, `vision`, `speculation`, `sources`,
`reasoning_effort_unavailable` and `tune_unavailable`. So does
`GET /api/slots/{name}/resolved` for a llama-server slot; the answer for a halogen
slot, like that of every other non-llama runtime, has `argv: null` and no
`tune_effective`. Sources are `profile`, `slot` or `profile-flags`;
`reasoning_effort_unavailable` is a string or null. `tune_unavailable` maps each
tune value the slot's engine cannot run to the reason, and is `{}` on a
llama-server slot; on a halogen slot it is
`{"speculation": "ngram: this engine has no n-gram drafter (auto or off)"}`.
This is an additive read contract. Model feasibility accepts a `slot` name per model
row to resolve its profile plus tune for the candidate; explicit `ctx` wins.

Every `GET /api/slots/{name}/resolved` answer also carries `footprint`: `null` for a
slot that is not on the halogen runtime and for a halogen slot with no model bound
or no figure, otherwise `{"resident_mb", "advisory_cache_mb", "host_free_mb",
"verdict"}`. `resident_mb` is the memory the engine's layout holds once loaded (the
checkpoint, KV pool, per-slot state, working memory, prompt cache and vision tower,
never the lookup table); `advisory_cache_mb` is the page cache the lookup table
wants, about 10 GiB, which is advised and never part of `resident_mb`;
`host_free_mb` is the host's free GTT pool, `null` when the host does not expose it.
`verdict` is the advisory fit of the first against the third: `fits`, `tight`
(within 10% of what is free), `exceeds`, `exceeds_total` (more than the whole pool)
or `unknown` (no host reading), and `loaded` when the slot already holds the memory.
It never blocks a load. The drawer may pass `profile` and `flags` query parameters to
preview the currently displayed engine settings; `flags` replaces the selected
profile's flags for sizing only. Omit them for the saved slot profile. The
preview uses the same provider footprint resolver and does not persist settings.
While the slot drawer is open, the UI refreshes this readout every eight seconds
so a load or unload performed elsewhere updates its verdict.
