hal0-api serves an OpenAI-compatible `/v1/*` inference surface (see
[OpenAI-compatible API reference](/docs/reference/api/openai-compat/)) plus an `/api/*`
management surface that backs the dashboard and the `hal0-admin` MCP server. This page
indexes every `/api/*` router group mounted in `src/hal0/api/__init__.py` — for full
request/response schemas for a given route, read the OpenAPI spec served live at
`/api/openapi.json` (interactive docs at `/api/docs`).

<Aside type="caution">
Unlike pre-1.0 docs may claim, auth is **not** unconditionally removed in this tree.
`[security].require_auth` (overridable via `HAL0_REQUIRE_AUTH`) and the `hal0 auth`
CLI group (`status`, `rotate`, `require`) are live — see
[Config schema](/docs/reference/config-schema/) (`[security]`) and
[CLI](/docs/reference/cli-operator/) (`hal0 auth`).
Verify the current default (`require_auth` defaults to `null`, which resolves to off)
before stating a blanket "no auth" or "auth required" claim.
</Aside>

## Auth tiers

Every route resolves to one of four classes in `src/hal0/security/exposure.py`
(`hal0.security.exposure.classify`), evaluated first-match-wins against an explicit
rule table:

- **OPEN** — no auth ever. A deliberately tiny, enumerated allowlist (the `/v1/models`
  probe, the Prometheus scrape, the two liveness checks, the dashboard bootstrap-urls
  endpoint, the login/status/logout routes themselves, the static SPA shell — same
  HTML/JS bundle for every visitor, no server data — and the Hermes
  dashboard-plugin static asset proxy at
  `/dashboard-plugins/{plugin_name}/{file_path}`).
- **BOOTSTRAP** — open only until an admin key is configured (`/api/install/*`).
- **CLIENT** — the `/v1/*` inference/writer surface plus a short list of genuinely
  read-only introspection `GET`s.
- **ADMIN** — everything else, including every mutating route and every route that can
  return secrets or config. **Unclassified paths fall back to ADMIN** (deny-by-default).

These classes are fully enforced once `[security].require_auth` is on. While it's off,
the surface is trusted-LAN-open with one exception (since v1.3.0): with an admin key
configured and the API bound past loopback, ADMIN-class requests from a non-loopback
peer still need an admin credential (`_lan_admin_gate` in `src/hal0/api/auth.py`; see
[Authentication](/docs/operate/auth/)). The table below states
each group's class as enforced by `exposure.py`, not as a claim about the current
default posture.

<Aside type="note">
`src/hal0/api/routes/events.py`, `activity.py`, and `journal.py` each carry a
module docstring claiming "no auth dependency" / "no auth gate" for first-run UX
reasons (the footer/journal/activity panels must render before any credential
exists). `exposure.py`'s own module docstring names eight routes not spelled out
in either explicit OPEN/CLIENT bucket list — `/api/status`, JSON `/api/metrics`,
`/api/features`, `/api/logs`, `/api/events`, `/api/activity`, `/api/journal`, and
the dashboard-plugin manifest — as an "UNSURE — please review" bucket that
defaults to ADMIN except where a close analogy to an existing CLIENT bucket
argued otherwise: `/api/status` and JSON `/api/metrics` were reasoned across to
CLIENT (and `/api/features` GET separately resolves CLIENT via its own exact-match
rule). That leaves `/api/logs`, `/api/events`, `/api/activity`, `/api/journal`,
and the dashboard-plugin manifest as the UNSURE items that actually landed
ADMIN. If `require_auth` is ever turned on, the events/activity/journal panels
will 401 during first-run before a credential exists — contradicting the
rationale their own route files state. Flagging this as a real discrepancy
between route-level intent and the enforced classification, not a doc error to
silently paper over.
</Aside>

roughly 43). `WS /v1/realtime` is documented separately — see
[Realtime API reference](/docs/reference/api/realtime/).

## Agent overview (`/api/agents/{name}/overview`)

`GET /api/agents/{name}/overview[?refresh=1]` is the one payload the dashboard's Hermes
and Pi cards render. ADMIN-gated with the rest of `/api/agents`. `name` is `hermes` or
`pi`; any other name is `404 agent.unknown`. The route builds the answer from live
probes and never fails for a normal box state: a missing systemd, a stopped gateway or
an unreadable file shows as `unknown`, empty or `null` in the matching key.

The probes are cached for 30 s per agent, counted from when the build finished, and
built once per miss: requests that miss while a build is running wait for it.
`?refresh=1` starts a new build and refills the cache. A Hermes build or repair starting
or ending is a miss too, so the state it leaves behind is never served from before it.
`generated_at` (an ISO-8601 UTC time, the start of the build behind the answer) tells a
client how old the probes are. `status`, `unit_active`, `units.agent`, `approvals.pending`,
`job` and `phase` are recomputed on every request.

A bundled agent that is not installed answers with only `name`, `kind`,
`installed: false`, `phase: "not_installed"`, `commands.install`, and the version it
would get: `pin` (`{ref, describe}`) for Hermes, `version` (`{installed: null, pin,
update_available: false}`) for Pi.

Hermes (`kind: "daemon"`):

| Key | Value |
|---|---|
| `name`, `kind`, `installed`, `status` | Identity and install state (`status` is `installed` or `broken`). |
| `unit_active` | `true`, `false`, or `null` when systemd cannot answer. |
| `version` | `live` and `previous` release (`id`, `ref`, `describe`, and for `live` also `built_at`, `python_minor`, `extras`, `platform_extras`, `hal0_version`), the `pin` (`{ref, describe}`), the `component` row (`installed`, `pinned`, `status`), and `update_available`. |
| `units` | `agent` is `active`, `inactive` or `unknown` (systemd could not answer). `gateway` is `active`, `inactive`, `failed`, `unknown`, or `absent` when the unit does not exist; its `activating`, `reloading`, `refreshing` and `maintenance` states read as `active` and `deactivating` as `inactive`, so a restart is not reported as down. The unit restarts forever (`Restart=always`) and never reaches `failed`, so `activating` with the `auto-restart` or `auto-restart-queued` sub-state is a crash loop and reads `failed`. `gateway_enabled` is `false` when the unit file is `disabled`, `masked` or `masked-runtime`, `true` for `enabled`, `enabled-runtime`, `static`, `linked`, `generated` and `transient`, and `null` otherwise. |
| `api_server` | `endpoint` (`host:port`, from config), `healthy`, and the `profiles` the gateway serves. The gateway and every profile are probed at once, with a 1 s timeout each. |
| `platforms` | Names of the configured gateway platforms. |
| `provision` | The last provision run: `present`, versions, `completed_at`, `reported_at` (the newest phase time), `phases`, `ok`/`warn`/`fail` counts, and the configured models, MCP servers, memory provider and approvals mode. `live_built_at` is when the live release was built, and `stale` is `true` when the report is older than that build: `hal0 update` rebuilds Hermes without rewriting `provision.json`, so a stale report no longer lists `provision_failed` or `provision_warn` in `degraded`. |
| `doctor` | Rows `{id, status, detail}` for `interpreter`, `plugins`, `ownership` and `gateway_unit`; `status` is `ok`, `warn`, `fail`, `absent` or `unreadable`. |
| `approvals` | `mode`, `effective`, `in_sync` and the `pending` approval count. |
| `memory` | `available`, `writes` and `last_write` of the agent's private namespace. |
| `links` | `desktop`: the `HAL0_HERMES_PUBLIC_URL` value without a trailing slash, or `null`. |
| `job` | The newest queued or running Hermes build, `{id, kind, state}` with `kind` `converge` or `repair`, or `null`. |
| `degraded` | Why a running Hermes is degraded: `{reason, detail, fix, command}`, where `fix` is one of `restart_gateway`, `repair`, `resync_approvals`, `cli` (a root command, in `command`) or `none`. A gateway the operator turned off (`gateway_enabled: false`) and a missing gateway unit raise no `gateway_down` (the `gateway_unit` doctor row names the install command), the API not answering is not raised while the gateway is starting, reloading or in maintenance, and `doctor_drift` is one reason per distinct fix (a `gateway_unit` row that is `unreadable`, because the check could not read Hermes' home, has fix `none`). |
| `phase` | `working`, `broken`, `unknown`, `down`, `degraded` or `ready`. The dashboard shows `ready` as `serving` when the agent slot is up. |
| `generated_at` | When the build behind the cached probes started. |

Pi (`kind: "cli"`):

| Key | Value |
|---|---|
| `name`, `kind`, `installed`, `status` | Identity and install state. |
| `version` | `installed` and `pin` as `{pi, adapter}` versions, and `update_available` (`true` when either is behind the installer's pin). |
| `profile` | The marker's `home` and `profiled_at`, `home_readable`, and `checks`: `{id, ok, detail}` rows where `ok` is `null` when the daemon cannot read the profiled home. |
| `memory` | `mcp_entry` and `hindsight_config` (from `profile.checks`), and `hindsight_api_reachable`. |
| `commands` | `install`, `upgrade` and `uninstall` commands to run as root. |
| `phase` | `installed` or `broken`. |

## Agent restart and repair

ADMIN-gated with the rest of `/api/agents`, no request body, `hermes` only (any other agent
is `404 agent.unknown`). Each action logs to `hal0.agents.audit` with `actor` (the
`X-hal0-Agent` header, `hal0-dashboard` when absent).

| Method | Path | Status | Notes |
|---|---|---|---|
| POST | `/api/agents/hermes/restart` | 200 | Restarts `hal0-agent@hermes.service` through the `hal0-systemctl` sudo wrapper, as the Services page does: hal0-api runs as the unprivileged `hal0` user, and a bare `systemctl restart` is denied by polkit. The command-approvals `PUT` restart takes the same path. Returns `{agent_id, unit, status: "restarted", detail}` once the verb exits 0. A failed verb is `500 agent.restart_failed` (the failure line, cut to 200 characters, in `message`); one still running after 90 s is `500 agent.restart_timeout`, outcome unknown. Events: `agent.restart.invoked`, then `.ok`, `.failed` or `.timeout`. |
| POST | `/api/agents/hermes/gateway/restart` | 200 | The same for `hermes-gateway.service`, with the same body (`unit` is the gateway's), errors and budget; `404 agent.not_installed` when Hermes has no install record. Events: `agent.gateway_restart.invoked`, then `.finished` (`status` is `restarted` or `error`). |
| POST | `/api/agents/hermes/repair` | 202 | Queues a repair job (below). |

A restart that went through drops the agent's cached overview.

### Repair job

`POST /api/agents/hermes/repair` runs `hal0 agent bootstrap hermes --repair --verbose` (the
code path of `hal0 agent reprovision hermes --repair`) as a child of hal0-api and returns the
queued job: `id`, `state: "queued"`, `phase: "repair:hermes"`, `kind`, `agent`, `steps: []`,
`log_path`, `created_at`, `updated_at`. The job is in the updater's registry, so
`GET /api/updates/status/{id}` serves it, and a repair and a converge refuse each other.

- `state` goes `queued`, `running`, then `applied` (exit 0) or `failed`. A running job has
  `pid` and `steps`, one entry per `[run ] <step>` line the provisioner prints. A finished one
  has `exit_code`; a failed one has `error`: `bootstrap exited <code>`, `could not start
  bootstrap: <os error>` or, after 45 minutes, `bootstrap timed out after 2700s`.
- The output goes to `log_path`,
  `/var/lib/hal0/state/agents/hermes/provision-logs/job-<id>.log` (`null` if it could not be
  opened; never pruned). Events: `agent.repair.invoked`, `agent.repair.finished`.
- Refused, with no job: `404 agent.not_installed` without a Hermes install record;
  `409 agent.busy` when an update, converge or repair job is `queued` or `running`
  (`details.job_id`) or another process holds the Hermes builder lock (`details.holder`,
  advisory: it can name a dead holder); `409 agent.builder_lock_unreadable` when the lock file
  cannot be opened (`details.error`).
- **`api_restarted`.** The child shares hal0-api's cgroup, so restarting hal0-api mid-repair (a
  `hal0 update`, `systemctl restart hal0-api`) kills the build. The live release is unchanged,
  because the builder swaps `current` only at the very end. The next status read of the job
  records it `failed` with `error_code: "api_restarted"`; run the repair again.

## Secrets (`/api/secrets`)

Backs the dashboard's Settings → Secrets panel. Persists to `/etc/hal0/api.env` — the
same systemd `EnvironmentFile=` the provider-credential writer targets — via the
shared atomic, mode-0600 writer in `hal0.api._env_store`. A successful write also
updates the running process's `os.environ` so the new value is observable without a
restart; the persisted file is the source of truth across restarts. ADMIN-gated
(whole prefix, `exposure.py` line-item `secrets`).

| Method | Path | Status | Notes |
|---|---|---|---|
| GET | `/api/secrets` | 200 | Lists secret **names** only — `{"secrets": [{name, set, masked, updated_at, protected}]}`. `masked` is always the constant `"••••••••"`; a value is never returned by any endpoint, logged, or echoed in an error body. |
| POST | `/api/secrets/{name}` | 204 | Set/overwrite. Body `{"value": "..."}`. Accepted alongside PUT because the shipped dashboard hook POSTs. |
| PUT | `/api/secrets/{name}` | 204 | Set/overwrite — the documented-contract verb; identical handler to POST. |
| DELETE | `/api/secrets/{name}` | 204 | Idempotent — 204 even if the name was never set. |

Validation, enforced server-side (not just in the UI, since this route is reachable
by anyone who can reach the API):

- **Name grammar**: `^[A-Z][A-Z0-9_]{0,63}$` — ALL_CAPS, leading letter, ≤64 chars.
  A non-conforming name is `400 secret.name_invalid`.
- **Protected prefix**: any name starting with `HAL0_` is hal0's own service
  configuration and auth surface (written by the installer, `hal0.toml` derivation,
  and `hal0 auth rotate`) — it is listed by GET (with `protected: true`, so an
  operator can see what the service is configured with) but every mutation against
  it is refused with `403 secret.protected`, including a DELETE of a name that isn't
  even currently set (so the response doesn't leak which `HAL0_*` keys exist on the
  box). Deleting `HAL0_ADMIN_KEY` would disarm every future login and deleting
  `HAL0_PORT`/`HAL0_UI_DIST` would break the service on next restart — this is the
  control introduced after #1450.
- **Value grammar**: non-empty and printable (`str.isprintable()`). Control
  characters — including the higher-codepoint line separators `U+0085`/`U+2028`/
  `U+2029`, not just the ASCII C0 set — are rejected as `400 secret.value_invalid`,
  because `api.env` is an unauthenticated-at-the-filesystem-level, LAN-writable
  systemd `EnvironmentFile`: an injected line separator could otherwise smuggle a
  second `KEY=value` pair into the file on round-trip.

Every set/delete emits a structured `hal0.audit` log line and a footer journal event
carrying the secret **name** only, never the value.

## Proxmox integration (`/api/settings/proxmox`)

Lets an operator configure the optional Proxmox API token the dashboard's "Proxmox
host" hardware panel uses (`hal0.hardware.pve`). Persisted to `/etc/hal0/proxmox.json`
— a separate file from `hal0.toml`, mounted as a sibling under `/api/settings` purely
for the dashboard's Settings-panel grouping. There is **no dedicated exposure.py rule**
for this path — it inherits ADMIN from the generic `/api/settings` prefix rule, the
same as every other settings sub-route.

| Method | Path | Notes |
|---|---|---|
| GET | `/api/settings/proxmox` | Returns `{configured, host, port, user, token_name, verify_ssl, token_value_set, status}` — the token **value** is never included; `token_value_set` is a boolean instead. `status` is a live `pve_status()` cluster snapshot fetched on every call. |
| PUT | `/api/settings/proxmox` | Body: `{host, port?, user, token_name, token_value?, verify_ssl?}`. `token_value` is optional on edit — if omitted and a config already exists on disk, the existing token is preserved so an operator can flip `verify_ssl` or change the host without re-entering the secret. If omitted with **no** existing config, the write is rejected `400 proxmox.token_required`. |
| DELETE | `/api/settings/proxmox` | Removes the config file entirely — returns to "not configured". |
| POST | `/api/settings/proxmox/test` | Body: same shape as PUT but `token_value` is **required** (there's no "test the saved config" path that can omit it — that's what GET's live `status` field already covers). Validates a candidate connection without writing anything to disk. |

`port` defaults to `8006` and is constrained `1-65535`; `verify_ssl` defaults to
`false`. Both request bodies are `extra: "forbid"` pydantic models — an unrecognized
field is a validation error, not a silently-dropped key.
