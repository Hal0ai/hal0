The `hal0` CLI is built with [Typer](https://typer.tiangolo.com/). The entry point is
`hal0 = "hal0.cli.main:app"`. Most subcommands are thin HTTP clients over the `hal0-api`
daemon; a few (`config show/edit/migrate/validate`, `agent install`,
`memory migrate`, `capabilities migrate`, `slot migrate-id-keying`) read or write
on-disk state directly and work without a running daemon.

```sh
hal0 --help          # top-level help (no args also prints help)
hal0 <group> --help  # per-group help, e.g. hal0 slot --help
```

<Aside type="caution">
`hal0 setup` is no longer the documented install entry point in v1.0. **`install.sh`
is the single user-facing entry point** — it drives the same first-run provisioning
non-interactively and calls `hal0 setup` internally. The `setup` command still exists
as a CLI subcommand (with all its flags, documented below) but is treated as an
internal fallback, not something operators are expected to run directly. See
[Getting Started → Install](/docs/getting-started/install/).
</Aside>

## Global

| Flag | Behavior |
|---|---|
| `--version` / `-V` | Print `hal0 {version}` and exit (eager callback). |
| `--help` | Print help. No flag = help (root app has `no_args_is_help=True`). |
| `--install-completion` / `--show-completion` | Typer's built-in shell-completion helpers (`add_completion=True`). |

There is **no** global `--verbose` or `--config` flag. Behavior that would normally be a
global flag is controlled per-command via environment variables instead — see
[Environment variables](/docs/reference/env-vars/) (`HAL0_API_URL`, `HAL0_HOME`,
`HAL0_BIND_HOST`, `HAL0_PORT`, `HAL0_FORCE`, `HAL0_PLAIN`, etc).

## Top-level commands

| Command | Purpose | Flags |
|---|---|---|
| `hal0 status` | System + slot summary. | — |
| `hal0 serve` | Start the hal0 API server (used by `hal0-api.service`). | `--host` (default `127.0.0.1`, env `HAL0_BIND_HOST`), `--port` (default `8080`, env `HAL0_PORT`), `--reload` |
| `hal0 uninstall` | Uninstall hal0. Conservative by default. | `--purge`, `--force`/`-f` (honors `HAL0_FORCE=1`), `--dev` (tears down a dev install at `$PWD/.hal0ai`) |
| `hal0 bench ...` | Benchmark pipeline. Raw argparse passthrough (`allow_extra_args`), see [Model roster & benchmarks](/docs/reference/model-roster-benchmark/). | verbs: `plan, run, worker, status, results, history, reindex, devices, publish, eval, bundle, upload` |
| `hal0 chat` | Interactive chat REPL. | `--model` (default `"agent"`), `--base-url` (default `http://127.0.0.1:8080/v1`, env `HAL0_CHAT_BASE_URL`), `--no-stream`, `--brain` (talk to the hal0-brain steward instead) |
| `hal0 system-info` | Host system info. | `--json` |
| `hal0 ports` | Port allocation view. | `--json` |
| `hal0 setup` | First-run provisioning (internal fallback in v1.0 — see caution above). | see below |
| `hal0 update ...` | Check/apply/roll back an update. | see below |

`hal0 chat` in-REPL slash commands: `/think on|off|default`, `/clear`, `/quit` / `/exit`
(Ctrl-D also exits).

### `hal0 setup`

```sh
hal0 setup [--auto] [--storage-dir DIR] [--no-pull] [--no-extensions] [--no-slots]
           [--answers FILE] [--emit-answers FILE] [--plan]
```

| Flag | Default | Meaning |
|---|---|---|
| `--auto` | `False` | Non-interactive, applies recommended defaults. |
| `--storage-dir` | `/var/lib/hal0/models` | Model storage root. |
| `--no-pull` | `False` | Skip pulling a starter model. |
| `--no-extensions` | `False` | Skip optional-extension prompts. |
| `--no-slots` | `False` | Skip seeding starter slots. |
| `--answers` | unset | Path to a `hal0-setup.yaml` answers file. |
| `--emit-answers` | unset | Write resolved answers to a file and exit, without applying. |
| `--plan` (alias `--dry-run`) | `False` | Resolve and print the plan; write nothing. |

### `hal0 update`

```sh
hal0 update [--channel stable|preview|nightly] [--check] [--rollback]
            [--target VERSION] [--yes|-y] [--restart-slots|--no-restart-slots]
hal0 update status
hal0 update component <id> [--check] [--target REF] [--clear-override] [--yes|-y]
```

| Flag | Meaning |
|---|---|
| `--channel` | Persist the update channel, then check it. |
| `--check` | Check only; don't apply. |
| `--rollback` | Roll back to the previous version. When it predates per-slot tune overrides ([ADR-0045](/docs/adr/0045-slots-carry-a-sparse-tune-override-table)), the keys it refuses are removed first: `[tune]` from slot files, `reasoning_effort` and `reasoning_budget` from `profiles.toml`, and stack entry `tune` plus embedded profile reasoning keys from `stacks.toml`. Each changed file is copied to `<file>.bak-<stamp>` first and listed under `tune_stripped` in the response. Updating forward does not put the keys back. |
| `--target` | Pin an exact version. A box below the release's `upgrade_from` floor is refused with `system.update_upgrade_path_unsupported`, which names the floor. From 1.6.0 through 1.7.0 the floor is `>=1.4.0`; after 1.7.0 it is `>=1.5.0`. `--target` pins only the version the channel's manifest serves now, so it cannot step a box through an older release: a box below the floor runs that release's installer in place (see [Upgrading from an older release](/docs/guides/update-and-rollback/#upgrading-from-an-older-release)). |
| `--yes` / `-y` | Skip the confirmation prompt. |
| `--restart-slots` | Bounce every drifted slot (image and argv drift) and stop. |
| `--no-restart-slots` | Skip the automatic restart of slots whose runner image changed; the CLI leaves them on the old image (the `hal0-api` start-up pass is controlled by `[updates].auto_restart_image_drift`). Cannot be combined with `--restart-slots`. |

An apply that leaves any component below still `pending`
exits **2** rather than reporting a clean success — distinct from a failed
update (`die()` → exit 1).


`hal0 update status` prints the same hal0 version/channel check plus a
per-component table (installed / pinned / status) for the five
release-pinned components — OpenWebUI, runner images, Hermes, Pi, and
Hindsight; their pins ride hal0 releases rather than updating
independently. Exits **2** if any component isn't converged yet
(`pending`, `stale`, or a failure status), so it doubles as a scriptable
convergence gate.

`hal0 update component <id>` re-runs one component's converge arm — a
per-component alternative to a full `hal0 update` for retrying just the
piece that's stuck. `--check` prints that component's status row without
converging it. `<id>` is one of `openwebui`, `runner-images`, `hermes`,
`pi`, `hindsight` (see `hal0 update status` for the live list).

`sudo hal0 update component pi` re-pins an installed pi and redeploys hal0's extensions into `~/.pi` without touching the extensions you added or your default provider, model and theme. Unlike the other components it runs in the CLI, not the daemon, so it needs root and not a running hal0-api; run it the same way you installed pi. It reruns the pinned installer and refreshes the hal0-memory MCP entry. It refuses, and changes nothing, when pi is not installed, when pi's profile is in a different home than the one it runs in, and when `settings.json` or `mcp.json` is not a JSON object; it takes no `--target` or `--clear-override`. `hal0 update` never re-pins pi; it only reports it. It also points Pi's section of `~/.hindsight/coding-agent.json` at hal0's `/api/memory/compat` with the hal0-managed bridge client `pi-coder`, and prints a line when it minted or rotated that key ([Generated files](/docs/reference/generated-files/)). That file is shared: other Hindsight-backed tools on the box read it too, and only Pi's section is written. The `pi-coder` key also holds the `agents` scope: whoever can read that 0600 file can start Hermes runs.

A plain `hal0 update` only reports pi, and the row never affects the exit code: `update-available` when pi or its adapter is behind the pin (with the command above as a note), `newer-than-pin` when it is ahead, which the command would downgrade, and `unknown` when the pin cannot be read. `--check` needs hal0-api, as for every component, and `POST /api/updates/components/pi/converge` answers 400.

For `hermes`, `--target SHA` builds a vetted commit other than the pin (a full 40-hex commit in `VETTED_HERMES_REFS`; nothing older than the live release). It persists across `hal0 update` until `--clear-override`, and `hal0 update status` shows the row as `override`. The pin's own commit counts as `--clear-override`. Clearing is refused, keeping the override, when the pin is older than the live release; it cannot check an override this release no longer vets, so that case needs a newer pin. Repair rebuilds the override, not the pin; an unvetted override is never built.

For `openwebui`, `--target DIGEST` (`sha256:…` or bare 64-hex) pins an explicit
digest instead of the release-carried one; it persists across future converges
until `--clear-override` drops it and converges back to the release pin. There is
no `--tag` float-to-upstream flag: the pin rides hal0 releases like every other
component. `--yes`/`-y` skips the confirmation prompt that `--target` and
`--clear-override` show on a terminal. `hal0 update owui` no longer exists; use
`hal0 update component openwebui`.

## Editing a slot tune

`hal0 slot edit NAME` accepts `--ctx`, `--thinking/--no-thinking`, `--reasoning-effort`,
`--reasoning-budget`, `--vision`, and `--speculation`. They write sparse
`[tune]` overrides. Use `--tune-reset` alone to resume profile inheritance:

```bash
hal0 slot edit fast --ctx 8192 --reasoning-effort low
hal0 slot edit fast --tune-reset
```

## `hal0 slot` — manage inference slots

Enums: `--type` = `llm|embedding|reranking|transcription|tts|image`; `--provider` =
`llama-server|flm|kokoro|moonshine`; `--hardware` = `vulkan|rocm|cpu`.

| Command | Args | Flags |
|---|---|---|
| `slot list` | — | `--json` |
| `slot status <name>` | `name` | `--json` |
| `slot load <name>` | `name` | `--model`/`-m`, `--json` |
| `slot unload <name>` | `name` | `--json` |
| `slot restart <name>` | `name` | `--json` |
| `slot rename <name> <new_name>` | `name`, `new_name` | — |
| `slot swap <name>` | `name` | `--model`/`-m` (required), `--no-persist`, `--json` |
| `slot logs <name>` | `name` | `--follow`/`-f` (when hal0-api cannot read the journal it prints the reason and returns instead of waiting), `--lines`/`-n` (default 200, 1-5000) |
| `slot create <name>` | `name` | `--type`/`-t` (default `llm`), `--provider` (default `llama-server`), `--hardware` (default: auto-detect), `--model`/`-m` (required), `--port`/`-p` (default: auto-assign, 1024-65535), `--profile` (the tune; default: inferred from `--type`/`--hardware`, and an `llm` slot with none runs the `chat` seed) |
| `slot edit <name>` | `name` | `--model`/`-m`, `--port`/`-p`, `--provider`, `--hardware`, `--profile` |
| `slot delete <name>` | `name` | `--force`/`-f` |
| `slot show <name>` | `name` | `--json` |
| `slot metrics [name]` | optional `name` | `--json` |
| `slot capacity` | — | `--json` |
| `slot migrate-id-keying` | — | `--apply` (default: dry-run), `--yes`/`-y`, `--stop-services` |

<Aside type="note">
`--provider` on `slot create`/`slot edit` selects the inference engine binary, **not** the
hardware backend. The hardware backend is selected with `--hardware`, and stored on the slot as `device` (`gpu-rocm`, `gpu-vulkan`,
`gpu-cuda`, `cpu`, `npu`) — see [Providers, profiles & devices](/docs/reference/providers-profiles-devices/).
</Aside>

`slot create --model` and `slot edit --model` bind only a model hal0 can resolve: a registered
id or a curated catalogue id (the first `slot load` pulls it). Any other id is refused with
`validation.model_not_registered`, naming the id, and the slot file is left untouched. NPU,
ComfyUI and the self-managed speech engines (Kokoro, Qwen3-TTS, Moonshine, VibeVoice) are not
checked, since their models are FLM tags, image catalogue ids and baked-in or operator-staged
weights, not registry rows. Register a model file with `hal0 model add <path>` or `hal0 model scan`, and list
the registered ids with `hal0 model list`. A slot file written before this check that
already names an unknown id keeps loading: `load` serves a registered model of the same capability
in its place and logs a `slot.model_default_fallback` warning that names both ids.

## `hal0 model` — manage the local model registry

| Command | Args | Flags |
|---|---|---|
| `model list` | — | `--json` |
| `model pull <ref>` | `ref` | `--cancel`, `--draft` (a drafter .gguf to download with the model), `--draft-repo` (the repo holding `--draft`; default the model's own) |
| `model default <ref>` | `ref` | `--clear` |
| `model update [ref]` | optional `ref` | `--check`, `--refresh` (only meaningful with `--check`) |
| `model rm <ref>` | `ref` | `--force`/`-f`, `--keep-files` (remove only the registry entry; files stay on disk, hidden from scans) |
| `model show <ref>` | `ref` | `--json` |
| `model scan` | — | — |
| `model add <path>` | `path` | `--id` (default `""`), `--name`, `--license` (default `""`), `--overwrite`, `--draft` (a drafter GGUF to pair; fit-checked) |
| `model set <ref>` | `ref` | `--draft` (a drafter path to pair, or `none` to unpair and keep the file) |
| `model store [path]` | optional `path` | `--migrate` |
| `model run <ref>` | `ref` | `--slot`/`-s` (default `""`), `--timeout` (default: the derived slot-load budget from `hal0.slot_lifecycle_budget`, `622` at time of writing — see [Slot lifecycle timeouts](/docs/reference/cli-operator/#slot-lifecycle-timeouts)) |

## `hal0 config` — inspect and manage configuration

`ConfigFile` enum: `hal0|upstreams|providers`.

| Command | Args | Flags |
|---|---|---|
| `config show [which]` | optional `which` (default `hal0`) | — |
| `config edit [which]` | optional `which` (default `hal0`) | opens `$EDITOR`/`$VISUAL`/`vi` |
| `config migrate` | — | — |
| `config validate` | — | — |
| `config reload` | — | — |
| `config hardware` | — | `--refresh` |

`config validate` checks `hal0.toml`, `upstreams.toml`, `providers.toml` and
every `slots/*.toml` (the typed slot load the daemon runs at boot); it exits
`1` if any file fails.
