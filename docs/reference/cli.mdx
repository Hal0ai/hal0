The `hal0` CLI is built with [Typer](https://typer.tiangolo.com/). The entry point is
`hal0 = "hal0.cli.main:app"`. Most subcommands are thin HTTP clients over the `hal0-api`
daemon; a few (`config show/edit/migrate/validate`, `agent install`,
`memory migrate`, `capabilities migrate`, `slot migrate-id-keying`, `profile migrate`) read or write
on-disk state directly and work without a running daemon.

```sh
hal0 --help          # top-level help (no args also prints help)
hal0 <group> --help  # per-group help, e.g. hal0 slot --help
```

<Aside type="caution">
`hal0 setup` is no longer the documented install entry point in v1.0. **`install.sh`
is the single user-facing entry point** — it drives the same first-run provisioning
non-interactively and calls `hal0 setup` internally. The `setup` command still exists
as a CLI subcommand (with all its flags, documented below) but is treated as an
internal fallback, not something operators are expected to run directly. See
[Getting Started → Install](/docs/getting-started/install/).
</Aside>

## Global

| Flag | Behavior |
|---|---|
| `--version` / `-V` | Print `hal0 {version}` and exit (eager callback). |
| `--help` | Print help. No flag = help (root app has `no_args_is_help=True`). |
| `--install-completion` / `--show-completion` | Typer's built-in shell-completion helpers (`add_completion=True`). |

There is **no** global `--verbose` or `--config` flag. Behavior that would normally be a
global flag is controlled per-command via environment variables instead — see
[Environment variables](/docs/reference/env-vars/) (`HAL0_API_URL`, `HAL0_HOME`,
`HAL0_BIND_HOST`, `HAL0_PORT`, `HAL0_FORCE`, `HAL0_PLAIN`, etc).

### `hal0 setup`

```sh
hal0 setup [--auto] [--storage-dir DIR] [--no-pull] [--no-extensions] [--no-slots]
           [--answers FILE] [--emit-answers FILE] [--plan]
```

| Flag | Default | Meaning |
|---|---|---|
| `--auto` | `False` | Non-interactive, applies recommended defaults. |
| `--storage-dir` | `/var/lib/hal0/models` | Model storage root. |
| `--no-pull` | `False` | Skip pulling a starter model. |
| `--no-extensions` | `False` | Skip optional-extension prompts. |
| `--no-slots` | `False` | Skip seeding starter slots. |
| `--answers` | unset | Path to a `hal0-setup.yaml` answers file. |
| `--emit-answers` | unset | Write resolved answers to a file and exit, without applying. |
| `--plan` (alias `--dry-run`) | `False` | Resolve and print the plan; write nothing. |

### `hal0 update`

```sh
hal0 update [--channel stable|preview|nightly] [--check] [--rollback]
            [--target VERSION] [--yes|-y] [--restart-slots|--no-restart-slots]
hal0 update status
hal0 update component <id> [--check]
hal0 update owui [--check] [--target DIGEST] [--clear-override] [--yes|-y]
```

| Flag | Meaning |
|---|---|
| `--channel` | Persist the update channel, then check it. |
| `--check` | Check only; don't apply. |
| `--rollback` | Roll back to the previous version. When that release predates the profile-centric conversion, every conversion backup is put back first (see [Update and roll back](/docs/guides/update-and-rollback/#rolling-back-past-the-profile-centric-conversion)). |
| `--target` | Pin an exact version. |
| `--yes` / `-y` | Skip the confirmation prompt. |
| `--restart-slots` | Bounce every drifted slot (image and argv drift) and stop. |
| `--no-restart-slots` | Skip the automatic restart of slots whose runner image changed; the CLI leaves them on the old image (the `hal0-api` start-up pass is controlled by `[updates].auto_restart_image_drift`). Cannot be combined with `--restart-slots`. |

An apply that leaves any component below still `pending`
exits **2** rather than reporting a clean success — distinct from a failed
update (`die()` → exit 1).

It also exits **2** when the profile-centric conversion ([ADR-0029](/docs/adr/0029-profile-centric-config)) left a slot, a stored profile or a stack unconverted. `hal0 update` prints one line per blocker: the target (a slot file, `profile:<name>` or `stack:<name>`), the reason, and the fix. A blocked slot keeps launching the command it ran before the update until its file is edited. See [`hal0 profile`](/docs/reference/cli-operator/#hal0-profile--inspect-and-edit-profiles).

`hal0 update status` prints the same hal0 version/channel check plus a
per-component table (installed / pinned / status) for the four
release-pinned components — OpenWebUI, runner images, Hermes, and
Hindsight; their pins ride hal0 releases rather than updating
independently. Exits **2** if any component isn't converged yet
(`pending`, `stale`, or a failure status), so it doubles as a scriptable
convergence gate.

`hal0 update component <id>` re-runs one component's converge arm — a
per-component alternative to a full `hal0 update` for retrying just the
piece that's stuck. `--check` prints that component's status row without
converging it. `<id>` is one of `openwebui`, `runner-images`, `hermes`,
`hindsight` (see `hal0 update status` for the live list).

`hal0 update owui` converges the bundled OpenWebUI companion container to
its release-carried pin — a thin alias for `hal0 update component
openwebui`. There is no more independent `--tag` float-to-upstream flag:
the pin now rides hal0 releases like every other component. `--target
DIGEST` (`sha256:…` or bare 64-hex) pins an explicit digest override
instead, which persists across future converges until cleared;
`--clear-override` drops it and converges back to the release pin.
`--check` prints the status row only; `--yes`/`-y` skips the confirmation
prompt.

## `hal0 doctor` — diagnostics and repair

Bare `hal0 doctor` (no subcommand) runs `installer/lib/preflight.sh`:
`--plain` (force ASCII, sets
`HAL0_PLAIN=1`), `--ports` (space-separated TCP port list override).

| Command | Flags |
|---|---|
| `doctor verify` | `--json` |
| `doctor logs` | `--unit` (default `hal0-api`; hal0 units only: `hal0.target`, `hal0-*`, `hindsight-api`, `hermes-gateway`, anything else is a 400), `--follow`/`-f`, `--lines`/`-n` (default `200`, 1-5000), `--level`, `--since` |
| `doctor toolbox-pull` | `--json`, `--manifest` (probes every `runners` pin in `manifest.json`: anonymous ghcr.io pull plus pinned-digest comparison; exit `1` when an image is unreachable or unpublished, `2` when the pin table is missing or malformed) |
| `doctor perms` | `--fix`, `--force`/`-f`, `--table-root` (audit old root-era table), `--json` |
| `doctor models` | `--fix`, `--force`/`-f`, `--json` |
| `doctor profiles` | `--json` |
| `doctor ports` | `--fix` (delete stale netavark DNAT rules found by the audit; privileged) |
| `doctor wrappers` | `--fix` (re-install `${LIB_DIR}/bin/hal0-*`, the matching `/etc/sudoers.d` drop-ins, and the `/usr/local/bin/hal0`(`-agent`) PATH links from the active tree; privileged) |
| `doctor all` | `--json` |
| `doctor bundle` | `--out`, `--no-rocm-smi`, `--include-logs` (default `auto`; `auto\|yes\|no`) |

`doctor all` rolls up every check into one report. All are read-only except
`memory_extraction_throughput`, which sends one bounded probe to the extraction slot (at most 512
prompt and 32 decode tokens, capped at 30 s) when the slot's metrics carry no reading. Each row has a stable id
(`Check.key`) used in `--json` output and cross-referenced elsewhere in the docs: `api`,
`dns`, `runners`, `capabilities`, `memory`, `openwebui`, `hermes`, `auth`, `models`,
`migrations`, `ui-dist`, `ports`, `port_dnat`, `netns`, `hal0_target`, `secret-modes`,
`hardware_freshness`, `seed_context_envelope`, `agent-uid`, `api-journal`, `stt-weights`, `seams`,
`mcp_mounts`, `hermes-api`, `hermes_mcp_auth`, `hermes_profiles_mcp`, `hermes_generation`, `hermes_command_approvals`, `hermes_delegation_slot`, `hermes_anchor_window`,
`hal0_linger`, `hindsight_llm_auth`, `memory_engine_version`, `memory_extraction_throughput`.
`hal0_linger` reads whether systemd linger is on for the `hal0` user (`loginctl show-user hal0 -p
Linger`) and warns when that does not match whether the Hermes gateway is installed.

The Hermes rows are advisory and never critical. `hermes-api` ("Hermes API upstreams") checks, for each served profile, that it has an API key, that its authenticated `/v1/models` answers 200, and that hal0 has registered the matching upstream. With no key it says to run `sudo hal0 agent reprovision hermes --repair`. With a missing upstream it says to restart `hal0-api` or `POST /api/agents/hermes/reconcile-upstreams`. `hermes_profiles_mcp` ("Hermes profile MCP wiring") warns when a named profile has no hal0-admin and hal0-memory entries, fails when an entry lacks a bearer on a box with auth on, and reports a profile that opted out with `hal0: {wire_mcp: false}`. `hermes_generation` ("Hermes pm generation") warns when Hermes's package manager has committed its own environment for the live release without the extras (such as `mcp`) hal0 built it with. `hermes_delegation_slot` ("Hermes delegation slot") passes for the default `agent` slot and warns when a `[hermes] delegation_slot` names a slot that is not ready.

There is no standalone `hal0 doctor seams`
command — `seams` is one of these roll-up rows, surfaced by `hal0 doctor all`.

| `agent approvals deny <approval_id>` | `approval_id` | — |

| `agent personas list` | — | — |
| `agent personas show <persona_id>` | `persona_id` | — |
| `agent personas activate <persona_id>` | `persona_id` | `--reload-url` |

`agent upgrade hermes` builds and activates a fresh Hermes release of the pin, or of `--to <sha>`, through the same release builder as install and `hal0 update`, and switches back to the previous release by itself if the new one fails its re-check. A ref other than the pin lasts until the next `hal0 update`.

`agent upgrade pi` re-pins an installed pi and redeploys hal0's extensions into `~/.pi` without touching the extensions you added or your default provider, model and theme. Run it with `sudo`, as the user who installed pi; it exits with an error when pi was installed for another user or is not installed.

`agent reprovision hermes --repair` forces every provisioning phase, builds a fresh Hermes release through the same builder as `upgrade`, rewrites the persona seeds and `config.yaml`, then re-registers the Hermes profiles as `/v1` upstreams. Run `sudo hal0 agent reprovision hermes --repair` once on a box where Hermes was installed before 1.6.0 so the default profile gets its API key and appears in `/v1/models` and Open WebUI. The same run wires hal0-admin and hal0-memory into every named profile (phase `profile_mcp_wire`) and writes any missing profile API key (phase `profile_api_keys`).

`agent dashboard-token hermes` prints the token Hermes Desktop needs for a remote pairing in token mode. `hal0-agent@hermes` mints it once under `/var/lib/hal0/state/agents/hermes/` and exports it to the dashboard as `HERMES_DASHBOARD_SESSION_TOKEN` at every start, so the pairing survives restarts and `hal0 update`. Run it as root or as the `hal0` user. A `systemctl edit hal0-agent@hermes` drop-in that sets `HERMES_DASHBOARD_SESSION_TOKEN` wins over the file.

`agent uninstall hermes` also runs `loginctl disable-linger hal0` (as root; otherwise it prints the command), undoing the linger the Hermes gateway turned on.

`agent install hermes` respects an operator-disabled gateway. If `hermes-gateway.service` is `disabled`, the unit file is refreshed with `--no-start-now --no-start-on-login` and the unit is not enabled or started (a copy already running is left running). If it is `masked-runtime` it is treated the same way. If it is persistently `masked`, the generator does not run at all. Either way the command prints how to turn it back on (`systemctl enable --now hermes-gateway.service`, preceded by `systemctl unmask` or `unmask --runtime` for a mask). A fresh or enabled gateway is installed and enabled as before.
