## `hal0 memory` — manage hal0 memory (Hindsight engine)

| Command | Args | Flags |
|---|---|---|
| `memory status` | — | `--json` |
| `memory enable` | — | `--json` |
| `memory disable` | — | `--json` |
| `memory recall <query>` | `query` | `--bank`, `--tags` (repeatable), `--types` (repeatable), `--max-tokens` (default `4096`), `--json` |
| `memory graph status` | — | `--json` |
| `memory graph enable` | — | `--slot`, `--model`, `--local`, `--json` |
| `memory graph disable` | — | `--json` |
| `memory graph check` | — | `--json` |

`memory graph enable` turns graph extraction on and can repoint the memory engine. `--slot <name>` runs it on a local LLM slot and clears any upstream model. `--model <id>` runs it on an upstream model id that hal0's `/v1` already routes (the ids `memory graph status` lists under `Upstream models`); the configured slot is kept as the way back. `--local` clears `--model` and returns the engine to the local `[memory.graph].extraction_slot`. `--model` and `--local` cannot be combined, and `--model` cannot be combined with `--slot`. hindsight-api always calls the virtual id `hal0/memory`, which hal0 resolves on every call, so the change applies at once and does not restart the engine. `memory graph status` prints `Engine target` (the local slot or upstream model `hal0/memory` resolves to) and an `Engine running` line naming the provider and model hindsight-api really loads; the line is marked as overridden when `/etc/hal0/hindsight-llm.env` sets the provider, base URL or model, and as `cannot verify` when hal0-api can read neither the engine process nor that file (see [Services](/docs/operate/services/#hindsight-apiservice)).

|---|---|---|

`memory models show` lists the embeddings, reranker and decision models from `[memory.models]` and `[memory.decision]`. It is idempotent, and `--dry-run` posts with `dry_run=true`.

### `memory embedder switch`

```sh
hal0 memory embedder switch MODEL [--provider local] [--apply|--dry-run]
                            [--allow-pending] [--json]
hal0 memory embedder switch --resume | --status | --clear-gate [--json]
```

Moves the memory store to another embedding model: pauses memory writes,
moves the engine to a private port so that nothing else can reach it, exports
every bank, restarts the engine on the new model, restores each bank (which
re-embeds it) under a temporary id, compares it with its archive, replaces
the originals, and returns the engine to its normal address. Memory is out of
service while it runs, recall included. See
[Change the embedding model](/docs/guides/enable-memory#change-the-embedding-model)
for the steps and the failure behaviour.

Unlike the other `hal0 memory` commands it does not call hal0-api: it runs on
the box, as root, and talks to the engine directly. It never asks a question.

| Flag | Meaning |
|---|---|
| `MODEL` | The embedding model to move to, for example `hindsight-ai/hs-embed-1`. Omitted with `--resume`, `--status` and `--clear-gate`. |
| `--provider` | The embeddings provider the model belongs to. Default `local`. |
| `--apply` / `--dry-run` | Default `--dry-run`: run the preflight, print the plan, write nothing. |
| `--allow-pending` | Go ahead while the engine has queued or running operations. What they have not written when a bank is exported is not carried over. |
| `--resume` | Finish an interrupted switch from its journal: carry a started swap forward, or undo a run that stopped before the swap. |
| `--status` | Print the journal, the write pause, where the engine listens, the banks and temporary banks on it, and what `--resume` would do for each, with the checks a resume would run. Changes nothing. |
| `--clear-gate` | Return the engine to its normal address and lift the write pause by hand. Refused while a switch is running or any journal shows an unfinished run. Checks no bank. |
| `--json` | Print the plan, status or result as JSON; progress goes to stderr. |

The preflight refuses, and the command exits 1, when: the store is already on
that embedder and is not mixed; the engine does not answer or its environment
cannot be read; the embedder record cannot be read or disagrees with the
engine; the engine's export or import API is off; a bank has queued or running
operations (without `--allow-pending`); free disk space is short on the
engine's filesystem or the archives'; the engine's `hindsight-admin` command
is missing, or the engine unit's `EnvironmentFile` is not readable; memory
writes are already paused, the engine is already on a private port, an
earlier switch did not finish, or a bank left by one is still on the engine;
an update or an engine upgrade is in progress; another switch is running; or
`--apply` is not run as root. An `--apply` or `--resume` also exits 1 when
the run fails. Then it has either been undone, or, if it stopped inside the
swap, the engine stays private and memory writes stay paused until `--resume`
completes; the message names the archive directory and `--status`. A finished
run whose store had to be recorded as mixed exits 0 and says so.

### `memory migrate unify`

```sh
hal0 memory migrate unify --source BANK [--source BANK ...] [--target shared]
                           [--apply|--dry-run] [--add-tag TAG ...]
                           [--on-conflict skip|replace|new-id] [--skip-observations] [--json]
```

`--source` is repeatable and required. `--target` defaults to `"shared"`. Defaults to
dry-run unless `--apply` is given. `--on-conflict` defaults to `skip`.

### `memory migrate platform`

```sh
hal0 memory migrate platform [--target BANK] [--source shared] [--agents-bank agents]
                             [--apply|--dry-run] [--skip-clone] [--skip-bank-config] [--json]
```

Moves the platform memory into the bank named by `[memory] bank` (ADR-0052).
`--target` defaults to that config value. The command clones `--source`
(default `shared`) into `--target` with the engine's clone call, folds the
retired `--agents-bank` (default `agents`, skipped when it does not exist) into
the same target, and then compares fact counts, exiting 1 if the target is
short. It is a dry run unless `--apply` is given, never modifies or deletes the
source banks, and never edits `hal0.toml`. The target must not exist yet; use
`--skip-clone` to fold and verify a target that already holds the clone.
`--skip-bank-config` leaves the source's config overrides, directives and
webhooks behind. `--apply` needs the engine's export and import APIs enabled.

## `hal0 runner-images` — manage the runner-image catalogue

Talks to the runner-image store/sync/pull/rm service layer directly (not
the API), so `ls` keeps working even when `hal0-api` is down. `rm` mirrors
`DELETE /api/runner-images/{id}/tags/{tag}`'s guard order, but cannot see
a dashboard pull job's in-memory state — a concurrently running `hal0-api`
pull of the same tag can race it.

| Command | Args | Flags |
|---|---|---|
| `runner-images ls` | — | — |
| `runner-images sync` | — | — (prints each catalogue entry it skipped and why) |
| `runner-images pull <id>` | `id` (catalogue id) | `--tag` (default: the row's headline tag) |
| `runner-images rm <id>` | `id` (catalogue id) | `--tag` (required) |
| `runner-images migrate` | — | `--apply`, `--restore <archive>` |

`runner-images migrate` previews the one-shot conversion onto the fresh
runner system (ADR-0028). `hal0 update` runs it automatically. `--apply`
runs it, backing up every file it changes to
`/var/lib/hal0/backups/runners-<ts>.tar.gz` first, and `--restore <archive>`
puts such a backup back.

## `hal0 profile` — inspect and edit profiles

A profile is the tune a slot launches a model with: flags, context window, reasoning
default, vision and speculation ([ADR-0029](/docs/adr/0029-profile-centric-config)). The
context window is a profile setting, not a slot one: `slot create` / `slot edit` have no
`--ctx-size`; use `profile create --ctx-size` / `profile edit --ctx-size`, then point the
slot at the profile with `slot edit <slot> --profile <name>`. Delete, generate, import
and export stay dashboard/API-only (`/api/profiles`).

| Command | Args | Flags |
|---|---|---|
| `profile list` | — | `--json` |
| `profile show <name>` | `name` | `--json` |
| `profile create <name>` | `name` | `--from <profile>` (duplicate a seed or custom profile first), `--flags`, `--ctx-size` (128-16777216), `--thinking`/`--no-thinking`, `--vision` (`auto`\|`off`), `--speculation` (`auto`\|`off`\|`ngram`), `--runner`, `--intent`, `--json` |
| `profile edit <name>` | `name` | `--flags`, `--ctx-size`, `--clear-ctx-size`, `--thinking`/`--no-thinking`, `--clear-thinking`, `--vision`, `--speculation`, `--runner` (`''` clears), `--intent`, `--json` |

Seed profiles are read-only: `profile edit` on one is refused with the duplicate-first hint (`profile create <new> --from <seed>`). Edits reach a running slot at its next restart, except `runner`: a launch resolves its image from the slot's `binary`, which is copied from the profile's `runner` only when the profile is applied to the slot (`slot edit <slot> --profile <name>`). After `profile edit --runner`, re-apply the profile to each slot that uses it. A llama-server slot with no profile runs its type's seed (`chat` for an `llm` slot), and one that names a profile that does not exist fails to launch with `slot.profile_missing`.

## `hal0 bridge` — admit remote coding agents

A bridge client is a named remote agent (Claude Code, Codex, a CI job) with a key of its own. The group goes through hal0-api, so the API must be running. See [Connect an external MCP client](/docs/guides/connect-mcp#connect-an-external-mcp-client), [Delegate work to the Hermes agent](/docs/guides/delegate-to-agents) and [ADR-0043](/docs/adr/0043-agent-bridge-and-bridge-keys).

| Command | Args | Flags |
|---|---|---|
| `bridge add <name>` | `name` (lower-case letters, digits, `_` and `-`; 1 to 32 characters; starts with a letter or digit) | `--note TEXT`, `--scope agents\|memory\|admin` (repeatable; default `agents` and `memory`) |
| `bridge list` | — | — |
| `bridge revoke <name>` | `name` | — |
| `bridge rotate <name>` | `name` | — |
| `bridge scopes <name> <scope>...` | `name`, one or more of `agents`, `memory`, `admin` | — |
| `bridge runs` | — | `--client TEXT`, `--status TEXT`, `--limit N` (1 to 200; default 20) |

`bridge add` and `bridge rotate` print the key once, as `hal0bk_<name>.<token>`, and cannot show it again: hal0 keeps only its sha256. Under the key they print one `claude mcp add` line for each scope the client holds, ready to paste on the remote machine:

```sh
claude mcp add --transport http hal0-agents http://<host>:8080/mcp/agents/mcp --header "Authorization: Bearer <key>"
claude mcp add --transport http hal0-memory http://<host>:8080/mcp/memory/mcp --header "Authorization: Bearer <key>"
claude mcp add --transport http hal0-admin http://<host>:8080/mcp/admin/mcp --header "Authorization: Bearer <key>"
```

`<host>:8080` is `[network].public_url` when it is set. Otherwise it is the address the command reached hal0-api at, which for `hal0 bridge` on the box is loopback, so hal0 prints the address of the box's default-route interface on the API port instead.

`agents` is always held; `--scope memory` and `--scope admin` add the `hal0-memory` and `hal0-admin` lines. `agents` alone already reaches memory: the teach tools of [`hal0-agents`](/docs/reference/mcp-tools-agents#memory) write and search a Hermes profile's memory, and the Hermes that runs a delegated task uses its own memory tools; `--scope memory` adds direct access to the `hal0-memory` server. `bridge revoke` ends a key at once and keeps the name, so it cannot be added again; `bridge rotate` replaces a live client's key at once and keeps its scopes and note, and refuses a revoked client. `bridge scopes` replaces the whole set (`agents` stays), so the same key opens different servers from the next request.

`bridge runs` lists the runs bridge clients have delegated to Hermes, newest first, as a table of `run_id`, `client`, `agent`, `status`, `started` and `updated`. The last two are ages (`45s`, `5m`, `2h`, `3d`). `--client` shows one client's runs, `--status` one status (for example `running` or `completed`). Pass a `run_id` to the `agent_run_status` tool of the [`hal0-agents`](/docs/reference/mcp-tools-agents) server to read a run.

A failed command prints the API's `error.message` and exits 1: a name that is taken, malformed or reserved (`hermes` and `pi`, the bundled agents' names, plus `admin`, `anonymous`, `shared`, `unknown`, `unresolved`, and any name starting `hal0`, such as `hal0-cli`, or `hermes__`, such as `hermes__scout`), an unknown scope, a client that does not exist, `rotate` on a revoked client. While `[bridge].enabled` is `false`, no bridge key works and `bridge add`, `bridge rotate` and `bridge scopes` and `bridge runs` exit 1 with:

```text
The agent bridge is disabled: set [bridge] enabled = true in /etc/hal0/hal0.toml and restart hal0-api.
```

`bridge list` and `bridge revoke` keep working while the bridge is off, so you can revoke a key before turning it back on.

The `admin` scope opens the hal0 admin tools: treat that key like an operator credential and grant the scope only to an agent that operates the box ([SECURITY.md](https://github.com/Hal0ai/hal0/blob/main/SECURITY.md#bundled-agent-trust-boundary)).

## `hal0 network` — browser origins hal0 accepts

## Slot lifecycle timeouts

Commands that drive the slot state machine — `slot load` / `unload` / `restart`
/ `swap` / `delete`, `model run`, `capabilities set`, `update --restart-slots` —
block until the server converges the slot. Their client read timeouts are not
hand-picked; they are derived from the server's own bounds in
`hal0.slot_lifecycle_budget` (the health poll, one container terminate per
unload, an allowance for the pre-load evictions and for queueing behind an
in-flight op on the same slot, plus a podman/systemd overhead factor).

| Verb shape | Budget |
|---|---|
| load (`slot load`, `model run`, NPU backend load) | 2139s |
| unload (`slot unload`, `slot delete`, NPU backend unload) | 1104s |
| restart / swap (`slot restart`, `slot swap`, `capabilities set`) | 3243s |
| `update --restart-slots`, per drifted slot | 3243s (3 slots = 9729s) |

These are ceilings on a *wedged* daemon, not expected durations — a healthy
load returns in seconds. While they wait, `slot load`/`unload`/`restart`/`swap`
and `update --restart-slots` show an elapsed counter and the slot's live state on
a terminal (one summary line when not a TTY; only the final JSON with `--json`),
and every `systemctl`/podman call the server makes is bounded — a wedged one
answers `504 slot.seam_timeout` — but a genuinely stuck slot can still hold the
terminal for the full budget. If you are
scripting against them (CI, smoke tests), wrap the call in your own
`timeout(1)` rather than relying on the CLI to give up first.

## `hal0-agent` (separate binary)

Not part of the `hal0` app — a standalone argparse binary invoked by
`hal0-agent@<id>.service`, not intended for direct interactive use:

```sh
hal0-agent <agent_id> serve|stop|status|reprovision|render-context
```
