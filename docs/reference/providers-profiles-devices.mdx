<Aside type="caution">
hal0's source has **two unrelated "provider" concepts**. This page covers both,
clearly separated — do not conflate them.
</Aside>

## (A) Local inference-backend provider

`hal0.providers.base.Provider` — the abstract class that runs a slot's inference
process. Concrete implementations:

| Provider | Module | Runs |
|---|---|---|
| `ContainerProvider` | `providers/container.py` | llama-server, via podman. |
| `FLMProvider` | `providers/flm.py` | NPU inference (FastFlowLM). |
| `ComfyUIProvider` | `providers/comfyui.py` | Image generation. |
| `KokoroProvider` | `providers/kokoro.py` | TTS. |
| `Qwen3TTSProvider` | `providers/qwen3tts.py` | TTS. |
| `HalogenProvider` | `providers/halogen.py` | Qwen3.8-Flash-Next on the halogen engine (ROCm, gfx1151). |
| `MoonshineProvider` | `providers/moonshine.py` | STT (CPU, ONNX). |

Every `Provider` is stateless — no per-slot mutable state lives on the instance.
Abstract methods: `build_env()`, `start_cmd()`, `health()`, `infer()`,
`container_spec()`. `_spec_provider_for` dispatches each slot to its family
provider by `runtime_family` — FLM, Kokoro, Qwen3TTS, Moonshine, ComfyUI,
halogen each build their own `RuntimeLaunchPlan` (frozen dataclass: image, command/argv,
env, typed mounts with read-only/SELinux flags, devices, cap_add,
security_opt, port, network_mode, extra_args, optional health check); only
plain llama-server slots fall through to `ContainerProvider.container_spec`.
Every plan, whichever provider built it, still lands on the same single
Quadlet renderer, and `ContainerProvider` owns the container lifecycle
(start/stop/health) for all of them regardless of which provider built the
plan.

`SlotConfig.provider` (the string field on a slot) is **deprecated** — every slot runs
as a podman container now, and this field is a legacy label round-tripped for
backwards compatibility and UI display only. The CLI's `SlotProvider` enum
(`llama-server, flm, moonshine, kokoro`) names *the inference engine binary that serves
the slot* — this is distinct from the slot's hardware backend (`vulkan`/`rocm`/`cpu`).

## (B) Remote/cloud upstream provider catalog

This is very likely the concept you mean when you say "provider" in a hal0 config
context — the built-in template registry for cloud/remote LLM APIs
(`hal0.upstreams.presets`, data in `config/data/provider_presets.toml`). The catalog is never mutated at runtime;
user config lives in `/etc/hal0/upstreams.toml`.

| Catalog id | Name | Base URL | Auth style | Category | Model kinds |
|---|---|---|---|---|---|
| `minimax` | MiniMax | `https://api.minimax.io/v1` | `bearer` | cloud | chat, tools |
| `openai` | OpenAI | `https://api.openai.com/v1` | `bearer` | cloud | chat, embed, tools |
| `anthropic` | Anthropic | `https://api.anthropic.com/v1` | `bearer` | cloud | chat, tools |
| `openrouter` | OpenRouter | `https://openrouter.ai/api/v1` | `bearer` | cloud | chat, tools |
| `google_ai_studio` | Google AI Studio | `https://generativelanguage.googleapis.com/v1beta/openai` | `bearer` | cloud | chat, embed, tools |
| `deepseek` | DeepSeek | `https://api.deepseek.com` | `bearer` | cloud | chat, tools |
| `groq` | Groq | `https://api.groq.com/openai/v1` | `bearer` | cloud | chat, stt, tools |
| `mistral` | Mistral | `https://api.mistral.ai/v1` | `bearer` | cloud | chat, tools |
| `ollama` | Ollama | `http://localhost:11434/v1` | `none` | local | chat, tools |
| `hal0_peer` | hal0 peer | — (you enter the peer's URL) | `bearer` | peer | chat, tools |
| `custom` | Custom OpenAI-compatible | — (you enter the URL) | `bearer` | custom | chat, tools |

"Model kinds" are the `type` values of the preset's suggested models, plus `tools` when
the preset allows tool calls (`preset_to_api` in `hal0.upstreams.presets`).

<Aside type="note">
The `anthropic` preset uses Anthropic's OpenAI-compatible endpoint with bearer auth, so
it needs no proxy. Auth styles overall: `bearer, anthropic, header, none`.
</Aside>

Persisted config is an `UpstreamEntry` per upstream in `upstreams.toml` (see
[Config schema → upstreams.toml](/docs/reference/config-schema-profiles/#upstreamstoml)):
`catalog_id`, `url`, `auth_value_env` (the **name** of an environment variable, never
the key itself — the actual secret lives in `api.env`), `enabled`, and either a curated
per-model list (`curated = true` plus `[[upstream.models]]` rows) or, on a row that has
not been converted yet, `model_filters`.

<Aside type="note">
Older installs also had a `providers.toml` with a per-provider model selection. It is
retired: once a provider answers, hal0 converts its row to a curated one, applies that
selection to the matching row, and renames the file to `providers.toml.retired`. The
file is never deleted, and a rename is skipped if a `.retired` file already exists.
</Aside>

The same conversion applies to every older remote upstream row that has no per-model rows:
when its provider answers, hal0 lists the provider's models, writes one row per model and
marks the row curated. Before the first change of a run, `upstreams.toml` is copied to
`upstreams.toml.pre-convert` (same mode, never overwritten); if that copy fails, nothing is
converted that run. A provider that is unreachable or lists nothing is left untouched and
retried at the next start. Two behaviour changes follow, and each is logged as a warning:

- Models your old `model_filters` hid are now disabled rows. They used to be reachable by
  name; they return 404 until you enable them.
- A bare model id enabled on more than one provider is rejected with 400; use the
  `<provider>/<id>` form (the warning lists the ids to use).

### Curated providers and per-model rows

A curated provider (`curated = true`) serves only the models whose
`[[upstream.models]]` row has `enabled = true`. The rows are stored in `upstreams.toml`;
routing reads them and nothing else, so a request is routed the same way before and after
a restart. Every start, after the conversion above, hal0 fetches each curated provider's
model list once in the background and adds each model it offers that has no row yet as a
row with `enabled = false`. Existing rows are never changed or removed by this, and an
unreachable provider is skipped. See
[Config schema → `[[upstream.models]]`](/docs/reference/config-schema-profiles/#upstreammodels)
for the fields.

To turn a model on with only the config file, set `enabled = true` on its
`[[upstream.models]]` row in `upstreams.toml`, then restart the API service. Upstreams are
read at start, so an edit to the file takes effect only after the restart.

```toml
[[upstream]]
name = "openai"
url = "https://api.openai.com/v1"
auth_value_env = "OPENAI_API_KEY"
catalog_id = "openai"
curated = true

[[upstream.models]]
id = "gpt-5"
enabled = true          # was false
type = "chat"
```

### How a model id is routed

In order, the first rule that applies wins:

1. A local slot, a pinned upstream that owns the id, or a model registry binding.
2. A curated provider with the model enabled. `<provider>/<id>` names the provider. A bare
   id matches every curated provider's enabled rows: one match routes there, several are a
   400 `upstream.model_ambiguous`. When `<provider>/<id>` has no enabled row on that
   provider, the whole string is tried as a bare id first, so a provider that lists
   `openai/gpt-5` as its own id (OpenRouter) still serves it. This step is skipped when a
   slot, an unconverted remote or an agent-managed upstream already advertises the exact
   string.
3. Any slot, unconverted remote or agent-managed upstream that advertises the id, fetching
   the model lists of unconverted remotes whose list is not loaded yet. Curated providers
   are never fetched here.
4. If nothing has routed the request and a curated provider stores the model switched off,
   or the request named `<provider>/<id>` and that provider has no enabled row for it, the
   answer is a 404 `upstream.model_not_enabled`. The message names the provider and how to
   enable the model: `hal0 upstream enable <provider> <model>`, or the provider's model
   list in the dashboard. A **bare** id is not refused here when the request is for
   embeddings, rerank, speech, transcription or images, or when the id is one of hal0's
   own alias names (such as `tts-1`): those continue to step 5 and the local slot serves
   them.
5. hal0's capability and path rules pick a local slot, as without any curated provider.

### What changes for an existing install

- Ids your old `model_filters` hid become disabled rows (see above).
- A bare id enabled on several providers needs `<provider>/<id>`.
- The picks in an old `providers.toml` now decide which models are enabled on the matching
  row.
- `/v1/models` lists a converted provider's models as `<provider>/<id>`. A bare id still
  routes, and `GET /v1/models/{id}` still answers for it.

### Rolling back to an older build

A converted `upstreams.toml` does not load on a build from before this change: the older
build rejects the new keys, and no remote provider loads. Before rolling back, restore
`upstreams.toml.pre-convert` over `upstreams.toml`. That copy was taken before the first
conversion, so it does not contain later edits; make them again after the rollback.

## Profiles

`hal0.profiles` + `ProfileConfig` — a profile is a reusable, device-agnostic backend
tune: the free llama-server flags, the context window, the reasoning default, whether
the model's mmproj loads and how it speculates — **not** a runtime image reference. The
model row holds only file facts (ADR-0029); a model runs differently by running under a
different profile.

| Field | Purpose |
|---|---|
| `flags` | Bench-tuned llama-server CLI flags. |
| `ctx_size` | Context window (128–16777216), or unset: the model's native window dense-capped at 32768, else 8192. |
| `enable_thinking` | Request-time reasoning default for slots running this profile (`true`/`false`/unset). |
| `vision` | `auto` (default; loads the model's mmproj when it has one) or `off`. |
| `speculation` | `auto` (default; drafts with the model's paired drafter when the runner can run it, else with its MTP heads when it has them and the runner supports it), `ngram` (n-gram lookup, no file needed) or `off`. Replaces `mtp`. Whether the file *has* heads is a model fact (the model's `mtp` field, else the `mtp` tag); the paired drafter is the model's `draft` field. |
| `runner` | Optional `RUNNER_IMAGES` registry key (str \| null, default null). Applying this profile to a slot sets the slot's `binary` to this runner key, and — only for a single-backend runner — derives the slot's `device` too (the profile wins over the slot's prior device within a device class). `null` (the default; every seed profile except `halogen`) means a flags-only tune that never touches the slot's runtime/device. |
| `cloned_from` | Provenance — set when a profile was cloned from a seed. |
| `intent` | Dashboard card headline. |

Setting `runner` on a profile via `POST`/`PUT /api/profiles` is validated against the registry: an unknown key 422s with `profiles.unknown_runner` (`hal0.profiles.screen_profile_runner`). Applying a runner-carrying profile to a slot is a server-side reconcile (`hal0.slots.config_write._reconcile_device_profile`): it rewrites the slot's `binary` and, when the runner declares exactly one `supported_backends` lane, the slot's `device` too. If the runner's lane is physically infeasible on this host — e.g. a ROCm-only runtime (like `qwen3tts`) on a host with no `/dev/kfd` — the apply is refused with a 400 `slot.config_error` (`SlotConfigError`) naming the runtime and the missing device node, rather than writing a config that would crash-loop.

A profile carries no hardware placement: the slot's own `device` field (see the device
taxonomy below) is the single authoritative hardware fact. `flags` may not set what another
layer owns: hardware flags (`-ngl`, `-dev`, `-t`), managed flags (`--model`, `--host`,
`--port`, `--alias`, `--ctx-size`), model-fact flags (`--jinja`, `--chat-template*`,
`--mmproj`, `--no-mmproj`, `--mmproj-auto`), derived placement (`--spec-draft-device`,
`--mmproj-device`), host-owned flags (remote model fetches such as `-hf`, host file reads
and writes such as `--api-key-file` and `--log-file`, listener and auth/TLS settings,
llama.cpp's built-in preset switches) and bare positional arguments. They are rejected when the profile is saved and refused again at launch, in every
spelling llama.cpp accepts. `--reasoning-format none` is rejected on save too, but launch strips it from the command instead of refusing. The error codes are listed in
[Config schema](/docs/reference/config-schema-profiles/#profilestoml).

Profiles carry **no `image` field** — image resolution is slot-owned
(`slot.image_pin` or `RUNNER_IMAGES[slot.binary]`).

`ProfileCatalog` provides CRUD over `/etc/hal0/profiles.toml`: `list()`, `resolve(name)`,
`create()`, `update()` (via a `ProfilePatch`), `delete()` (blocked if the profile is
still referenced by a slot). Seed profiles are
**virtual** — reapplied from code on every load, so they can't be deleted or edited,
only cloned.

A resolved profile (`ResolvedProfile`) adds derived fields: `runtime_family`
(`llama-server, flm, kokoro, qwen3tts, moonshine, comfyui, halogen` — classified structurally
off the profile's `runner`, else its seed name, not by sniffing an image string),
`supported_slot_types` (e.g. `flm` → `llm, embedding, transcription`;
`kokoro`/`qwen3tts` → `tts`; `moonshine` → `transcription`; `comfyui` → `image`;
`halogen` → `llm`; everything else → `llm, embedding, reranking`),
`used_by` (slot names referencing the profile), and static `tps`/`rtf` numbers from the
bench table.

The seeded `moonshine` and `kokoro` profiles are classified into their runtime family by
name. `moonshine` is the STT sibling of the seeded `kokoro`
profile: `runtime_family = "moonshine"`, `supported_slot_types = ("transcription",)`,
image `ghcr.io/hal0ai/hal0-runner-moonshine` (resolved via `RUNNER_IMAGES["moonshine"]`,
tag and digest pinned in `manifest.json`), and self-managed (operator-staged) weights — see
[Voice: STT and TTS](/docs/guides/voice-stt-tts/) and ADR-0001, "Reinstate
Moonshine as the CPU STT engine" (`docs/adr/0001-moonshine-cpu-stt-reinstatement.md`
in the repository, not published to these docs).

### How a launch is composed

A llama-server slot's command is built from four layers, lowest precedence first, then deduplicated last-wins:

| Layer | Contributes |
|---|---|
| `base` | `--host`, `--port`, `--model`, `--alias`, `--ctx-size` (from the profile's `ctx_size`) |
| `model` | family quirks, `--jinja`, `--chat-template-file`, `--mmproj` when the profile's `vision` is `auto`, and, when speculation is in effect, `--spec-type` (`draft-<kind>` plus `--spec-draft-model` for a paired drafter, `draft-mtp` for MTP heads) |
| `profile` | the draft bundle for the kind in effect (the n-gram bundle for `speculation = "ngram"`), then the profile's `flags` (its own `--spec-draft-*` values win over the bundle; `--spec-type` is refused in `flags`) |
| `slot` | `--device` (`ROCm0`, `Vulkan0`, `CUDA0` or `none`, from the slot's device), `-ngl`, `--threads`, `--metrics`, and, only for embedded MTP heads, `--spec-draft-device` taken from the slot's device (none on a `cpu` slot). A paired drafter file gets no device flag and runs on the same devices as the model |

`GET /api/slots/{name}/resolved` returns the deduplicated `argv` and, for each surviving flag, the layer (`base`, `model`, `profile` or `slot`) that set its final value. Repeatable flags (`--override-kv`, `--draft-model`) are kept at every occurrence and have no provenance entry, because no single occurrence wins. A llama-server slot with no profile runs its type's seed (`embedding` or `reranking`), else `chat`; a profileless `tts`, `transcription` or `image` slot uses its engine's default (see [Config schema: slot files](/docs/reference/config-schema-slots/)). A slot that names a profile the catalog does not have refuses to launch with `slot.profile_missing`.

### Seed profiles

The code-shipped seeds are `chat`, `agent`, `utility`, `coding`, `embedding`, `reranking`, `cpu-chat`, `flm`, `kokoro`, `moonshine`, `qwen3-tts`, `comfyui`, `brain` and `halogen`. `ctx_size` is set by `agent`, `utility` and `brain` (`65536`), `embedding` and `reranking` (`4096`), `flm` (`16384`) and `halogen` (`262144`). `vision = "off"` is set by `agent`, `coding` and `brain`; `halogen` sets `vision = "auto"`. No seed sets `speculation` or `enable_thinking`, and `halogen` is the one seed that sets `runner` (`runner = "halogen"`). A seed with no `ctx_size` follows the model's native window, capped at 32768 (8192 when the native window is unknown). The shipped slots point at these seeds.

### Halogen profiles

A profile whose `runner` is `halogen` (the seed `halogen`, or a clone) configures an engine with no command-line flags: its `flags` are `HALOGEN_NAME=value` environment tokens, and the llama-server flag screen above does not apply to it. The halogen screen accepts only `^HALOGEN_[A-Z0-9_]+=.+$` tokens and refuses the names another layer owns (the listener, checkpoint and model id; the slot tune's context, thinking, reasoning, vision and speculation variables; `HALOGEN_DOWNLOAD`, `HALOGEN_API_KEY*`, `HALOGEN_NPU_*`, `HALOGEN_CACHE_DIR`, `HALOGEN_CACHE_FILE` and `HALOGEN_RECORD_*`), range-checks the curated engine settings, and refuses `HALOGEN_HOST_RESERVE_GIB` under 10, each with a 422 (`profiles.halogen_flag_malformed`, `profiles.halogen_flag_denied` with the owner of the name in `details`, `profiles.halogen_flag_out_of_range`). A profile `ctx_size` past the engine's native 262144 positions is refused the same way (`profiles.halogen_flag_out_of_range`) unless `flags` carries `HALOGEN_ROPE_YARN`. `speculation = "ngram"` is refused for the family (`profiles.speculation_unsupported`, 422; on a slot, `slot.tune_unsupported_value`, 400, which also refuses a context past the native window). `GET /api/system-info` lists each setting under `backends.halogen.knobs` and the refused names under `backends.halogen.knob_denied` (both are empty for every other runner). See [Run Flash-Next on halogen](/docs/guides/run-flash-next-on-halogen/#engine-settings).

## Runner images

`hal0.runners.RUNNER_IMAGES` is the code registry of runner keys hal0 can launch. Every entry carries a `runtime_family`, a `device_class` (`gpu`/`cpu`/`npu`/`img`), an optional `backend` (`rocm`/`vulkan`/`cuda`), a `supported_backends` tuple, operator-facing display metadata (`title`, `blurb`), and a `tier` (`default` / `optional`). Its image is not stored on the entry: `Runner.image` reads the runner's row in the `manifest.json` `runners` pin table (`image`, `tag`, `digest`, `lanes_gated`; see [Manage runner images](/docs/guides/manage-runner-images/#the-pin-table)). `GET /api/system-info`'s `backends` object (keyed by runner key, one entry per `RUNNER_IMAGES` row) surfaces `title`, `blurb` and `tier`, plus `supported_backends`, `format_arch` and the launch capabilities in `supports` (`mtp`, `jinja`, `mmproj`); `GET /api/runner-images` copies `title`, `blurb` and `tier` onto each catalogue row, plus the runner key as `runner`. `tier` is the only record of whether a runtime is a default (ADR-0027): the runtime pickers sort by it and the Runner Images page groups by it.

As of ADR-0006 (`docs/adr/0006-every-shipped-image-is-a-registry-runner.md`), every image hal0 ships gets its own `RUNNER_IMAGES` entry. `image_pin` remains available as a debug-only hatch (a custom build, a rollback, a hand-edited ref) but is never how an operator normally reaches a shipped runtime.

The registry today:

| Key | `runtime_family` | `backend`(s) | `tier` (title) | Notes |
|---|---|---|---|---|
| `standard` | `llama-server` | `rocm`, `vulkan` | `default` (Standard) | The only runner with two `supported_backends` — one AMD GPU image serves both lanes, HIP for `gpu-rocm` and RADV for `gpu-vulkan`. The Vulkan lane is admitted per digest via `lanes_gated`. Runs plain GGUF models. |
| `cpu` | `llama-server` | `cpu` (device_class `cpu`) | `default` (CPU) | Portable `-march`, no GPU required. |
| `flm` | `flm` | `npu` (device_class `npu`) | `default` (NPU (FastFlowLM)) | FastFlowLM on the XDNA 2 NPU. |
| `xdna` | `llama-server` | `npu` (device_class `npu`) | `optional` (NPU (ggml-xdna)) | Tether's ggml-xdna llama.cpp fork on the AMD XDNA2 NPU; plain GGUF, open kernels, baked into the image at build time. `xdna_model_fit` classifies each model `fused` or `per-op`; today only requantized Qwen3.5-0.8B gets the fused path. Coexists with `flm` (warn, not refuse) on shared NPU hardware. See [Run GGUF models on the NPU with ggml-xdna](/docs/guides/run-xdna-npu/) and [ADR-0057](/docs/adr/0057-ggml-xdna-optional-npu-runner/). |
| `kokoro` | `kokoro` | `cpu` (device_class `cpu`) | `default` (Kokoro speech) | TTS. |
| `moonshine` | `moonshine` | `cpu` (device_class `cpu`) | `default` (Moonshine transcription) | STT, ONNX. |
| `comfyui` | `comfyui` | `rocm` (device_class `img`) | `default` (ComfyUI) | Image and video generation. |
| `qwen3tts` | `qwen3tts` | `rocm` | `optional` (Qwen3 TTS) | GPU TTS. |
| `cuda` | `llama-server` | `cuda` | `optional` (NVIDIA CUDA) | NVIDIA GPUs. Pins the upstream `ghcr.io/ggml-org/llama.cpp` `server-cuda-b<N>` image rather than a hal0 build. |
| `halogen` | `halogen` | `rocm` (device_class `gpu`) | `optional` (halogen (Flash-Next)) | Peonist's closed-source engine for Qwen3.8-Flash-Next on Strix Halo (gfx1151); checkpoints are `.hgn` files (`format_arch` `hgn`) and no llama drafter kinds apply. Pins the vendor's `ghcr.io/peonist-ai/halogen-flash-server` by tag and digest. Never derived from a device: a slot gets it from the `halogen` profile or the runtime picker. See [Run Flash-Next on halogen](/docs/guides/run-flash-next-on-halogen/). |

Every other runner's image is `ghcr.io/hal0ai/hal0-runner-<key>`; `cuda` and `halogen` are the two external images (ADR-0047).

A slot's `binary` field selects a runner key directly; left empty, it derives one from the slot's `device` via `hal0.runners.runner_for_backend` (`cuda` → `cuda`, `cpu` → `cpu`, anything else → `standard`). Either way, the slot's actual launch image is resolved through `hal0.providers.container._resolve_image_ref`: `slot.image_pin` (the debug-only escape hatch) outranks `[slots].default_images[<runner key>]` (an operator's per-runner override, settable from the dashboard), which outranks the `HAL0_RUNNER_IMAGE_<KEY>` env override (see [Environment variables: bootstrap, install-time & preflight](/docs/reference/env-vars-install/)), which outranks the `manifest.json` pin. A slot dispatched to a non-llama provider (ComfyUI, FLM, Kokoro, Moonshine, Qwen3-TTS, halogen) resolves through that provider instead, in the same order keyed by its runner key: `image_pin`, then (ComfyUI only) a plain `image` string, then `[slots].default_images[<key>]`, then the env override or pin.

### Unsupported quantizations

hal0 does not ship a llama.cpp fork, so no runner loads ROCmFPX-family (ROCmFP4, …), IU4 or ActiveFPX GGUFs. They are refused up front rather than at load: adding from a path and pulling answer 422 `models.unsupported_quant`, a library scan skips the file with reason `unsupported_quant:<label>`, and launching a slot whose model is one answers 422 `slot.unsupported_quant` (`hal0.registry.detect.unsupported_quant`). Use a plain GGUF build of the same model.

See [Manage runner images](/docs/guides/manage-runner-images/) for the
catalogue page (Slots → Runner Images) and the Vulkan lane's image gate, and
[Manage runner images: pulling, pinning & upgrading](/docs/guides/manage-runner-images-lifecycle/)
for what pulling/pinning/updating an image does and does not do to a running
slot.

## Device taxonomy

See [Hardware matrix](/docs/reference/hardware-matrix/) for
the full table. In short: `hal0.model_meta.CANONICAL_DEVICES` is the single source of
truth for the 5 valid device ids (`gpu-rocm`, `gpu-vulkan`, `gpu-cuda`, `cpu`, `npu`),
consumed by `SlotConfig.device` and every
other call site that used to duplicate this list.
