<Aside type="caution">
hal0's source has **two unrelated "provider" concepts**. This page covers both,
clearly separated — do not conflate them.
</Aside>

## (A) Local inference-backend provider

`hal0.providers.base.Provider` — the abstract class that runs a slot's inference
process. Concrete implementations:

| Provider | Module | Runs |
|---|---|---|
| `ContainerProvider` | `providers/container.py` | llama-server, via podman. |
| `FLMProvider` | `providers/flm.py` | NPU inference (FastFlowLM). |
| `ComfyUIProvider` | `providers/comfyui.py` | Image generation. |
| `KokoroProvider` | `providers/kokoro.py` | TTS. |
| `Qwen3TTSProvider` | `providers/qwen3tts.py` | TTS. |
| `MoonshineProvider` | `providers/moonshine.py` | STT (CPU, ONNX). |

Every `Provider` is stateless — no per-slot mutable state lives on the instance.
Abstract methods: `build_env()`, `start_cmd()`, `health()`, `infer()`,
`container_spec()`. `_spec_provider_for` dispatches each slot to its family
provider by `runtime_family` — FLM, Kokoro, Qwen3TTS, Moonshine, ComfyUI each
build their own `RuntimeLaunchPlan` (frozen dataclass: image, command/argv,
env, typed mounts with read-only/SELinux flags, devices, cap_add,
security_opt, port, network_mode, extra_args, optional health check); only
plain llama-server slots fall through to `ContainerProvider.container_spec`.
Every plan, whichever provider built it, still lands on the same single
Quadlet renderer, and `ContainerProvider` owns the container lifecycle
(start/stop/health) for all of them regardless of which provider built the
plan.

`SlotConfig.provider` (the string field on a slot) is **deprecated** — every slot runs
as a podman container now, and this field is a legacy label round-tripped for
backwards compatibility and UI display only. The CLI's `SlotProvider` enum
(`llama-server, flm, moonshine, kokoro`) names *the inference engine binary that serves
the slot* — this is distinct from the slot's hardware backend (`vulkan`/`rocm`/`cpu`).

## (B) Remote/cloud upstream provider catalog

This is very likely the concept you mean when you say "provider" in a hal0 config
context — the built-in template registry for cloud/remote LLM APIs
(`hal0.upstreams.integrations`). The catalog itself is code, never mutated at runtime;
user config lives in `/etc/hal0/upstreams.toml`.

| Catalog id | Base URL | Auth style | Category | Capabilities |
|---|---|---|---|---|
| `openai` | `https://api.openai.com/v1` | `bearer` | cloud | chat, embed, vision, tools, tts, stt |
| `anthropic` | `https://api.anthropic.com/v1` | `anthropic` (`x-api-key` + `anthropic-version` header) | cloud | chat, vision, tools |
| `openrouter` | — | — | cloud | — |
| `google_ai_studio` | `https://generativelanguage.googleapis.com/v1beta/openai` | `bearer` | cloud | chat, vision |
| `deepseek` | — | — | cloud | — |
| `minimax` | — | — | cloud | — |
| `ollama` | `http://localhost:11434/v1` | `none` | local | — |

<Aside type="note">
`anthropic`'s catalog entry speaks the native `/v1/messages` shape only — it needs a
proxy for OpenAI-shape compatibility. Auth styles overall: `bearer, anthropic,
header, none`.
</Aside>

Persisted config is a `ProviderEntry` per upstream (see
[Config schema → providers.toml](/docs/reference/config-schema/)):
`catalog_id`, `name`/`base_url` overrides, `auth_value_env` (the **name** of an
environment variable, never the key itself — the actual secret lives in `api.env`),
`enabled`, `models`.

<Aside type="caution">
`hal0 upstream` CLI commands (`upstream create`, `upstream credentials set`, etc.) and
`upstreams.toml`/`UpstreamEntry` are a **separate schema** from `providers.toml`/
`ProviderEntry` above — both represent "remote provider" concepts but are distinct
tables with distinct fields (`UpstreamEntry` adds `kind`, `warmup_strategy`,
`model_filters`; see [Config schema](/docs/reference/config-schema/)).
Verify which one a given feature actually reads before documenting behavior.
</Aside>

## Profiles

`hal0.profiles` + `ProfileConfig` — a profile is a reusable, device-agnostic backend
tuning template: a bench-tuned flag bundle plus a few classification hints, **not** a
runtime image reference.

| Field | Purpose |
|---|---|
| `flags` | Bench-tuned llama-server CLI flags. |
| `mtp` | **Informational only** — MTP is model-owned, not profile-owned (see [Model roster & benchmarks](/docs/reference/model-roster-benchmark/)). |
| `device_class` | `gpu \| cpu \| npu \| img \| null`. |
| `backend` | `rocm \| vulkan \| cuda \| null`. |
| `runner` | Optional `RUNNER_IMAGES` registry key (str \| null, default null). Applying this profile to a slot sets the slot's `binary` to this runner key, and — only for a single-backend runner — derives the slot's `device` too (the profile wins over the slot's prior device within a device class). `null` (the default; every seed profile) means a flags-only tune that never touches the slot's runtime/device. |
| `cloned_from` | Provenance — set when a profile was cloned from a seed. |
| `intent` | Dashboard card headline. |
| `quant` | Display chip only — the runtime reads quant from the model, not the profile. |

Setting `runner` on a profile via `POST`/`PUT /api/profiles` is validated against the registry: an unknown key 422s with `profiles.unknown_runner` (`hal0.profiles.screen_profile_runner`). Applying a runner-carrying profile to a slot is a server-side reconcile (`hal0.slots.config_write._reconcile_device_profile`): it rewrites the slot's `binary` and, when the runner declares exactly one `supported_backends` lane, the slot's `device` too. If the runner's lane is physically infeasible on this host — e.g. a ROCm-only runtime (like `qwen3tts`) on a host with no `/dev/kfd` — the apply is refused with a 400 `slot.config_error` (`SlotConfigError`) naming the runtime and the missing device node, rather than writing a config that would crash-loop. Model-swap adoption of a model's preferred profile (`hal0.slots.profile_adopt`) follows the same device-class check before adopting a `runner`-carrying profile.

<Aside type="note">
As of v1.0, `device_class`/`backend` are **inert match-only fit hints**. The
slot's own `device` field (see the device taxonomy below) is the single
authoritative hardware fact; the profile hints are retained on-disk only
because published `.hal0profile.json` export artifacts carry them and their
checksums cover the field.
</Aside>

Profiles carry **no `image` field** — image resolution is slot-owned
(`slot.image_pin` or `RUNNER_IMAGES[slot.binary]`).

`ProfileCatalog` provides CRUD over `/etc/hal0/profiles.toml`: `list()`, `resolve(name)`,
`create()`, `update()` (via a `ProfilePatch`), `delete()` (blocked if the profile is
still referenced by a slot or by a model's `defaults.profile`). Seed profiles are
**virtual** — reapplied from code on every load, so they can't be deleted or edited,
only cloned.

A resolved profile (`ResolvedProfile`) adds derived fields: `runtime_family`
(`llama-server, flm, kokoro, qwen3tts, moonshine, comfyui` — classified structurally off
name and `device_class`, not by sniffing an image string), `supported_slot_types` (e.g.
`flm` → `llm, embedding, transcription`; `kokoro`/`qwen3tts` → `tts`; `moonshine` →
`transcription`; `comfyui` → `image`; everything else → `llm, embedding, reranking`),
`used_by` (slot names referencing the profile), and static `tps`/`rtf` numbers from the
bench table.

The seeded `moonshine` profile sets no `device_class` at all (neither does the
seeded `kokoro` profile) — both are classified into their runtime family by
name, not by device. It's the STT sibling of the seeded `kokoro`
profile: `runtime_family = "moonshine"`, `supported_slot_types = ("transcription",)`,
image `ghcr.io/hal0ai/hal0-runner-moonshine` (resolved via `RUNNER_IMAGES["moonshine"]`,
tag and digest pinned in `manifest.json`), and self-managed (operator-staged) weights — see
[Voice: STT and TTS](/docs/guides/voice-stt-tts/) and ADR-0001, "Reinstate
Moonshine as the CPU STT engine" (`docs/adr/0001-moonshine-cpu-stt-reinstatement.md`
in the repository, not published to these docs).

## Runner images

`hal0.runners.RUNNER_IMAGES` is the code registry of runner keys hal0 can launch. Every entry carries a `runtime_family`, a `device_class` (`gpu`/`cpu`/`npu`/`img`), an optional `backend` (`rocm`/`vulkan`/`cuda`), a `supported_backends` tuple, operator-facing display metadata (`title`, `blurb`), and a `tier` (`default` / `optional`). Its image is not stored on the entry: `Runner.image` reads the runner's row in the `manifest.json` `runners` pin table (`image`, `tag`, `digest`, `lanes_gated`; see [Manage runner images](/docs/guides/manage-runner-images/#the-pin-table)). `GET /api/system-info`'s `backends` object (keyed by runner key, one entry per `RUNNER_IMAGES` row) surfaces `title`, `blurb` and `tier`, plus `supported_backends`, `format_arch` and the launch capabilities in `supports` (`mtp`, `jinja`, `mmproj`); `GET /api/runner-images` copies `title`, `blurb` and `tier` onto each catalogue row, plus the runner key as `runner`. `tier` is the only record of whether a runtime is a default (ADR-0027): the runtime pickers sort by it and the Runner Images page groups by it.

As of ADR-0006 (`docs/adr/0006-every-shipped-image-is-a-registry-runner.md`), every image hal0 ships gets its own `RUNNER_IMAGES` entry. `image_pin` remains available as a debug-only hatch (a custom build, a rollback, a hand-edited ref) but is never how an operator normally reaches a shipped runtime.

The registry today:

| Key | `runtime_family` | `backend`(s) | `tier` (title) | Notes |
|---|---|---|---|---|
| `standard` | `llama-server` | `rocm`, `vulkan` | `default` (Standard) | The only runner with two `supported_backends` — one AMD GPU image serves both lanes, HIP for `gpu-rocm` and RADV for `gpu-vulkan`. The Vulkan lane is admitted per digest via `lanes_gated`. Runs plain GGUF models. |
| `cpu` | `llama-server` | `cpu` (device_class `cpu`) | `default` (CPU) | Portable `-march`, no GPU required. |
| `flm` | `flm` | `npu` (device_class `npu`) | `default` (NPU (FastFlowLM)) | FastFlowLM on the XDNA 2 NPU. |
| `kokoro` | `kokoro` | `cpu` (device_class `cpu`) | `default` (Kokoro speech) | TTS. |
| `moonshine` | `moonshine` | `cpu` (device_class `cpu`) | `default` (Moonshine transcription) | STT, ONNX. |
| `comfyui` | `comfyui` | `rocm` (device_class `img`) | `default` (ComfyUI) | Image and video generation. |
| `qwen3tts` | `qwen3tts` | `rocm` | `optional` (Qwen3 TTS) | GPU TTS. |
| `cuda` | `llama-server` | `cuda` | `optional` (NVIDIA CUDA) | NVIDIA GPUs. Pins the upstream `ghcr.io/ggml-org/llama.cpp` `server-cuda-b<N>` image rather than a hal0 build. |

Every other runner's image is `ghcr.io/hal0ai/hal0-runner-<key>`.

A slot's `binary` field selects a runner key directly; left empty, it derives one from the slot's `device` via `hal0.runners.runner_for_backend` (`cuda` → `cuda`, `cpu` → `cpu`, anything else → `standard`). Either way, the slot's actual launch image is resolved through `hal0.providers.container._resolve_image_ref`: `slot.image_pin` (the debug-only escape hatch) outranks `[slots].default_images[<runner key>]` (an operator's per-runner override, settable from the dashboard), which outranks the `HAL0_RUNNER_IMAGE_<KEY>` env override (see [Environment variables](/docs/reference/env-vars/)), which outranks the `manifest.json` pin. A slot dispatched to a non-llama provider (ComfyUI, FLM, Kokoro, Moonshine, Qwen3-TTS) resolves through that provider instead, in the same order keyed by its runner key: `image_pin`, then (ComfyUI only) a plain `image` string, then `[slots].default_images[<key>]`, then the env override or pin.

### Unsupported quantizations

hal0 does not ship a llama.cpp fork, so no runner loads ROCmFPX-family (ROCmFP4, …), IU4 or ActiveFPX GGUFs. They are refused up front rather than at load: adding from a path and pulling answer 422 `models.unsupported_quant`, a library scan skips the file with reason `unsupported_quant:<label>`, and launching a slot whose model is one answers 422 `slot.unsupported_quant` (`hal0.registry.detect.unsupported_quant`). Use a plain GGUF build of the same model.

See [Manage runner images](/docs/guides/manage-runner-images/) for the
catalogue page (Slots → Runner Images), the Vulkan lane's image gate, and
what pulling/pinning/updating an image does and does not do to a running
slot.

## Device taxonomy

See [Hardware matrix](/docs/reference/hardware-matrix/) for
the full table. In short: `hal0.model_meta.CANONICAL_DEVICES` is the single source of
truth for the 5 valid device ids (`gpu-rocm`, `gpu-vulkan`, `gpu-cuda`, `cpu`, `npu`),
consumed by `SlotConfig.device`, a profile's (now inert) `device_class`, and every
other call site that used to duplicate this list.
