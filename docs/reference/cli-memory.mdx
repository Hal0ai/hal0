## `hal0 memory` — manage hal0 memory (Hindsight engine)

| Command | Args | Flags |
|---|---|---|
| `memory status` | — | `--json` |
| `memory enable` | — | `--json` |
| `memory disable` | — | `--json` |
| `memory recall <query>` | `query` | `--bank`, `--tags` (repeatable), `--types` (repeatable), `--max-tokens` (default `4096`), `--json` |
| `memory graph status` | — | `--json` |
| `memory graph enable` | — | `--slot`, `--model`, `--local`, `--json` |
| `memory graph disable` | — | `--json` |
| `memory graph check` | — | `--json` |

`memory graph enable` turns graph extraction on and can repoint the memory engine. `--slot <name>` runs it on a local LLM slot and clears any upstream model. `--model <id>` runs it on an upstream model id that hal0's `/v1` already routes (the ids `memory graph status` lists under `Upstream models`); the configured slot is kept as the way back. `--local` clears `--model` and returns the engine to the local `[memory.graph].extraction_slot`. `--model` and `--local` cannot be combined, and `--model` cannot be combined with `--slot`. hindsight-api always calls the virtual id `hal0/memory`, which hal0 resolves on every call, so the change applies at once and does not restart the engine. `memory graph status` prints `Engine target` (the local slot or upstream model `hal0/memory` resolves to) and an `Engine running` line naming the provider and model hindsight-api really loads; the line is marked as overridden when `/etc/hal0/hindsight-llm.env` sets the provider, base URL or model, and as `cannot verify` when hal0-api can read neither the engine process nor that file (see [Services](/docs/operate/services/#hindsight-apiservice)).

### `memory bank`

| Command | Args | Flags |
|---|---|---|
| `bank list` | — | `--json` |
| `bank stats <bank>` | `bank` | `--json` |
| `bank profile get <bank>` | `bank` | `--json` |
| `bank profile set <bank>` | `bank` | `--retain-mission`, `--observations-mission`, `--reflect-mission`, `--skepticism`/`--literalism`/`--empathy` (1-5), `--min-refresh-interval <seconds>` (mental-model refresh floor; `0` = after every consolidation), `--json` |
| `bank export <bank>` | `bank` | `--out` |
| `bank import <bank>` | `bank` | `--file` (required), `--dry-run`, `--json` |
| `bank seed` | — | `--config <hal0.toml>`, `--state-dir <dir>` (default: this box's), `--json` |
| `bank delete <bank>` | `bank` | `--confirm` (required, must equal the bank id), `--json` |
| `bank consolidate <bank>` | `bank` | `--scope` (repeatable), `--json` |

`bank profile set --reflect-mission` writes the same per-bank config override as the description editor on the dashboard's Memory ▸ Facts tab: the description in the bank bar is the bank's Hindsight `reflect_mission`, and clicking it edits it in place. `hal0 memory bank seed` seeds this box's default banks, the same ones hal0-api seeds when it first gets the engine: on a two-bank store `[memory] bank` and `[memory] private_bank` (`hal0:shared` and `hal0:private` by default), on an old layout its platform bank alone. It reads the layout record and talks to the memory engine directly, not to hal0-api, so the installer can run it before hal0-api has the engine. A bank is seeded only while it is missing, or empty with no retain mission, and nothing is seeded while an embedder switch is running; the command then prints `not seeding now: <reason>`. It exits 0 when it seeded at least one bank, 3 when every bank was already set up (nothing seeded), 4 when an embedder switch held the seed back, and 1 when the layout cannot be read or a bank could not be seeded. The installer runs it after the engine first answers and reports each of those outcomes in its own words, so it never says "seeded" when nothing was. A bank id may contain dots as well as colons (`coding-agent::ultrareview-1.4`); a leading dot, a dot-only segment and any `..` are refused with `invalid bank_id`.

### `memory mm` (mental models)

| Command | Args | Flags |
|---|---|---|
| `mm list <bank>` | `bank` | `--json` |
| `mm refresh <bank> <model_id>` | `bank`, `model_id` | `--json` |
| `mm history <bank> <model_id>` | `bank`, `model_id` | `--json` |
| `mm repair` | — | `--bank` (repeatable; omit = every bank), `--apply`/`--dry-run` (default `--dry-run`), `--refresh`/`--no-refresh` (default `--refresh`), `--json` |

`mm repair` gives agents back their own mental models and knowledge pages.
An agent reads a model while its bank holds another agent's private memory
only when the model's scope strictly requires that agent's `agent:<id>` tag
and its trigger sets `exclude_mental_models`, which hal0 sets on every model
an agent creates through it (see
[MCP tools: hal0-memory](/docs/reference/mcp-tools-memory/)). A model made
before hal0 set the flag, or written straight to the engine, answers 404 to
its own agent on every route, and the agent cannot add the flag itself.

The command lists, one line per model, every model that lacks the flag and
whose scope would then be confined to exactly one agent: tags or
`trigger.tag_groups` on that agent's tag under `all_strict`, `exact`, or
`any_strict` over that one tag. Whole-bank, project-wide and shared models are
never listed or written. A line marked `hidden from its owner now` is one
that agent cannot read today. With `--apply`, for each model in turn:

1. a model hidden from its owner is emptied first (the engine's
   `POST .../mental-models/{id}/clear`), while it is still hidden, so the
   flag never shows its owner content written from other agents' memory
   (the engine keeps the model's `reflect_response`; hal0 returns it to
   agents as `null` while a model's content is empty);
2. `exclude_mental_models: true` is set (only that field is sent; the engine
   keeps the rest of the trigger);
3. a full refresh is queued (`{"mode": "full"}`; a delta-mode model keeps its
   mode), so nothing of the old content survives.

`--no-refresh` skips step 3, and the model stays empty until its next
refresh. If the refresh fails, the line says the model is flagged and
cleared and the refresh failed; it stays empty, not stale. A model is
skipped, with the reason, when another agent's private document in its bank
also carries the owner's `agent:<id>` tag: the owner's scope would read it.
A repaired model is not listed again, so running it twice changes nothing.
It goes through hal0-api's admin memory routes and exits `1` when a bank
cannot be read or a write fails. Nothing runs it for you, `hal0 update`
included. The `memory_model_owners` row of `hal0 doctor all` counts the
models hidden from their owner and names this command.

### `memory models`, `memory agents`, `memory spec`

| Command | Args | Flags |
|---|---|---|
| `memory models show` | — | `--json` |
| `memory agents install <harness>` | `harness` (e.g. `claude-code`, `cursor`, `codex`) | `--bridge-key-file <path>` (`-` reads stdin; the file holds only the key), `--bridge-key <hal0bk_…>`, `--dry-run`, `--json` |
| `memory spec apply` | — | `--dry-run`, `--bank BANK` (a bank id, or the role `platform` or `private`), `--api URL` (default `http://127.0.0.1:9177`), `--json` |

`memory agents install <harness>` runs the pinned `hindsight-coding-agents` installer for the harness (with no server flags, so it does not write the flat `apiUrl`), then sets `harnesses.<harness>` in `~/.hindsight/coding-agent.json`: `serverMode: self-hosted`, `apiUrl` = hal0-api's address plus `/api/memory/compat`, `apiToken`, and the showcase defaults (`pageTriggerType`, `observationScopes`, `retainTags: [agent:<harness>]`). The flat keys and other harnesses are left alone and the file is narrowed to 0600. The key is read from `--bridge-key-file` (a file, or stdin for `-`, that holds only the key: `hal0 bridge add` prints a panel, so save the key from it rather than piping) or taken from `--bridge-key`. It is refused unless it has a bridge key's shape (`hal0bk_<name>.…`), so the admin key is never written, even though the endpoint accepts it, and refused if the endpoint rejects it; without either, a bridge key already in that section that the endpoint accepts is reused. Prefer the file: a key on the command line is visible to every user in the process list while the command runs. The command never mints or rotates a key: without one it stops before running anything and says to run `hal0 bridge add <harness> --scope memory` (or `hal0 bridge rotate <harness>` when that client exists). A harness name must be letters, digits, `.`, `_` or `-`, starting with a letter or digit (at most 64 characters); anything else is refused before anything runs. When the harness name is not a valid client name, or is reserved (`pi`, `hermes`, `admin`, anything starting `hal0`, …), it suggests another name instead, such as `pi-memory`. The installer runs with stdin closed and never prompts; with no server flags it changes no flat key unless an older per-harness plugin config is carried over, and the command says when it did. The printed config and the installer's output, in the panel, `--json` and an error, mask every token in the file and anything shaped like a bridge key (`hal0bk_…`). The file is written as for Pi ([Generated files](/docs/reference/generated-files/)): never through a symlink that leaves the home. The memory identity is the bridge client's name. A bridge key always carries the `agents` scope as well as `memory`, so whoever can read the file can also start Hermes runs through `/mcp/agents`.

`memory models show` lists the embeddings, reranker and decision models from `[memory.models]` and `[memory.decision]`. The embeddings row shows the provider and model the memory store was built with, which is what the engine runs; when `[memory.models]` names a different provider or model, the row says that value is not applied and names `hal0 memory embedder switch`. `memory agents install` wires a coding-agent harness to `hal0-memory`; `--dry-run` prints the installer command and config merge without running or writing anything. `memory spec apply` applies the packaged bank spec (templates, `config_extra`, knowledge-base pages) through Hindsight's `/import`. The spec names roles: `platform` and `private` are this box's banks ([Memory banks](/docs/concepts/memory-banks#bank-spec-and-seeding)). It refuses the per-project observation scope on an old unified bank and the private template's mental models on `hal0:private`, and says so. It is idempotent, and `--dry-run` posts with `dry_run=true`.

### `memory embedder switch`

```sh
hal0 memory embedder switch MODEL [--provider local] [--apply|--dry-run]
                            [--allow-pending] [--json]
hal0 memory embedder switch --resume | --status | --clear-gate [--json]
```

Moves the memory store to another embedding model: pauses memory writes,
moves the engine to a private port so that nothing else can reach it, exports
every bank, restarts the engine on the new model, restores each bank (which
re-embeds it) under a temporary id, compares it with its archive, replaces
each original with a second restore into its own id, and returns the engine
to its normal address. Knowledge-page, directive, mental-model and document
ids are kept; fact ids are not, and the dry run says so. Memory is out of
service while it runs, recall included. See
[Change the embedding model](/docs/guides/enable-memory#change-the-embedding-model)
for the steps and the failure behaviour.

Unlike the other `hal0 memory` commands it does not call hal0-api: it runs on
the box, as root, and talks to the engine directly. It never asks a question.

| Flag | Meaning |
|---|---|
| `MODEL` | The embedding model to move to, for example `hindsight-ai/hs-embed-1`. Omitted with `--resume`, `--status` and `--clear-gate`. |
| `--provider` | The embeddings provider the model belongs to. Default `local`. |
| `--apply` / `--dry-run` | Default `--dry-run`: run the preflight, print the plan, write nothing. |
| `--allow-pending` | Go ahead while the engine has queued or running operations. What they have not written when a bank is exported is not carried over. |
| `--resume` | Finish an interrupted switch from its journal: carry a started swap forward, or undo a run that stopped before the swap. |
| `--status` | Print the journal, the write pause, where the engine listens, the banks and temporary banks on it, and what `--resume` would do for each, with the checks a resume would run. Changes nothing. |
| `--clear-gate` | Return the engine to its normal address and lift the write pause by hand. Refused while a switch is running or any journal shows an unfinished run. Checks no bank. |
| `--json` | Print the plan, status or result as JSON; progress goes to stderr. |

The preflight refuses, and the command exits 1, when: the store is already on
that embedder and is not mixed; the engine does not answer or its environment
cannot be read; the embedder record cannot be read or disagrees with the
engine; the engine's export or import API is off; a bank has queued or running
operations (without `--allow-pending`); free disk space is short on the
engine's filesystem or the archives'; memory writes are already paused, the engine is already on a private port, an
earlier switch did not finish, or a bank left by one is still on the engine;
an update or an engine upgrade is in progress; another switch is running; or
`--apply` is not run as root. An `--apply` or `--resume` also exits 1 when
the run fails. Then it has either been undone, or, if it stopped inside the
swap, the engine stays private and memory writes stay paused until `--resume`
completes; the message names the archive directory and `--status`. A finished
run whose store had to be recorded as mixed exits 0 and says so.


### `memory migrate fold-in`

```sh
hal0 memory migrate fold-in [--apply|--dry-run] [--resume] [--status] [--clear-gate]
                            [--bank ID]... [--owner HARNESS=CLIENT]... [--map BANK=HARNESS]...
                            [--skip BANK]... [--json]
```

Folds a store's old banks into `hal0:shared` and `hal0:private` (ADR-0058
decision 7a): the old platform bank, `coding-agent::<repo>` and
`<harness>::<repo>`, `project__<id>`, `pi-coder`, `Hal0::Agents` and every
`private__<agent>` bank, one bank at a time, by export, rewrite of the tags in
the archive, and merge import with `document_conflict=skip`. A dry run by
default, which reads every bank and writes nothing; `--apply` and `--resume`
need root. It never deletes, replaces or renames a bank. See
[Fold the old memory banks in](/docs/guides/fold-in-memory-banks) for what
happens to each fact, observation, mental model and directive.

| Flag | Meaning |
|---|---|
| `--apply` | Do it. The engine is moved to a private port and memory writes are paused for the whole run. Every bank of the run is checked before any is imported; if any would be left, nothing is imported and the run exits 3. When every old bank is folded, the layout record says `two_bank` and hal0-api is restarted. When any bank is left or not in the run, there is no cutover: the engine returns to its normal address, writes resume on the old layout, and the banks folded so far are kept in `state/memory-fold-in-ledger.json` for the next run. |
| `--resume` | Carry an interrupted run on from its journal (`state/memory-fold-in.json`, mirrored as `fold-in-journal.json` in the run's archive directory), with the owners it was planned with; a different `--owner` is refused. An import still running is waited for, never cancelled. With no unfinished journal it does what `--clear-gate` does. |
| `--status` | Where a run stands, from the files on disk: the journal, the pause, the isolation drop-in, the ledger's banks folded and left, the layout record, and the archive directories to keep until the cutover. Asks nothing of the engine. |
| `--clear-gate` | Root only. Lift a memory-write pause a finished fold-in left behind (it stopped between retiring its journal and lifting the pause). Refuses unless the pause is the fold-in's, no fold-in journal is unfinished, the engine is at its normal address, and the newest fold-in journal is the paused run's and finished. |
| `--bank ID` | Repeatable. Fold only these banks, typically ones an earlier run left. Banks an earlier run folded are exported and checked again as well (never imported twice; only what the targets are missing is sent), and naming one is refused. The run cuts over only if no other bank is still to fold. |
| `--owner HARNESS=CLIENT` | Repeatable. File a coding bank's facts written by `HARNESS` (their `agent:` tag, else the bank's harness) under bridge client `CLIENT`, and a private fact's `agent:` name in the other banks too. Without it: a memory-scoped bridge client of the harness's own name, else the reserved `hal0-legacy-<harness>` (a private agent name outside coding banks is kept, lower-cased). `pi` maps to `pi-coder` by default. Frozen per bank, with the list of bridge clients, once anything of the bank was sent: a later run that names different owners for it is refused. |
| `--map BANK=HARNESS` | Repeatable. Fold a bank the fold-in does not know as a coding bank written by `HARNESS`, its project taken from each fact's `project:` tags. Without it, or `--skip`, such a bank is refused and holds the cutover back. Kept in the ledger and reused by every later run; a different `--map` for a bank an earlier run folded (or sent part of) is refused. |
| `--skip BANK` | Repeatable. Leave a bank the fold-in does not know, or the retired `agents` bank, out of the two banks: it stays on the engine and nothing reads it after the cutover. Without it, an unknown bank holds the cutover back even when it is empty, and so does `agents` while it is not empty. Kept in the ledger and reused by every later run. The run that cuts over lists each skipped bank with its fact and document counts (`skipped` in `--json`). Refused for a bank the fold-in folds, and for one an earlier run folded: it may have taken writes since, and needs a re-check, not a skip. |
| `--json` | One JSON document on stdout: the plan, the result or the failure. |

Exit codes: 0 when the dry run has no refusal, the run cut over, or
`--clear-gate` lifted the pause; 3 when the run ended without a cutover
because a bank was left, not in the run, or a bank on the engine held the
cutover back (the output lists them, why, and what to do; a left bank's ids
are in `left-ids.json` in the run's archive directory; writes are open on the
old layout); 1 when the dry run or `--apply` is refused, or a run fails; 2 for
a usage error; 130 when interrupted. A run that fails after it sent an import keeps memory writes
paused and the engine private until `--resume` completes; one that fails
before is undone.

### `memory migrate platform`

```sh
hal0 memory migrate platform [--target BANK] [--source shared] [--agents-bank agents]
                             [--apply|--dry-run] [--skip-clone] [--skip-bank-config] [--json]
```

Moves the platform memory into the bank named by `[memory] bank` (ADR-0052).
`--target` defaults to that config value when it is set in `hal0.toml` (and is
not the two-bank default `hal0:shared`); otherwise pass `--target`. The
two-bank layout's `hal0:shared` and `hal0:private` are refused as targets: a
store moves into them through the fold-in, which splits private memory out.
`hal0 memory migrate unify` was removed. The command clones `--source`
(default `shared`) into `--target` with the engine's clone call, folds the
retired `--agents-bank` (default `agents`, skipped when it does not exist) into
the same target, and then compares fact counts, exiting 1 if the target is
short. It is a dry run unless `--apply` is given, never modifies or deletes the
source banks, and never edits `hal0.toml`. The target must not exist yet; use
`--skip-clone` to fold and verify a target that already holds the clone.
`--skip-bank-config` leaves the source's config overrides, directives and
webhooks behind. `--apply` needs the engine's export and import APIs enabled.
