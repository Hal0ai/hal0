## `hal0 doctor` — diagnostics and repair

Bare `hal0 doctor` (no subcommand) runs `installer/lib/preflight.sh`:
`--plain` (force ASCII, sets
`HAL0_PLAIN=1`), `--ports` (space-separated TCP port list override).

| Command | Flags |
|---|---|
| `doctor verify` | `--json` |
| `doctor logs` | `--unit` (default `hal0-api`; hal0 units only: `hal0.target`, `hal0-*`, `hindsight-api`, `hermes-gateway`, anything else is a 400), `--follow`/`-f`, `--lines`/`-n` (default `200`, 1-5000), `--level`, `--since` |
| `doctor toolbox-pull` | `--json`, `--manifest` (probes every `runners` pin in `manifest.json`: anonymous ghcr.io pull plus pinned-digest comparison; exit `1` when an image is unreachable or unpublished, `2` when the pin table is missing or malformed) |
| `doctor perms` | `--fix`, `--force`/`-f`, `--table-root` (audit old root-era table), `--json` |
| `doctor models` | `--fix`, `--force`/`-f`, `--json` |
| `doctor profiles` | `--json` |
| `doctor ports` | `--fix` (delete stale netavark DNAT rules found by the audit; privileged) |
| `doctor wrappers` | `--fix` (re-install `${LIB_DIR}/bin/hal0-*`, the matching `/etc/sudoers.d` drop-ins, and the `/usr/local/bin/hal0`(`-agent`) PATH links from the active tree; privileged; the PATH links are refreshed only when run from the installed venv, `/usr/lib/hal0/venv`) |
| `doctor all` | `--json` |
| `doctor bundle` | `--out`, `--no-rocm-smi`, `--include-logs` (default `auto`; `auto\|yes\|no`) |

`doctor all` rolls up every check into one report. All are read-only except
`memory_extraction_throughput`, which sends one bounded probe to the extraction slot (at most 512
prompt and 32 decode tokens, capped at 30 s) when the slot's metrics carry no reading. Each row has a stable id
(`Check.key`) used in `--json` output and cross-referenced elsewhere in the docs: `api`,
`dns`, `runners`, `capabilities`, `memory`, `openwebui`, `hermes`, `auth`, `models`,
`migrations`, `ui-dist`, `api-env-entries`, `ports`, `port_dnat`, `netns`, `box`, `hal0_target`, `secret-modes`,
`hardware_freshness`, `gtt_leak`, `seed_context_envelope`, `agent-uid`, `api-journal`, `stt-weights`, `seams`,
`mcp_mounts`, `hermes-api`, `hermes_mcp_auth`, `hermes_profiles_mcp`, `hermes_default_memory`, `hermes_brain_memory`, `hermes_generation`, `hermes_command_approvals`, `hermes_delegation_slot`, `hermes-gateway-unit`, `hermes_anchor_window`, `hermes_model_choice`,
`hal0_linger`, `hindsight_llm_auth`, `memory_engine_version`, `memory_engine_env`, `memory_embedder`, `memory_extraction_throughput`, `memory_retain_chunk`, `memory_decision_lane`, `memory_projects`.
`hal0_linger` reads whether systemd linger is on for the `hal0` user (`loginctl show-user hal0 -p
Linger`) and warns when that does not match whether the Hermes gateway is installed.

`api-env-entries` ("api.env entries") warns when `/etc/hal0/api.env` holds a name the Secrets API now refuses to write: a loader, interpreter, TLS, configuration or proxy variable (`LD_PRELOAD`, `PYTHONPATH`, `SSLKEYLOGFILE`, `OPENSSL_CONF`, `NODE_TLS_REJECT_UNAUTHORIZED`, `XDG_CONFIG_HOME`, `HTTP_PROXY` and the rest of the families listed under [Secrets](/docs/reference/api/rest-api/)), or a TLS trust variable (`SSL_CERT_FILE` and the others) whose value is not a root-owned path `hal0` cannot write. It names the keys, never the values, and words proxy variables apart, since a box behind a corporate proxy sets them as root on purpose. Remove an entry you did not add in Settings → Secrets, or delete the line as root, then restart `hal0-api`. Run as a user that cannot read the file, it warns and asks for `hal0` or root.

`gtt_leak` warns of unexplained GPU memory and never refuses a load.

`memory_embedder` ("Memory embedder") is advisory. The embedder is the pair of `[memory.models].embeddings_provider` and `embeddings_model`. hal0 records the pair a memory store was built with in `/var/lib/hal0/state/memory-embedder.json` and starts the engine on it, whatever `[memory.models]` says, because stored vectors are not re-embedded and a different embedder would degrade recall over them with no error. On a box with no record, hal0 takes the embedder from what the engine runs: the running engine's own environment, else what its unit files would start it on (every drop-in in systemd's order, then `/etc/hal0/hindsight-llm.env`), else `BAAI/bge-small-en-v1.5` with the `local` provider, the engine's default, when a store exists. The row has these outcomes:

- **pass** when the recorded and configured embedders match, naming the recorded one.
- **pass, with a note** when they differ only because `[memory.models]` is still at its defaults (`local`, `hindsight-ai/hs-embed-1`). That is every box upgraded with an existing store. The note says the store was built with the recorded model, stays on it, and that the configured model takes effect only through an embedder switch, which a later release adds.
- **warn** when you have set a provider or model of your own that differs from the recorded one. Both are named, and nothing is changed.
- **warn** when the record is marked mixed: the store existed before the engine was moved off its default embedder and may hold vectors from both.
- **warn** when the record and the engine disagree: the running engine, or the unit files it would start from, name a different embedder, for example a hand-written drop-in that sorts after hal0's. Both are named and hal0 changes neither; while the engine is running, hal0 keeps rendering the embedder it runs. The `memory_engine_env` row judges these two keys on the same evidence, so the two rows do not contradict each other.
- **warn** when the record file cannot be read or parsed. hal0 leaves the file as it is, names its path, and keeps the engine on what it runs for now.
- **warn** when the store's location is unavailable (a symlink that does not resolve, or an `/etc/fstab` mount point above it that is not mounted). Nothing is recorded until it is back.

hal0 does not ship a command that re-embeds a store yet. Setting `[memory.models]` to the recorded embedder clears a mismatch; a mixed store stays flagged.

`memory_decision_lane` ("Memory decision lane") is advisory. With `[memory.decision]` enabled it passes when the decision server answers `/health`, and warns when it does not, or when `provider = "local"` but the `hal0-hs-decide` unit is not installed. The installer does not lay that unit down yet, so on most boxes the memory engine runs without a decision model and sends decision-gated calls to its LLM lane; hal0 leaves the decision settings out of the engine's environment until the unit exists. Set `[memory.decision].provider = "off"` to silence the row. The hosted `hindsight-cloud` provider is not probed.

`memory_projects` ("Memory projects") is advisory and measures how memory is filed under projects (see [Memory projects](/docs/concepts/memory-projects)). It lists the `project:*` tags of the platform bank (`[memory] bank`) with their fact counts, through `GET /api/memory/banks/{bank}/tags`, with a 10 s budget per page of 500 tags. It reports three figures: how many of the project-tagged facts name a project that `[memory.projects]` knows (listed under `registered`, an alias, or the target of an alias), as a count and a percentage; the number of facts tagged `project:unresolved`; and the projects in use that the registry does not know, most-used first, up to ten by name. A fact that carries two `project:` tags is counted once for each. The row has these outcomes:

- **pass** with the figures in every case not listed below, including when no fact carries a project tag yet.
- **warn** when the `project:unresolved` count is not zero: a coding client is writing without naming its project.
- **warn** when more than five projects in use are missing from the registry. List the real ones under `registered`, map other spellings under `aliases`, and put names that are not projects in `deny`.
- **pass, with a note** when memory is off, the engine is unreachable, or the tags cannot be listed (a fresh box has no platform bank until the first write). Nothing is counted.

Run as a user that cannot read `hal0.toml`, the row counts against the `shared` bank and an empty registry, and says so.

`api-journal` ("API journal read") warns until `hal0-api.service` carries `SupplementaryGroups=systemd-journal`. `hal0 update` does not rewrite that unit, so the fix is to re-run the installer once; until then the Logs page and `hal0 slot logs --follow` report that the journal cannot be read.

The Hermes rows are advisory and never critical. `hermes-api` ("Hermes API upstreams") checks, for each served profile, that it has an API key, that its authenticated `/v1/models` answers 200, and that hal0 has registered the matching upstream. With no key it says to run `sudo hal0 agent reprovision hermes --repair`. With a missing upstream it says to restart `hal0-api` or `POST /api/agents/hermes/reconcile-upstreams`. When the operator turned the gateway off (`hermes-gateway.service` neither enabled nor running, so the API's `/health` is unreachable) the row warns instead of failing once per profile: it says the API path is not checked and names `sudo systemctl enable --now hermes-gateway`. An enabled gateway that does not answer still fails. `hermes_profiles_mcp` ("Hermes profile MCP wiring") warns when a named profile has no hal0-admin and hal0-memory entries, fails when an entry lacks a bearer on a box with auth on, and reports a profile that opted out with `hal0: {wire_mcp: false}`. `hermes_default_memory` and `hermes_brain_memory` check that the `X-hal0-Private` header on the default and `hal0-brain` profiles matches `hal0: {memory_private: ...}` (shared unless it is set; a value that is not a boolean is read as private unless it is false, no, 0 or off, and warned about); the default profile needs `sudo hal0 agent reprovision hermes --repair` after the opt-in is added by hand. `hermes_generation` ("Hermes pm generation") warns when Hermes's package manager has committed its own environment for the live release without the extras (such as `mcp`) hal0 built it with. `hermes_delegation_slot` ("Hermes delegation slot") passes for the default `agent` slot and warns when a `[hermes] delegation_slot` names a slot that is not ready. `hermes-gateway-unit` ("Hermes gateway unit") passes when no Hermes agent is installed. With Hermes installed it fails when `/etc/systemd/system/hermes-gateway.service` is missing, when a `gateway run --idle-exit` process is running (the row names its pid and cgroup), or when a profile with `gateway.standalone: true` lacks its own `hermes-gateway-<profile>.service`. It also fails when the gateway runs from Hermes's suffixed `hermes-gateway-<8 hex>.service` instead, which a 1.6.0 nightly fresh install got by running Hermes's generator as root (#2943), or when both units exist after an interrupted move; `sudo hal0 update` (or `sudo hal0 agent install hermes`) moves the gateway onto `hermes-gateway.service` and keeps its enabled and running state. From 1.6.0 the installer and `hal0 agent install hermes` write `hermes-gateway.service` from hal0's own template and never run Hermes code as root. A unit that is installed but disabled, stopped or masked passes: from Hermes v0.22.3 a profile-scoped dashboard chat and `hermes chat` are gateway clients, and an installed unit in any state is what stops them from starting a gateway of their own. See [Services](/docs/operate/services/#hermes-gateway-and-linger).

There is no standalone `hal0 doctor seams`
command — `seams` is one of these roll-up rows, surfaced by `hal0 doctor all`.

## `hal0 upstream` — manage upstream LLM providers

<Aside type="note">
"Upstream" here is the cloud/remote provider concept (`upstreams.toml`) — distinct from
the local inference `Provider` abstraction. See
[Providers, profiles & devices](/docs/reference/providers-profiles-devices/) for the
disambiguation.
</Aside>

| Command | Args | Flags |
|---|---|---|
| `upstream list` | — | `--json` |
| `upstream advertise <name> <state>` | `name`, `state` (`on\|off`) | — |
| `upstream show <name>` | `name` | `--json` |
| `upstream create <name>` | `name` | `--catalog`/`-c`, `--url`/`--base-url`, `--auth-style` (`bearer\|anthropic\|header\|none`), `--auth-header`, `--auth-env`, `--timeout`, `--api-key`/`-k`, `--advertise-models`/`--hide-models` (default advertise), `--enabled`/`--disabled` (default enabled) |
| `upstream update <name>` | `name` | partial update — `--url`/`--base-url`, `--auth-style` (`bearer\|anthropic\|header\|none`), `--auth-header`, `--auth-env`, `--timeout`, `--advertise-models`/`--hide-models`, `--enabled`/`--disabled`, `--model` (repeatable), `--include` (repeatable), `--exclude` (repeatable), `--clear-filters`. No `--catalog`/`--api-key` — use `upstream credentials set` to rotate the key. |
| `upstream delete <name>` | `name` | `--force`/`-f` |
| `upstream test <name>` | `name` | — |
| `upstream credentials set <name>` | `name` | `--key` (required, prompts securely if omitted), `--env-var` |

<Aside type="note">
`google_query` is a retired `--auth-style`. The valid values are `bearer`, `anthropic`,
`header`, and `none` — that's what the CLI's own `--help` lists. An existing upstream
config with `auth_style = "google_query"` still loads: it's coerced to `bearer` on read
(with a one-time retirement warning) rather than failing.
</Aside>

## `hal0 comfyui` — image models and files

| Command | Args | Flags |
|---|---|---|
| `comfyui models list` | — | `--json` |
| `comfyui models install <id>...` | one or more model ids | — |
| `comfyui models remove <id>` | `id` | `--include-shared` |
| `comfyui files` | — | — |

`models install` installs the models one at a time, following each download, and exits 1 if any fails. A failure does not stop the models after it. `models remove` keeps a weight file another installed model loads and lists it; `--include-shared` deletes it too.

|---|---|---|
| `agent install <name>` | `name` (e.g. `hermes`) | `--switch`, `--gateway`/`--no-gateway` (default gateway), `--reset-personas`, `--terminal-tool`/`--no-terminal-tool` (default: off on a fresh install, preserved on an existing box) |
| `agent uninstall <name>` | `name` | `--keep-memory`, `--force`/`-f` |
| `agent list` | — | `--json` |
| `agent peers` | — | — |
| `agent status [name]` | optional `name` (default `hermes`) | `--json` |
| `agent log [name]` | optional `name` (default `hermes`) | `--phase` |
| `agent dashboard-token [name]` | optional `name` (default `hermes`) | — |
| `agent reprovision [name]` | optional `name` (default `hermes`) | `--repair`, `--offline` (never builds; a needed build fails and names the step that needs the network), `--verbose`/`-v` |
| `agent command-approvals [mode]` | optional `mode` (`smart` or `manual`); omit to show the setting | `--json` |
| `agent approvals list` | — | — |
| `agent approvals approve <approval_id>` | `approval_id`; needs root, on the box | — |
| `agent approvals deny <approval_id>` | `approval_id`; needs root, on the box | — |
| `agent personas list` | — | — |
| `agent personas show <persona_id>` | `persona_id` | — |
| `agent personas activate <persona_id>` | `persona_id` | `--no-apply` |

`hal0 update component hermes` builds and activates a fresh Hermes release of the pin, or of `--target <sha>`, through the same release builder as install and `hal0 update`, and switches back to the previous release by itself if the new one fails its re-check. A `--target` commit persists across `hal0 update` until `--clear-override`.

hal0 pins Hermes v0.22.4 (`4d04303818b61bf3aa09278af48356315515965b`). `--target` is refused when the ref is older than the live release: once v0.22.4 is live, `--target d923a5eb487a17c0a68801bba9ef0f56c81040a8` (v0.22.2) fails with a `downgrade` error, because v0.22.3 and later write gateway runtime state into `state.db` that v0.22.2 cannot run over. The automatic flip-back after a failed activation is not a build and is unaffected.

`agent reprovision hermes --repair` forces every provisioning phase, builds a fresh Hermes release through the same builder as `hal0 update component hermes`, rewrites the persona seeds and `config.yaml`, then re-registers the Hermes profiles as `/v1` upstreams. Run `sudo hal0 agent reprovision hermes --repair` once on a box where Hermes was installed before 1.6.0 so the default profile gets its API key and appears in `/v1/models` and Open WebUI. The same run wires hal0-admin and hal0-memory into every named profile (phase `profile_mcp_wire`) and writes any missing profile API key (phase `profile_api_keys`).

`agent dashboard-token hermes` prints the token Hermes Desktop needs for a remote pairing in token mode. `hal0-agent@hermes` mints it once under `/var/lib/hal0/state/agents/hermes/` and exports it to the dashboard as `HERMES_DASHBOARD_SESSION_TOKEN` at every start, so the pairing survives restarts and `hal0 update`. Run it as root or as the `hal0` user. A `systemctl edit hal0-agent@hermes` drop-in that sets `HERMES_DASHBOARD_SESSION_TOKEN` wins over the file.

`agent uninstall hermes` also runs `loginctl disable-linger hal0` (as root; otherwise it prints the command), undoing the linger the Hermes gateway turned on.

If the daemon reports a partial uninstall, the command lists the residual paths and why removal failed, gives cleanup guidance, and exits with status 1. Review and remove those files with sufficient permissions, then re-run the uninstall.

`agent install hermes` respects an operator-disabled gateway. If `hermes-gateway.service` is `disabled`, the unit file is refreshed with `--no-start-now --no-start-on-login` and the unit is not enabled or started (a copy already running is left running). If it is `masked-runtime` it is treated the same way. If it is persistently `masked`, the generator does not run at all. Either way the command prints how to turn it back on (`systemctl enable --now hermes-gateway.service`, preceded by `systemctl unmask` or `unmask --runtime` for a mask). A fresh or enabled gateway is installed and enabled as before.

While the terminal tool is off (the default; `--no-terminal-tool` or `HAL0_HERMES_TERMINAL=0`), hal0 writes `terminal.backend: hal0-terminal-off` into the Hermes root `config.yaml` and into every profile it wires. Hermes rejects that backend in the terminal tool's own availability check, so `terminal` and `process_manage` leave every tool schema, including the one built for the gateway's preview-restart side agent, which ignores `agent.disabled_toolsets` from Hermes v0.22.3. Cloned profiles also lose `execute_code` and `delegate_task` while the terminal is off. A docker or ssh backend you chose is saved under `hal0.terminal_backend_saved` and restored when you turn the terminal back on. `hal0 update` applies the gate to an existing box and restarts Hermes when `terminal.backend` changed. Hermes logs `Unknown TERMINAL_ENV 'hal0-terminal-off'` at ERROR about every 30 seconds while tools are listed; on a terminal-off box that line is expected.
