## Shared context (same in both handoff docs)

Two related but independently-shippable pieces of work came out of a single design session (operator: thinMint, on `hal0.thinmint.dev` / LXC105, `10.0.1.142`):

1. **Slot edit drawer cleanup** (sibling doc) — a UI polish + wiring pass on the existing slot create/edit flow: field layout, a stale/misleading default-slot picker, an activity-log spam bug, and splitting `device` (create-time only) from the runner binary/image fields (edit-time).
2. **Runner Image catalogue** (this doc) — a new "Runner Images" subpage under Models, backed by a sync job that discovers container images the operator publishes to `ghcr.io/Hal0ai/hal0-runner-images` and displays them with a Model-Card-style detail view, a download job, and (once downloaded) makes them selectable from the slot edit drawer's Runner Image field.

**Why split into two branches**: the drawer cleanup is same-day UI/wiring work with low risk. The catalogue is a multi-day net-new feature with its own architecture (sync mechanism, job system, card schema) that would otherwise block the drawer fixes on unrelated design decisions. They're sequenced so the sibling branch ships a Runner Binary dropdown sourced from the existing static `RUNNER_IMAGES` registry (`src/hal0/runners/__init__.py`) as a stop-gap — this branch's job is to build the real catalogue that eventually backs the Runner **Image** dropdown (not the Binary dropdown, which stays sourced from `RUNNER_IMAGES`).

**Motivation** (operator's words, condensed): hal0 aims to ship the latest runner builds (new model tech/features — MTP, TurboQuant, etc.) quickly. The operator builds and publishes these images themselves; there needs to be a dashboard page to browse them, see what each one supports, and pull one down without SSHing in and running `docker pull` by hand.

## Branch 2 scope: `feat/runner-image-catalogue`

### Key architecture decisions (already made — do not relitigate, ask thinMint only if reality on disk contradicts these)

1. **Discovery mechanism: scheduled poll + manual "sync now" button.** Not a GitHub webhook (would need a public-reachable receiver endpoint — real infra work for marginal latency gain over a 15-30min poll) and not manual-only registration (contradicts "automatically shown in the list"). Mirrors the existing `pull_jobs.py` registry-pull pattern already in this codebase.

2. **No new credentials needed for discovery.** This repo already has anonymous-GHCR-token helpers: `_ghcr_anon_token()` and `_ghcr_manifest_digest()` in `src/hal0/cli/doctor_commands.py` (used today by the updater, `src/hal0/cli/update_commands.py`, to resolve the Open WebUI image digest). As long as `ghcr.io/Hal0ai/hal0-runner-images` packages stay public (matching the existing `ghcr.io/hal0ai/hal0-rocmfpx` images referenced elsewhere in this codebase), the same anonymous-token flow works against the Docker Registry v2 `tags/list` endpoint for package/tag discovery. **Verify this assumption early** — if the operator ends up publishing privately, this whole discovery path needs a real GitHub PAT, which is a Tier-3 credential decision requiring explicit operator sign-off (see workspace CLAUDE.md "Hard boundaries") before adding.

3. **Card metadata source: GitHub repo content, not the image itself.** Rather than pulling every image or attaching OCI referrer artifacts (both considered and rejected as overengineered for a first pass), the operator will maintain a folder per image in the `Hal0ai/hal0-runner-images` **source repo** (the git repo backing the GHCR packages, not the packages themselves):
   - Convention: `runners/<package-name>/card.json` — folder name matches the GHCR package name exactly (e.g. `runners/hal0-rocmfpx/card.json`).
   - Fetched via `raw.githubusercontent.com/Hal0ai/hal0-runner-images/main/runners/<package-name>/card.json` — anonymous, CDN-backed, no auth, no rate-limit concern for a repo this size.
   - `card.json` holds **structured fields** the UI renders directly — no markdown parsing needed: `title`, `description`, `features: []` (inline tags like `MTP`, `TurboQuant`), `supported_models: []`, `cherry_picked_commits: []`. A sibling `README.md` in the same folder may hold longer prose, rendered as a secondary section on the card if present — but `card.json` is the source of truth for anything the list/tag UI needs.
   - **This means card metadata is decoupled from package publishing** — the operator can update a card without re-pushing an image, and vice versa. Handle the case where a package exists in GHCR with no matching `card.json` folder gracefully (show the card with just tag/digest/size, no features/description) — don't fail the whole sync over one missing file.

4. **Download UX: a real background job, mirroring `pull_jobs.py`.** Not fire-and-forget-with-polling. New job type parallel to the existing model-pull pattern (`src/hal0/registry/pull_jobs.py`, `src/hal0/registry/pull.py`) — persisted job state, SSE progress stream, cancel support. Frontend mirrors `usePullJob()` / `DownloadRow` / `DownloadsPane` in `ui/src/dash/models.jsx` and the `modelPull*` endpoints in `ui/src/api/endpoints.ts` (`/api/models/{id}/pull`, `/pull/status`, `/pull/stream`, `/pull/cancel`) — build the equivalent surface for runner images (e.g. `/api/runner-images/{id}/pull...`) rather than inventing a different progress-UX pattern. This gives operators the same download experience they already know from the Models page.

5. **Once downloaded, an image becomes available in the slot edit drawer's Runner Image field** (owned by the sibling branch, `fix/slot-edit-drawer-cleanup`) — that's the integration point between the two branches. Design this branch's data shape (an endpoint returning "locally-downloaded runner images") with that consumer in mind; coordinate the exact shape with whoever's picking up the sibling branch if both are in flight simultaneously (check for a Superset task/PR on `fix/slot-edit-drawer-cleanup` before diverging).

### Concrete implementation shape

**Backend**

- New page/domain: "Runner Images", a subpage of the existing Models feature (not top-level nav) — mirror `src/hal0/registry/` (model registry) and `src/hal0/registry/pull.py` / `pull_jobs.py` for the sync + download job patterns. Where the model registry uses `src/hal0/registry/model.py` (`Model` class) and `src/hal0/registry/store.py` (`TomlModelRegistry` / `SqliteModelRegistry`), design an equivalent lightweight store for runner-image rows (package name, tag, digest, card fields, local-download state) — check whether SQLite (`src/hal0/db/connection.py`) or TOML is the better fit by looking at which one the model registry actually uses today (both `TomlModelRegistry` and `SqliteModelRegistry` exist — confirm which is current/primary before picking a pattern to copy).
- Sync job: two independent fetches merged by package name —
  1. GHCR anonymous discovery (`_ghcr_anon_token` + Docker Registry v2 `tags/list`) against `ghcr.io/Hal0ai/hal0-runner-images` — gives package names, tags, digests.
  2. `card.json` fetch from `raw.githubusercontent.com` per discovered package name — gives display metadata. Missing file = degrade gracefully (point 3 above).
- Download job: new job type, `src/hal0/registry/pull.py`-shaped (or a sibling module if runner-image pulls diverge meaningfully from model pulls — e.g. these are `podman`/`docker pull` of OCI images, not HuggingFace file downloads, so the actual pull mechanics will differ even if the job/progress/SSE *shape* is copied). Reuse `SlotManager`'s or the provider layer's existing container-pull code if any already exists (check `src/hal0/providers/container.py`, referenced via `_resolve_image_ref()` in the graph) rather than writing a third way to pull an image.
- API surface: new routes under `src/hal0/api/routes/` (look at `models.py` in that directory for the pattern to mirror) — list runner images, get one (card detail), trigger sync, trigger download, stream download progress, cancel download.

**Frontend**

- New page component mirroring `ui/src/dash/models.jsx`'s shape: `ModelsView` → `RunnerImagesView`; `ModelRow` → `RunnerImageRow` (title, container URL beneath it, inline feature tags, download icon on the far right); `ModelDetail` → `RunnerCard` (Model-Card-style detail view rendering `card.json`'s fields: features, supported models, cherry-picked commits, etc., in place of the model card's own fields); `DownloadRow` / `DownloadsPane` → the equivalent for runner-image downloads, reusing `usePullJob()`'s shape from `ui/src/api/hooks/useModels.ts` (SSE event handling, `bytes_downloaded`/`progress`/`completed`/`failed`/`cancelled` states) against the new runner-image pull endpoints.
- New hook file, e.g. `ui/src/api/hooks/useRunnerImages.ts`, mirroring `useModels.ts`.
- New endpoint constants in `ui/src/api/endpoints.ts` alongside the existing `modelPull*` block.
- Inline feature tags: reuse whatever tag/pill component the Models page already uses for model capability tags (search `models.jsx` / `model-drawer.jsx` for how modality/capability tags render — `modalityLabel()` in `model-drawer.jsx` is a relevant reference point) rather than building a new tag component.

### Things to verify with the operator before or during implementation

- Confirm `Hal0ai/hal0-runner-images` package visibility (public vs private) before writing the discovery code — changes whether anon GHCR tokens work at all (decision 2 above).
- Confirm whether the `Hal0ai/hal0-runner-images` **git repo** (source of `card.json` files) is the same repo the Packages are attached to, or a separate repo — the design session assumed the same org/repo but this wasn't explicitly pinned down.
- The exact SQLite-vs-TOML storage choice for the new runner-image rows (see "Backend" above) — pick the pattern the model registry actually uses today; don't introduce a third storage convention into this codebase without a reason.
