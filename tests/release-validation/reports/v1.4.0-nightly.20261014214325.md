## Verdict

**Do not ship 1.4.0-nightly.20261014214325.** On any box whose `/var/lib/hal0/backups` was created by an earlier root-run tool, an in-place upgrade silently fails the runner-system and profile-centric conversions. `hal0 update` still records the update as `applied`, leaves the `agent` slot in `error` and `hal0/agent` returning 404, and tells the operator to restart to retry, which cannot work.

Fresh installs are in the best shape any release has reached: there is no fresh-install GA-blocker, all three rc.7 blockers are fixed, and 50 of 58 register entries are fixed. The upgrade path is what broke, and the next tools an operator would reach for all mislead on exactly that broken box:
- rollback dies on a 10 s timeout;
- drift detection reports nothing to restart;
- the component table offers no command to run.

The specific blockers:

**GA-blocker: `upgrade-migration-backups-eacces`** (regression `runner-system-conversion` is **regressed**).
- **Setup.** On ct150, `/var/lib/hal0/backups` is `root:hal0 2755`, with no group write. A root-run tool such as the v1.0 profile-catalog reset or `hal0 slot migrate-id-keying` created it under umask 022. hal0-api runs as `User=hal0`.
- **Failure.** Both post-swap migrations fail at their backup step with `[Errno 13] Permission denied: '/var/lib/hal0/backups/runners-<ts>.tar.gz'` (and `profiles-<ts>.tar.gz` for the profile migration), each reporting "nothing was changed".
- **Reported as success.** Update job `3ead21a27b2a` is recorded `status: applied` with `post_activation_migrations.ok=false`. Its "Migration incomplete" panel says to restart hal0-api to retry, but the boot retry hit the same EACCES at both activations (18:01:12 and 18:04:35).
- **Resulting state:**
  - No `runners-*.tar.gz` exists, and `hal0 runner-images migrate` still plans the conversion.
  - `agent.toml` keeps `profile="chadrock-dense"` and `binary="promptforge"`.
  - `GET /api/slots/agent` → `error "profile 'chadrock-dense' is invalid as stored and was set aside"`.
  - `POST /v1/chat/completions` with model `hal0/agent` → 404.
  - All three user profiles are quarantined at load.
- **Cause.** `runner_system._backups_dir()` (`src/hal0/config/migrations/runner_system.py:812-830`, also used at `profile_centric_apply.py:599`) has left an existing directory's mode alone since #2558 (`9f6c871a`). It assumes the directory is 2775, but no code ever makes it 2775. `install/perms.py` has no `backups` row, so `doctor perms` neither reports nor fixes it.
- **Workarounds the product never mentions:** `chmod g+w /var/lib/hal0/backups` and then restart, or run both `migrate --apply` commands as root. The profile-blocker hint suggests `sudo -u hal0 … --apply`, which hits the same EACCES.
- **Who is exposed.**
  - Fresh installs are not: ct151 has no such directory, and hal0-api creates it hal0-owned.
  - Prod is not: its directory is 2775, almost certainly set by hand.
  - Long-lived boxes upgraded from before 1.0 are, and those are exactly the boxes carrying the old runner shapes this conversion exists to remove.

Five majors are on the gate. Four of them make the blocker worse or hide it; the fifth is a regression that has failed for four releases running.

**Major: `update-rollback-cli-timeout`** (#2027 **regressed through a new mechanism**).
- **Cause.** `hal0 update --rollback --yes` POSTs with `api_post`'s default 10 s timeout (`update_commands.py:704`; default at `_shared.py:268`). The rollback route reinstalls the prior tree with pip synchronously, which took 13 s even on a 32-core box.
- **What the operator sees.** The CLI prints `did not respond within 10s` and exits 1, while the server finishes the rollback and flips `hal0.previous`. The #2230 renderer never runs, so the operator never sees the reverted-to version, `previous_now`, `schema_warning` or the restart panel.
- **Proof.** A stub server returning the real response shape renders correctly at 5 s and fails at 13 s.
- **Why it is worse than #2027.** An operator who trusts the error and runs `--rollback` again reinstalls the version they were trying to leave. It is on the gate because rollback is the documented way out of the blocker above.

**Major: `slot-drift-blind-when-render-fails`.**
- **Cause.** When `container_spec` raises for a running slot, `expected_argv` swallows the exception and returns `None` (`providers/container.py:2280-2284`). `compute_config_drift` then returns at `drift.py:199-200`, before the #2024 image block runs.
- **Seen on ct150.** Brain runs `hal0-combined:0826` instead of `hal0-runner-standard:b11596`. `/api/slots/brain` says `image_mismatch=true`, yet `GET /api/updates/slot-drift` returns `{"count":0}` and the update summary prints "no slots need restart".
- **Link to the blocker.** The render failure itself is a downstream effect of the blocker.
- **Fix caveat.** Do not just emit the image diff. With `auto_restart_image_drift = true` (as on ct150), that would bounce a slot that cannot re-render and take the brain down. Surface a `render_error` drift state and exclude it from auto-restart.

**Major: `brain-steward-fabrication-shipped-model-unverified`** (#2022 **partial**, fourth release).
- **What now works.** On the shipped `hal0-brain-sft-q8-rocmfpx` (ct150), the original repro no longer fabricates, 3/3. The `_asks_for_live_state` guard fires and logs `hal0.brain_chat.ungrounded_round_rerouted`.
- **Why it is still partial.** The guard is a keyword regex:
  - `_CONCEPTUAL_RE` (`chat.py:1420`) treats every "why is/are/do/does…" question as conceptual.
  - `_LIVE_STATE_SUBJECT_RE` (`chat.py:1395`) has no word for services, health, hindsight or memory.
- **Bypass results on the shipped 1.1 B model:**
  - *"Why is the agent slot offline? Answer in one short sentence."* → two different invented causes in 2/2 runs, with zero tool frames. The real cause is the set-aside `chadrock-dense` profile.
  - *"Is the hindsight memory service healthy? Answer in one short sentence."* → "Yes … healthy", with zero tool frames.
- Without the brevity clause, the model calls tools for both questions.

**Major: `brain-steward-false-memory-claims`.**
- **The gap.** The dashboard steward has **no way to read or write memory**. `chat.py:600` drops every `memory_*` tool by prefix, and nothing else in brain chat calls Hindsight, so `private:hermes__hal0-brain` is never written or read.
- **What promises otherwise.** `docs/concepts/brain.mdx:174-176,204-208` describe a private bank, and the seeded persona auto-approves `memory_search`, `memory_list` and `memory_add`.
- **Observed.** "Remember that my cat is called Zorbo." → *"I've noted that your cat is named **Zorbo**."* with zero tool frames and nothing stored.
- **Scope.** Every install has this gap; only the wording depends on the model. On ct150's shipped model the same prompt instead chose `profile_delete`, which was gated and denied.

**Major: `hermes-wrong-answer-after-slot-list`** (what is left of #2021, which is itself fixed).
- **Cause.** hermes 0.19.0 cuts any tool result longer than its context-scaled budget (39,321 chars at 65,536 ctx) to a 1,500-char preview whenever no sandbox environment exists. That covers every `hermes -z` and CLI turn. hal0's MCP `slot_list` result is about 2.9 KB per slot as hermes sees it.
- **Effect.** At roughly 14 or more slots, the model sees half of the first slot and answers *"1 slot … 0 loaded"*. The failing session's result was 48,652 chars; at 11 slots (31,858 chars) the answer was correct.
- **Why gating is conditional.** The failure is deterministic, but a default fresh install has 11 slots and stays under the cap. It goes on the gate only if a read-only check on ct105 shows more than 13 slots; otherwise it is next-minor.

Everything else is major or lower and would not hold GA on its own. That includes `capabilities-npu-apply-accepted-dead`: the dashboard refuses an unadvertised `npu` backend loudly, and only the API and CLI accept it.

1. **`memory-retain-zero-yield-silent`: refuted.** The claim was that "no hal0 surface reports it". The op record every poller reads does report it:
   - The single-op GET returned by `POST /api/memory/add` carries `facts_extracted:0, document_fact_count:0, nothing_learned:true` and the notice *"completed, but nothing was learned …"*.
   - MCP `memory_operation_get` uses the same `annotate_retain_yield` path.
   - The dashboard shows a toast (the bundle contains "nothing was learned").

   The reporter read `ops list`, the one view `108b366d` deliberately leaves unannotated, because annotating list rows would cost a document fetch per completed row on every poll. The "Output too long … dropping this sub-chunk" path is Hindsight hitting hal0's deliberate 4096-token retain cap (#1834) when the extractor runs away. That is yield variance, covered by `memory-extraction-quality-is-anchor-dependent`.
   - **Proposed entry:** `memory-retain-zero-yield-visible-on-op-record-only`.
   - **Report only if:**
     - the single-op GET or MCP lacks `nothing_learned` for a zero-unit retain;
     - the toast is missing;
     - the raw document is also absent;
     - or a future CLI retain or `ops get` verb hides it.
2. **`brain-tool-budget-exhaustion-empty-reply`: by-design.**
   - **What the cap is:** `max_rounds` is a backstop against runaway tool loops. When it is hit, the turn always ends with a typed `error` frame and then `done` (`toolloop/engine.py:545-639`). The test `test_loop_budget_terminates_with_typed_error` pins this.
   - **Nothing is lost:** the streamed `tool_result` frames stay in the thread as tool cards (`useBoard.ts:1385`).
   - **Unreachable at the default of 8:** on ct151 the turn made 11 calls in one parallel round, and on ct150 round 2 degrades on the parked agent.
   - **Proposed entry:** `brain-tool-budget-exhaustion-typed-error`. Also amend `brain-chat-sse-silent-until-first-frame` to "no token frame AND no error frame", so the typed budget error no longer matches it literally.
3. **`v1-chat-bad-json-404-agent`: by-design.**
   - **Documented parsing:** `_read_json_body` (`v1.py:264-298`) documents "Empty / malformed bodies become `{}` … validation belongs to the upstream", unchanged since `517d47c3`.
   - **Routing:** `{}` takes ADR-0023 rule 9 to the `agent` anchor. On a model-less box that case is already covered by `model-default-marker-is-per-type-fallback`.
   - **The contrasting 400:** the 400 returned for a body with a model but no messages is llama-server's own envelope.
   - **Client impact:** the client still gets a loud 4xx, and the maintainer closed the same class (#1840 items 7 and 8) as cosmetic.
   - **Report only if:**
     - a malformed body yields a 2xx, a cold load or a completion;
     - or a body that carries `model` is reported as no_route for `agent`.
4. **`memory-add-bank-id-ignored`: by-design.**
   - `/api/memory/add` parses its body by hand, which is the house convention per `brain-chat-hand-parsed-body`. It ignores any unknown key; a misspelling such as `datset` behaves the same way.
   - The documented key is `dataset`. `bank_id` exists only as a path segment on the engine-admin router.
   - Under ADR 0005 the only write namespace a body can select is `shared`, so an ignored key cannot misroute a write.
   - **Report only if:**
     - a doc, client or tool sends `bank_id` in a body;
     - or the set of write namespaces grows beyond `shared` plus the header-gated private one.
5. **`podman-healthcheck-transient-failed-units`: by-design, upstream.**

The slots lane's port, failed-unit and capacity results from that window are unreliable. The rc.7 rule of one agent per stateful lane per box held for the lanes but not for the probes.
- **A validation agent again created `/root/.hermes`** at 22:00:11 by running the venv hermes binary as root, the exact behaviour rc.7 proposed banning. It cost the cli, hermes-e2e and doctor-perms probe agents time to work out where it came from.
- **The idle reaper repeatedly took brain, embed and rerank offline**, so lanes reloaded them; this is expected and not filed. The memory lane's two deliberate hal0-api restarts caused two retries of its own making.
- **Timings are not product timings.** ct151 has 8 cores and 16 GB and ran at a load average around 17 under concurrent agents.
- **ct150 runs on UTC−4.** One probe lost minutes to an absolute UTC `--since`.

**What the fleet cannot test at all**

- **No box is both a fresh install and has `/dev/kfd` visible.**
  - ct151 and ct163 are fresh installs but have no kfd.
  - ct150 and ct105 have `/dev/kfd`, but one is the update box and the other is production.
  - So "does a fresh install on bare-metal AMD with amdkfd work?" is **unanswerable by this fleet**. That is the configuration where the ROCm lane is the default, and where `ui-overview-no-gpu-on-vulkan-box` would **not** fire.
  - Every ROCm-lane statement in this report comes from an upgraded box or from production.
- **The shipped fresh-install model and the shipped brain-sft model now live on different boxes.** A fresh install seeds `lfm2.5-2.6b`. The 1.1 B `hal0-brain-sft` that drove #2020 and #2022 exists only on the upgraded ct150, so regressions tied to the small anchor model can only be probed on an upgrade box.
- **A CPU-only fresh install with lanes is not exercised.** ct163 qualifies but ran preflight only.
- **Configurations no box has:**
  - an unprivileged LXC with `/dev/kfd` (#1953);
  - non-AMD hardware (the NVIDIA and Intel paths in `probe.py`'s Vulkan fallback are inferred from source);
  - an FLM image anywhere but prod, so the NPU apply happy path is untested;
  - Python 3.13;
  - more than about 13 slots. The hermes truncation cliff was shown by reproducing the mechanism, not on a natural configuration.
- **Telegram, Discord and the other hermes gateway platforms:** none configured, not exercised.
