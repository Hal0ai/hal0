## Verdict

**Do not ship 1.0.0-rc.7 as GA — hal0's own `/v1` gateway injects a chat-template kwarg that hard-400s every structured-output request against the only model a fresh install ships, which takes all memory retention down with it; hermes ships with no MCP client at all so it has zero hal0 tools on every rc.7-installed box; and the brain steward confidently fabricates live platform state on the seeded anchor.** rc.7 is nonetheless a materially better release than rc.6 — the rc.6 GA-blocker is genuinely dead, the Vulkan lane serves coherent text on the exact hardware class that broke it, and 30 of 47 register entries came back fixed.

The specific blockers:

* **GA-blocker — `hindsight-extraction-samplers-400`.** `hal0/api/routes/v1.py::_normalize_chat_body` → `hal0/normalize/thinking.py::apply_thinking_policy` unconditionally injects `chat_template_kwargs: {"enable_thinking": false}` into every chat body that does not already carry the kwarg. The installer-seeded model's template (`hal0-brain-sft.jinja:172-176`) emits a `<think>\n\n</think>` block on that branch, and combined with a `response_format: {"type":"json_object"}` grammar, llama-server b109-0a59add in `hal0-combined:0822` throws in sampler init. Decisive A/B on identical bodies: through hal0-api `:8080/v1/chat/completions` → **HTTP 400 `Failed to initialize samplers: std::exception`**; the byte-identical body direct to the slot's own `:8090` → **200**. Isolated further direct-to-slot: `json_object` + `enable_thinking=false` → 400, `enable_thinking=true` → 200, kwarg absent → 200. Because `HINDSIGHT_API_LLM_BASE_URL=http://127.0.0.1:8080/v1`, **every** `retain_extract_facts` call 400s — 28+ failed ops and climbing on a fresh box. Blast radius is wider than memory: any OpenAI-compatible client asking hal0 for JSON mode gets a hard 400 whenever the serving model has a Qwen3-family template, and the seeded brain-sft is the only template a fresh install has. Backend-independent (sampler-chain construction is host-side); **refuted** as a profile-flags issue (switching `utility` to the `dense` profile changed nothing) and **refuted** as model garbage (coherence canary passed). Prod does **not** reproduce — its `utility` serves `chadrock-35b-ace-saber-rocmfp4-mtp`, whose template has no such branch, which is exactly why this escaped every prior RC. There is no CLI escape hatch for a fresh-install user. Fix site is `normalize/thinking.py`, not hindsight.
* **GA-blocker — `hermes-fabricates-live-slot-count`, root cause: hermes has no MCP client.** `installer/agents/hermes/requirements.txt` installs `hermes-agent[web]`, but upstream gates its MCP client behind the `mcp` extra (`Requires-Dist: mcp==1.26.0; extra == "mcp"`), which hal0 never requests. `/var/lib/hal0/venvs/hermes/bin/python -c "import mcp"` → `ModuleNotFoundError`. Both MCP servers hal0 itself provisions into hermes' `config.yaml` are dead: `hermes mcp test hal0-admin` → *"requires HTTP transport but mcp.client.streamable_http is not available"*; `hal0-memory` → 40 s timeout. A logging proxy captured 91 outbound `/v1/chat/completions` bodies, every one identical, `tools=[...16 native tools...]` with **zero hal0-admin tools**. Meanwhile `hermes tools list` prints *"hal0-admin — all tools enabled"*, `hermes mcp list` prints ✓ for both, and `provision.json` reports `mcp_wire.status: ok, mcp_server_count: 2` — and its `admin_tools_list` smoke passes because it probes the **server**, never the hermes client. Net: hermes' prelude tells the model it has hal0 tools, the model gets none, and every live-state question is answered from STATE.md with a confabulation (`journalctl -u hal0-api | grep -c "client_id=hermes"` → **0**, vs 19 for `client_id=hal0-brain`). Reproduced on ct151, ct163 **and ct150** — this is not fresh-install-only; an upgrade that rebuilds the hermes venv loses MCP too. Only prod escapes, on `mcp 1.27.0` left over from a pre-rc.7 venv. One-line fix: `hermes-agent[web,mcp]`, plus a provisioning assertion that `mcp_wire` actually connects.
* **GA-blocker — `brain-steward-fabricates-live-platform-state`.** With the shipped seeded model serving and its canary passing, `POST /api/brain/chat` answers live-state questions with invented numbers and **zero tool frames**. `"What port is the brain slot running on? Answer in one short sentence."` → *"port 8085"* on one run and *"port 8080"* on a repeat (ground truth 8089), no `tool_call`, no `notice`, no error. Dropping the brevity clause flips it: 2/2 runs emit `tool_call: list_slots` and answer **8089** correctly. Wrong-tool selection reproduces without any brevity hint: *"How many models are registered?"* → calls `model_catalogue` (the pullable HuggingFace catalog) → *"**39 models** registered"*; ground truth 6. *"Which port is the brain slot bound to?"* → calls `get_board` → *"not currently active on the board."* This fires the `still_report_if` of by-design entry `brain-tool-model-points-at-modelless-slot` verbatim and fails the `expect` of #1789 (*"Confident invented … with zero tool frames is the regression"*). Mechanism datum: **170 tool schemas** (23 local + 147 admin) are surfaced in one shot to a ~1.1 B model, and `_tool_routing_llm._routed` only reroutes to `tool_model` when a **mangled** tool attempt is detected — a confident plain-prose fabrication produces no artefact, so the reroute never fires and no grounding guard exists on that path. Prod (larger `lfm2-5-2-6b-q8-0` brain) answers the identical probe correctly via `slot_config`, so the exposed population is exactly the fresh-install user the seeded 1.1 B anchor targets — i.e. the default first-run experience.

Two majors are close to the line and are on the gate for the same reason the rc.6 output-sanity gate was:

* **Major — `seeded-anchor-slots-rocm-on-kfd-less-box`.** `install.sh`'s seed loop copies `installer/etc-hal0/slots/*.toml` verbatim, so **all eight** llama.cpp lifecycle slots land at `device = "gpu-rocm"` on any host regardless of hardware. The hardware-aware ladder that exists for exactly this (`profile_derive.derive_device`, whose own comment says deriving gpu-rocm without kfd *"would hand every seeded slot a load-time refusal"*) never runs, because the seed loop precedes the scaffold pass and the scaffold skips slots that already have a config. On a kfd-less box every one of them hard-refuses at load, and because the installer binds the brain model to `brain` (`autoload: true`), the primary chat anchor is in `state=error` from t=0 — contradicting the same install run's own preflight line *"OK gpu: no /dev/kfd — LLM slots will use the Vulkan lane"* and the seed file's own comment *"On a box without it this slot derives gpu-vulkan instead."* Confirmed on ct163 (all 8 at gpu-rocm, zero GPU devices) and reconstructed from ct151's install-window journal. **Fresh-install-only** — the updater's `relabel_stale_vulkan_slots` keeps upgraded boxes on their loadable gpu-vulkan seeds.
* **Major — `slot-drift-ignores-image-and-device`.** `slots/drift.py::_CONFIG_DRIFT_KEYS` = `('--ctx-size','--model','--alias','--port','-b','-ub')` — it compares only the container **command**. Neither the runner image nor device passthrough is in the comparison, and both consumers go blind: (1) `hal0 slot edit <s> --hardware cpu|vulkan|rocm` then `hal0 slot load <s>` on a ready slot prints `Loaded → state=ready` while `_should_converge` returns False, so the quadlet is never re-rendered — a "cpu" slot keeps live `AddDevice=/dev/dri/renderD128` + `--group-add 991` while `declared_backend` reports the new device (reproduced both directions; control on a **tracked** key does converge); (2) on ct150 after the rc.7 upgrade the on-disk units correctly read `Image=…hal0-combined:0822` while podman still runs the retired `…hal0-rocmfpx:ade07ba`, and `GET /api/updates/slot-drift` returns `{"count":0}` — so the post-update banner never appears and `hal0 update --restart-slots` is a guaranteed no-op on image-only drift.

Everything else is major-and-below and would not, on its own, hold GA.
