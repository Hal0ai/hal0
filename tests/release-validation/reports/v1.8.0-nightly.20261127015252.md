## Verdict

**Do not ship v1.8.1 from this nightly (`d649d5dbf`): one blocker.** The #1792 self-healing retry for dead-lettered memory retains is silently dead on the newly pinned hindsight-api 1.2.3. Failed retains stay failed until an operator runs `hal0 memory ops retry` by hand, while `memory_write_health` reads `degraded:false, reason:"ok"` over 208 failed ops on ct150. The fix is XS. Everything else this run found is either a known open issue that did not get worse, by design, or a minor.

**Blocker:**
1. **`update-restart-fails-inflight-retains` → #1792 auto-retry dead against hindsight-api 1.2.3** (new, major, proposed **P0** as a regression of a closed fix, fix size XS).
   - `HindsightProvider.maybe_auto_retry_dead_letters` (`src/hal0/memory/hindsight_provider.py:1365`) sends `GET /v1/default/banks/{bank}/operations?status=failed&limit=200` (`_AUTO_RETRY_MAX_OPS = 200`, `:627`, used at `:1410`).
   - hindsight-api 1.2.3 caps `limit` at 100: `limit=100` → 200 with 100 ops; `limit=200` → **422** `{"type":"less_than_equal","loc":["query","limit"],"msg":"Input should be less than or equal to 100"}`.
   - The provider catches the `HTTPStatusError`, logs `hal0.memory.auto_retry_list_failed` at **debug**, and returns `None` (`:1407-1414`). Each `/api/status` poll still spends one of the 5 sweeps (`_AUTO_RETRY_MAX_SWEEPS`, `:624`), so the sweep is dead for the life of every hal0-api process.
   - The provider's own comment near `:600` already notes the engine's `le=100` cap. The tests in `tests/memory/test_memory_write_degraded.py` mock the client, so they cannot catch it.
   - **Introduced by this candidate:** the pin was 1.2.0 on the last validated nightly and on the v1.8.0 tag (`installer/install.sh:4003`); it is 1.2.3 here.
   - **Live on ct150:** 7 retain + 7 batch_retain rows failed with `APIConnectionError` during the update window (hal0-api restarted 10 times between 21:09 and 21:17 EST, from the update plus the lanes), `retry_count=2` (ladder exhausted). They are still `failed`, `journalctl -u hal0-api | grep auto_retry` is empty since 2026-11-01, and `memory_write_health` reports `failed: 208` with `reason: "ok"`.
   - **Why it blocks:** it is silent wrongness in a shipped fix, introduced by this release's own engine bump. Every box gets it, whatever the hardware. The worst case is the one #1792 exists for: retains that dead-letter before a chat model is available never recover on their own.
   - **Not claimed:** that one routine update restart exhausts the retry ladder (`WORKER_MAX_RETRIES=2`, 120 s backoff, ~4 min). ct150 hit it because of repeated restarts. A single 20–40 s restart costs one attempt.
   - **Fix:** set `_AUTO_RETRY_MAX_OPS` ≤ 100 (or page through), and log the list failure at warning.

**Release-note items (known, not blockers):**
- **First-provision Hermes smoke ends `warn` on a fresh install** (#2671, open). The Agents card reads `degraded: provision_warn` until the next reprovision.
- **Memory work serialises with chat on a fresh install** (`--parallel 1` brain, ADR-0053 / #2734). This run Hermes turns took 83–155 s and an 8-token chat took up to 92.7 s behind Hindsight. Workaround: bind a model to the memory slot or the agent slot.
- **`.stale-*` trees on upgraded boxes are reaped on the next update, not this one.** #3931 ships here, but extraction runs the from-version's reaper (by design, see refutation 11).
- `embed`/`rerank`/`tts` `type="llm"` residue on upgraded boxes needs `hal0 doctor profiles --fix` (#2693/#2710).
- On a Proxmox host that shares one NPU across containers, the NPU "util" figure shows the whole device's runtime-PM residency (refutation 1).

   - **Claim:** `/api/stats/hardware npu_util = 1.0` and "100% NPU DUTY" beside "Nothing holds the NPU" on an idle ct151.
   - **Why it died:** the number is right; the NPU is not idle. The runtime-PM counters belong to the one physical device the host passes into every container. ct105 and ct151 showed identical counters at the same moment (suspended time 17854 ms on both), and on ct105 an `flm` process holds `/dev/accel/accel0` with two FLM models loaded.
