## Verdict

**Do not ship `1.4.0-nightly.20261015021622` as is.** Ship the next nightly that contains `f6cc2218` and `a9328ebe` (`20261015032919` or later), once it passes the targeted gate below. This build has **no GA-blocker**, and the upgrade path is no longer broken. Four things keep it from shipping:

1. **`brain-steward-false-memory-claims` (#2658, major): the fix is not in this build.**
   - **What happens:** every install still answers "Remember X" with *"I've noted that your cat is named **Quillon**"*, with zero tool frames and nothing stored.
   - **Cause:** installed `brain/chat.py:600` still drops every `memory_*` tool by prefix.
   - **Status:** the fix `f6cc2218` merged at 03:06Z, 50 minutes after this build was cut. It was gate item 5 last run. It is silent wrongness on every install.
2. **`upgrade-unassigns-brain-dead-remedy` (new, major): an upgrade silently strips a slot's model and then recommends a remedy that cannot work.**
   - **Trigger:** the ADR-0028 runner_system conversion unassigns any fork-only-quant model, which on ct150 was brain's `hal0-brain-sft-q8-rocmfpx`. The unassignment is by design.
   - **Defect (a):** its WARNING goes only to the journal. `migrate_runner_system`'s report is dropped (`updater.py:1933` keeps only `.backup`), so `hal0 update` never says a slot lost its model.
   - **Defect (b):** the render error then blames the registry ("model_info has no 'path' — registry lookup failed").
   - **Defect (c):** the update verdict ends with "run `hal0 update --restart-slots` … (exit 2)", but by #2660's design `--restart-slots` refuses that slot (`update_commands.py:889-921` against `:546-550`).
   - **Who is exposed:** upgraded boxes with a fork-only quant bound to any slot, meaning GPU boxes installed before rc.10. That is the population prod belongs to.
3. **`hermes-utility-kv-pool-exhaustion` (new, major): one overflow kills every in-flight request on the utility slot.**
   - **Cause:** the seed `utility` profile launches with `--ctx-size 65536` and no `--parallel`. llama.cpp's `-np auto` therefore runs 4 sequences that share one 65,536-cell KV pool.
   - **What happens:** when the combined in-flight tokens exceed 65,536, llama-server returns 500 "Context size has been exceeded" to **every** active request on the slot. That includes small, unrelated Hindsight extraction and consolidation calls and hermes turns. hal0-api passes the 500 through unchanged.
   - **Reproduced:** in the journal (7,316 + 19,133 + 25,036 + 15,615 = 67,100 > 65,536, then `send_error` on all 4 slots) and with synthetic concurrent prompts.
   - **Who is exposed:** every install, fresh or upgraded, because they all run the same seed profile. On ct151 hermes landed on this slot through #2665.
   - **Contradiction:** hal0's own schema comment (`config/schema.py:1944`, "usually one llama-server with --parallel 1") assumes serial service.
4. **`hermes-slot-list-payload-truncated` (#2662, major, conditional): the fix is not in this build.**
   - **Status:** `a9328ebe` is in `032919`. This item comes off the gate as soon as the re-probe on that build passes.
   - **Measured on this build:** the cliff is at 15 `/api/slots` rows (14 slots plus the synthetic `hal0` row). Hermes cuts the result to a 1,589-char preview (`[Truncated: tool response was 40,686 chars …]`) and then answers from stale context.
   - **Exposure:** ct150 already has 13 rows.

Everything else is major or lower and would not hold a release on its own.
